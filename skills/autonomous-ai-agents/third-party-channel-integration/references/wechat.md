# 微信渠道（iLink / 微信机器人）

**证据等级**：本页事实**没有找到可稳定引用的官方规范文档**，多数来自第三方 SDK 文档与厂商社区文章
（腾讯云开发者社区）—— 只当作"实际怎么用"，**不当平台承诺**。用前重核。

## 连接方式

- **HTTP 长轮询**（`getupdates`，约 35s 一轮），**不是** webhook，也不是 websocket → **不需要公网地址**。
- 官方 SDK 侧：`await bot.login()` 显示二维码（iLink 登录）→ 手机微信扫码 → 机器人上线；
  凭据由服务端在扫码后下发并由 SDK 持久化（"凭证自动保存，会话自动恢复"）。

## 凭据

- **只能扫码** —— 没有"填 AppID/Secrct 就上线"这条路。**没有自动重扫 API**。
- 会话过期（`errcode=-14`）只能人在手机微信里再扫一次。
- `bot_id` 与微信 openid 在平台侧 1:1 写死：**换微信号 = 重走扫码流程**。
- **不要复用另一个客户端（如 Hermes 网关）的同一个 token** —— 一个账号一个连接。

## 配额与保活（设计必须考虑）

| 项 | 值 | 对设计的影响 |
|---|---|---|
| `context_token` 续期 | 需**每 24h 由用户主动给 bot 发一条消息**（二手口径） | 做不了全自动；只能倒计时提醒 + 引导 |
| 主动推送配额 | 称每用户 24h 内最多 **10 条**，超出回 **429**（被动回复不计） | "轮次完成提醒"类功能**必须降频/合并** |

## 依赖（若照官方 SDK 实现）

`aiohttp` + `cryptography`（可选 `certifi` / `qrcode`）。
若只为纯文本收发而自实现，出站用 HTTP 轮询即可，依赖可降到零。

## 只能人工的步骤

1. 手机微信**扫码**登录（必须人扫）→ 手机端**确认授权**；
2. 每天给 bot 发一条消息续 `context_token`（不能代替人发）。

## 对本地 Agent 的含义

- **二维码必须能在桌面应用/终端里显示出来** —— 否则用户每 24h 就要回命令行，体验崩掉。
  这是**必需项**，不是增强。
- 会话保活成本高 → 渠道适合跑在**独立子进程**（关窗仍收），否则每次重启都要重扫。
