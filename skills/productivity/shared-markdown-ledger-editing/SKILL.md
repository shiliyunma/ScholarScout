# 共写 Markdown 台账的安全编辑

适用：任何「一行一实体 + 唯一编号 + 汇总计数」的 markdown 文件 —— 投递台账、库存/资产表、任务清单、跟踪表，
**且同一批文件会被别的会话、cron 任务或另一个 agent 同时修改**。

核心判据：**上下文里的行号、计数、状态快照、乃至「今天是哪一天」都会过期。** 写之前现读，写完现算。

- **跨天会话先跑 `date`。** 同一段对话常从前一天拉到几天后；按上下文里那句「今天是 X」算截止倒计时、算「今天该做什么」、算定时任务的时间点，会全错而且错得不明显。把真实日期写进回复与落盘记录。

## 1. 写之前先定位，不用快照

- 用脚本现读目标行的单元格：`[c.strip() for c in line.strip().strip("|").split("|")]` —— 确认它还在预期文件里、编号与列位对得上。
- 目标行搜不到时，**先在所有同族文件里各搜一遍再决定动作**。`patch` 报 `Could not find a match` 最常见的含义是「**这行被搬到别的文件了**」，不是「文本写错了」；直接重建一行会造成重号。
- 汇总/计数行同样现读。上一轮看到的数字只能当线索，不能当依据。
- 搜行用结构化判据（`line.strip().startswith("| NN |")`）而不是整行文本匹配 —— 行内 emoji、粗体、路径随时被别的会话改过。

## 2. 跨文件搬行

- **唯一编号跟着行走**，搬行时不要重新分配。
- 在原文件留一行 HTML 注释占位（`<!-- #NN 名称：已投，行已移至 xx.md -->`）—— 否则下一个会话会把它当「缺失」重建。
- 搬行动作一次做全：目标文件插入 + 原文件留占位 + 两边汇总同步。漏最后一项等于把错误留给了下一次读文件的人。

## 3. 编辑超长行

- 表格行超过约 800 字符（含 emoji、反斜杠路径、多处粗体）时，**不要用 `patch` 整行匹配**：按行索引读出 → 在 Python 里重建该行 → `write_file` 整份写回。
- 写回时保留行尾符：`split("\n")` 会留下行尾 `\r`（CRLF），**插入的新行也要补 `\r`**，否则文件里混用 CRLF/LF。
- 同一实体的多个列（状态、流程、下次跟进日、备注）要在**同一批**里改完；分批改容易出现「状态改了、跟进日还是旧的」这种半更新。
- **`patch` 的 `old_string` 绝不只用行首前缀。** 拿「某条 bullet 的开头几个字」或「某行前半截」当 `old_string`，patch 会**就地替换这段前缀、把原行剩下的部分留在后面**，拼出一条混行：新内容后面粘着上一条记录的尾巴。**症状**＝两件事写在同一行、读起来还挺通顺，肉眼极难发现。纪律：动 bullet / 表格行时 `old_string` **必须包含到该行行尾**（或直接按行索引整行替换）；**纯追加**用脚本 append 并补 `\r`（CRLF 文件用 `newline=''` 读写）；改完按行号复读那一行再报完成。
- **用脚本写含 Windows 路径的文本时，反斜杠后面跟数字是雷区。** shell heredoc 传进 Python 的字符串若被吃掉一层转义，`\2` 会被当成**八进制转义** → 写出一个控制字符 `U+0002`，**连它前面的反斜杠一起消失**（`…VC\2a59476c9b\` 变成 `…VC<CTRL>a59476c9b\`）；而 `\` + 字母只是「无效转义」警告、原样保留。于是**只有数字那几处会静默损坏**，`grep` 看行文完全正常，肉眼扫不出来。两条纪律：① 拼反斜杠一律用 `chr(92)`，或干脆不在字符串里裸写盘符路径；② **每次脚本写盘后扫一遍控制字符** —— `[c for c in s if ord(c) < 32 and c not in "\t\n\r"]` 必须为空 —— 并把这条并入「完成校验」。修复时注意：`\2` 被吃掉后**反斜杠也没了**，只删控制字符会留下 `VCa59476c9b`，要连反斜杠一起补回。
- 改之前 `cp` 一份到归档目录，或先写临时文件比对行数与字节数无异常再替换。
- **多行脚本不要走 shell heredoc，落成 `.py` 再执行。** 待写内容里一旦出现成对的引号、反引号、全角括号、`|` 或中文标点，heredoc 会在 bash 层被解析崩掉 —— 症状是 `exit 2` 加一句 `unexpected EOF while looking for matching`，**不是 Python 报错**，于是你会去找 Python 的毛病。纪律：**超过十来行、或内容含上述符号的脚本，一律 `write_file` 写成 `<工作区>/_wip/<名字>.py`，再 `python <该文件>`**；顺带留下可复跑的底稿，改一处不必重打全文。只有短到一行、且只含 ASCII 的临时命令才用 `python -c`。

## 4. 汇总与计数

- 任何插入 / 删除 / 搬行之后，**同步汇总行**（`合计：N 条 / M 家` 这类）。
- N、M **用脚本数出来**（`sum(1 for l in lines if <判据>)`），不要心算。
- 汇总一漂就传染：下一个会话按错误总数做判断，再写出下一个错误的数。

## 5. 新编号分配

- 扫**所有同族文件**取 max 再 `+1`。编号在全库唯一 —— 只在目标文件内查重会撞号（另一个文件里已经占了）。
- **取的是「全族 max + 1」，不是「本册 max + 1」。** 分批分册维护的编号里，最大号可能在任意一册：实测 A 册最高 106、B 册已占到 107–110，此时 A 册的下一条必须取 **111**，按本册 max（107）给号当场撞号。先跑全族扫描再落笔。
- **新建一册时给它一个独立前缀**（如 `N01`、`N02`；前缀取该册语义首字母），与数字册**完全隔离** → 此后任何一册怎么长都不会撞号。同时每行保留一列**「原编号」**（迁出前的旧号 / 旧章节），否则跨册引用会断。

## 5.5 册子集合：一本一态，新建时只增不删

台账长大后的自然形态是**一本一态**：一个总入口（只放共享章节）＋ 按状态拆开的多本（如待办 / 已完成 / 已废弃），
**每个实体必须恰好有一个家** —— 同一行在两册里各有一份，早晚会漂成两种说法。

把「被否决/被排除的实体」从主表里拆出去单独成册：**留在主表附录里的否决记录等于不存在**（没人会重读附录），导致同一个对象每隔几周被重新调研一遍。
独立成册时给它一个开头就写明的用法段：**“拿到任何新对象名，先在本册全文搜一遍，命中即停”**。

新建一册是**三处、只增不删**的编辑：

1. 总入口的册子清单加一行 ＋ 用法段加个指针；
2. **被拆的那册**改头部口径（“本册只放 X 了”），并把它那个旧附录标成**历史留档**；
3. **迁走的行不删除** —— 它们是跨册引用的锚点。删除是破坏性动作，先问再做。

计数跟着变：**按实体去重，不是按行** —— 同一实体的多行让「条数 +1」而「实体数不变」，两个数都要报、都要用脚本重算。

### 5.6 「投前必查」：多册台账的第一道闸

**任何新实体入库前**，把实体名（含简称、英文名）**与它的标识域**（邮箱域名、官网域名）在**所有同族册子里各搜一遍**：

- **否决册命中 → 直接停**，不再读 JD、不再问“要不要投”。这是否决册存的全部意义。
- **其它册命中 → 先判那一行是「已在册的实体」还是「只是别行的备注里顺带提到过」**。关键词命中 ≠ 重复：实测一家公司只在另一行的备注里被提了一句（作为另一场活动的同名单），差点当成重复项。**判据＝该行是否以 `| <编号> |` 开头**（结构化判据，不是全文命中）。
- **真重复 → 把新情报补进那一行**（状态 / 流程 / 跟进日一起看），**不要新建第二行** —— 同一实体两套状态，此后每个会话都按两套走。
- **同一实体的不同子项（不同岗位 / 不同批次）算新条目、不算新实体**：条目计数 +1，实体计数不变。

漏掉这一步的后果是**同一实体建出两套记录**，而且**写入时两边都不报错**，只到下一次入库才炸出来。

**排除/黑名单类登记本的证据分档**（适用于任何“决定不再碰”的登记）：

- **只有两类证据可以坐实一条排除**：**① 一手口头确认**（对方当面/电话说的）；**② 实测结果**（提交后被受理或拒绝）。
- **书面规格（海报 / 简章 / 官网页上的门槛）不作为排除依据** —— 它通常是“理想候选人画像”，实际常接受低于规格的人。书面门槛只能让你写「待确认」并给一条零成本核验动作，不能替用户判定不投。
- **反向也成立**：一手口头排除**不被「书面没写这条」推翻**。证据等级比“有没有写下来”重要。
- 每条都标一个 **「可复议？」** 列：⚠️ = 当初的依据是软的（渠道断了、岗位可能变），值得重看；❌ = 硬的（地域、无匹配岗位、名额已用），重看是浪费时间。
- **原因照抄原话，不要自己改写**。读者是几个月后另一个没有对话上下文的会话；「原话」比一句工整的概括安全。原行根本没写原因时，**就写“原行未记原因”并标出需要用户回忆** —— 不要替它编一个。

## 6. 归属：把事实挂到正确的实体上

- 口头或转述来的实体级事实（业务范围、联系人、条件、金额、渠道）**默认不隶属于刚刚讨论的那一个实体**。落库前先确认它属于谁。
- 无法确认时两件都做：① 写入时标注「归属待确认」；② 在对话里给 **A/B 两个候选的编号选项**，让对方一个字确认。
- **问用户之前，先搜他自己的工作区**——尤其是那些“看起来是全新事件”的状态。实测“某公司的测评已完成”在三本台账里 **0 处记录**，看着像新环节；而判定它到底属不属于独立环节的依据，其实躺在**我早前自己产出的备考文档**里（一行「笔试后另有性格测评，走完笔试才会收到」）。顺序：`grep -rn "<事件关键词>" --include="*.md" .` → 换公司与近义写法搜第二遍 → 确实没有才问。落库时把**依据的文件名与行号写进备注**，别写“待核”。
- **一次只问一个问题，且优先自己查。** 对方习惯单字回复；一次抛三个选项他会把原话重发一遍。**他重复发同一句 = 他已经答过 / 让你别再问**：此时直接按最佳解释落盘、在备注里标「待补」，把不确定项写成台账里的一条待办，而不是对话里的第二个问句。
- 纠正时**把错挂的那一行整行回滚**（状态 / 流程 / 下次跟进日一起回滚），再把事实落到正确实体（必要时新建一行）。只追加一句「其实不是这家」是不够的 —— 状态列不回滚，之后每个会话都会照着错的排期走。
- **标识符必须来自权威来源**：编号、名称、邮箱、卡号以官方页面/截图的原文为准，**照抄不改写**。转述值与官方清单对不上时标「待核」并要求对方照抄原始页面，不要顺手改成听起来对的写法 —— 台账与对外沟通都要用官方原名，改一个字就两边对不上。
- 联系方式（邮箱域名、链接、入口）写入前先做可达性核验，例如 DNS：
  `python -c "import socket; print(socket.gethostbyname('example.com'))"`
  核验失败时**不要让对方照它行动**，改指到已验证的通道（扫码 / 官网），并把失败原因写进备注 —— 否则下个会话会把一个死通道当可用入口报给他。
- **用户改口径时，要撤销旧口径留下的标记，不能只追加新口径。** 实测：先说「这一批提醒我线上投递」→ 给几行打了「⏰ 需本人网申」；随后改口「已线下投递，不用网申」→ 那几条标记**必须整段撤掉**，**并同步扫一遍派生物**（自动生成的待办清单、当天进度小节、存档日报里的对应行）。只追加不改旧，下一轮会话会拿着作废口径反复催他，而且看起来完全合理。
- **现场口述与书面材料冲突时，口述赢，并把冲突本身写进备注**（门槛、城市、要不要某个环节，都属这类）。
- **口述来的“后续环节”要单独建成一条待办，不要塞进备注**（例：「需要线下去上机做算法题」）—— 它自带“时间、地点待补”两个字段，且是与网申并列的独立关卡；埋在长备注里等于不存在。
- **同理：口述的一个环节不能被扩写成整套流程。** 他说「需要线下去上机做算法题」只证明**存在「上机」这件事**；**它排在流程第几步、由什么载体承载（纸质表 / 邮件附件 / 线上系统）全是未知**。实测由「上机要带材料」推断出「那份问卷是现场手填的」并写进台账当事实，后来 HR 邮件推翻（真实流程＝把资料作为**邮件附件**提交、审核通过才面试），错记录还带偏了准备动作。纪律：**环节顺序与载体只认书面材料（HR 邮件 / 招聘公告 / 网申页）**，口述只提供「有这件事」；被书面材料推翻时**就地改掉那句话**（不叠「更正：…」），并同步改派生物（待办清单、当日进度、自己刚出的准备文档）。
- **HR 要「一套应聘资料」时先逐项对账本人现有材料**，拆成 **已齐 / 部分缺 / 需动手** 三态报，每项指向本机真实路径或真实待办。若某份材料含身份证号这类敏感字段，**另存一份「<公司>专用版」**，通用版保持原样 —— 他还要投几十家，没必要每家都给身份证号。

## 7. 完成校验

- 三件各查一次：目标行单元格数 = 表头列数；汇总数 = 脚本数出的实到行数；被搬走的行在原文件只留占位注释。
- 回报时给「改了什么 → 现在几个 → 还差什么」，不要复述过程。
- **聊天里的汇报与调研对比一律用编号 / 短横线列表，不用 markdown 表格。** 微信里表格会挤成一团不可读，用户会直接回一句「以列表形式给我」。长内容落 `.md` 存档，聊天里只给列表摘要 + 文件路径；要发文件时另存一份**纯 ASCII 文件名**的副本（中文路径在微信上会发送失败）。

## 8. 引用完整性体检（他说「检查链接」时）

「检查链接」**不是只测外链**。三类引用都要查，分开报结论：

1. **外链可达性** —— 逐条 curl（写临时文件，**不要 `-o /dev/null`**）；报 404/500 的先把正则可能吞进的 markdown 粗体、中文括号剥掉裸测一遍再下结论；带 `referralCode` 的招聘链接常态是 302，要 `-L` 跟到最终码；**设计上就短命的链接（一次性上传/报名入口）标「已过期」即可，不算故障**。
2. **文档内部路径引用** —— 含 `文件:行号` 锚点的**行号越界**。解析要分层（精确路径 → 唯一 basename → 多命中判歧义），并且**先排除非路径**：光文件名、光扩展名、URL 路由（`/llms.txt`）、glob（`rules-*.md`）、占位符。不排除就会刷出几十上百条假阳性，把真断链淹掉。
3. **cron 任务 prompt 里写死的路径** —— 任务定义在 `~/AppData/Local/hermes/cron/jobs.json`，逐 job 查 `script` / `workdir` / `prompt`。 **prompt 里写死 `YYYY-MM` 月份文件名是头号杀手**：跨月那天会把当月内容写进上个月的文件；改法是让 prompt 先跑 `date +%Y-%m` 再拼文件名。
   同一次检查里顺手看三样：① 每个 job 的 `script` 与 `workdir` 是否还存在；
   ② **投递目标与创建渠道是否匹配** —— 群聊收不到主动消息，在群里建的 job 必须显式写用户的私聊 id；在私聊/桌面建的 job 用 `origin` 是正常的（不要一律改成私聊 id）；
   ③ **gateway 是否在跑**（`hermes gateway status` / job 列表里的 `gateway_running`）——不在跑时 job 存着但**一个都不会触发**。拉起要用系统启动项/启动脚本以 detached 方式起，**不要从 agent 自己的 shell 里起**：那样起的进程会随 shell 所在的 Job Object 一起被杀，之后状态显示「started successfully but died without a clean shutdown record」。

**体检发现「定时推送断链／gateway 未运行」时，这条写在报告最前面** —— 它比任何一条断链都严重（一个任务都不触发）。
完整脚本、假阳性排除清单、修复纪律 → `references/引用完整性检查.md`。

## 8.5 数行数与数格数：单一判据必漏

「本册有几条」「这一行有几格」是每次编辑都要报的数，而**最容易错的地方就是数法本身**。三条实测过的漏数陷阱，每条都会给出一个自信的错数字：

- **加粗编号行**：`| **101** | …` 这种把编号写粗了的行，`^\|\s*(\d+)\s*\|` **匹配不到** → 少数一条。症状是「表头声称 N 条、我数出来 N-1」—— 那一刻的默认反应是**怀疑表头的数**，但错的是你的正则。
- **缺格行**：行里少一个单元格（历史编辑吃掉一格，例如只有 11 格而表头 12 格）时，任何 `len(cells) < 表头列数` 的守卫会**整行静默丢弃** → 又少数一条。**守卫条件自己就是漏点**：写完守卫要回头逐行对一遍「哪些行被挡住了、为什么」。
  - **「少一格」先看行尾有没有 `|`**：行尾漏掉收尾竖线时，`[x.strip() for x in line.split("|")][1:-1]` 会**把最后一个单元格一起丢掉** → 看上去就是「只有 11 格」。这和「真的少一个单元格」是两种病：前者补一根竖线即可（`if not line.rstrip().endswith("|"): line = line.rstrip() + " |"`），后者才要判断缺的是哪一列。**报「少一格」之前必须先看行尾那个字符**，否则会去「补」一个本来就存在的单元格，把 12 格补成 13 格。
- **`split(" | ")` 会合并空单元格**：这是带空格的写法，`A | | B` 只切出两段 → **列数少数**。判「这行与表头对齐吗」一律用 `line.count("|") - 1`，不要用 split 的长度。同一批数据的「行数是 11 还是 12」在两个会话给出两个答案，就是这两种数法混用的结果。
- **格数偏多（比表头多一格）有两种成因，修法不同，别一律当成「多了一根尾巴竖线」**：
  - **多一个空尾格**：行尾写成 `… | 备注 | |` → 末尾多出一个空单元格。修法 `re.sub(r"\s*\|\s*\|\s*$", " |", line)`。
  - **某格内容里混进了裸 `|`**（备注里粘过子表格，或把两个字段写成 `A | B`）→ 该格被劈成两格，**它之后的所有格位整体右偏**（实测：备注被劈成「一个日期」+「正文」两格）。**这种改不掉**：上面那个尾竖线正则在它身上匹配不到、格数纹丝不动 —— 症状就是「改完再数还是多一格」。
  - **定位法（两步，别猜）**：先 `line.count("|") - 1` 确认偏几格；再**逐格打印「序号 + 字符数」**，异常格自己会暴露 —— **空串格、或明显短于邻居的格就是劈开点**（实测那个多出来的格只有 9 个字符的日期，邻居是上千字的正文）。然后按「把那几格合并回一格，用 `／` 或全角 `｜` 替掉裸 `|`」重建整行。
  - **有两种多格是自己写坏的，先查这两处再怀疑历史数据**：① 刚往单元格里**追加**的文本自带半角 `|`（例如写成 `…张思浩」 | 📧 邮箱…`）→ 当场把一格劈成两格；② 新补的那行手打时行尾多了一根竖线。**预防纪律：把待追加字符串拼进单元格之前，先把它里面的半角 `|` 全部换成全角 `｜`（或 `／`）。** 实测追加文本里只有一处 ` | `，就把 12 格变成 13 格。
  - **改完必须重跑全册校验，不能假设修好了。** 修复动作本身会引入新缺陷（实测：修 A 行时顺手改 B 行，A 修好了、B 变成 13 格）。纪律：**每一次 `write` 之后都重跑一遍全册 `count("|") - 1 == 表头列数`，直到返回空列表**再报完成；不要只复读「我改的那一处」。

纪律：① **行数至少两种判据交叉**（编号正则 ＋ 行首 `|` 计数 ＋ 与汇总行对账）；② **格数只认 `count("|")`**；③ 报数前把「被守卫挡下的行」列出来看一遍；④ 数出来的数与文档里的计数不一致时，**先假定自己的数法有漏**，去查异形行，再下结论。

## 8.6 写盘后的两类「假故障」

- **终端回显会再转义一层反斜杠，别据此「修」正确的文件。** 工具输出常以 JSON 包装，文件里 1 个反斜杠在回显里会变成 2 个 —— 于是看到 `D:\\x` 就以为文件里存的是双反斜杠、动手去「修」，反而把正确内容改坏。**判文件里到底几个反斜杠，只用正则数连续串的长度**（`re.finditer(re.escape(chr(92)) + "+", s)` 看每段长度是 1 还是 2），**不要信 `repr()`、也不要信工具回显**。同理，反斜杠只剩一半时（详见 §3 的八进制转义坑）也要先量再修。
- **`.md` 里别把 `>` 写成 `&gt;`。** 在 markdown 文件里 HTML 实体**不被解码、原样显示**（页面上就是字面的 `&gt;`），而它读起来很像引用块、极难在自查时发现。写文件后扫一遍 `&gt;` / `&lt;` / `&amp;` 残留（应为 0）；改成真字符后，再确认没有留下孤立的 `>` 空行。另外**引用块里不要嵌 `##` 标题** —— 渲染成「引用里的标题」很难看，标题要拉出引用之外。

：同一批文件在两个工具调用之间就被人改过是常态 —— 每次写都重读那一行。
- **别把「找不到」当成「不存在」**：跨文件搜一遍再下结论。
- **别追加更正、要就地修正**：把错的那句直接改掉（或整行回滚），不要写成「UPDATE: 实际上…」叠在下面 —— 两句话并存的表格，后面每个读者都要自己判断哪句有效。
- **别用整文件 `write_file` 重写历史部分**：只改需要改的行，重打全文一次闪失就丢历史。
- **两份记录打架时，去翻一手证据，不要在文档之间「对齐口径」。** 台账行与日志段说法不一致时，真相在原始聊天截图 / 邮件 / 短信里 —— 两份都是转述，两份都可能是错的。互相校准会产出一个**自信的错事实**（一次按时交掉的表格被记成「逾期三天」，此后每个会话都照着错的排期走）。**冲突时的第一动作是找一手证据，不是找另一份二手记录。**
