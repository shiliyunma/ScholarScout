# 多条目交付物：一条目一份文件

触发：产出覆盖 N 个条目 —— N 个技术栈的讲义/启动方案、N 个仓库的学习资产、N 个岗位的台账、
N 篇文献的精读、N 个产品的监控。

## 铁律：一个条目一份自包含文件，不要一份大汇总

这条是**用户明确纠正出来的**。曾把 13 个 demo 的启动方案写成一份 28 KB 汇总文档，被要求拆开：
「**每个写一份，而不是一个大汇总**」。

机制上为什么拆：

- 汇总文档里改一条要重写整个文件，而实际使用总是「我只看第 7 个」
- 长汇总没法单独发给别人，也没法单独版本化
- 写的时候一长就容易开始压缩内容（因为总长在那里），反而每个条目都变薄

## 目录形态

```
<根>\
├── 00-公共前置.md        只放真正所有条目共用的东西
├── 01-<条目A>.md         自包含
├── 02-<条目B>.md
└── ...
```

- **编号前缀**让目录自己读起来像一条顺序。
- `00-公共前置` 里只放共享部分：依赖的外部程序、怎么起后台服务、端口/资源避让表、排查顺序。
  它**不是引言**，不要写「本文档目录如下」这种导航内容。
- **每个条目文件必须自包含**：把它需要的前置条件就地重写一遍，不要写「见 00 第 2 节」。
  重复几行好过让用户在两份文件间跳。
- 建完把旧的汇总文件**删掉**，不要留两份。

## 每个条目文件里必须有的几块

具体字段随任务变，但以下四块几乎总是要：

1. **前置条件** —— 需要先起什么、需要什么 Key/凭据。
2. **怎么做** —— 可复制的完整命令或步骤，含工作目录。
3. **怎么确认成功了** —— 预期输出长什么样，或一条能返回确定值的验证命令。
4. **怎么收尾** —— 怎么停、怎么清、怎么重来。

## 依赖的外部程序：要说清它在本机能不能直接调用

每个条目的「怎么做」里，凡用到外部程序，交代它在**这台机器**上是不是开箱可用：

- **可直接调用**（在持久 PATH 里）：直接给命令名。
- **不可直接调用**：给**完整路径**，并给该用户实际会用的每种 shell 的等价写法
  （bash 的 `export PATH=...`、cmd 的 `set PATH=...`、PowerShell 的 `$env:Path = ...`），
  并说明「只对当前窗口有效」。

判据是**持久 PATH**，不是当前会话的 `$PATH` —— 子进程或 agent 会话常常注入了自己的
node/python/工具目录，拿会话 PATH 去回答「是不是全局装的」会答错。Windows 上读注册表：

```python
import winreg, os
sysp = winreg.QueryValueEx(winreg.OpenKey(winreg.HKEY_LOCAL_MACHINE,
        r"SYSTEM\CurrentControlSet\Control\Session Manager\Environment"), "Path")[0]
usrp = winreg.QueryValueEx(winreg.OpenKey(winreg.HKEY_CURRENT_USER, r"Environment"), "Path")[0]
```

（Windows 上服务类条目的启停、验证、脚本坑见 `windows-local-service-ops`。）

## 交付后：统一入口 + 逐条验证

- 把新目录写进上级域的**总索引**，否则下次找不到。总索引那一行写清「这里是什么、怎么用」。
- 用户偏好**入口放在最显眼处**：该双击的启动脚本放项目根，不要藏在子目录。
- **逐条验证，不是抽样**：条目多的时候人会倾向于抽查两三个就宣布完成。要么全跑，要么在
  汇报里明确写「已验 N 个，剩下 M 个未验」。

## Pitfalls

- **别把共享前置写成第二份汇总。** `00-公共前置` 一旦开始出现「条目 A 要注意…」，就说明那条
  该回到条目 A 自己的文件里去。
- **写完汇总再拆分时，先核对每份子文件真的自包含**：从汇总里裁出来的一段常常还指着「见上文」。
- **条目名不要用显示名当目录名。** 展示用的中文名（「PG 图数据库」）与实际落盘目录（`PostgreSQL-AGE`）
  不一致时，写清单脚本按显示名去查会报「目录缺失」，而目录就在那儿。
- **清单/索引用脚本生成，不手写**：手写必然漂（漏项、路径写错、编号断档）。生成时用
  `assert` 把「条目数 == 清单行数」钉死。
