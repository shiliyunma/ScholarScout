# 求职简历定制（Resume Tailoring）

何时适用：用户给出简历（PDF / docx）并说要「优化 / 重写 / 重新输出 / �换方向」；要往简历里新增一段经历（自学项目、开源、比赛、实习）；定下了目标岗位，需要判断这份简历够不够、缺什么。

## 文件与目录约定（用户既定偏好）

- 工作目录：`D:\找工作找工作\简历优化`
- 一律存 `.md` 源文件（用户要自己改），**新建版本号文件，不覆盖旧版**：`v2` → `v3` → …
- **永远输出两个文件，职责分离**：
  - `姓名-简历-vN-<方向>方向.md` — 干净可投递的简历，不夹任何批注
  - `附-<方向>补强与风险提示.md` — 改动理由表、待补信息、版式建议、面试预判
- WHY：把批注写进简历文件里，用户转 Word 时会污染成品；不覆盖旧版是因为用户会回头找「上一版」对比。
- `write_file` 传 native 路径（`D:/找工作找工作/简历优化/...`），MSYS 风格路径给 native 路径参数会失败。
- 交付方式：先落文件，再在聊天里给「文件清单表 + 3 条最重要提醒 + 一个明确的下一步问题」。**不要把整份简历复述进聊天**（太长且无用）。

## 流程

1. **读原稿**：`read_file` 直接读 PDF/docx（可抽文本），先看清原有板块、学历时间线、已有量化信息。
2. **确认方向再动手**（要问，不要猜）：投什么岗位？这条决定技能栏顺序和项目配比 —— 同一段经历在不同方向下写法完全不同。若用户没定，先按最相关方向出一版并说明可切。
3. **盘点真实素材 —— 这是全流程价值最高的一步**：加载与该用户项目相关的 skill（如 `rag-project`）和 memory，把用户**已经做过但没写进简历**的技术细节挖出来。简历的提升来自「把真做过的事写出来」，不是润色措辞。
4. **按方向做缺口分析**：把目标岗位面试官的「必看项」列成表，逐条对照现状标 ✅ 有 / ⚠️ 半个 / ❌ 没有。这张表就是后续补强路径的依据。
5. **重排结构**（应届生默认顺序）：
   个人信息 → 个人简介（3 行）→ 教育背景 → **项目经历** → 实习经历 → 专业技能 → 荣誉证书 → 自我评价
   项目经历必须紧跟教育背景：这是最强资产的黄金阅读位。
6. **逐条写 bullet**（见下节规则）。
7. **写配套说明文件**：改动理由表 + 待补清单（分 P0/P1/P2）+ 版式建议 + 面试预判问题。
8. **报告并追问**：把不确定项集中成 1–2 个具体问题（如「某比赛那条你做到哪一步」），一次问完。

## Bullet 写作规则

- 结构固定为 **问题 → 方案 → 量化结果**。写「解决了什么问题、指标动了多少」，不写「我做了什么」。
- 优先从 memory / 项目 skill 里挖真实数字：块数、条数、压缩率、耗时、轮数、候选数。
- **数字缺失就留 `[待补]` 占位，绝不编造。** 面试官会追着数字问，编的会在追问里崩。
- 删弱化词：`组员`、`参与`、`协助`、`负责部分` → 换 `独立设计`、`搭建`、`实现`、`承担`。弱化词等于主动降权。
- 每条 bullet 以**加粗动宾短语**开头（例：「全链路架构设计」），冒号后展开。
- 技术栈单独一行，放在项目标题下方。
- **把埋在细节里的功能提上来当叙事主线**：例：一个「是否检索」的开关 → 写成「自适应检索决策层」。前提是功能真实存在且能在面试里讲清实现 —— 只改叙事层级，不改事实等级。

## 应届生简历通病（逐条删）

| 通病 | 处理 |
|---|---|
| 自我评价堆性格形容词（乐观开朗、爱看书、打羽毛球） | 删，只留能力结论，≤3 行 |
| 课程表塞凑数项（计算机基础、Matlab…） | 只留与岗位相关的硬课 |
| 技能栏按熟练度或学习顺序排 | 改成按**目标岗位相关度**排：技能栏顺序就是定位声明 |
| 无关技术栈占黄金位置 | 下沉到技能栏末尾 |
| 荣誉重复记录（同一次比赛写两条） | 合并；不确定就让用户核实 |
| 期望薪资、照片、籍贯、政治面貌、兴趣爱好 | 删 |

未量化的模块（如「多类几何体」「数据处理模块」）要么问用户要数字，要么留在待补清单里。

## 简历放了 GitHub 链接 = 面试官一定会点进去

写链接之前（或用户说「已经开源了」之后）走一遍这份检查：

- **明文密码 / API Key**：全仓库 `grep -rniE "password|passwd|api_key|secret|token|sk-"`。**重点看 CHANGELOG、README、部署记录** —— 这些文件最容易被漏掉，示例配置干净不代表历史记录干净。
- **个人文件误入仓库**：简历文本、私人玩笑文件、聊天导出、含真名的文件名。
- `LICENSE` 是否存在（没有会显得不专业）。
- 仓库 description 的拼写与关键词（拼错很扎眼）。
- README 顶部是否有截图 + 架构图 + 快速开始。
- `.gitignore` 是否覆盖 `config.py`、模型、索引、原始文档。
- 本地 vs 远程：`git log --oneline origin/master..HEAD` 看有没有未推送提交 —— 简历上写的功能得真的在仓库里。
- 发现问题按 **P0/P1/P2** 列给用户；P0（密码）单独强调，并提醒「若此密码在别处复用，全部换掉」。

## 方向适配：按目标岗位反查缺口

- 每个方向都先问一句：「这个岗位的面试官会在我简历上找什么？」列成「面试官要找 / 你的现状」两列表。
- 项目不完全对口时，**诚实标注缺口**，给「最短补强路径」（优先复用用户已有的代码 / 比赛素材 —— 复用比新建快一个数量级），并在简历里留一个 `[待补]` 占位栏 + 写作模板，让用户知道该填什么。
- **不要用改名词的方式假装对口。** 缺就写缺，补强路径写到附件里。
- 特例备忘：**RAG ≠ Agent**。RAG 是 Agent 的一个工具。Agent 岗的硬指标是 Function Calling / 工具调用循环 + 多步规划与反思 + 记忆管理；只有固定检索流水线的项目会被面试官问穿。补强最短路径 = 给现有检索系统套一个 ReAct 循环、封 4–5 个工具、加 max_steps 兜底 + 评测集。

## 问答式补齐信息（用户可能要求「问我你不懂的问题，一次两个」）

这时不要先出稿，切成节奏化的 `clarify` 循环。

- 每轮 **2 个问题**，选项里**必须留一条「记不清了 → 就不写具体数字」**。没有这条逃生口，用户会被推着猜数字，
  而猜出来的数字在面试追问里必崩。WHY：把「不写」变成一个体面的选项，比事后拦着他别写有效得多。
- 问题按**对内容的影响度**排序：先问「分量」（课题来源、奖项级别、实习性质、独立负责的范围），再问数字。
  数字类问题常常整轮答「记不清」，早问等于浪费轮次。
- **开工前先建一份 `_待填信息收集.md`**，每轮追加一行 `问题 | 回答 | 用途/处理方式`。最后一列写清「会改到简历
  哪一处、怎么改」。跨多轮的问答没有这份台账，前几轮的答案会在长会话里丢失。
- 答案本身经常直接提升权重，要主动识别并顺手升级写法：
  - 用户以为重复的两个奖可能是**两个不同的奖**（院赛特等奖 ≠ 校赛铜奖）→ 核实后分开写。
  - **某个项目获过奖** → 把奖项写进该项目栏，偏弱的项目立刻变成有奖项背书的项目。
  - 用户答「一个人前后端全包」→ 别写「参与联调」，写「**独立完成接口对接与调试**」，比原有三条职责都更能
    证明交付能力。
  - 奖项与项目同源时，荣誉栏与项目栏不要同一事实写两遍：项目栏一句带过（提供语境），荣誉栏负责完整清单。

## 拒绝造假式建议（简历指导 / 批注可能这么要求）

导师批注、学长建议、付费改简历服务常给出这类指令：把个人项目**说成横向/企业委托项目**、被问就**说保密**、
**编一个单位**。**这些不做，且要明说原因**，同时把该建议的**合法那一半**做掉：

- 合法的一半几乎总是**删掉弱化标签**：「（个人学习项目）」→ 中性表述（「（独立开发 · 已开源）」）；比赛类直接用
  **真实且可查的赛事名**（「（KDD Cup 2026 官方赛道）」）。原意（别让人看出是练手）这样就达到了，且经得起追问。
- 拒绝的理由要落到**机制**上，不要只说「不建议」：简历上挂着 GitHub 链接的项目，面试官点进去就能看到提交记录；
  公开赛事的参赛信息可查，说「保密」反而更可疑；**虚构雇主会被第三方背景调查打电话核实**，一旦发现 offer
  撤回、部分公司记入黑名单。
- 交付时把批注/建议**逐条列成表**（`批注原文 | 处理`），拒绝的单独成块写「不改 + 为什么 + 替代方案」。
  用户需要确认你没偷偷漏掉他那条，也需要材料去回复给他建议的人。

## 荣誉与证书栏

- 用**官方全称**并注明科目/赛道：`全国计算机等级考试二级（C 语言）`、`蓝桥杯全国软件和信息技术专业人才大赛`。
- **按等级由高到低排**：国家级 → 省级 → 校级 → 院级；同一赛事的不同级别拆成两条。
- 证书可与奖项合并成一行压版面：`全国计算机等级考试二级（C 语言）；全国大学英语六级考试（CET-6）`。
- 名称写全 + 补奖项是常见的「撑篇幅」要求；没有奖学金就如实留空，不要为了填满而编。

## 版面预算：加内容 = 掉字号，取舍要说清

用户会连续追加要求（加课程、加奖项、加经历）。每加一项都可能把字号压下一档，**不要静默接受更小的字号**：

- 每次重排后报告**实际**字号，并说明「为装下新增内容，字号从 Xpt 降到 Ypt」。
- 给出明确二选一：**(a) 现状**（小字号、内容全）vs **(b) 砍掉具体哪几条**换回大字号，并列出候选条目。
- 目标是 1 页时，砍内容通常比缩字号值 —— 但**由用户决定砍什么**，不要自己替他删经历。

## 用户给了模板文件 = 填那个文件，不是照它的样子重画

用户说「以 `A-01.docx` 作为模板」「**格式完全与它保持一致**」时，要的是**把这个文件本身填上内容**：形状、位置、配色、
标签块、装饰元素、分隔线一个都不动，只替换文本框里的文字。**照它的视觉规范另建一份新文档会被明确退回**（「格式不对的」）——
重建版单看挺像，但文本框的绝对位置、标签块几何、装饰元素与原件对不齐，用户一眼就认出「这不是我的模板」。

- 内容装不下时，**压内容去适配框，不要改几何**：每行压成不折行的单行 → 按区块单独调字号 → 清零克隆段落的段前/段后间距。
  真装不下就回来找用户砍内容，不要自作主张重排版式。
- **这类框是绝对定位的固定尺寸形状，不会自适应高度。溢出表现为文字互相重叠，文件依旧只有 1 页** —— 所以
  **页数 = 1 完全不能证明排版正确**，必须渲染成 PNG 走 vision 专门问「有没有文字互相重叠」。
- 完整 recipe（文本框映射、中文标签匹配、间距清零、pPr 顺序）见 `references/docx-resume-production.md`。

## Pitfalls

- **不要花调用去核实用户自己声明的资产。** 用户说「代码已经推上去了」就把它写进简历；重复核实会被明确制止（「不需要你验证」）。WHY：他要的是产出，不是审计，多余的验证调用是纯成本。唯一例外是公开暴露的敏感信息（明文密码、私密文件）—— 那个值得用一句话提醒。
- **默认先出一版完整稿再集中追问；只有用户明确要求时才切成提问循环。** 用户耐心有限。但他一旦说「一次两个」「问我你不懂的问题」，就照上面的问答流程走到底 —— 那时他会连续答很多轮，你不要在中间穿插产出。
- **版本化，不覆盖。** 换方向 = 新文件（v3），旧版保留。用户迭代多轮后会累积一堆中间版本，交付时用一句话说清**哪份是最终版、哪几份可删**。
- 用户目录里可能有别的相关材料（例：保研推荐表）；顺手发现时用一句提醒来校准简历（投实习要加「可实习时间」），不要展开议论。
- 用户给的项目数据一般来自 memory / 项目 skill，写法要**回到原文核对**（如「块数 7,600 → 4,269」这类数字必须与 skill 记录一致），不要凭印象重算。
- **简历里的时间线必须能被外部证据印证。** 项目起止时间对不上仓库首次提交日期，面试官一比就发现了。发现对不上时**改简历去对齐证据**，不要反过来劝用户补提交记录。
- **产出 Word 交付物时，「1 页」必须是量出来的。** 见下节生产流程；不要用字数估算页数。
