# 中文求职简历优化

## 工作目录与版本约定（用户的固定习惯）

**动手前先 `ls` 这两处，用当时的最新版本当底稿；不要凭本 skill 里记的版本号开工。**

| 目录 | 装什么 |
|---|---|
| `D:\找工作找工作\2-简历\` | **底稿与交付物**：`张思浩-简历-v10-B02-软件开发.docx` / `.pdf`（另有 `-B01-AI应用开发` 等方向变体与更早的 pdf）、说明稿 `附-*.md`、`压力面记录\`、`_tools\` `_render\` `_素材\` |
| `D:\找工作找工作\简历优化\` | 早期工作目录，**可能已被并入下一条的四模块结构、不再存在** |
| `D:\找工作找工作\3-面试\` | 投递台账、面试问答稿；压力面记录正本在 `1-面试准备\压力面记录.md` |

**入口认文件、不认分区名。** 用户会重构目录（`简历优化\` → `1-情报\` `2-简历\` `3-面试\` `4-刷题\` `5-重要事项\`，
另加 `hermes-learn\`）。先 `ls D:\找工作找工作\`，看有没有 `00-总索引.md`（四模块导航）和 `_交接说明.md`（现状快照 / 铁律 / 未完成清单）——
**两份都要读**。按 skill 里记的分区名硬编码路径，会让你整场会话写进不存在的目录。

用户说「用过去的简历」时，指的是 `2-简历` 里的最新一版；**交付形态是 docx，不是 md**。

**`2-简历` 里的现成真材料，优先级高于自己重新组织事实**（先读它们，再从源码核实数字）：
`项目与经历-详细简介.md`（38KB）、`附-Hermes毕设条目-面试口径.md`、`RAGLearn-技术详解.md`、
`RAGLearn-性能数据-日志实测.md`（**真实日志实测数据 —— 它能把「过程指标」升级成「结果指标」，是补强短板的现成弹药**）、
`个人简介-一段话-2027届.md`、`成绩单-90分以上编程相关课程.md`。

- **每版一个新文件，绝不覆盖旧版**：`<姓名>-简历-vN-<方向>.md`（如 `v3-AI-Agent方向`）；固定模板版则沿用 `.docx` 命名。
- 说明文档单独成篇：`附-<主题>.md`（改动说明、缺口分析、面试预判），不要塞进简历正文
- 原始稿（PDF/DOC/免试推荐表之类）留在目录里不动
- 交付形状：表格列文件清单 + 按 P0/P1/P2 分层的待补清单

## 流程

### 1. 先确认目标岗位，再动笔

同一份经历投不同岗位要重排配比。先做一张「**面试官要找什么 vs 用户有什么**」的对照表：

| 面试官要找 | 用户现状 |
|---|---|
| … | ✅ / ⚠️ / ❌ |

**这张表是整份工作的核心产出**——它决定哪些 bullet 提到前面、哪些下沉、哪一栏还空着必须补。先给表，再给简历。

已知的领域对照（AI/LLM 方向）：

- **RAG ≠ Agent**。RAG 只是 Agent 的一个工具。投 Agent 岗必看的证据是 Function Calling / 工具调用循环、多步规划
  与反思、记忆管理。一套固定流水线的 RAG 系统会被问穿「你的 LLM 在哪里做决策」。
- **「精读源码 + 跑通官方 baseline」是读懂，不是做过。** 面试官必问「所以你改了什么？」。发现这种落差要当场指出，
  并给最小改造方案（换模型做对比实验 / 重写工具 description 并量化误选率 / 加反思节点），标上工作量。
- **固定流水线里的「决策」是半个 Agent**：自适应检索开关、意图路由、多轮记忆窗口——这些本来是项目里的小功能，
  提到前面单独成条就能撑住 Agent 岗位的半栏。

### 2. 结构（应届生投技术岗）

个人简介 → 教育背景 → **项目经历** → 实习经历 → 专业技能 → 荣誉与证书 → 自我评价

- 最强的资产放教育背景**之后的第一栏**，不要埋在最后。
- **项目经历排在实习之前**：自研项目通常比打杂实习更能证明能力。
- 页数严格 1 页（应届）。内容超了就砍 bullet，并明确告诉用户砍的是哪几条。
- GPA 与排名并列写上，有排名优先写排名。

### 3. 每条 bullet 的写法

**问题 → 方案 → 量化结果**，不要写「我做了什么」。完整对照表见 `references/bullet-rewriting.md`。

- 动词：设计 / 实现 / 搭建 / 独立完成 / 定位并绕过 / 重构。不要「参与」「协助」「负责」这类弱化词，
  也不要「组员」「开发人员」这种自降身份的头衔。
- 每个数字都必须扛得住追问，有源码支撑的才写。**先判定它是「结果指标」还是「过程指标」**：命中率 / 准确率 /
  延迟 / 错误率是结果指标（可以暗示质量）；块数 / 文件数 / 压缩比 / 耗时是过程指标（只能证明「程序改过了」）。
  把过程指标写在质量宣称旁边，面试官会读成夸大。判定表、自证三栏卡与最小对照实验配方见
  `references/bullet-rewriting.md` 第 5 节。
- **项目自带评测集 / 指标口径文档时，它必须进简历 —— 这是「我怎么证明有效」的唯一直答，比任何形容词都硬。**
  用户往往把它当内部资料不写。判据：文档里锁死了每个指标的**分子分母 + 对照组 + 统计方法**
  （如自建评测集与「改口径必须重跑全部数字」的纪律）→ 把**评测集规模 + 口径可复算**直接写进那一条。
- 把用户没意识到的亮点提前：**已开源**（附链接）、消融开关、全链路可观测性（日志落库）、定位并绕过框架缺陷。
  这类「工程素养」证据比功能罗列值钱得多，而且面试官爱问、用户答得出来。

### 4. 诚实原则（用户明确认可这个做法）

**先核底层实况，再谈改写。** 用户说「把 X 写进去」时，他的简历条目通常**写小了**而不是写大了：先去项目仓库与
规划文档取**可证实的规模**（`git rev-list --count HEAD`、源码行数、测试文件、打包产物、评测集规模），
再和简历现有措辞逐条对比。实测落差可以很大 —— 简历写「已完成运行时骨架」，仓库已有一百多次提交、八千多行代码、
pytest + ruff + mypy 齐备。**「据实补强」与「不许拔高」不矛盾：拔高是写了没做到的，补强是把做到了而没写的写上。**

用户只做了 X 就写 X，**不要拔高**；同时**必须给出补强路径**——指出落差 + 可执行的最小改造方案（带工作量估计）。
把「复现」写成「自研」会在面试第一轮就崩，而「据实写 + 给补强方案」用户接受度很高。

**`【待补】` 占位符是模板，不是事实。** 用户自己攒的 `面试准备\*.md`、`_待填信息收集.md`、旧版简历里，
大量句子是当初留的填空模板（写作 `【待补：…】`、`[▸待填：…]`），读起来像已发生的事。**任何要写进简历、
或写进「要背的稿子」（面试问答稿、自我介绍）的案例，落笔前先向用户确认是否真实发生过**；一次确认不到就撤掉，
换成他答得上来的真事。面试稿比简历更危险——简历被追一句就过，稿子被背下来后追三层就崩，而那是同一条主张。

**内部文档里的事实是转述，不是事实。** 从 `附-*-口径.md`、学习笔记、旧版简历里抄一句**带细节**的话进新稿之前，
必须回到**用户本人或仓库实证**再确认一次——那些话可能是上一轮按错误前提写下的，而 agent 写下的稿子会被下一轮当成事实传下去。
**越具体的细节越要先问**：源码行为、数量、「我实测过」的对比结论——它们读起来最可信，也最容易被追问穿。
落笔进任何要交出去的东西（简历 / 网申表 / 自我介绍 / 面试稿）之前，把「这句是用户说的还是文档里抄的」过一遍。

**用户说某处「比较虚」时：降级动词、保留事实，不要整条删。** 把一句拆两部分看——
**数量与归属通常是真的**（「10 余张表」「独立承担」「独立开发」），**虚的是动词与深度**
（「设计表结构 + 索引定义」实际只是按业务对象做字段拆解；「通读了全部源码」实际只是跟着教程走了一遍）。
改法：`独立设计 N 张表并完成表结构与索引定义` → `并完成 N 张表的字段拆解与建表`；`通读了全部源码` → `参照其架构设计`。
**降级后必须同步技能栏与所有相关行**：正文写「字段拆解」而技能栏仍写「MySQL 表结构与索引」，细心的面试官会拿两处对账——
一处降级不彻底，等于没降。反过来，用户明确说某处「不用改」就照办，别再返工去游说（把风险讲一次、留一句替代文本即可）。

**顺带做一次三处一致性核查**：简历正文、面试问答稿、自我介绍里关于同一组事实（团队结构、协作对象、
谁 review、项目边界）的写法必须一致。用户稿子里「先跟**前端**对齐字段」和「前后端**自己全包**」同时存在时，
不要挑一个用——先问哪句是真的，再按事实统一三处。

### 5. 专业技能栏

按**目标岗位**排序，不是按掌握程度。投 AI 方向：大模型/Agent 应用 → 后端/数据 → 前端 → C++/桌面端 → 工具。
用户原来会但一个字没写的技能（如 RAG 全链路）要主动补上——技能栏的顺序本身就是定位声明。

### 6. 删掉这些

照片、籍贯、政治面貌、期望薪资、"喜欢看书/打羽毛球"一类性格形容词。自我评价压到 1–3 行**能力结论**。

### 7. 简历挂 GitHub 链接之前

先做仓库脱敏（见 `repo-secret-scrubbing` skill）：面试官真的会点进去，还会看 `git log`。提醒用户轮换可能泄露的
密码。

**个人信息栏的 GitHub 只写账号主页 `github.com/<user>`，不要带具体仓库路径**——仓库可能未公开（404）、可能改名，
写死一个仓库名会让整栏失效；具体仓库链接写在对应项目条目里。

**项目条目的起止时间必须和仓库实证对得上**：`git log --reverse --format='%ad %s' --date=short | head -1`
看最早 commit。写「9 月起」而最早 commit 在 10 月，面试官点开仓库第一眼就撞上。**以仓库/文件的实证时间为准，
不用「感觉开始做的那个月」。**

## 信息收集

- **项目上下文先查 skill，不要问用户**：`skill_view('rag-project')` 有 RAGLearn 的全部细节；毕设/ScholarScout 细节在 `skill_view('edu-agent-thesis')`。
- **派子 Agent 或动笔之前，先把「底稿在哪个目录、最新是哪一版」亲手 `ls` 出来。** 凭印象给的路径会让子 Agent
  从一开始就在错目录上干活（本轮派活时先写成了 `简历优化\`，用户随后纠正为 `2-简历\`，只能靠 steer 追回来）——
  **路径这种事实，先查再派，别先派再纠。**
- **一次问清所有待补信息**，别挤牙膏：GPA/排名、竞赛的真实级别、实习/兼职/全职性质、项目起止时间、GitHub 地址。
  能从已有上下文推断的不要问。
- 时间不确定时：先填合理值并**在说明文档里标注待核实**，不要在简历正文留 `[XX]` 占位——看起来像没写完。
- 不要代跑用户的命令、不要长篇复述过程；交付以文件路径 + 命令块 + 待补问题为主。

## 套用现成模板（Word 固定版式）

用户给了模板文件（如 `A-01.docx`）时，**必须以它为底稿填字，不要"按模板风格重画"**——重画出来的版式用户一眼就否掉
（原话："格式不对，我希望你格式完全与 A-01 保持一致"）。做法与坑：

- 模板正文多在**文本框**里（`w:txbxContent`），一个形状在 `mc:AlternateContent` 里存 **Choice + Fallback 两份**，两份都要改。
  **改动落在 `w:t` 层级，不要落在 `mc:AlternateContent` 块层级。** 在块层级拼接时极易把整块替换成
  「只是 `<mc:Choice>` 那一半」——**Fallback 副本凭空消失、XML 立刻不可解析**，之后所有块级正则全部失配，
  报错位置离真因很远（表现为「找不到含某关键字的块」，而那个块明明存在）。
  非要在块内拼接，必须**保留块外壳**：`新块 = 块[:Choice段起点] + 新Choice段 + 块[Choice段终点:]`，
  且 Fallback 段要**在已更新的块上重新定位**（前一次替换会移动它之后的偏移）。
  更省事的做法是根本别碰块结构——按 `w:t` 精确文本全局替换，落盘前断言一处不剩。
- 定位文本框用**模板里的真实文字**作匹配键：模板写的是 `姓　　名`（全角空格），用 `姓名` 匹配会静默漏掉整块替换，
  而页数仍然正常——不核对就看不出。跑完必须打印"已处理的框"清单，逐个核对数量。
- **固定尺寸 + 绝对定位的文本框，溢出不会翻页，而是两组文字直接叠在一起、或被下一个色带盖住。** 所以「页数 = 1」
  绝不能当通过标准。**改字之前先量容量，别写完才发现溢出**：
  ```bash
  cd "D:/找工作找工作/简历优化"
  "C:/Program Files/LibreOffice/program/soffice.exe" --headless --norestore \
    -env:UserInstallation=file:///D:/找工作找工作/简历优化/_render/loprofile \
    --convert-to pdf --outdir "_render" "张思浩-简历-v10-A01 .docx"
  gswin64c -dNOPAUSE -dBATCH -sDEVICE=png16m -r150 -dFirstPage=1 -dLastPage=1 \
    -sOutputFile="_render/v10-p1.png" "_render/张思浩-简历-v10-A01 .pdf"
  ```
  `gswin64c` 只吃 PDF/PS，**不能直接读 docx**，必须先过 LibreOffice；`-env:UserInstallation=` 指向工作目录下的
  临时 profile，避免和已开着的 soffice 抢锁。渲染完**拿改前版本同样渲一张做对照**，逐块确认无粘连、无裁切。
- **容量由外框尺寸算出，不由肉眼数。** 从 `word/document.xml` 取该形状的 `<wp:extent cx cy>` 与 `<wps:bodyPr
  lIns tIns rIns bIns>`：`可用宽 = cx/914400*72 - 2*lIns/914400*72`。单行宽度按 9pt 微软雅黑估算：
  **全角/中文 9.0pt、ASCII 字母数字 4.8pt、空格 2.6pt、ASCII 标点 3.0pt**；`ceil(总宽/可用宽)` 即行数，留 ~3% 余量。
  先算一遍**已经排好的旧版这段**来标定（它当前的首行通常占满 95–98%），再算新文案。
  实测：A-01 的「实习经历」框（cx=6429375 / cy=1200150 / lIns=rIns=914400）可用区 491.9 × 87.3pt，
  **只装得下「标题 1 行 + 正文 3 行」≈ 中英混排 ≤190 字**，第 4 行会被下方「专业技能」色带遮掉。
  超了**压措辞，不要降字号**——用户要求格式与模板完全一致。
- **框已满又要加新内容时，腾空间的第一顺位是「删同框内的重复句」，不要先砍实质内容。** 两类零损失可删项：
  正文开头重复标题括注的句子（标题已写「（校级重点大创项目 · 横向课题）」，正文又写一遍），
  正文末尾重复下方荣誉栏的奖项句。**判据是「删掉后该信息在别处仍出现一次」**；腾不出等量字数再考虑砍 bullet。
  净增字数控制在 **≤ 删掉的字数**，别指望估算器上那点百分比余量。
- 模板段落自带**段前/段后间距**，克隆段落时会一起复制，几段下来就把框撑爆。填字后逐段把 `w:spacing` 的
  `before/after` 置 0 并设固定行距（`lineRule="exact"`）。
- `w:pPr` 子元素有 schema 顺序，插入 `w:spacing` 必须**按序插入**（`snapToGrid` 之后、`ind` 之前），
  直接 append 会让 Word 判定文档损坏。
- 想在固定框里装更多内容：先**把每行压成单行**（≤50 全角字宽），再降字号到 **8.0–8.5pt**，通常能多装 30–50%。
- 模板自带照片 / 籍贯 / 政治面貌等字段时**保留**——以模板字段为准，不按通用规则删。
- 版本号**沿用用户的命名**（v7 / v8 / v9…），不自造。

### 文本框改字的可复现做法（`scripts/docx_textbox_edit.py`）

不要手工拼 XML。用脚本三步走：`probe` 量全部文本框容量 → `width` 试探文案宽度 → `rewrite` 落地并自检。要点：

- **匹配键必须是「单个 run 内部」的子串。** 一段文字在 XML 里被切成十几个 run，用整段原文当键会**静默 0 命中**
  （断言数要对得上，两个副本就该是 2）。脚本 `expect` 不匹配就**不写文件**。
- 只换 `<w:p>` 内部，**保留原 `<w:pPr>`**（段间距、缩进、编号都在里面）。
- **新 run 的 `<w:rPr>` 从原段落里抽，不要自己拼**：取第一个含 `w:b w:val="0"` 的 run 当正文样式、第一个含
  `<w:b/>` 的 run 当加粗样式。模板的加粗 run 用的是 `w:cs="Times New Roman"`，自己写会和模板不一致。
- 加粗数量对齐原版风格（A-01 那种一段 3–4 处），别把半段都加粗。
- 改完验三样：① 全文 `w:t` 文本 diff，确认**除目标段外零改动**；② PDF 页数与改前相同；③ 渲染 PNG 目视无粘连。
- 收尾必须提醒用户**在 Word 里再开一次**（LibreOffice 与 Word 换行点可能差一两个字），并给一句具体退路：
  「若某处变成 N+1 行，把 X 改成 Y 就少 N 字」。

### 固定框改字的硬核验收（LibreOffice 会说谎，务必按这五步走）

**LibreOffice 会把溢出内容直接裁掉——多出来的那一行凭空消失，页数和下方版面都不动。**
**Word 同样会静默裁掉溢出的最后一行，`ComputeStatistics(2)` 依旧报 PAGES=1。**
所以「页数=1」「下方没位移」「目视没粘连」**都不能证明框没溢出**，必须数框里的文字行数。

⚠️ **不要用 PDF 文本抽取（`pypdf` / `pdftotext`）当裁切检查 —— 被裁掉那一行的字形仍在 PDF 内容流里，抽取得到全文，
看起来「完整」，实际渲染时根本不显示。** 唯一可靠的检查是**渲染成图后逐条目视每段正文的末句是否都在**。

1. **数行数**（不看渲染图，用像素）：在框的 x 范围内统计每行暗像素，聚成行后数数量。
   改前改后必须**相等**；若新增一行其高度明显变小（如 h=5 而正常 h=20），就是被裁了。
   ```python
   a = np.array(Image.open(png).convert('L')).astype(int)
   dark = (a[y0:y1, x0:x1] < 150).sum(axis=1)          # 框内区域
   rows = [y for y in range(len(dark)) if dark[y] > 3]
   # 把相邻 y 聚成行；行的 (起点,终点,高度) 就是每行文字
   ```
2. **逐行像素差**：改前/改后渲染逐行比对 `|a-b|>40`。差异必须**只落在被改的那个框内**；
   框以下整片像素相同 = 下方版面没被挤动。这一条比目视可靠得多。
3. **估算器按 ceil 用**：单行宽 9pt 微软雅黑（全角 9.0 / ASCII 4.8 / 空格 2.6 / 标点 3.0pt），
   行预算 = `cy/914400*72/12pt`。实测**估算器的 ceil 与 LibreOffice 的实际换行完全一致**，
   可以放心当预算尺：新增文案要卡在 `est ≤ 原段落行数`（留 10–15% 余量给 Word 换行差异）。
   ⚠️ **但 `probe_boxes.py` 打印的 `est height used: N% of M pt` 是另一套读数，而且系统性偏乐观 —— 实测报 70% 时框其实已经满了。**
   判读规则：**把该百分比按「无余量」读（≥70% 即视为满）**；框里还能不能加字，用「同框内已排好的现有行数」去推，不要用这个百分比。
4. **整块移动用「段落 XML 原样搬运」**，不要重排文字：把 A 段的 run 内容整体复制到 B 段的槽位
   （只换 `<w:p>` 内部、保留各自 `<w:pPr>`），被搬运的那段**零重排风险**，只需重算新写的那段。
5. **Word 渲染才是交付标准**（LibreOffice 只用于快速迭代）。Windows 上可用 COM 导出，先确认没有 WINWORD 在跑
   （`tasklist | grep -i winword`；`~$xxx.docx` 锁文件可能是崩溃残留，不等于 Word 开着）：
   ```powershell
   $w = New-Object -ComObject Word.Application; $w.Visible=$false; $w.DisplayAlerts=0
   $d = $w.Documents.Open($src, $false, $true)      # ReadOnly
   $d.ExportAsFixedFormat($out, 17)                  # 17 = PDF
   Write-Output ("PAGES=" + $d.ComputeStatistics(2))
   $d.Close($false); $w.Quit()
   ```
   **含中文路径的 `.ps1` 必须以 UTF-8 BOM 存盘**，否则 PowerShell 5.1 按 ANSI 读、路径乱码、`Documents.Open` 报 COMException。
   可靠做法：**复制上一版已跑通的 `.ps1`，用 `sed 's/vNN/vMM/g' 旧.ps1 > 新.ps1` 改版本号** —— `sed` 按字节处理，
   BOM 与中文路径原样保留；`write_file` 直接生成的脚本往往没有 BOM，别用它写这类 ps1。
   执行时 `cd` 进脚本所在目录、用**相对 ASCII 文件名**调用（`powershell -ExecutionPolicy Bypass -File toword_pdf_vMM.ps1`），
   别把中文绝对路径放到命令行上再转一次码。
   交付的 `.pdf` 用 Word 导出的那份，别用 LibreOffice 的。
   发给用户时**同时给一份纯 ASCII 文件名的 PDF 副本**（如 `ZhangSihao-Resume-vNN-AI-Agent.pdf`）：IM 通道上传
   非 ASCII 路径偶发失败，多这一份几乎零成本，用户也能直接换名投出去。

### 增量改版：一版一脚本，从**上一版 docx** 改

用户会一版一版提小改动（去掉某条 / 某栏换个写法）。这类改动**不要回到底版重建**，也不要手改 docx——
**新建 `_tools\build_vNN_<方向>.py`，SRC = 上一版 docx，DST = 本版 docx**，只做那几处增量。
理由：回底版重建等于把上一版已验收的十几处排版参数再赌一遍；增量改天然满足用户那句「其他地方不许动」。
运行方式：`python _tools/build_vNN_<方向>.py build`（脚本里内建全部断言与文本级 diff）。

增量改的落地方式：**按 `w:t` 精确文本替换**（只换内容完全等于旧串的那个 `<w:t>`，外层 `<w:r>` / `<w:rPr>` 一字不动），
比按文本框块改写稳得多，也不受块结构变化影响。

四条必须做的自检：

1. **替换数 == 改动前该串的出现数**。先数旧串出现几次，替换后再数，不等就断言失败、**不写文件**。
2. **断言必须用 `w:t` 精确相等，不能拿子串包含当检查**。子串会骗人：新串 `github.com/user` 是旧串
   `github.com/user/repo` 的前缀 —— 用 `count(新串) == 2` 当检查时，**两个副本改好一个、漏一个也会「通过」**。
   正确姿势：`len([x for x in w_t列表 if unescape(x) == 期望整串]) == 2`。
3. **不能只改「第一个命中该文本框的块」**。同一个框可能在不同结构里各存一份（`mc:Choice` + `mc:Fallback`，
   个别文件还有独立存在的 VML 文本框），按块找会只改到一份，Word 与其他渲染器显示不一致。
   按精确文本**全局**替换，落盘前断言一处不剩。
4. **交付前跑一次 `w:t` 文本级 diff（改前/改后 Counter 对比）并把它贴给用户** —— 这是「其余一字未动」的唯一证明。
   正常结果只有寥寥几行变化（目标串、被删条目的标题/正文/填充空格），多出第九项就说明动到别处了。

**删段落会让固定高度的框底部空出一块。** 文本框不会自动收缩，删掉一两行后框底到下一个标题之间会留白（几行高）。
用户说「其他地方不许动」时**不要顺手调版面**：把留白量估出来，给 2–3 个修法（把下方各框整体上移 / 缩小该框高度 /
不动）让他选。

**但先问一句「上一版这里是什么」。** 用户提「去掉某条」时，真正想干的常常是**恢复更早一版的结构**，而不是
留一块空。首选修法是**从旧版把被换掉的那一条整条搬回来**（标题段 + 正文段按 run 原样搬运，搬回后断言与源
版本**逐字一致**），一次同时解决留白与「框架不要变」；只有旧版也没有对应条目时，才按上面三个修法让他选。

**用户只说改动范围、不说具体改法时，只落有实证支撑的那一处，并把推断讲明。** 例：「仅修改与毕设相关的地方」
—— 那就只在毕设条目上做**可证实**的那一处（起止日期与仓库 `git log` 对齐），并明确告诉用户「我这样理解、
只改了这一处，你要的是这个吗」，而不是自己替他把那条重写一遍。

### 条目的删 / 并 / 回搬

**用户问「X 能不能并进 Y 里？不行就不加」时，先翻旧版简历找依据，别凭感觉答。** 判据是**它们在更早那一版里
本来就是不是同一条**：如果是（例：毕设条目的旧标题就是「…（毕业设计）—— 基于 <某框架> 架构的运行时实现」），
答案就是**能，而且本来就该并**——把「源码研读 / 框架学习」这类内容压成一句话接在它所服务的项目正文末尾，
独立那一条整条删掉。用户说的「不行就不加」是真的：**这不是补内容的许可，是删条目的许可**，找不到依据就别塞。

- **「自学 / 精读源码 / 框架研读」类内容不该单独成条**，除非它自身就是交付物（有仓库、有报告）。单独列出来
  面试官只会问「所以你改了什么」，而且会把同一件事拆成两条、把主项目拆弱。
- 合并后必须回头核对面稿 / `项目与经历-详细简介.md`：被删的那条在别处往往还有旧表述。

**并进正文的那句话按「字数和」定长度，不按行数试。** 拿**已排好的旧版同一框**的正文总字数当容量基准：
新增字数 ≤ 删掉那几条的字数，就不会溢出（实测 529+62 字 vs 旧版 597 字，一次过）。定稿前给新句子设一个
字数上限（这类收尾句 **60 全角字左右**够用），别写完再看。

**回搬旧条目时按 run 原样搬运，连标题里的填充空格 run 一起搬**（模板靠这些 run 把日期顶到右端），搬完断言
`与源版本文本逐字一致`。搬回来的条目正文里常带一句奖项（如「项目获 X 竞赛院级特等奖与校级铜奖」），会和下方
荣誉栏撞车——**用户说了「原样搬回」就不要擅自删，把它列为可选项交给他**，同时回搬后必须重扫一遍全文重复。

## 正文段落版（STAR）与压缩版

用户会把要点 bullet 要求改写成两组文本，都要给：

- **完整版**：每项目约 400 字、一段话，S→T→A→R 齐全。适合不走固定模板的排版。
- **压缩版**：每项目约 200 字、2–4 句；可能进一步要求"某项目压成两句"，那就只留最强的 A 和 R。
- 写完后附一张 **S/T/A/R 落点表**（哪句是哪个字母），用户会拿它核对。
- 标题行已有**项目名与时间**时，正文段落**不要再重复**——用户会要求"把前面那句去掉，直接开始介绍"。
- 段落版字数远超模板可容量，交付时必须主动提醒"直接塞回固定模板会溢出"。
- 用户可能**不知道 STAR 是什么**（会直接问）。解释时用**他自己简历里的项目**做 S/T/A/R 对照表，别只背英文定义；
  并点明 **A 和 R 是重点、S 和 T 可以极短** —— 他接着就会自己提出"把前面那句去掉"。

## 模拟面试 / 压力面

用户会要求以**面试官视角**做压力面。约定：

- 记录目录：`D:\找工作找工作\简历优化\压力面记录\`，一份记录文件含简历要点 + 逐轮问答 + 当场判定。
- 开问前先 `read_file` 提取用户指定的**当前最终版**简历，把要点落进记录文件 —— 面试官手里只有这页纸，凭记忆提问会失焦。
- **一次只问一题**，答完追问；用户答虚了就继续追同一题，不给台阶。**不要一次性把题库倒给用户。**
- **每轮答完立刻把「问答 + 当场判定」追加进记录文件**，不要攒到面试结束再写：长访谈会跨很多轮甚至触发上下文压缩，记录文件是唯一活下来的凭据。
- 判定分**给分 / 扣分 / 致命处**三栏写；用户会拿它复习，笼统的「表现一般」没有用。
- 追问最有力的方式是**念他自己写的原文**：把简历那一行读出来，用他自己的用词当证据
  （例：条目里「官方」出现两次、他自己的贡献一个字没写 → 问「这个主循环是你写的还是你读的」）。
- 用户的原始回答**逐字保留**，不要润色。
- 面试结束后，对**每一处表现不佳**给出可执行的方法建议，而不是笼统评价。
- 出题要打在简历最软的地方：岗位与项目的错位（投 Agent 岗却只有 RAG）、量化数字的方法论、
  "独立开发"却没有测试/CI、奖项重复与级别、GPA 换算。
- **收尾必问两题**：①「这个岗位只招一个人，我为什么选你？（30 秒，不要套话）」
  ②「你简历上哪一句话，是你自己心里最没底的？」——第 ② 题是**直接把最脆弱的条目引出来**的最快手段，
  不需要面试官自己猜。诚实指认 + 能定位根因的要给分（成长性），但**必须接着要"你打算怎么补"**：
  只说出短板、不给补法，恰恰是本类候选人最常见的缺口（"发现而不给方案"）。
- **面试本身就是一次简历审计**：把每轮的失分点攒成一张按严重度排序的修复清单交给用户，
  而不是只给一个笼统评价。清单要带优先级与工作量估计（哪些是 30 分钟就能修的）。

## Pitfalls

- **「页数 = 1」不等于排版没问题**：绝对定位文本框的溢出表现为文字重叠，必须渲染目视检查。**Word 也会静默裁掉溢出的最后一行，页数照旧报 1。**
- **PDF 文本抽取不能用来验裁切**：被裁掉的字形仍在内容流里，抽全文会给出**假通过**，只能渲染成图目视。
  同理 `probe_boxes.py` 的 `est height used` 百分比要**按无余量读**（报 70% 通常已经满了）。
- **匹配键必须用模板原文**：全角空格（`姓　　名`）会让看似合理的键静默失配，整块内容不替换。
- **重复记录会减分**：奖项里「铜奖」和「三等奖」可能是同一次比赛被记了两遍；实习和项目可能是同一件事写了两栏。
  看到疑似重复必须主动核实。**从旧版回搬条目后要重扫一遍**：旧条目正文常自带一句奖项，回搬即与荣誉栏撞车。
- **版面次序错误是常见退步**：把 VTK/桌面端这类与目标岗位无关的经历留在第 2 位，会把黄金位置浪费掉。
- **markdown 里含 `\` 的 Windows 路径**：patch 工具会双重转义，先 read_file 确认文件里的实际字符再改。
  **尤其小心路径里含 `\r` `\t` `\b` 的片段**（如 `` `_tools\rewrite_x.py` ``）：patch 的 new_string 会把 `\r` 当成**真实回车**写进文件，
  直接把这一行劈成两行（`_tools` + 换行 + `ewrite_x.py`），而控制字符扫描只查「非 CR/LF」时查不出来。
  写这类路径要么用 `\\` 转义，要么改用 python 脚本做替换，改完用 `repr(行)` 逐行验一遍。
- **多人/多 agent 同时维护同一个 md（如 `00-总索引.md`）**：patch 前先 read_file 读全文。工具会警告「被兄弟 agent 改过」，
  如果只看片段就 patch，很容易把它刚补的注释 revert 掉——事后必须重读并恢复。
- **别把待补信息写进简历正文**：`[待补]` 只属于内部工作稿，交付前清掉或换成合理值 + 说明文档标注。
- **过程指标冒充结果指标**：`块数 -44%`、`清洗压缩 24%` 这类数字证明的是「流程变了」，不是「效果变好了」。
  要么补最小对照实验把它升级成结果指标，要么降级成动作描述——**不能留在质量宣称旁边**。
- **定义不出分子分母的指标一律不留**：典型是「边界误差 <1%」。留在简历上等于给面试官递刀；改成做法描述
  （「跨段边界采用偏移映射对齐，已人工抽检 N 处」）风险归零。
- **真实但规模小的数字同样是负债**：判定不是「是不是真的」，而是「**它会不会引出答不上的追问**」。
  「最大表几万条记录」会招来「百万级还行吗」「这量级你怎么验索引」。只写动作不写规模，见 `references/bullet-rewriting.md` 5.7。
- **同一句里弱化词与强化词互斥**：「参与一套系统开发，前后端由本人独立承担」——面试官第一刀就问这个。
  清理时把弱化词删干净，别让两种口径在同一行对打。
- **别给「没有 bug 的经历」编 problem→solution**：用户答「整体顺利」时，简历里就不要出现「针对 X 问题…」；
  真实摩擦点只用来准备**面试口答**（见 `references/bullet-rewriting.md` 5.8）。
- **贪心 `re.sub(r'(<w:pPr>.*?</w:pPr>).*', ...)` 会连段落的 `</w:p>` 一起吃掉**，写出的 docx XML 不可解析
  （LibreOffice 只报一句 `Error: source file could not be loaded`，看不出真因）。改前先 `ET.fromstring` 硬断言，不通过就不写文件。
  正确做法是只替换 `</w:pPr>` 之后、最后一个 `</w:p>` 之前的内容。
- **拼接重建段落序列时，切片上界用「段落起点」会静默吃掉那一段**：`inner[:spans[0][0]] + 新段 + …` 里
  `spans[0][0]` 是第 0 段的**开头**，于是第 0 段整段消失。危险在于**段落计数断言抓不到它**——删两条补两条时
  计数守恒，断言照样通过。拼接后必须**逐条断言「每条保留条目的标题与正文仍在」**，计数相等不能证明内容对。
- **`<w:t` 的正则要写成 `<w:t(?:\s[^>]*)?>`**。写成 `<w:t(?:[^>]*)?>` 会把 `<w:txbxContent>` 当成前缀匹配上，
  diff 出来的「文本」全是整段 XML，改没改根本看不出来。
- **`soffice -env:UserInstallation=file:///...` 在中文路径 + 反斜杠下会加载失败**（`source file could not be loaded`）。
  同一台机上省略该参数直接 `--convert-to pdf` 反而正常；只有用户已经开着 LibreOffice 时才需要隔离 profile。
- **做完简历改动，必须回头核对面稿与自我介绍**：新栏目一进简历，`项目与经历-详细简介.md` / 自我评价 / 面试稿里
  关于同一项目的旧表述立刻变成矛盾源。交付时把「哪几处还写着旧项目名」列成一张待改清单一起给。
  **反向也要查**：`附-*-面试口径.md` 里的「真实状态表」常停留在项目开工前（写着「目前还没有这个代码」），
  项目推进后它会变成**自伤**——照它背等于主动少说自己最强的资产。每次更新简历都要重读该表并逐行刷新状态。
  **最重的一种是两份材料里写着两个不同的项目**：简历写「面向开放世界的调研型智能体」，
  详细简介却按另一种架构（如「课程知识库 + 某检索底座」）写。这不是措辞差异而是**叙事冲突**——
  面试官一问「你的检索工具叫什么名字」，报出工具名就当场自证了另一套不存在。
  **处理顺序：先让用户在两个叙事里选一个（把课题名一起定下来），再动任何一份稿子**；
  选完要一次改干净，漏掉的那份会在网申表单、答辩 PPT、导师周报里各出现一次。
