# 核实简历上的项目 claim（用仓库历史与运行期埋点，不靠记忆）

简历上每个数字/技术名词都会被追问，而当事人**几个月后普遍记不清自己为什么这么做**。
只要那个项目有本地 git 历史或运行期日志，就不要靠回忆——读提交历史、他自己写的项目文档、以及数据库里的埋点。

## 何时用

- 要为他准备面试，且简历上有**未自证的量化指标**、或他自己说“忘了当初为什么”
- 准备「项目最难的点是什么」这类必问题
- 要把一段经历扩写成网申用的项目简述/职责
- 用户问「这个数字/这个功能到底存不存在」

## 步骤

1. **找到仓库历史**
   - 本地备份：`2-简历\_repo备份\<项目>-完整历史备份-*.bundle`（脱敏前的完整历史）
   - 或线上仓库：`github.com/<user>/<repo>`
   - 恢复：`git clone "<bundle 原生路径>" C:/Users/Lenovo/AppData/Local/Temp/<短名>`
     然后用 `git log --oneline`、`grep -rn "<数字>" .`、`git show <commit>^:file.py` 对比改动前后。
2. **先 grep 指标数字**：`grep -rn "4269\|7600\|43%" --include="*.md" --include="*.py" .`
   往往直接命中 CHANGELOG 或 references 里的说明。
3. **读项目自己的文档**（按价值排序）：
   - `CHANGELOG.md` —— 每次改动的背景/改动/效果
   - `references/decision-log.md`（或 `docs/decisions*`）—— 决策编号 + 根因 + 方案对比 + 敲定理由
   - `README.md`、`todo.txt`、配置模板——参数与策略名
4. **读配置拿硬参数**：chunk 大小/重叠、嵌入与重排模型、TOP_K、索引库类型。
   面试报得出这些具体值，是“真做过”和“读过文章”的分界。
5. **定位那个数字的成因**，并准备一句能自证的替换说法（动作描述 + 已知代价），
   而不是继续引用一个没有对照实验支撑的百分比。
6. **grep 功能名词是否真存在**（比核数字更重要，因为功能名被追问的几率更高）：
   ```bash
   grep -rn "<功能名>" --include="*.py" --include="*.md" .   # 整仓库
   git log --all --oneline --grep="<功能名>" | cat              # 含已删除的历史提交
   ```
   典型结局：**零命中**（简历上写了、代码里从来没有）或**只存在于已被移除的提交里**（`git log --grep` 能查到但当前代码没有）。
   两种都必须处理：删掉，或换成代码里真实存在、能指到文件与行号的等价功能。
7. **参数值不在仓库里就别硬报**：`config.py` 常被 `.gitignore` 排除（模板 `config.example.py` 里也没有），
   于是「8 轮窗口」这类具体数值**无法从仓库确认** → 让他去本机 `config.py` 看一眼，或把措辞降成范围描述。

## 运行期埋点：性能数字的唯一可靠来源

比读代码更值钱的是**他应用自己写下来的日志**。以本地 RAG 项目为例：查询日志落 MySQL
（`logs_ui.py` / `config.py` 里有库名表名与连接参数；库名形如 `ragsearch`、表 `qa_logs`），
每行带**分段耗时 + token + 策略名**，天然支持“前后对比”：

```sql
-- 按策略分组，一次拿到前后两代的全部指标
SELECT chunk_strategy, COUNT(*) n,
       ROUND(AVG(embed_time_ms)) embed_ms, ROUND(AVG(retrieval_time_ms)) retr_ms,
       ROUND(AVG(rerank_time_ms)) rerank_ms, ROUND(AVG(llm_time_ms)) llm_ms,
       ROUND(AVG(total_time_ms)) total_ms,
       ROUND(AVG(CHAR_LENGTH(final_context))) ctx_chars,   -- 上下文长度
       ROUND(AVG(llm_input_tokens)) in_tok
FROM qa_logs GROUP BY chunk_strategy ORDER BY MIN(created_at);
-- 按天看趋势（策略切换那天往往就是分水岭）
SELECT DATE(created_at) d, COUNT(*) n, ROUND(AVG(rerank_time_ms)) rk
FROM qa_logs GROUP BY DATE(created_at) ORDER BY d;
```

关键点：
- **先查这类现成埋点，再考虑跑东西**。他明确反对为核对一个数字重跑整条流水线（“不要你跑这么详细……查数据库的日志就行了”），
  而且重跑常因缺 `docs/`、缺索引/模型而根本跑不起来——仓库里 `.gitignore` 掉的正是这些。
- 用 `pymysql`，写成脚本交给 `terminal` 跑（沙箱解释器不一定装了驱动）。
- **MySQL 8 不允许在 `LIMIT` 里用同表的 `COUNT(*)` 子查询**（`ERROR 1064`）→ 分位数把整列取回 Python 侧算。
- **归因要克制**：不同策略的样本在不同时间段、索引内容也可能变过（例如中途移除了某类块）→
  「观测到 X 变了」可以讲，「因为 Y 所以 X 变了」要加前提。面试话术：
  “日志显示这两个阶段快了，但我没做受控实验，不能排除索引规模与机器状态的影响。”
- 这类数据能证明**素材更多 / 更快 / 更贵**，但**不能证明检索更准**（仍缺命中率评测集）——两条边界要分开说。

## 输出

- 突击稿里换掉不可自证的表述，补上「根因 → 方案对比 → 效果」的完整叙述
- 一份 `2-简历\<项目>-技术详解.md`：全链路、参数表、关键决策与踩坑、边界（哪些没做）、面试速答卡，
  外加一节**运行期实测数据**（表 + 解读 + 哪些不能由此推出）
- 一张诚实红线表（不能说 / 改说）

## 两种高价值产出模式

- **指标其实是“修 bug 前后对比”**：把“提升 X%”讲成“我发现自己中间版本有缺陷…根因是…改了…指标回归”，
  比宣称提升更有说服力，也解释了为什么现在没有评测集。
- **静默失效的功能**：上游没把字段传下来、调用方判空直接跳过，功能**不报错也不断言**地一直没生效。
  这类发现讲出来，等于在说“我会读数据流，不只看日志”。

## 注意

- 机试/测评原图带「保密资料，请勿外传」水印 → 只在本机留存，不外传、不上传。
- 仓库里的 API key、个人邮箱等敏感信息**不要抄进任何交付文件**（数据库连接参数同理，写“读项目里的 config”而不是抄值）。
- 没查到就说没查到，别用“大概是…”补一个听起来合理的成因——那是把风险转移到面试现场。
- 核出来的“代码里没有”的结论，要**明白告诉他并给出替换话术**，不要只是不提。
