# 多轮对话与工具调用轨迹的指标

单轮结果集量不出"第 3 轮有没有引用第 2 轮产出的 id"这类**跨轮状态依赖**，也算不出"轨迹对不对"。
这一层专门补它：**同一个任务，结果分与工序分可以完全背离**。

## 一、先分档：指标是怎么算出来的

外部标准里的同名指标，官方口径常常不是代码。三档（arXiv:2507.21504 §4.3）：

| 档 | 适合 | 代价 |
|---|---|---|
| **code-based** | 有确定性判据的（工具名、参数、顺序、产物计数） | 最客观、可离线复算；对开放式回答无能为力 |
| **LLM-as-a-judge** | 语义判断（faithfulness、相关性） | 可扩展但需人工校准 |
| **human-in-the-loop** | 主观 / 安全关键判定 | 金标准，但贵、不可扩展 |

**把能用 code 判的全部压到第一档**，其余显式标注"本表未纳入"，不要为凑齐指标表而给语义项硬造代码。
报告里 code 档与 judge 档**分表或分栏**。

## 二、工具调用 / 轨迹指标（定义与出处）

### RAGAS —— 文档里有专门的 "Agents or Tool use" 指标组

| 指标 | 官方定义（摘） | 实现要点 |
|---|---|---|
| **ToolCallAccuracy** | *"a **binary** score based on **exact order and content match**"*；另有 `strict_order=False` 的 Flexible Order Mode 供并行调用 | 二值。同时报两种匹配口径：`名字+参数逐字相等` 与 `只看工具名` |
| **ToolCallF1** | *"**softer** evaluation… helps quantify how close the agent was to the expected behavior even if it **over- or under-calls**"* | ⚠️ **官方由 LLM 判**"两次调用算不算同一次"；纯代码实现只能做近似，必须标注 |
| **AgentGoalAccuracy** | *"binary metric, 1 indicating that the AI has achieved the goal"* | 可用产物计数做 code-based 代理（该会话是否产出应有类型的产物）——**必要不充分**，要写明 |
| **TopicAdherence** | precision = 在域内作答 /(在域内作答 + 在域外作答)；recall = 在域内作答 /(在域内作答 + 本该答却拒答)；F1 = 2PR/(P+R) | 需要预定义主题 + 一组**域外探针题**（"帮我写个 Java 快排""今天几号"），否则算不出来 |

出处：`docs.ragas.io/en/stable/concepts/metrics/available_metrics/agents/`

### TRAJECT-Bench（arXiv:2510.04550）—— 解决"只看最终答案看不出根因"

| 指标 | 定义 | 实现要点 |
|---|---|---|
| **Trajectory Exact-Match** | 整条轨迹与 gold 完全一致 | 布尔 |
| **Trajectory Inclusion** | *"whether the required tools are invoked and **in the correct order**"* | 求"必需序列"与"实际序列"的**最长公共子序列 / 必需项数**；=1.0 ⟺ 必需序列是实际序列的子序列。**用 LCS 而非贪心匹配** —— 贪心在"必需顺序与实际部分相反"时依赖扫描方向，同一输入会给出不同结果 |
| **Tool-Usage** | *"**schema constraints, formats, and value checks** of the tool's inputs"* | 必填齐全 + 枚举合法 + 数值区间合法。**枚举与区间从被测系统的工具 schema 里读，不另立标准** |

**它点名的四类失败模式**（按这几类去分组报，比只报一个总分有用）：
相似工具混淆 / **参数盲选**（只看描述不看参数）/ **冗余调用**（`Related-but-unhelpful`：保守的"全都查一遍"；
`Unrelated`：跑偏）/ 从间接问法里推不出意图。

> ⚠️ **冗余调用是最容易被误读的一类**：结果分与严格轨迹分同时出现 "1.0 / 0.0" 时，
> 先量**冗余调用数**再下结论 —— 多数情况是"多做"而不是"做错"。

### τ-bench（arXiv:2406.12045）—— 可靠性

| 指标 | 公式 | 含义 |
|---|---|---|
| **pass^k** | `C(c,k)/C(n,k)`（c 次成功 / n 次试验）无偏估计 | **k 次试验全部成功**的概率 → 量**一致性/可靠性** |
| **pass@k** | `1 − C(n−c,k)/C(n,k)` | **至少一次成功** → 量**能力上限** |

两个要对照着看：能力上去而可靠性没上去，是最常见的失败形态（原文实测 pass^1≈61% 时 pass^8 已跌到 <25%）。
`n < k` 时返回"无法估计"，不要返回 0。

## 三、多轮题集怎么设计

1. **每题都要能判"该调哪个工具 + 参数是什么"**，且**规则写在数据里**（`expect_tools` 一类字段），
   加题不用改代码。
2. **必须包含跨轮状态依赖的轮次**，这是多轮集唯一不可替代的价值：
   后一轮要求"改上一条路线"（要引用上一轮产出的 `route_id`）、"把刚才那篇抓下来"（要用上一轮的 `source_id`）。
   判据写死"必须复用上轮 id，不能重新生成也不能反问用户要 URL"。
3. **覆盖全部可调用工具**，尤其那些**只在特定句式下才该出现**的边角工具（拆并行子任务的、
   改已有产物的）—— 它们在自造集里最容易被漏掉。
4. **最容易判错的是 `kind` / 枚举参数**：用户说"做成抽背卡"就必须 `kind=card`、说"记条笔记"就必须 `kind=note`。
   单独列成重点轮次。
5. **配一组域外探针**（不计入对话轮数），供 TopicAdherence 用。
6. 每轮标注"这轮在测什么"，汇报时能直接指出弱在哪一环。

## 四、按轮归属：两个必踩的坑

- **不要用 `step` 号当跨轮游标**：`step` 是**轮内**编号，跨轮用会把后面几轮全漏掉。
  用"每轮前后各取一次快照 + id 差集"归轮。
- **列表常常是逆序的**（`ORDER BY created_at DESC`）：取完差集还要按 `(created_at, step)` **升序**排，
  否则轨迹顺序全反，Inclusion / Exact-Match 一律判错。

## 五、汇报口径

固定四行起：目标达成 · 必需工具全中且顺序对 · 参数合法率 · **冗余调用数**。
另外报准确率时**带上置信度区分力**（答对平均置信度 − 答错平均置信度），
它决定"低置信转人工"这条策略能不能立。
