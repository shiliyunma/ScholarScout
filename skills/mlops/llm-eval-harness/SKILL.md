# 自动化评测流程（LLM / RAG / Agent）

把「系统好不好」变成能进论文、答辩、简历的数字。适用：比较两条臂、做消融、给系统定基线，
或用户说"设计一套自动化测试流程 / 评估指标要合理有效"。

产出物固定三样：**题库文件**（判分规则写在数据里）、**可重跑的跑批脚本**、**可视化报告**。
指标要三层（规则自动 / 检索金标准 / 语义与人工），每项都写清分子、分母、谁判的。

## 工作顺序

1. **先搜业界标准，再定指标**——不要凭感觉发明指标。至少查到并引用：RAG 三维度
   （RAGAS / TruLens RAG Triad：context relevance / groundedness / answer relevance）、
   细粒度诊断（RAGChecker）、Agent 可靠性（τ-bench 的 pass^k；BFCL 的 AST 口径 + 延迟与成本并列）、
   LLM 判官的偏置与正确用法（MT-Bench 的位置/啰嗦/自我增强偏置；G-Eval 的 CoT 判分）。
   有领域标准就一并查（教育场景：北师大「北极星」基础教育大模型评测场，其
   "改写类题型成绩骤降"的发现直接支持把"同一知识点多种问法"做成独立测试组）。
   **交付一份口径文档**：每条写明「采用 / 不采用 + 为什么 + 出处」，用户会拿它去答辩。
2. **先写题库，再写指标代码**。每行 = 输入 + 金标准 + 判分规则
   （`gold_ids` / `gold_points` / `must_contain` / `must_not_contain` / `expect_tools`）。
   规则放数据里，加题不用改代码。分层覆盖：单跳 / 多跳 / 多轮指代 / **不可答** / **改写鲁棒**
   （同一知识点 3 种问法）/ 领域专项 / **边界对抗**（提示注入、要求编造并伪造出处、
   **前提错误**——学生说错前提时测"抗谄媚"）。用户在"输入要全面"上的底线是 **≥30 条**。
3. **定臂**：下界（无检索）/ 最强基线（固定流水线）/ 完整系统，三档跑**同一批题、同一套判分规则**，
   提升才可归因；有第二条能力通道就另加它自己的对照臂。消融用配置开关，不要改代码注释。
4. **实现三层指标 + 统计**（口径与公式见 `references/metric-design.md`）。每项写清分子/分母/谁判的。
5. **写指标自检 + 做注入验证**（见 `references/metric-integrity.md`）。这步最容易跳过，也最容易出事。
6. **跑批落 jsonl + 出可视化报告**：分组强弱、成本–质量、臂间差异是否显著、逐题热力图、
   失败清单（答辩要举失败案例时直接从这抄）。
7. **跑完复核再汇报**——复核清单见 `references/metric-integrity.md`。

## 硬规矩

- **标签由被测系统自己产出的指标，是护栏不是度量**：若题集的"期望值"本身就是用被测规则表/被测逻辑生成的，
  那它跟实现的一致率**恒为 100%** —— 它只能证明"规则没漂移"，证明不了"判对了"。报数时**两类必须分开写**：
  **护栏型**（改了实现就红的自洽性检查）与**度量型**（与人工/外部金标准比出来的准确率）。
  答辩上一句"我们的一致率 100%"会被"这不就是自己判自己"当场问穿；真带上信息量的是另一层指标与对照臂。
  自查：翻出题集，看每一列的"期望值"到底是谁写的 —— 人写的、外部拿的，还是被测代码跑出来的。
- **成对指标必须成对报**：拒答召回 ↔ 误拒率；出处命中 ↔ 引用可溯。只报前者，"一律拒答"
  或"乱编出处"的系统能刷满分。
- **结果分与工序指标分开报**：答案对 ≠ 流程跑全了（实测过一臂结果满分、工序只有 1/3）。
- **过程指标用严格口径，且“步骤要求”要写进题库**：“预期步骤全做到”才算命中；用并集会把“只跑一半”判成正确。
  同时**保留一个宽松口径做对照**（严格/宽松两个数一起报），否则分不清“口径变严了”还是“系统退步了”。
  要求走特定流水线的题必须显式标 `expect_tools`，否则模型可以自己把流程讲一遍而根本没调工具——
  实测一臂答案满分、工序实际只走了 2/6 步，**只看结果分完全看不出来**；靠人读记录才发现等于没有指标。
- **每个比例配置信区间**（小样本用 Wilson）；**同题多臂比较用配对检验**（McNemar 精确）。
  没检验支撑的"提升/下降"不许写进结论；p 不显著就说"这个样本量下区分不出来"。
- **重复运行报 pass^k**（k 次全对才算稳），别用单次成绩宣称可靠性。
- **判官分数必须人工校准**（Cohen's kappa ≥ 0.6）才能进结论；理想情况判官不用主模型。
- **题库/代码/配置版本要对齐**：跑批前先 commit；`--tag` 让不同批次结果并存、不互相覆盖。
- **mock 和小模型的数字只能证明链路通**，报告顶部要自动打警示条；结论只能来自目标模型。
  本地小模型不会可靠地发出结构化 tool_call（会把调用写进正文文本），会把 Agent 架构
  显得比固定流水线更差——那是模型问题，不是架构问题，别据此下结论。
- **离线打桩集只证明逻辑自洽，证不了"能跟真实接口对上话"**：另配一套真接口端到端集，
  **每个里程碑收尾跑一次**。接口边界上的缺陷在离线集里是零信号，实测一次性暴露过五类：
  工具名/参数字符集被 API 拒收（点号 → 400）、合规逻辑把官方 API 也拦了（robots 禁 `/api/`）、
  查询语法写成精确短语导致恒 0 条、"全部来源失败"被当成"没结果"返回、推理模型的 token 额度不足。
  离线集全绿时它们一条都不会红。
- **改了判分规则就重算分数，不重跑模型**（实现一个 rescore 入口；模型有随机性，重跑会让两次不可比）。
- **门槛只用稳定统计量**：比率型指标（占比 / 命中率 / 撞车率这类）可以当 pass 门槛；
  **极端值统计量**（如"全部样本里的最小距离"——从上万到上百万个样本里取极值）与**全局聚合量**
  （如单一全局序参量）逐次波动可达 10 倍，只能展示或做宽松兜底。给它们设严格门槛的自检会随机失败，
  然后人就会去调阈值而不是修问题——这是自检设计里最容易走歪的一步。
- **消融必须写进判据，而不只是跑一遍展示**：同一份代码只把一个组件 / 权重置 0，**要求该臂指标显著劣于基线**
  才算通过。只展示不判定的话，一个"什么都没做"的退化实现能通过全部单项指标（真实踩过）。
- **各臂条件必须完全相同，包括预热 / 静置时间**：基线 300 步、消融 360 步这种不对等会让只在后期才现形的
  缺陷照不出来（实测：把静置时间拉长后才发现"修补后又立刻被下一步积分推翻"的残留问题）。
- **阈值取与实测同量级并留 3~10 倍余量**：测出 1e-4 就不要写 2e-2 的门槛。报告里注明结果是单次快照
  还是多次统计、以及逐次波动幅度，别把单次快照写成小数点后两位的规格值。
- **别在会冻结 / 虚拟化时钟的环境里测时序**：虚拟时间（`--virtual-time-budget`、fake timer、模拟时钟）
  会让 `performance.now()` 不再推进，每步耗时全测成 0 且不报错；要真实耗时就用真实时钟跑。
- **题集的来源要分档，别拿最差的一档当证据**：`Synthetic`（LLM 读规则生成，中）<
  `SessionDB`（**从真实对话历史里挖**，高）< `Golden`（人工手写，最高）。自造题集最典型的两种失真：
  **分布是假的**（真实流量里"你好/测试/继续/卡住了"这类过程性对话能占到近四成，自造集却常是每类均匀几条）
  与**漏掉真实分支**（真实用了某个动作、某个 `kind`、某个参数组合，自造集里压根没设）。
  先去挖真实历史、再按真实分布补题，顺序别反；先造题再找数据必然对不上。
- **基线与题集必须出自不同来源**：看完题集再写的 if-else 规则 = 把答案抄进了规则里，它会跑出接近满分，
  而这个数字**零外推价值**。要么盲标（写规则的人只看接口定义、不看题集），要么如实标成"上界"。
  这条与"护栏型 vs 度量型"是同一族问题：**先问每个数字是谁写的**。
- **预测标签与金标标签必须走同一套口径**：换了判据键的语言/命名，模型会**忠实地按新键返回**，
  而金标还是旧键 → 字符串永不相等 → 判出**一个完全错误的 0 分**，读起来像"模型这一类完全不会"。
  加一层规范化映射，并在自检里放一条"同一份输出换键口径评，分数应等价"的用例。
- **轨迹指标必须分层报，否则画像会反向**：结果分（目标达成）与工序分（工具调用对不对）能同时出现
  "1.0 / 0.0"——真相常常是**它多做而不是做错**（该调 1 个却调了 5 个，即 TRAJECT-Bench 点名的
  `Redundant tool calling`）。固定同报这四项：目标达成、必需工具是否全调到且顺序对、参数合法率、
  **冗余调用数（实际调用次数 − 期望次数）**。少报任何一项都会给出错误结论。
- **置信度区分力比准确率更能决定这套东西能不能用**：算"答对时平均置信度 − 答错时平均置信度"。
  它才是"低置信转人工 / 退回大模型"这类路由策略的依据 —— 准确率 56% 但区分力 +0.3 可用，
  准确率 60% 而区分力 +0.15 反而不可用。**换提示词语言或换判据写法会让模型更自信、同时区分力变差**，
  所以两个数必须一起看，不许只挑好看的那个报。
- **prompt / 判据文本的详细度必须实测选，别凭感觉加细节**：把"带典型例句的详尽判据"与"一句话判据"对拍，
  实测详尽版反而明显更差，且**在中文自造集、英文自造集、真实集上三次方向一致**（差值 −36.7pt / −23.3pt / −8.4pt）。
  改 prompt 是**实验**，不是编辑：必须留对照臂。
- **code-based 与 LLM-judge 两套数字不许混着比**：外部标准里的指标，官方口径常常是 LLM 判
  （如 RAGAS 的 Tool Call F1），而你的实现是确定性代码。要么两版都报（"名字+参数逐字相等"与"只看工具名"），
  要么在报告里显式标"这是 code-based 近似"。混着比会得出错误的优劣结论。
  三档划分依据：code-based / LLM-as-a-judge / human-in-the-loop（arXiv:2507.21504 §4.3）。

## 常见坑

- **自检/验证脚本必须走产品代码的同一条解析路径**：脚本自己读配置、把哨兵值（`auto` / `default` 这类"交给程序展开"的值）当成一个实体名去查，结果就是"查不到 → 跳过 → 退出码 0"：报出全绿而**一条都没验**。
  让检查器调用产品的解析函数，并且**任何解析不出来的名字都硬失败**；"一个都没解析出来"也不能算通过。
  （实测：默认配置下自检报成功，而当时唯一可用的来源根本没跑——这类假绿比报错危险得多。）
- **验证脚本的失败判据只对准"预期可用"的集合**：可选来源因未配密钥/未配实例而跳过属预期，要打印原因但不计入失败；
  否则脚本会因环境差异长期红着，人就开始无视它。
- **记录字段名别猜**：读错字段会让指标**恒为 0 且不报错**，看起来像"系统完全不会 X"。
- **"产物到底有没有"这类验收查询，先核对表结构再写 SQL，且宽 `except` 不许把它吞成假阴性**：
  判断"这轮有没有产出某类产物"时，先跑 `pragma table_info(<表>)` 确认外键列在不在——
  实测踩过：`documents` 表**没有 `session_id` 列**，`... WHERE session_id=?` 直接抛异常，
  被 `except` 吞成 `None`、再被当成 0，于是**把做对的对话判成失败**（目标达成率报成 5/6，实际 6/6）。
  产物与会话的关联常常要经中间表（如 `source_mentions` 才有 `session_id` + `doc_id`）。
  规则：验收查询的错误**要能让这一项标成"未测"而不是"未达成"**，并顺手把这条坑写进常量旁边的注释 ——
  静默失败比报错危险得多，因为它看起来只是一个普通的数。
- **引用至少两种写法**（直接写 id / 按序号 `[1]`），只认一种会系统性低估；"写了出处标记但说不出
  是哪一条"要算假引用，否则"假装引用了"反而不扣分。
- **不可答题的检索指标返回"不适用"**，不要当 0 分算进平均，否则不可答题会拉低检索指标。
- **分母为 0 时返回"无样本"而不是 0**：`0/0` 与 `0/N` 在纸面上必须分得开——"没有样本"
  和"全错"是两件事，写成 0.0 会把"这一轮根本没产出任何东西"读成"做得全错"。
  进一步：**一个在真实数据上分母恒为 0 的指标等于没测**。先查清它为什么是 0 —— 是这一轮没样本，
  还是判据在真实数据上**永不成立**（如"兜底命中"类指标，而真实来源永远会被某条通用规则兜住）。
  后者要么换判据，要么如实说明它只覆盖一种异常，**不要把它当成绩报**，也不要因为它在题集上分母是 2 就
  以为它在生产里也有分母。
- **推理模型把 reasoning token 也算进 completion**：`max_tokens` 给小了会出现 `content` 为空
  且 `finish_reason=length`，上层"解析失败 → 走兜底"看起来像解析器有 bug。额度按实测留 3 倍余量，
  并把 `finish_reason=length` 当成可判定的事实上报，不要静默返回空串。
- **离线兜底要标注**（检索源限速落回 fixture），否则那组数字会被读成"在线检索质量"。
- **报告只信结构校验**（SVG 合法、无 NaN/None、关键数字确实出现在页面里）；
  截图验证不一定可用，别把"打不开浏览器"当成"报告没问题"。
- **文档里的数字必须由结果文件生成**（脚本幂等、按锚点整块替换，不按行号），不要手抄：手抄必然与实测脱节。
  有后台跑批时注意它可能是**结束时才写回**结果文件的——改完代码要重跑并刷新表格，
  否则"文件里有数据、文档里有数字"但两者对不上，是最难发现的不一致。
- **让"跑挂了"与"跑完但没过"在产物里长得不一样**：把异常 / 未捕获错误也写进同一个结果文件，
  否则事后只能靠猜是哪一种。
- **降级必须带原因，且原因写进产物本身**（不只是报告）：产物走了兜底 / fallback 时，把
  截断、空输出、解析失败、未用模型这些原因存进产物字段（如 `mode_reason`），报告再按原因归并。
  只报一个"降级率 100%"而不给原因，会让诊断整整绕一圈才找到真因。
- **每个聚合比率旁边都要能追到原因清单**：失败数 / 降级数 / 分歧数各自列出 reason 与样本 id，
  并在报告里原样保留分歧与失败样本——只报好看的一半，等于把这轮评测的信息量丢掉一半。
- **报告要高亮哪条臂必须显式指定**（如 `--focus a2`），**别按顺序取最后一条**：臂的题量可能差很多，
  "取最后一条"会拿一条只有三五道题的臂去和其他臂比。
- **用例之间会污染**：某个用例改了参数却没恢复，下一个用例就继承了它（实测：消融把分离权重置 0，
  紧接着的"对撞专项"就测出了"对穿"）。**每个用例开头显式写全套参数**，不依赖上一步的残留。
- **多轮轨迹的"按轮归属"要用 id 差集，不要用 step 号**：`step` 通常是**轮内**编号（每轮从 1 重数），
  拿它当跨轮游标会把后面几轮的调用**全部漏掉**，报告成"第 2、3 轮没有任何工具调用"——
  看起来像系统退化，其实是量错了。每轮前后各取一次快照、用 id 差集归轮；若列表是 `ORDER BY ... DESC`
  （新的在前），还要按时间/步号**升序**还原真实调用顺序，否则轨迹指标全错。
- **评测要跑在临时库上，且别让清理失败把报告冲掉**：`tempfile.TemporaryDirectory` 让跑批"跑完即删"，
  不碰真实数据目录。Windows 上 SQLite 句柄未及时释放会让清理抛 `NotADirectoryError`
  （把 `state.db` 当目录递归），而**异常发生在 `with` 退出时，会把之后写报告那一步一起冲掉**：
  用 `ignore_cleanup_errors=True`、退出前显式关库、并把报告写盘放进 `with` 块内部。
- **指标函数的参数解析要防御式**：落库的调用参数形态不固定（dict / JSON 字符串 / 键值对序列），
  直接 `dict(raw)` 会崩。收口成一个 `_as_mapping`，**收不了的记成 `{"_raw": ...}` 让后续判为"参数不合法"，
  不要静默跳过** —— 静默跳过会让参数合法率虚高。
