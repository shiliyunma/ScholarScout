# 浏览器可视化交付（仿真 / canvas / WebGL / 交互可视化）

适用：用户要的是"一个能跑、能看、有交互的可视化程序"，不是一篇说明。
判定标准只有一个：**真实执行产出了数据 + 真实渲染产出了画面，两者你都亲自看过**。

## 交付形态（默认，不要问）

- **单文件 `.html`**：仿真 + 渲染 + UI + 自检全在里面。不要 CDN、不要 npm、不要构建步骤——
  用户在中国且经常离线打开，任何外部依赖都是故障点。双击 `file://` 必须能跑。
  → 所有 `fetch` 都要用 `if (location.protocol.indexOf('http') === 0)` 之类的守卫包起来。
- 交付时给 **`::preview{file="绝对路径"}`**（聊天里活的控件）**并**在正文写出文件路径，
  两条路都留：内嵌控件若在 webview 里拿不到 WebGL/canvas 权限，用户还能自己双击打开。
- 配套文件落盘：`docs/<主题>调研.md`、`docs/report.json`（实测数据）、`docs/render-*.png`（真实抓图）、
  `README.md`（画什么、怎么操作、实测数字表）、`tools/*.py`（可重跑的验证脚本）。
  文档里的数字表要**由脚本从 report.json 生成**；生成脚本用字符串锚点定位插入位置时，锚点必须在全文
  **唯一**——拿一个文档别处也出现的串当锚点，`index()` 取到第一个，会把两处之间的**整段章节静默删掉**
  （实测 README 14KB → 8KB、第 2/3/4 节全没）。两条保险：① 锚点只取生成块自带的串；
  ② 替换后断言文件没变短（`len(new) > len(old)*0.9`），触发即中止。验证要逐行比对文档数字与 JSON。
  用户要的是"能自己复现"，不是"你说你测过"。

## 顺序

1. **先调研**，把结论连来源一起写进 `docs/<主题>调研.md`：算法本源、同类实现的做法与实测数字、
   技术路线对比表（各自能撑多大规模、依赖什么）、最后是你采纳的清单。调研是为了定路线，不是为了凑字数。
2. **再建**。仿真内核与渲染分开写，内核要能被自检同步调用（不要只存在于 `requestAnimationFrame` 回调里）。
3. **无头验证**（见 `references/headless-chrome-verification.md`）：真实时钟跑一遍，落 `report.json` + 抓图。
4. **看抓图**（`vision_analyze`）：数值对但画面空/糊/错位是常态，必须亲眼看。
5. **派 2-3 个子 agent 并行审查**（见下），等结果回来逐条核实再改。

## 自检设计：能被证伪，且不是"没崩就算过"

- 页面带 `?autotest=1`：加载后同步跑完所有用例，把结果写进 `<pre id="report">`（`--dump-dom` 能读到），
  有条件时再 POST 落盘。同时挂 `window.onerror` / `unhandledrejection` → 写进同一个 report，
  否则页面里一次未捕获异常的表现只是"什么都没发生"。
- 测**涌现属性**，不是"跑完没崩"：粒子/群体类要报序参量、局部一致性、聚拢度（对比均匀分布的理论值）、
  碰撞/重叠率。阈值取"明显正确 vs 明显错误"的分界，并写下为什么是这个分界。
- **必带一个对抗用例**：一个坏实现会明确失败的那种（例：两个个体正面对撞，测最小间距）。
  只测稳态统计量时，把某个权重调成 0 的半坏实现也能过。
- 把"时间花在哪"拆开报（例：网格重建 vs 邻居遍历+积分）。`Math.hypot`、每帧 `new Float32Array`、
  未提升的对象属性读取这类开销只有拆开计时才看得见。
- 自检要在**测完之后恢复现场**（`snapshotParams`/`restoreParams`），不然用户点完自检发现参数被改了。
- 自检可以顺便当开发工具：`?sweep=1` 扫参数矩阵、`?shots=1` 抓图，都走同一个 POST 通道。
- **"视觉上要一直变／不能老是个球"这类审美要求也要能验证**：先把几何量化（位置协方差特征值 → 形态谱、
  主轴比；相邻采样间归一化协方差的 Frobenius 距离 = 变化率），
  在**平衡态窗口**上扫参数做筛选；指标跑动比配置差异还大时**只当筛选**，最终用
  **同机位·同距离·4 个不同时刻**的抓图肉眼定夺（`?shots=series`）。
  纯局部规则会松弛到准平衡（"形状冻住"），要它持续变化就必须给**持续驱动**（小幅随机扰动/捕食者）。

## 调参：扫，不要猜

参数一多（≥4 个相互作用），靠"我调大一点试试"必然低效。
写一个 `runSweep()`：URL 参数触发、逐组合同步跑、每组都把关键指标 POST 出去，最后打印成表。
一次 20 组、每组几秒，比来回改十次代码快得多，而且能看出参数之间是不是耦合。
把扫出来的最优值写进代码默认值，并在注释/README 里说明"这组值是怎么来的"。

## 子 agent 审查阶段

- 2-3 个**不同视角**并行，各写各的：算法/数值正确性、渲染与性能、交付严谨性与用户视角（后者给它看抓图）。
- 明确要求：**不要改文件**，只出报告；每条给 `severity / 位置(文件:行号) / 问题 / 依据 / 建议改法`。
- 子 agent 的结论是**自述**，不是事实：改之前自己验证一遍（读代码、跑一次）。
- 交付质量审查要专门问一句："这套自检能不能被一个退化实现蒙混过去？"

## 配色与外观：先对齐宿主应用，不要自创

大浩的硬要求是**界面跟他正在用的应用同体系**（他的原话：不要深蓝色，要跟“你现在的主题框架与颜色”相似）。
所以任何自建界面的**默认第一步**是去读宿主应用（Hermes 桌面端）的样式文件拿令牌，按它的结构派生颜色，
不要凭感觉挑一套配色——挑了深蓝就得整段重做。

令牌原值、派生结构、主题切换与自检清单见 `references/host-app-theme-tokens.md`。
**界面改完必须自己先看**：拓浅色与深色各一张图 + `vision_analyze` 逐张检查（配方见
`references/headless-chrome-verification.md`）——"测试全绿"证明不了界面能看。

## 坑（每条都值得先想清楚再动手）

- `--virtual-time-budget` 会把 `performance.now()` 冻住 → 所有耗时测出来是 0，`rAF` 驱动的仿真也可能不推进。
  要测性能就必须真实时钟，见 references。
- `--dump-dom` **看不到 JS 报错**。页面白跑时加 `--enable-logging=stderr` 再 grep `INFO:CONSOLE`，
  一次就能指出"未捕获异常: 标识符重复声明"这类致命错误。别靠猜。
- git-bash 里给原生 exe（chrome 等）**传原生路径**（`D:/x/y` 或 `C:/...`），`/d/x` 会被当成无效路径。
  每个无头实例用**独立的 `--user-data-dir` 和端口**，并发跑会互相抢 profile/端口。
  并发还会**抢 CPU**：性能基准必须独占跑——同时开两个 Chrome 会把同一份代码的每步耗时测高 50%+
  （实测 12000 个体 10.1ms → 16ms），据此下“跑不动”的结论就错了。
- 无头下 WebGL 走软件光栅（SwiftShader），**帧率数字对用户的显卡毫无意义**。
  报"CPU 每步毫秒"这类与显卡无关的数，并说明渲染部分是软件跑的。
- 抓图要在 `rAF` 回调里、`render()` 之后立刻 `readPixels`：绘制缓冲在合成后会被清空。
- CSS 里 `height:100vh` 在聊天预览的内嵌 iframe 里会循环测量 → 给画布容器一个 `min-height`。
