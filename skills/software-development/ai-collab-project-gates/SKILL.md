# AI 协作项目的规则文件与可执行门禁

## 触发

- 新开一个会长期让 AI 写代码的项目，用户要求“规则写清楚”“AI 不许随手加依赖”“lint 测试不过就不合”
- 用户抱怨过：AI 顺手重构整个项目 / import 不存在的包 / 提交信息乱 / 一上来就“帮我写个系统”
- 要给已有项目补“规则文件 + 门禁”，或用户交了一份类似“防止屎山代码”的条目清单

## 用户的固定要求（照做，不商量）

1. **先定接口、数据模型、目录结构，再让 AI 填实现**。三份文档落盘并**冻结**之前，不写业务代码。
2. **一次只改一个文件或一个函数**，不许顺手重构。
3. 规则文件必须写清：技术栈（含**明确禁止**的选型）、命名、错误处理、依赖政策、门禁、提交规范。
4. lint / 类型检查 / 测试 / 自定义校验，**一个不过就不合**。
5. 关键路径人工逐行 review —— 在规则文件里列成表（数据迁移、出网、权限、支付、密钥、计分逻辑等）。
6. 新增依赖要审批：白名单文件 + 校验脚本，未审批即构建失败。
7. 小 PR 勤提交、能回滚；出问题先 `git revert`，不手改历史。
8. **需求模糊时先摆选项再实现**：给"面向清单 + 带推荐档的编号选项"让他点选（一次问完、推荐项放第一），
   别先实现一版再返工；含糊处先复述自己的理解让他确认。两类必须先问：会改数据模型/接口的、
   以及自己可能理解偏的。
9. **每一处修复都要把“修改过程”写进文档，并与代码同一笔提交**（用户原话级别的要求）。两处：
   ① **特性文档**里写**行为**（路径怎么解析、参数、降级策略、哪些进程适用）；
   ② 一份**缺陷修复记录**（如 `docs/23-缺陷修复记录.md`），列固定为
   `日期 | 缺陷 | 证据（文件:行 / 实测输出）| 改法 | 怎么验的 | 提交`。
   列固定不是格式癖："证据"必须能被复核（哪一行、哪次 grep、哪条测试输出），"怎么验的"要写具体断言。
   一个实用细节：一笔提交无法内嵌自己的 SHA，所以最后一列写**提交主题**并在表头注明取法。

## Procedure

### 1. 规则文件：一份权威 + 两个分发副本

- 权威副本放 `docs/项目规则.md`，正文用 `<!-- RULES:BEGIN -->` / `<!-- RULES:END -->` 包住。
- 分发副本：`AGENTS.md`（Hermes 与多数 AI 读）+ `CLAUDE.md`（Claude Code 读），正文与之**逐字一致**。
- `scripts/check_rules_sync.py` 强制一致；不一致即门禁失败。两份各自维护、内容漂移比重复更危险 —— AI 会按旧规则写代码。

**Pitfall（会当场卡住你，必须提前告知用户）**：`AGENTS.md` / `CLAUDE.md` 属于 **agent 指令文件，受保护**。写入需要用户在弹窗里显式批准，**弹窗超时不算同意**；被拒后**不许绕道**（terminal、脚本、改名都算绕道）。正确做法：规则全文先落成普通文档（`docs/项目规则.md`），并明确告知用户“授权后我生成两个副本，校验才会转绿”，把这一项作为**预期内的唯一红项**写进交付说明。

### 2. 门禁脚本：默认宽容，CI 严格

- `scripts/check.sh`：`full`（默认）/ `--fast`（提交前）/ `--strict`（CI）。
- **缺工具时默认 SKIP 并计数**，不要直接失败：新克隆的仓库还没装依赖，直接跑挂会让人以为仓库坏了。
- 结尾必须打印「失败 N 项，跳过 M 项」；**M > 0 时不许说“全绿”**。失败 > 0 时退出码非 0。
- 把“装依赖”和“跑门禁”分开：单独的 `scripts/bootstrap.sh`（建 venv + 装依赖），装完再跟一次依赖审批校验。

**Pitfall（实际踩过）**：**门禁与提交不能串在同一条无短路的命令里**。
`bash check.sh; pytest -q; git commit -F msg` 会一路跑到底 —— 门禁已经报了 5 个失败 + 1 条 lint，
提交照样发生、红着灯推上远程。做法：

1. 提交前**用汇总行当判据**，而不是只看退出码：`check.sh` 的退出码会被管道吃掉
   （`check.sh | tail -1` 拿到的是 `tail` 的状态），而且**已经 grep 到“失败 1 项”还照样提交**是人都会犯。
   可靠的形状是一个 `if`（可直接复制）：

   ```bash
   export PATH="$PWD/.venv/Scripts:$PATH"      # 少了这句，ruff/mypy/pytest 不在 PATH → 全 SKIP，而汇总行照样写"失败 0 项"
   bash scripts/check.sh > "$TMP/gate.log" 2>&1
   grep -E "汇总" "$TMP/gate.log" | tail -1
   if grep -q "失败 0 项，跳过 0 项" "$TMP/gate.log"; then
     git add -A && git commit -q -F "$TMP/msg.txt" && git push
   else
     echo "== 门禁未通过，不提交 =="
     grep -E "\[FAIL\]" "$TMP/gate.log" | head -3
   fi
   ```

   **把顺序变成结构，比“下次一定注意”可靠**：这样串起来之后当场拦下过多次红灯提交，
   而只写 `&&`（或只在心里记着）时同类失误重复过五次。
2. 门禁失败时**先读失败清单**（脚本要把失败项打成一行一项，别只回退出码），不要凭“刚才似乎绿了”提交；
3. 失败来自**契约变更**（改了实现、测试还没跟上）时，就在**同一轮**里改测试，
   并把这类提交单列成 `fix(tests): …`，在提交信息里写清“失败项都是契约改了测试没跟上，不是实现错”；
4. HEAD 已经带红灯的话，**立刻**补一个修复提交，并在回复里如实说明是自己的流程错误 —— 不要静默抹掉。
5. **判据必须同时看两个数：`失败 0 项` 且 `跳过 0 项`**。工具不在 PATH（缺 `export PATH=...venv/Scripts`）时
   四项全 SKIP，汇总行**照样打印"失败 0 项"** —— 只看这一半就是假绿，会把没验过的代码当成验过。
6. **不要 `export PYTHONPATH=<repo>/src`**：打包类测试会读子进程 env，注入源码路径会让它**假红**，
   与你的改动无关，很容易误判成自己弄坏了。
7. **新写的 Python 先跑 `ruff format`**：`ruff format --check` 常是门禁里的一项，手写的新行经常不合格。
8. **测试里不许读真钟**：函数内部读"今天"（`datetime.now` / `date.today`）而测试里写死日期 ——
   **今天绿、明天红**，diff 里没有任何解释。规则：凡是"是否到期 / 距今"的判断，时间一律从参数注入
   （`f(db, *, now=None)`），测试传固定时刻。**症状识别**：门禁报失败但你的改动解释不了那一条时，
   先 `grep -rn "datetime.now\|date.today" src/`，再看测试里有没有写死的日期。
9. **设计新模块前先找"落点"**：先 `grep` 确认要替换的调用点真的存在且只有一个。照着设计文档里的签名开工，
   可能发现**根本没有那个循环**。落点也**不能靠改"模型可见工具"的 schema 得到** —— 那会改系统提示词哈希，
   等于换了对账条件（对照实验的数字不再可比）；换一个不改哈希的落点。落点变了就同步改文档签名。
10. **新增配置键同步三处**：示例配置、目录/规则文档、**以及守卫测试里的键清单**
    （`test_*_runtime_keys.py` 里的非默认值表）—— 少一处，CI 当场红。
11. **门禁清单本身就是契约，改范围要同一轮同步三处**：门禁脚本里 `ruff`/`mypy` 扫哪些目录变了，
    规则文件里的命令块（`docs/03` 的门禁表 + `AGENTS.md` + `docs/项目规则.md`）必须一起改；
    后两者的命令块必须**逐字一致**（同一段文本分别 patch），否则同步校验当场红。
    （真实漂移：脚本已扫 `src tests scripts eval`，文档还写着 `src tests` —— 文档看起来对，只是不全。）
12. **在共享 checkout 里提交，只 add 自己的文件**：别的 AI 会话/另一条线常常在**同一个工作区**未提交地写东西，于是——
    永不用 `git add -A` / `git add .`；**按 hunk 过滤不可靠**（同文件里两处改动相距 < 3 行时 `--unified=3`
    会把它俩并成**一个 hunk**，只能整块要或整块不要）；**不要 `git checkout -- <file>` 再回填来隔离自己的改动**
    （回填用的是你手里的旧副本，对方期间保存的新内容会被**静默丢掉**）。提交前用 `git diff --cached --name-only`
    逐个确认名单；把没进去的文件与原因写进回复，别默默提。
    另外**先读 `git status --short` 的第一列**：第一列有字母 = 已被暂存；若 index 与工作区完全一致
    （全是 `M `/`A `、第二列空）说明**对方正在准备提交** —— 此时**不要 `git reset`**，
    那会清掉人家备好的暂存区；正确做法是按现状提交，或只按自己的路径暂存。
    对方文件在最近几分钟内还在变时，先做不依赖它的部分；要改同一文件就用 `patch` 做最小改动，别整文件重写。
13. **别人把你的门禁弄红了：报告，不要修**。另一条线正在写的文件常常是红的（类型错、测试失败、待格式化）——
    那是他的中间态。自己这边把**独占文件的 lint/格式/用例单独跑绿**，给出具体 `文件:行` 与报错，让他去修；
    在他动过的文件里顺手补一刀，很可能与他的下一次保存冲突。
14. **"pytest 全绿"不等于"门禁全绿"**：子 Agent 在一批多笔提交（尤其重构轮）里逐笔只跑 `pytest -q`，汇报"每笔都全绿"——
    真正第一次跑门禁时 `lint`/`format`/`types` 三灯全红，因为这三项**从未被跑过**。判据只能是八项门禁的汇总行；
    **多笔提交的批次在 push 之前，必须对最终树（所有并行改动合并后）完整跑一次门禁**。逐笔的快速测试只是过程检查，
    报"绿"时要说明跑的是哪几项。
15. **同一类违规反复出现时，交付物是"递减白名单闸"而不是又一轮人工清理**：
    形状（实测有效）：一个测试扫全仓、拿**当前违规清单**当冻结白名单（`{相对路径: 处数}`，逐文件计次），
    断言"实际命中 == 白名单" —— 修一处删一个数字，**在已列入的文件里新增一处也会红**；
    扫描用 `ast`/`tokenize`（正则会把注释与字符串里的名字算进去，假阳性一多，人就学会无视这道闸）；
    再加一条**僵尸自检**（白名单里每个文件必须存在且计数 > 0，防重构后留下死条目虚增数字）。
    **必须证明它会红**：临时加一行违规 → 闸红 → 撤销 → 复绿。
    还要注意**扫描口径就是数字**：同一件事在无闸时会出现 12 / 69 / 56 三种计数，因为没人定义"什么算一处"
    （只 grep `.execute(` 会漏掉走门面的 `db.query("SELECT …")`）。闸落地时用它的口径报数，并明确说它替掉了哪个旧数字。
16. **空开关比没有开关更坏：删掉它，并立墓碑**。配置项写着 `enable_x: true` 但 `src/` 里根本没有对应实现
    → 用户在"以为已支持"。修法是删配置字段、删死过滤（`toolset="x"` 之类）、同步文档把它从"功能"挪到"已知未实现"，
    并加一条墓碑守卫（`getattr(profile, "enable_x", None) is None`）防人悄悄加回。
    **不要顺手把它实现掉**：新能力会改工具表→改系统提示词哈希，等于换了对账条件。
    对应的铁律：**黄金提示词哈希只能因"确有意图"而变**；门禁因它变红时，停下报告，**不许更新哈希去换绿** ——
    那等于把"不小心改了提示词"藏起来。
17. **配置的读端与写端必须共用同一个 normalize，写在前面而不是读的时候才夹**。实测过的坏形状：
    读端对非法值整对丢弃（回默认尺寸），写端只做 `max(1, int(x))` —— 于是把 `width: 158`、`x: -21333`
    这类值写进 `config.yaml`，下次启动被丢弃、回默认、又被写回脏值，用户看到的是"窗口大小每晚自己失效"，
    而日志里一个字都没有。规则：**写前先过读端的同一个函数**（不另写一套夹紧逻辑）；最小化/隐藏（0 或负尺寸）
    **一个字节都不写**；写入后与现有值相同则**不重写文件**（否则每次关窗都在改文件）。测试要盯四件：
    脏值落盘后要么合法要么 `null`、合法值原样保留、0 尺寸不写、几何不变时写调用数为 0。
    同类推广：任何"用户可手改、程序又会回写"的配置块（窗口几何、列宽、最近打开的路径）都适用这条。

### 3. 依赖审批

- `pyproject.toml` 的 `dependencies` 是唯一来源，`deps-allowlist.txt` 是白名单。
- `scripts/check_new_deps.py`（stdlib `tomllib`）逐条比对，**规范化后再比**：去版本区间 / extras / 环境标记，转小写，`_` → `-`。
- 未列入白名单 = 退出码 1。申请新增要写清：用途 / 为何 stdlib 不行 / 体积 / 许可证 / 近半年是否维护。
- **批准后要把"批准痕迹"写进声明本身**：白名单条目与 `pyproject.toml` 注释里写清 **批准日期 + 批准人（用户）+ 一句话理由**
  （如"用户 2026-10-22 批准：docx/xlsx 目标编辑，是代码执行能力的前提"）。理由不是形式：半年后没人记得这个包是谁放行的，
  下一个人只能重新考古；而"历史上被批过一次"也是复审时唯一能拿出来的证据。
- **登记依赖 ≠ 安装依赖**：改声明与白名单是**配置决定**（可单独一笔提交），`pip install` 进运行时是另一个决定 ——
  两者混在一轮里，会让"只是改了个清单"变成"顺手改了环境"，而环境变化无法用 `git` 回滚。
- 版本一律带上界 `>=floor,<next_major`；无上界会在上游破坏性发版时直接炸。
- 非运行期依赖（pytest / ruff / mypy / 构建后端）也要登记，但另开一栏，不进运行期白名单。

### 4. 验证：“看起来成功” → “验证过”（最容易被跳过的一步）

- **门禁是真门吗 → 篡改测试**：把被校验文件复制到临时目录，改掉一个字，跑校验脚本，**必须报错并打印首个差异行**；未改的那份必须通过。只跑一遍“通过”不算验证。
- **新加一项门禁后，两个方向都要演示**：做一次"应当绿"的改动（只加注释 / 只改行数）确认**不红**，
  再做一次"应当红"的改动（新增一个顶层函数、删一个文件）确认**红**。只跑一次绿不算验证 ——
  一个永远红的门禁和一个永远绿的门禁，信息量都是零。
- **"钉住已知缺陷"用 `xfail(strict=True)`，不用 `skip`**：本轮查出、但决定这轮不修的真缺陷（一个工具回扁平 dict 而其余回信封、壳层裸写错误码），
  写成 `xfail(strict=True)` + 一句"待修"备注并在报告里点名。`strict` 的意义是：**修好那天它会变成失败**，逼人摘掉标记；
  用 `skip` 则永远不会再提醒你。摘标记那一笔要与"缺陷已修"同一个提交，防止只改测试不改产品。
- **把"零新增"守卫改成具名白名单时，必须留一条反例用例**：例如"新增样式块里不许出现新令牌"改成"只允许这四个几何令牌"之后，
  要断言"**白名单之外的名字仍然会红**"（喂一个假名字进去）。否则白名单会悄悄退化成"什么都不拦"，而它看起来还在。
- **验证一条 lint 规则真会拦：探针文件必须“只违反这一条”**。实测白跑两轮，两次都是探针本身不合法：
  ① 文件名/目录名以 `_` 开头 → ruff 视为私有，`D100`/`D104` 根本不管它；
  ② 文件里顺手带了未使用的 import → 报的是 `F401`，把目标规则的信号盖掉。
  形状：一个只有一句赋值、名字正常的最小文件，跑完即删。**看不到预期报错时，先怀疑探针，别怀疑“规则没生效”。**
- **判据字段必须抗日常编辑**（否则门禁会被无视）：凡"每改一次就变"的字段（行数、时间戳、文件大小）
  **不许进判据** —— 它们会让每次日常提交都红，红久了就没人看了。做法：比对前把这类字段从**两份文本**
  都抹掉（同一个 normalize 函数处理两边），只比**结构**（文件、符号、依赖、注释首句）；
  这些字段仍写在产物里给人看，允许滞后，且错误信息要**明写下一步该跑哪条命令**。
- **生成物门禁要在 HEAD 上绿，不只是工作区**：生成物是按**工作区**算的；工作区里含别人未提交的新文件时，
  提交自己的生成物描述的是一个 **HEAD 上并不存在**的代码树，HEAD 上的门禁会红。
  做法：`git worktree add -q --detach <tmp> HEAD` → 在那边重生成并跑 `--check`（这里就该退出码 0）
  → 拷回 → `git add` + `git commit --amend --no-edit` → `git worktree remove --force <tmp>`
  → 再按工作区重生成一次（两边都绿）。
  **并行写者存在时，生成物只能在"合并后"生成一次**：多个子 Agent 各按自己的分支重生成符号清单/索引，会得到两份
  "谁都不成立"的清单（一份漏掉对方已落地的改动，一份带进对方未完成的中间态）。等所有改动落地、`ruff format` 跑完，
  在**合并后的工作区**生成一次再提交；按分支各生一次比不生成更有害，因为它看起来是新的。
- **docstring / 风格类门禁：先量再开，且只开最小的那几条**。开之前先数：全库多少个 py 文件、缺 docstring 的有几个
  （实测 273 个（含 28 个 `__init__.py`）全有 → 当天开、零报错，收益纯防御性）。**开 `D100` + `D104`，不要只开 D100**：
  `__init__.py` 归 `D104`，只开前者会把所有包的入口漏掉；**不要开整个 `D` 族** —— `D2xx`/`D4xx` 是 docstring 的
  **格式**规则，会与中文全角标点打架（中文项目通常已 ignore `RUF001-003`），只制造噪音。
  盲区写进 `pyproject.toml` 注释：`_` 开头的模块被 ruff 当私有，`D100` 不管它；注释里同时写“为什么开这两条、为什么不开口族”。
- **界面类改动，只断言“界面状态”就是假绿 → 必须断言副作用**：卡片变选中、按钮变置灰、文字变了，都能在**副作用一次没发生**时成立。
  要断言的是：桥真的收到了什么（逐字段比对 `{session_id, text}`）、**恰好一次**（再点一次不得新增）、以及跨会话时记在**哪个会话**。
  探针本身也常“假失败”：事件处理器里调用的函数是**声明时闭包捕获**的，事后在全局 `var send = spy` 覆盖**不生效** ——
  症状是“UI 状态都对、但发送函数一次没被调”。修法是用 `new Function` 把探针注入到产品的词法作用域（或包一层），
  **不为探针改产品签名**。多条异步用例不要 `Promise.all` 共享一份 spy（前一条记录被后一条清空 → 同时造出假红与假绿）。
- **提交真的推上去了吗 → 双端比对**：`git rev-parse HEAD` 对比 `git ls-remote origin <branch>`，再确认工作区未提交数为 0。
- **仓库自包含吗 → 克隆到临时目录**，在克隆副本里跑项目自己的门禁脚本（不是只看 git 状态）。
- **远程库“不存在”还是“存在但空”？** `git ls-remote <url>` 返回 **exit 0 + 空输出** = 存在但无引用（空仓库，可直接 push）；**exit 128 + `Repository not found`** = 不存在。用一个故意写错的库名跑一次当**对照组**。错误信息常被管道（`| head`）吞掉，别凭“输出为空”下结论。

### 5. Shell 坑（含中文的内容必踩）

- **含中文引号/反斜杠的 `python -c` 会崩** → 写临时 `.py` 文件再跑。
- **多行或含中文的 `git commit -m`**：少一个引号，bash 会把它**后面所有命令**吞进字符串，现象是“提交了前半段、推送根本没执行” → 用 `git commit -F 消息文件`（消息用 heredoc 写入），提交后再做 §4 的双端比对。
- **消息文件的写入不能放在“门禁绿”分支里**：门禁一红，文件压根没生成；下一次 `printf … >> msg.txt` 会**新建**一个只含这行追加内容的文件，提交标题就变成那句说明（推完才发现）。规则：`cat > msg.txt <<EOF` 与门禁判断**同级、无条件先跑**；`git push` 之前先看 `git log -1 --oneline` 的首行是不是想写的标题。
- 已经推错的标题：单用户仓库用 `git commit --amend -F <正确消息>` + `git push --force-with-lease origin <branch>` 修（多协作者仓库别这样干）。
- **`**dict` 解包进关键字参数 = mypy 报错看不懂**：`f(layout, **placement)` 里 `placement: dict[str, str]`，而签名里有 `root: Path | None` 这类参数时，报的是 `Argument 3 … expected "Path | None"`（看着像第 3 个实参错，其实是没显式给关键字）→ 改成逐个关键字实参；**顺手删掉那个已无人用的字典**，否则 ruff 立刻 `F841`，门禁再红一次。
- Windows git-bash 给原生程序传路径写 `D:/x` 而不是 `/d/x`；删注册表项别用 `reg delete`（中文输出乱码），改用 PowerShell。
- **用 Python 生成补丁/脚本/配置文件时必须 `newline=""`**：Windows 上 `Path.write_text("\n".join(...))`
  会把 `\n` 翻成 `\r\n`，于是内容看着没错、`git apply` 一律报 `patch does not apply`（费力去查行尾才对得上）。
  形状：`p.write_text(text, encoding="utf-8", newline="")`；写完 `--check` 一次再 apply。
- **批量改文件的脚本：锚点从代码里查，不要凭记忆猜**。面板/容器的 id、函数名、标签名都要现查：
  用“该区域对应的那个源文件里的 id 清单（如 `el("...")`）去正则匹配”定位容器，
  用“从这一行往上找最近的 `function NAME(`”定位所属函数。凭印象猜锚点会反复对不上、白跑好几轮。
- **同一份文本里“先删后插”，坐标绝不能复用**：被搬走的块若位于插入点**之前**，删掉它会让后面所有偏移整体前移，
  继续用旧偏移找锚点会**静默插到别的容器里** —— 脚本不报错、测试也不红，只是东西放错了地方（本轮把两块内容插进了
  主窗口区域，直到用户截图才发现）。顺序固定为：按**内容**切出块（用块内唯一标记当首尾，不靠行号）→ 删净 →
  **重新定位**锚点 → 插入 → 回读**两条判据**（源区已无、目标区已有），任一不满足就不写盘。
- **写盘放最后**：所有 `assert` / 前置校验走完，才 `open(..., "w")`；定位失败就 `sys.exit(1)` ——
  “一个字都没写”远好于“写了一半”。写完**立刻回读校验**（断言目标区已变、要删的串已为 0），
  “脚本打印成功”不等于“文件真的改了”。
- **拆了模块/做了“门面再导出”之后，新写的公共函数必须同步进门面**的 import 与 `__all__`，
  否则 `AttributeError` / mypy `Module has no attribute` 立刻红；新增接口时按这条自查。
- **多处类型报错常是同一根因**（典型：某个 loader 返回 `X | None`，后面连锁报
  `union-attr` / `index` / `arg-type`）—— 先修那一处可空分支，别逐个打补丁。

## 派子 Agent 干批活：下单与验收

长期项目里的批量工作（多文件改动、成体系的文档产出）适合派给子 Agent，但**它的汇报是自述，不是事实**。

**下单时**
- **按价值排序，最值钱的放最前**：子 Agent 常撞迭代上限，排在最后的会一件不做（四件里后两件常常归零）。
  宁可分两次派，也别一次排四件。
- 指令里写死：依赖白名单、**不得改动会影响对照条件的哈希**（系统提示词 / 工具声明）、门禁链（绿才提交）、
  `git commit -F`、一次提交一件事、**明说要不要 push**（不说它就不推）。
- 要求它**"读不到就标 unknown，禁止编造实现名 / 行号"** —— 这条会真的被执行，也是它报告可信的前提。
- 把上一轮侦察到的事实（`文件:行号`、函数名、落点）写进下一轮 context，别让它重搜。
- 只读约束写死：哪些仓库不动、唯一允许的写操作是哪个文件。

**验收时（逐条自己复算）**
- 产物是否真存在 + 字节数；**提交 SHA 是否真在 `git log` 里**；门禁汇总行要**原文**而非它转述的"绿了"。
- **抽查它引用的源码行号 / 函数名**（`grep -n "def <name>" <file>`）。
- **`git status` 看它有没有留下未提交的文件** —— 它经常把新建的文档忘在工作区。
- 它报"基线本来就是红的"：**信，但自己复跑一次**确认（往往是真的、且与本任务无关，如上面读真钟那条）。
- 它动了别人的测试时**要 diff 说明**：允许改造数（前提是原造数根本触发不了它声称的场景），
  **不允许为绿改断言**。
- **守卫类测试被动过时，要它给结论与依据**：分层规则（`test_layering.py`）、配置键清单、黄金哈希这三类被改时，
  必须回答“是合法扩展还是放宽”；本轮那次是合法新增一行（新顶层包必须登记，不登记当场红），但**每次都查**，
  因为“放宽规则拿绿”是拿绿最省事的手法。
- **画运行态禁区**：机器上有监听进程/隧道/`config.yaml`/`.env` 在服务时，提交轮必须写明“不要 kill 进程、不要改这些文件”，
  否则它会为了跑干净测试把刚跑通的链路弄断；同理不要在同一轮里顺手改运行中的配置。
- **一轮一件事**（最狠的一条）：给 2–4 件的轮次几乎必撞上限、以“代码写完但没跑门禁、没提交”收场；
  单件轮次能收干净。加保险句：“若迭代将尽，先把第 N 件交付并提交，其余做多少算多少并如实报告”。
- **撞上限的批次不要重派全量，派“收尾单”**：把剩余项整理成**编号清单**，每条带**确切报错原文**与**修法方向**
  （例：“`settings.py:89` 把 `str | None` 传给要 `str` 的 `discover()` → 没 key 就跳过探测、回落配置，不许强转/ignore”），
  并写明哪些已完成**不许推翻**、哪些文件不许碰。“收尾单”比“重做一遍”快一个数量级，也避免子 Agent 把已跑绿的代码重新改坏。
- **子 Agent 交回的“半成品”先验树再动手**：它常在改到一半时撞上限，可能留下**语法错/半改的文件**（装饰器与函数定义被一行 patch 合并等）。
  第一步是 `py_compile` / 最小 import 把树跑通，再谈功能；否则后续所有“跑一下试试”都会报不相干的错。

## 交付与汇报的口径（用户偏好，跨任务）

- **README 固定五节**：项目简介（名称 + 一句话：是什么 / 解决什么问题）/ 功能特性（**3–5 条**，每条要能
  对应到具体文件）/ 安装（依赖 + 命令）/ 使用（启动 + 最简示例）/ 许可证。事实一律从仓库核
  （`pyproject.toml`、依赖白名单、`scripts/README.md`、`<cli> --help`），**不写营销词**；
  许可证要同时看 `LICENSE` 文件与 `pyproject.toml` 的 `license` 字段 —— 两者常常不一致，不一致就写出来。
- **给他解释指标/测试用大白话 + 表**：`指标 | 大白话 | 那次跑出来的数`。术语先翻成"它在量什么"
  （例：工具调用准确率 = 这一轮挑的工具对不对，二值 1/0；整条轨迹完全一致 = 操作流水跟标准答案一模一样；
  "冗余 49 vs 15" 不是比率而是**数数**）；用户会明确要求"尽可能说大白话"。
- **说数字先说服龄**：一套评测数字是哪天、哪版代码跑的，必须一起说。旧代码的成绩不能当
  "当前代码的成绩" —— 要引用就先重跑，或者明写"这组数字来自 X 日，其后已有 N 项改动影响该指标"。
