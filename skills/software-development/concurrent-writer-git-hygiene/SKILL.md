# 并行写者下的 Git 卫生（多个会话共用一个工作区）

触发：用户在同一个仓库里同时开着别的会话/代理（或他自己在用编辑器/应用在改），
而你要在中间提交自己的改动。此时 `git status` 会在几分钟内自己变来变去，
"只提交我的那一半"既不能靠 `-A`，也不能靠直觉。

## 0. 先判定"有没有活写者"——它决定后面每一步

- `find <被 lint 的根> -name "*.py" -mmin -8` → 近几分钟被改过的文件 = 疑似活写者。
- 连续两次 `git status --short`（间隔几十秒）：条目在变 = 活的。
- `git ls-remote origin refs/heads/main` 与 `git rev-parse HEAD` 比对：弄清谁在推、推到哪了。
- **有活写者时，绝不 `git checkout --` / `git restore` 他们可能在编辑的文件**：
  你能拿回的只是旧版本，回填会吞掉他们刚落盘的新改动。这就是"分不干净就别硬分"的理由。

## 1. 只提交自己独占的文件（首选路径）

- `git add <显式路径…>`，**不要 `-A`**（在并行仓库里 `-A` = 替别人提交）。
- 提交前 `git diff --cached --name-only` 数一遍，核对没有别人的文件混进来。
- **多个自己批次的提交：一次整树门禁 + 多笔显式路径提交**。门禁是整树判定，所以顺序必须是：所有批次都到“可提交” → **跑一次门禁** → 连续 N 笔 `git add -- <显式路径>` + `git commit`（树不变，门禁结论仍成立，不必每笔重跑）。先提交后验证 = 把“不知道对不对”的东西入库。
- **意图是“这个目录下我改过的都提交”时，用 `git add -u -- <dir>`**：只更新**已跟踪**文件，未跟踪的草稿（评审稿、临时脚本）天然不会被扫进来，比逐个人肉拼路径可靠。中文文件名尤其不要靠记忆写（拼错一个关键字就整条 `pathspec did not match`）；路径一律从 `git status --porcelain` 或 `ls` 取。
- **`git add` / `git commit` 后面永远不加 `|| true`、不重定向 stderr**：那会把“一个文件也没匹配到”变成“命令成功”，下一句 `git commit` 提交了空暂存区，全程输出看着干干净净。要在提交前显式判定 `git diff --cached --quiet`；为空就不提交、把真实路径先打出来。
- **并行批次可暂存出工作区**，让门禁只判一批；暂存位置放**仓库内的 `_wip/`**（gitignore 且不会被系统清理），**不要放 `%TEMP%`**。

## 1.5 把旧稿/暂存重新应用到“之后又被改过”的文件上

`_wip/` 里躺着某个未完成批次的旧副本时，**永远不整份覆盖**：那几份文件可能已经被别的批次改过
（新增参数、新分支、新默认值）。只从旧稿里**读设计意图**，把新增的键 / 函数 / 接线**重新加到当前版本**上，写完逐文件核对：

```bash
git diff --numstat -- <关键文件>
# 71  0  config.py        → 纯追加，安全
# 60  2  feishu_send.py   → 那 2 行必须能逐条说出理由（签名加默认参数 / 注释措辞），否则就是覆盖
```

**“纯追加，或每一条删除都能说出理由”才是没覆盖的证据**。把这条校验写进子 Agent 的收尾指令：
它自报“没覆盖、只是追加”不算数，`--numstat` 才算。

## 2. 自己的改动与别人的改动在同一个文件里

- 想按 hunk 分离：`git diff -- <file>` → 只保留自己的 hunk → `git apply --cached --check` → `git apply --cached`。
  - **`--unified=3` 会把相邻的不同作者的改动并进同一个 hunk** → 按 hunk 选就可能把别人的改动一起暂存。
    选完必须 `git diff --cached --stat` 核对行数是否正好等于自己那几处。
  - 写补丁文件时用 `write_text(..., newline="")`：Windows 上默认的换行翻译会把补丁写坏（`\r\n` 变 `\r\r\n`），
    `git apply` 于是报 "patch does not apply" —— 症状是"内容看着没错，就是打不上"。
- **分不干净就别硬分**：把自己的改动留在工作区不提交，让它随该文件作者的提交一起入库（改动不会丢）。
  这比强行动他们的文件安全得多。
- **对方已经 `git add -A`（index 与工作区一致）时，直接提交那份暂存内容比 `git reset` 打扰更小**：
  reset 会毁掉对方准备好的提交。提交信息里把两个主题都写清，并告诉用户这条提交包含谁的工作。

## 3. 让提交在 HEAD 上自己能过门禁

生成物（符号清单、报告、锁文件、版本号表）若按**工作区**生成，会把别人未提交的新文件写进去
→ 提交后 **HEAD 上跑门禁必红**。修法：

```bash
git worktree add -q --detach <tmp> HEAD     # 临时工作区 = HEAD 的内容
cd <tmp> && <重新生成生成物>                  # 按 HEAD 的文件集生成
cp <生成物> <主仓库同路径>
cd <主仓库> && git add <生成物> && git commit --amend --no-edit
git worktree remove --force <tmp>            # 生成过东西，必须 --force
git <重新生成>                                # 主工作区也重生成一次，让它保持绿
```

**在临时 worktree 里跑一次门禁、确认 exit 0**，才算证明了提交自洽。

**门禁耗时可能超过终端默认超时**（整套检查常见 3–5 分钟，而默认 180s）：被 SIGTERM 杀掉时只会剩一行 `bash: no job control in this shell`——**被杀 ≠ 红**，拿不到汇总行就当“结果未知”，不要据此改代码。用 `timeout=600` 前台跑，或后台 + 完成通知并把输出重定向到文件。
终端汇总行被吞时，用 `pytest -q --junitxml=run/junit.xml` 解析 `tests/failures/errors/skipped`：**`skipped=0` 本身是正面信号** —— 恒 skip 的“假绿”用例会在这里露出来。
主工作区那份生成物作为"待提交差异"随对方的提交入库 —— 这是正确的归属（谁加了文件谁重生成）。

## 4. 报告纪律

- 门禁红时**逐条定位到 `文件:行`**，并明说哪一项是你的、哪一项不是 ——
  不要让"门禁红"含糊成"活没干完"。
- **别人正在改的报错不要顺手修**：可能撞他们的意图；给出修法 + 位置，让他们自己修。
- 报推送状态要**问远程本体**（`git ls-remote origin refs/heads/main` 对比本地 `HEAD`），
  不要只读本地 `origin/main` 引用 —— 它什么时候更新取决于谁 fetch/push 过。
- 你不是自己推的也可能已经在线上了（对方推流会把你的提交一起带上）：说清"谁推的"，别默认是自己。
- **子 Agent 的自报是“声明”不是“事实”**：它说“未提交/未完成”可能已过期（撞上限前一刻已提交），反之亦然；说“patch 已应用”也可能没落盘。**以 `git status`、`git log`、`py_compile`、回读文件为准**。
- **收尾先收尸**：子 Agent 随会话结束被丢弃，未提交的工作会留在盘上但提交永远没发生 → 收尾时先 `git status` 核一遍，把已完成批次替它提交，并写 `_wip/<日期>-续做说明.md`（HEAD、未提交清单、卡在哪一行、下一条命令）。

## Pitfalls

- **别用 `git stash` 分拣别人的改动**：它会把两边一起藏起来，取回时又是一堆冲突。
- **别对未跟踪文件用 `git checkout --` 回滚**：新文件不在 HEAD 里，救不回来。
- **门禁状态是分钟级快照**：报给别人之前**重跑一次**。上一轮看到的 4 项红，很可能已经被对方修掉 ——
  拿着旧结论让人去修，是在指挥他们修不存在的问题。
- **两次 `git status` 之间状态变了，别先怀疑自己**：先怀疑活写者。
- **一次门禁绿不等于稳定**：带锁/带文件的用例可能 1/3 概率红，而门禁那次恰好绿 → 会带着假绿提交。**“连跑 30 次全绿”是最弱的证据**——真正的验收是**注入延迟**（对端 1/3/8ms）再跑 30 次，能同时看到“旧判据 3/3 红、新判据 30/30 绿”才算修好。
  偶发红先分清是**测试自己的同步手法**还是产品真问题：只汇合第一轮的屏障、桩里 `wait(timeout=N)` 这类硬超时，会把机器卡顿变成红，而产品其实没问题（事件一条没少，只是顺序变了）；反之若真是产品，必须给线程名/锁持有者证据再改产品，**不许改测试掩盖**。
  固定名 `.tmp` 多写者并发会间歇 `PermissionError`（临时名带 pid+线程号，根上是让写者只有一个），`os.replace` 在目标被**另一个进程**打开时 Windows 直接 `EACCES`（`threading.Lock` 跨不了进程 → 结构上单写者 + 短重试退避）。
- **几条异步用例共享一份 spy，会同时造出假红与假绿**：并发跑（`Promise.all`）时后一条的 `sent.length = 0` 抹掉前一条唯一的记录 → 一条报“实际是 []”，另一条报“再点没发”（其实从未发过）。异步断言一律**串行 await** + 每条前重置 spy + 记一份调用序日志。
- **提交前把"这次提交该包含什么"写下来再 `git add`**：在并行仓库里这是唯一能防 `-A` 事故的习惯。
