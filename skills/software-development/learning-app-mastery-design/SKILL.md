# 学习类应用的掌握度 / 间隔重复 / 出题机制（设计规则）

适用：给学习/辅导类应用加“学到哪了 / 下一步学什么 / 什么时候复习 / 怎么出题”。
这些规则是从一个重型学习系统的实现里提炼的，可用可复算，不靠模型自我报告。

## 核心：掌握度是确定性纯函数，不是模型的一句话

- 掌握度 = `f(证据)`，**输入是只追加的作答/复习记录，输出是 [0,1] 的数**。同输入必同输出，能跑回放。
- **类型化门槛**：知识点分类型（记忆型 / 概念型 / 程序型 / 综合型…），每类不同阈值
  （记忆型要求高、程序型可略低），**不用一个全局阈值打天下**。
- **近因加权 + 置信度封顶**：越早的证据权重越低；证据少时不允许给出“高掌握”（防止答对一题就判精通）。
- 落成一个**纯函数模块 + 单测**，不依赖模型、不依赖数据库连接，这样口径才能在论文/评审里交代清楚。

## 门槛即游标：下一步学什么算出来，不靠计数器

- 推进 = **扫第一个未达标的点**，而不是 `stage += 1`。好处：天然支持跳级/压缩，学习者已会的部分自动跳过。
- 给界面一个“下一个目标”：`未达标点 + 它缺什么证据 + 建议动作`，三样一起给。

## 证据日志 + 确定性回放（让掌握度可审计）

- 作答/复习写入**只追加**的事件/记录表（含时间、评分、间隔、算法参数），掌握度与复习排程都从它**算出来**。
- 好处：算法换了可以重放旧日志重算（新旧对比有据）；用户质疑“为什么说我薄弱”能追溯到具体哪几次作答。
- **反面教材**：把整棵进度树塞进一个 JSON 大列（`state_json`）——查询、统计、增量更新全难做。
  进度应按「知识点 / 掌握度 / 复习队列」分表。

## 间隔重复：先能用，再变细

- SM-2（单一 ease + 间隔 + 连对/失误计数）**足够起步**，但要把评价→质量的映射与 ease 下限写进单测。
- 升级路径：三参数模型（stability / difficulty / retrievability）+ **期望保留率**（如 0.9）——
  调保留率即自动伸缩所有间隔，是产品旋钮。升级只换计算，**证据不用动**（这就是上一条的价值）。
- 排程字段全部可空：老数据没有排期也要能算，别让“没排期的卡”被当成“没练过”。

## 出题与判分：谜底服务端托管

- **正确答案绝不下发到前端**（也不进同一份响应）；前端只拿题干与选项 id，交卷后再判。
  “界面上点『看答案』才显示”不是防护 —— 答案已经在客户端了。
- 选项拆成 `{label, body}` 并**打乱顺序**，投影时用白名单字段拼输出，避免顺手把 `expected_answer` 带出去。
- 抽背/测验优先**离线可跑**（零模型调用）：出题是确定性的，判分也是；只在“生成新题”时才调模型。
- 若测验由模型出：把“出题”当**收尾动作** —— 发完题本轮就结束，作答作为下一条消息进来，别让一轮对话挂着等用户。

## 复习排程的写路径：卡号口径与错误可见性

掌握度算得再对，只要"练完之后写不回去"，整个系统就是死的。这一类 bug 的共同形状是**静默**：

- **索引字段只能有一套基数，并写进契约**。同一个 `card_index` 在一个接口里 0 起（`cards[]` 数组下标）、
  另一个接口里 1 起（“第 N 张卡”），前端再读一个**回包里根本不存在的键** —— 结果是 `review` 恒回 `-32602`（传 -1 / 越界），
  前端 `catch` 吞掉，界面一切正常，**复习排期永远不更新**。规则：数组下标就 0 起，面向用户的“第几张”就 1 起，二者不混用；
  **输入歧义值（如 0）要显式拒绕**，不要替调用方猜它是哪一种。
- **既有契约已经把某一族钉死时，不要为了好看去统一**：那会翻掉已有测试。显式分成两族 + 各加守卫，并把“两族并存”记成设计债（要统一就连同那些契约测试一起改，单独排期）。
- **消费方要读载荷里真实存在的键**：取 `card.card_index` 之前先用一条契约测试钉住服务端回包里确实有它。
  读 `undefined` 不报错，只会让功能静默失效。
- **后台副作用（排期、掌握度写回）的失败必须可见**：至少 `console.error` + 界面一条可见提示；服务端与前端都不许空 `catch {}`。
  看不见的失败等于没发生 —— 与“掌握度可审计”是同一条原则。
- **验收是“排期真的前进”，不是“不报错”**：一次 good 之后 `due_at > reviewed_at`；再评一次 good，
  `interval_days` 与 `due_at` 都应比第一次更大（`reviews == 2`）。只断言“没抛异常”的修法等于没修。

## 业务不变量用数据库约束表达

- 能写成约束的规则就别写成“希望代码别忘了”：例如“一条学习路径同时只有一道未结算的题”、
  “事件流 `UNIQUE(turn_id, seq)`”。建库即可用，并给一条单测。
- 分层方向（谁可以 import 谁）用一条**标准库写的测试**就够，不必为此引新工具/新依赖。

## 指标口径（会被追问的那个）

- **覆盖率 ≠ 语义支持度**：先统计“引用 id 真不真”，再单独算“引用是否真的支持该说法”，两层分开报。
- 分母为 0 时**回 null，不回 0**（0 会被读成“一个都没做到”）。
- 区分“声称有出处”与“本来就没有出处”（练习/行动类条目不应计进无出处分母）——
  否则指标压力会逼模型给练习硬挂一个来源，那才是真幻觉。
- 指标不好看时，**先把产物原文 + 被丢弃的引用落盘再看**，不要凭猜改。
