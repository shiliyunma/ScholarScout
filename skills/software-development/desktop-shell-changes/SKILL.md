# 改桌面应用窗口外壳：先量再交付

## 何时用

- 需求是「隐藏最上面那行标题栏」「边界像 XX 一样简洁」「自定义窗控按钮」「去掉系统边框」。
- 改了窗口尺寸/位置/最大化行为，或改了宿主 webview 里的前端资源，需要证明真机长什么样。
- 典型宿主：pywebview / Electron / 任何「壳 + HTML 前端」的桌面应用。

## 铁律

1. **去掉系统外框 = 连带失去 OS 提供的能力**（拖动、四边缩放、双击最大化、系统菜单）。
   先**假定会全部失去**，再逐条验证 —— 不要假定框架会帮你兜住。
2. **这类改动单独一批、排在最后交付**，并且**必须留一个配置开关能一键退回原生窗口**，
   默认取「一定能用」的那一档。先告诉用户代价（自绘窗控 = 拖动/最小化/最大化/缩放都得自己接管），
   再让他选：一行标题栏换「窗口能动」，这个交换通常是值得的。
3. **交付前的真机验收清单（缺一不可，全部在真机上量，不看感觉）**：
   ① 非客户区高度；② 拖动位移 ≠ 0；③ 边缘/角缩放后宽度真的变了；④ 最小化/最大化/关闭各点一次。
4. **截图/点击前先确认窗口在前台**：`GetForegroundWindow() == 目标 hwnd`。合成鼠标事件会落到
   盖在上面的窗口上 —— 不确认就会得到「点了没反应」的假阴性。

## 量的方法（可复用的硬指标）

| 要验什么 | 怎么量 |
|---|---|
| 原生标题栏还在不在 | `GetWindowRect`（含边框）减 `GetClientRect`（客户区）= 非客户区高度。有标题栏约 30–40px，无边框 **0px** |
| 能不能拖动 | 合成鼠标在标题区按下→分步移动→抬起，比较前后 `GetWindowRect` 的位移 |
| 能不能缩放 | 合成鼠标在边缘拖动，比较窗口宽度变化 |

`ctypes.windll.user32` / `gdi32` 就够（`EnumWindows` 找窗口 → `IsWindowVisible` +
`GetWindowTextW` 认标题 → `GetWindowThreadProcessId` 比对 pid）。**别只按标题认窗口**：
残留的旧实例会让所有测量都量到旧窗口，还会让你以为「改动没生效」。

**直接用现成脚本，别每次手写**：`scripts/measure_window_chrome.py`
（`--cmd "C:/path/app.exe" --title ScholarScout [--drag] [--resize]`）：会先清掉残留实例、按 pid 认新窗口、
打印非客户区高度与拖动/缩放结论，输出全 ASCII（中文控制台是 GBK，中文输出会乱码到没法当证据）。

## 已知结论（先看这条能省一整轮）

- **pywebview 5.4 / Windows：`frameless=True` 确实去掉了原生标题栏（非客户区 0px）**，
  但**同时丢掉了标题区拖动与边缘缩放**（实测：拖动位移 0、右缘宽度不变）—— 窗口变成「能看不能动」。
  自己用 JS 打桥实现移动/缩放（顶栏拖动 + 右/下/右三边抓手）**没跑通**：诊断读出 class 已加上、
  自绘窗控条已显示，但抓手节点数 **0**（接线没执行到）。**别再花时间在这条路线上**，
  除非愿意在一台真机上专门调试它。
- **桥的能力 ≠ 界面的接线**，必须分开验。已证可用的桥级能力（直调可验证）：关窗、按最小尺寸夹取缩放、
  精确移动窗口到指定坐标。

## 真机可观测的三种手段

1. **让应用自己把内部状态画到页面上**：多数应用会留一个排障口子（跑一段 JS）。把
   `typeof 某函数 / 某 class 在不在 / 节点计数 / 桥方法是否存在` 拼成 **单行** JS 写进一个 `<pre>`，
   再抓真窗口截图用 vision 读。**多行 JS 塞进 `evaluate_js` 那类通道不可靠，拼成单行最稳。**
2. **前端资源顶部放版本常量**（`var APP_REV = "..."`），诊断时一起打印。
   否则「改了没生效」与「改错了」看起来一模一样（WebView 按 URL 缓存资源，这也顺便回答了缓存疑虑）。
3. **桩桥/无头探针全绿不算真机通过**：探针只证明「给对了数据、这个渲染函数能画对」，
   证明不了启动时序、全局状态、外壳行为。实测反例：探针里窗控条渲染正确、按钮接线也通，
   真机上同一个函数根本没执行到。**依赖启动时机或外壳的界面，至少要在真实窗口里验一处。**

**截真窗口的两个技术坑**：① GDI `BitBlt` 拿到的 DIB 是自上而下，而 BMP 文件格式要求自下而上 ——
不倒序写行会得到上下翻转的图，读图时会误判成「内容不对」；② 早期启动阶段的接线不要往
`document.body` 挂节点（可能还是 null，静默抛错），固定定位的元素挂 `document.documentElement` 更稳。

## 一次性改脚本的纪律（这类改动几乎都是脚本改文件）

- **先探换行符**：老仓库常见 CRLF。脚本里用 `\n` 写的**多行**字面量永远匹配不上，
  表现是「断言失败 / 什么都没改」，很容易误判成「代码结构变了」。读文件用
  `io.open(path, "r", encoding="utf-8", newline="")` 并探测换行符；多行改动优先用 patch 工具
  （容忍换行差异），脚本里只做**单行**替换。
- **每处替换先 assert 真的匹配上了再打印** —— 无条件打印「完成」会撒谎，你会以为改好了其实没改。
- **每改完一个文件立刻落盘**，别把所有 `write` 堆在脚本末尾：末尾一处断言失败会让前面
  所有已算好的改动一起丢。多步骤改动就拆成几次小调用。
- 判断「改动生效」要落在可观测处（版本常量 / 节点计数 / 真机指标），别靠「我改过了」。

## 收尾

- 提交信息写清**代价与回退方式**（哪个配置项、改成什么值能退回原生窗口）。
- 没验成的事项如实说明，别把「没量过」写成「已验证」。
