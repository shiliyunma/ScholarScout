# 技术栈讲义包：一次给十几个栈做「讲义 + 资料 + 能跑的 demo」

大浩说「**分派子Agent去处理这些技术栈的学习路线**，有现成教程就下载，没有就按官方文档总结，
不能超过 8 讲、五六讲最好」时，指的就是这个交付形态。

与 `repo-learning-workbench`（单仓源码工作台六件套）是**两个不同的模式**：那个有源码可读、以「行号锚点」
取证；这个没有源码，知识点来自**官方文档**，产出以「份」计，常常一次 10~15 个栈。
两条铁律共用：数字现查、不凭记忆写。（那个 skill 是用户自有资产，不能直接改；本 skill 是它的姊妹篇。）

## 触发

- 「分派子Agent去处理这些技术栈的学习路线」「学习资料和安装都放在 X 目录下」
- 一次列一串技术栈（前端框架 + 数据库 + 消息队列 + 语言/框架 + 认证 + 各种 RAG/知识库项目）
- 目标措辞总是这三个：**知道是什么 / 能解决什么问题 / 能看懂能跑 demo**
- 「参照 hermes 的完整讲义，给 X 也设计一套」+「每份讲义不要包过多技术性词汇，以我能读懂的方式介绍，
  适当穿插少量技术词汇和伪代码」→ 这是**源码讲义体系**变体，见下节与
  `references/source-lecture-series.md`（`repo-learning-workbench` 是用户自有资产、改不了，配方放这里）

## 交付形态（固定）

```
<root>\
├── 00-总索引.md                    学习顺序分几条线 + 讲义清单表 + 凭据表 + 已知缺口
├── 启动所有服务.bat / 停止所有服务.bat   他的偏好：入口放最显眼处（项目根、双击即用）
├── 01-学习路线\<栈>-学习路线.md      讲义，一个栈一份
├── 02-学习资料\<栈>\               官方文档离线副本 + 00-来源清单.md
├── 03-env\                       运行时（目录名必须 ASCII，见 references）
├── 04-demo\<栈>\                  最小可跑示例 + README.md + expected-output
├── 05-环境清单与安装记录.md         逐条安装命令 + 真实输出 + 踩过的坑
├── 06-VSCode上手.md                → 配 vscode-runnable-workspace（扩展 + 终端 + launch/tasks）
├── 07-启动方案\                   ★ 一个 demo 一份文件，外加一份 00-公共前置.md
└── _tmp\                          中间件；注明哪些可删、哪些（如模型文件）删了就得重下
```

**`07-启动方案\` 一个 demo 一份文件**（外加 `00-公共前置.md` 放共享事实）。他曾明确要求「每个写一份，
而不是一个大汇总」——写成大汇总会被退回来拆开。方案里**凡未全局注册的程序必须写完整路径 + 启动方式**，
这也是他的硬要求；查「新开的终端能认什么命令」要读注册表里的持久 PATH，别用 agent 自己 shell 的 PATH
（那里面被注入了 Hermes 自带的 node/python），配方见 `references/runtime-env-and-audit.md`。

## 讲义固定格式（他的口味，别自创）

每讲六段、顺序固定：

```
## 第 N 讲 <标题>
- **是什么**：一到两句，直白
- **解决什么问题**：为什么需要它 / 不用会怎样 / 它替代了什么
- **读物**：官方文档页面标题 + 完整 URL
- **关键概念**：3-5 条，每条一句话
- **动手 demo**：具体命令或代码，指向 04-demo\<栈>\
- **自测**：1 个问题，能答上来才算过这讲
```

开头写「讲什么 / 不覆盖什么」（做成表格最好）；结尾写「学完之后你应该能…」+
「如果我来做，我会/不会照抄它，为什么」。

**硬约束**：

- **5-6 讲最佳，绝对不超过 8 讲。**
- 只讲主干：不讲内部实现细节、不讲性能调优、不讲边缘场景、不讲历史包袱。
- 每条事实后带官方 URL；查不到就写「待核实：<具体问题>」，**不许凭记忆写**。
- 中文为主，代码 / 命令 / 术语保留英文。
- 面向「会写代码但没接触过这个栈」的人。

## 给子Agent 的 brief

一个栈一个子Agent，三个交付物（讲义 / 资料 / demo）。brief 里必须写死这几条：

1. **先定格式再排预算**：把六段模板**原文**贴进 brief，加一句「不许自创结构」。描述格式不如贴格式。
2. **迭代预算顺序**（不写这句必然出事）：① 只抓 3-5 个「讲义里真会引用」的官方页面
   → ② **立刻写 5 讲讲义并落盘** → ③ 再回头补资料 → ④ 最后才调 demo。
   实测：3 个子Agent 全把预算烧在下载和调 demo 上，**讲义一个字没写就被截断**。
3. **补救轮做成单交付物**：「素材已在本地，**只**写讲义，不要重新下载、不要重建项目」——
   同样的事一个小时候能干完且质量更好。
4. 报告必须贴：讲义路径 + 实际讲数 + 每讲标题、资料文件数与字节、demo 的**真实命令与真实输出**、
   「待核实 / 不确定」清单。**跑不了就写「未跑通，原因：X」，不许编造输出**——这句要明写，很管用。
5. **凭据只以环境变量出现**：写「你自己从 <文件> 读，不要把值写进任何文件」，收尾再自查一遍。
6. 环境事实（端口、凭据、已装什么）统一放 `05-环境清单与安装记录.md`，brief 里只写「动手前先读它」。
7. 给一份**端口避让清单**：用户自己常驻的容器占了哪些端口、还有哪些可用，一并列出。
   不给的话子Agent 会照默认值起，撞上后只会反复重试。同理，要抓 GitHub 就提前告知可用的镜像前缀。

## 父Agent 的职责

子Agent 干的是资料与讲义；**环境、验证、索引是老父的活**，也正好填满等待时间。

- **每个 demo 父Agent 自己复跑一遍**再写进总索引。子Agent 的「已验证」经常是「我以为会通过」。
- demo 卡住时，父Agent 去读**那个子系统的日志**（`docker compose logs`、nginx error.log、netstat），
  把原始错误行 + 机制 + 确切改法 steer 给还在跑的子Agent —— 比重新派一个便宜得多。
  实测三次这样的 steer（端口被用户自己的容器占、`proxy_pass` 用变量就必须配 `resolver`、
  认证策略回 407 而 nginx 只映射 401）每次都让子Agent 下一轮就修好。
- 子Agent 说「某交付物缺失」先重跑一次自己的核验脚本 —— 那个结论可能是十分钟前的快照。
- 报告里给一份**诚实的缺口清单**：哪些没跑通、原因是什么、绕开需要什么。他要的是「能实际工作」
  加上「哪里没做到」并列，不是一份全是绿勾的报告。

## 并发编排

- 单批 3 个，其余排队。**池子满时 `delegate_task` 会转为同步执行**，所以别在兄弟还在跑时发新批。
- 交付物拆分：一个栈一个子Agent；强耦合的一对（如 Go + Gin、GraphRAG + LightRAG）可以同一个人
  做两份讲义，但写进 brief 时要说清优先级顺序。
- 长跑任务里环境搭建和核验是并行 lane，不要串行等子Agent。

## 资料离线副本与 00-来源清单.md

- 抓取先试**内容协商**：`curl -sSL -H "Accept: text/markdown" <url>`（redis.io 直接返回官方 markdown，
  比抓 HTML 干净得多、省一大截预算）。静态站（react.dev / mui.com / vite.dev）直接 `curl -sSL` 拿 HTML 也行。
- `00-来源清单.md` 格式：`标题 | URL | 抓取时间 | 本地文件名`，并写清抓取手法。
- **URL 不要手抄**：从每份 `raw-html/*.html` 里正则抽 `<link rel="canonical" href="...">` 与 `<title>`，
  用 `assert` 校验「页面数 = 抽到的行数」「每个页面都有对应 md」。
  实测：`react-start-new-project` 的规范 URL 其实是 `creating-a-react-app` —— 照文件名猜必错。
- 每抓完做一次「404 检查」：猜 slug 会静默抓到 404 页并当成正文存下来，要用页面 `<title>` 反查确认。

## Pitfalls

- **把「不超 8 讲」与「枚举的内容不得缺」一起写进 brief 时要留活口**：两者会冲突（如「React ①-⑤ + MUI
  至少 2 讲」就是 7 讲）。按硬约束 8 讲处理并让子Agent 在交付时说明取舍，不要为凑 6 讲删掉它真读过的一讲。
- **六段格式检查要容忍附录多出一两条**（`len(讲) <= 计数 <= len(讲)+2`），否则会把格式正确的讲义判成缺陷。
- **同一份讲义会被不同轮次的子Agent 改到**：核验数字在补写轮后要重跑，不要把第一轮的数字写进总索引。
- **教学性缺陷会被当成缺陷去「修」**：`01-go-basics` 故意不带 `go.mod`（教单文件模式 vs 模块模式），
  加了 `go.mod` 就把这堂课毁了。动手前先读子Agent 的 README 看它是不是故意的。
- **不要相信自己的路径假设**：`03-环境` 和 `03-env` 这种一字之差，会造成「目录消失」「文件不见了」的假象。
- **一个栈的 demo 失败了不等于讲义废了**：如实标注「未跑通 + 根因 + 绕开方式」比注水或删掉它有价值得多。
- **引用计数要分清「文件数」与「目录数」**：`find X -type f | wc -l` 是文件数，`ls -d X/*/ | wc -l` 才是目录数。
  实测把某目录的 213 个**文件**当成 213 个命令**目录**写进路线（真值 87 个目录）——这类数字会被用户当面试素材引用。
  文件数 / 行数 / 体积用一条命令一次算齐再落笔。
- **校验脚本的计数器要在两个分支都累加**：只在失败分支累加而漏掉成功分支，全过时会打印 `0/0`——
  看着像「一个都没匹配上」，会白排查一轮。最后断言 `total > 0`。
- **非官方源码（source map 还原 / 拆包 / 泄露版）必须在 `00` 里写清出处**：三句话——架构是真的、
  细节可能是补丁、官方发布版**裁剪了功能**；讲义里统一口径「只引用能 grep 到的」。
  用户会拿这些内容去面试，出处不清等于埋雷。
- **别按常识解释目录名**：先 grep 它的实际用法（实测某仓库 `hooks/` 是 React 钩子，不是事件钩子——写错就是给面试埋错答案）。

## 变体：源码讲义体系（有源码可读的仓库）

当讲义的主题是**一个能读源码的仓库**时，形态换成：

```
<root>\<项目名小写>-learn\
├── 00-总索引.md / 01-学习路线.md / 02-源码地图.md / 03-核心机制速查.md / 学习进度.md
├── 讲义写作规范.md        ← 先写它，再写任何一份讲义（批量生产时唯一的质量闸门）
└── 讲义汇总\阶段N-<名字>\<讲号>-<主题>\<讲号>-①讲义-<主题>.md
                                       <讲号>-②材料-<主题>.md   ← 仓库自带的一手文档
```

**讲义风格是硬要求，每份都照做**（落到八段骨架）：
一句话总结 → 先看一个场景 → **用比喻讲一遍**（厨师、菜单、档案柜那种）→
本讲要记住的几个词（表格 3–6 个，每个一句人话）→ 关键代码长什么样（伪代码 ≤20 行 + 中文注释）→
源码锚点表（5–10 条 `文件:行号`）→ **和已学过的那份源码对照**（他学过第一份，这是最大杠杆）→
必答三问 + 延伸两问 + 下一讲预告。正文 150–250 行，段落 ≤5 行。

**不许**：堆术语、写「顾名思义 / 众所周知」、通篇英文、上来就贴代码。

**先自己写 2 份样板**（定位那一讲 + 核心机制那一讲）给用户过目，再派子Agent 批量产。
讲次划分、并行派活模板、父的复核、②材料分发、以及常见错误口径，全文见
`references/source-lecture-series.md`。

## 支持文件

- `references/source-lecture-series.md` — 当讲义的主题是**有源码的仓库**时的整套配方：八段骨架、
  讲次划分、并行派活模板（规范 + 样板 + 锚点纪律）、父的复核、②材料分发。写源码讲义前读它。

- `references/runtime-env-and-audit.md` — 运行时目录的 ASCII 硬规则、免安装解压版与启停脚本、
  服务的**正确起法与生命周期**（别起成 agent 受管进程，否则会被静默回收）、
  **用服务自己的客户端验证活着**（netstat 会骗、跨行正则会假阳性）、
  `0xC0000142` 这类子进程异常退出码的诊断、.bat 的编码与 PATH 抢占坑，以及全库核验脚本的固定坑。
  **动手装环境前、写核验脚本前读它。**
