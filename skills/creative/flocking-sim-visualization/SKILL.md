# 浏览器里做鸟群/粒子群可视化（boids / flocking）

适用：用户要"一堆个体 + 几条局部规则 → 涌现"的实时可视化（鸟群、鱼群、粒子群、羊群）。
也覆盖：O(N) 邻域加速、WebGL2 实例化渲染、以及"怎么诚实地验证"。
参考实现：`D:\boids\boids.html`（单文件、零依赖、WebGL2、3000–12000 只）。

## 1. 三条规则与力的量级（最容易错的地方）

- 分离 = 反向加权和；对齐 = 朝邻域平均速度；凝聚 = 朝邻域平均位置。
- **Reynolds 式 steer**（期望速度 − 当前速度，再截断到 maxForce）会把目标方向**归一化**：
  期望速度的大小恒为 maxSpeed，所以"按 1/d² 加权"在这条路径上**完全丢失**（只影响方向不影响幅度）。
  要点：想要"越近越猛"，就不能只用 steer，必须另加一个**幅度随紧迫度变化**的项。
- **分离不要用单一超大 cap 的力**：若分离的饱和幅值 ≫ 对齐/凝聚（如 `sepCap×maxForce` 是它们的 17 倍），
  群会被自己的分离力撑散——实测 `spreadNorm≈0.5`（等于均匀分布）。正确做法分三层：
  1. **软分离**：归一化 steer，与对齐/凝聚**同量级**，只负责"形状"；
  2. **硬核**：只对"贴脸或正在接近（径向接近速度>0）"的邻居生效，幅度按紧迫度放大；
  3. **硬球（位置投影）**：d < 个体半径时直接做位置分离（各退一半）。**这才是"别撞"的硬保证**——
     只靠力，稠密群里必然偶发互相穿过（实测 minDist 掉到 0.01，个体体长约 1）。
- 权重经验顺序会因为上面第 2 点而变：拆层之后往往 **凝聚 ≥ 分离**，与"分离>对齐>凝聚"的教科书说法相反。

## 2. 环形空间（torus）的两个非直觉结论

- **纯局部规则的平衡态是"很多个小群"，不是"一个大群"**：均匀分布是平移对称下的精确平衡点。
  实测 3000 只在边长 110 的环面上跑 10 秒，`spreadNorm` 从 0.12 漂到 0.47（散开）。
  想要"一群"：加**长程归群**（Reynolds 的 goal seeking，只在超出"允许群半径"时生效），
  并让它随世界边长缩放（否则 N 越大挤得越死）。把这个权重滑到 0 就是"纯三规则"，要能切换给用户看。
- **自动居中**（每 k 步把全体平移回盒子中心）能让群永远在取景框里，且**平移不改变动力学**——
  但前提是：① 平移量用"圆均值"算时，必须用合矢量模长（R）判断它是否可信，R 小时（多群/对称分布）
  跳过，否则每 k 步整体跳一次；② 所有用**绝对世界坐标**的东西（鼠标吸引点、捕食者）必须一起平移。

## 2.5 可切换的"实心墙"（非环形边界）：改一处是错的

把环形世界换成"穿不过去的盒子"时，**不能只改积分末尾的越界回绕**——整条"环形"链路都要一起改，
漏一处就会得到"看起来能跑、其实穿了墙/邻居算错"的结果：

| 环节 | 环形 | 实心墙 |
|---|---|---|
| 邻域格扫描 | 跨边界格回绕 + 平移一个世界长度 | **越界格直接跳过、偏移恒为 0**（回绕会把对侧算成真邻居） |
| 窗口跨满整轴的分支 | 扫遍该轴全格 | 强制关闭（没有镜像周期，跨轴必错） |
| 群心 | 圆均值 | **算术均值**（不跨边界就是精确解），可信度 R 恒为 1 |
| 归群/鼠标/捕食者方向 | 最小镜像位移 | 直接位移 |
| 硬球位置投影 | 回绕 | **夹在墙内**（否则推开那一瞬会穿出去） |
| 积分末尾 | 回绕 | 夹到 `[r, L−r]` + **反射法向速度**（速度写回必须移到墙响应之后） |
| 自动居中 | 可用 | **必须停用**（平移会把个体推出墙外，且"平移是对称变换"的前提不存在） |
| 渲染 | 只画亮边 | 墙面只画**背面**（`cullFace(FRONT)`）：单层淡色，前后重叠会糊成一片斑 |

- **硬约束要用"纯弹道探针"证明，不能只看批量统计**：把三条规则/归群/温度全关掉，让一个体正对墙飞。
  实测它停在 `maxX = L − r`（正好是自身半径）、逐帧越界 0、法向速度反向。批量用例用"全域均匀起始"
  保证开头就有个体贴墙（否则可能是"没碰到墙所以没越界"的空过）。
- 批量用例的逐帧越界检查要 `O(N)` 每步累加，阈值写死 0，不要只信任最后那一帧。
- 墙会压缩活动空间，聚拢度阈值要相应放宽（实测 0.3/0.4 → 0.45）。
- 多邻居同时推开同一个体时位置投影是**逐次累加**的，所以"夹回前越界量"可以远大于 `maxSpeed·dt`；
  那是诊断量，不是穿透（穿透由逐帧越界 0 保证）——别把两者混为一谈。

## 3. 性能：O(N²) → O(N·k) 的四层

1. **均匀网格 + 计数排序**重建（每帧 O(N)），单元边长 ≈ 感知半径；环形回绕用"每格算一次平移量"，
   候选循环里不做分支式最小镜像。
   ⚠️ 窗口跨满整条轴时（世界相对感知半径很小）必须改为"扫遍该轴全部格子"：
   把半径裁剪成 `floor(g/2)` 会在 g 为奇数时漏真邻居、偶数时重复计入。
   ⚠️ 2D 模式下 z 轴循环只应跑一次，否则同一个邻居被算 3 遍。
2. **平方距离**比较，不开根号；三力**一次遍历**同时累加。
3. **邻居上限 k 必须逐候选检查**（放在换格处等于没限制：实测平均邻居 51 ≫ k=18）。
   再加**候选测试预算** `kCand≈4k`：这才是每只鸟开销的硬上界（实测 12000 只从 63ms/步降到 13ms）。
4. **由近到远扫格**（先自己格再一圈圈向外，方向按个体随机化避免触顶偏置），预算截断时留下的是最近邻居。

参考量级（纯 CPU 仿真，不含渲染）：3000 只 ≈2.5–3ms/步；6000 ≈8ms；12000 ≈13–16ms（≈60 步/秒）。
坑：热点路径别用 `Math.hypot`（比手写 sqrt 慢一个数量级）。

## 4. WebGL2 渲染要点

- 顶点着色器里用"实例位置 + 速度"**现场构造朝向基**，CPU 不建矩阵；一次 `drawArraysInstanced` 画完。
- **WebGL2 没有 `baseInstance`**：把"特殊个体"（捕食者/鼠标标记）写进主实例缓冲的尾部槽位是**读不到的**，
  会被画成第 0 个个体的复制体。必须给它**独立 VBO+VAO**。
- 拖尾/残影：把场景画进 FBO 纹理，每帧先用半透明黑幕衰减再加法混合。
  **采样单元必须解绑该纹理**，否则报 `Feedback loop formed between Framebuffer and active Texture`。
- 2D 模式下把机体的"上"参考向量设成 (0,0,1)：固定用 (0,1,0) 会让机翼轴落到正对相机的方向，
  个体被压成约 1 像素薄片。
- 个体显示大小随世界边长缩放，否则大世界/大 N 时个体小到看不见。

## 4.5 WebGL 里“特殊个体”画不出来的四类真因（都真踩过）

画一个与主体不同的对象（捕食者/鼠标标记/参考物）时，以下每一个都能让它“完全不可见”且不报错：

1. **程序被前面的绘制换走了**：任何 `drawBox()`/画线/画UI 的绘制都可能在内部 `useProgram(其它程序)`；
   主对象画在前面恰好没事，**特殊对象画在后面就中招**。症状极隐蔽：**一个模式正常、另一个模式不正常**
   （例：3D 下看不见、2D 下正常，因为 2D 不画盒子）。画特殊对象前重新 `useProgram` 并重设它的 uniform。
2. **VAO 里缺几何属性**：顶点属性的**绑定属于 VAO 状态**。只为“实例数据”建 VAO（只绑 location 2/3/4）时，
   location 0/1 会取默认常数 (0,0,0) → 整个对象塔成一个点。**每个要绘制几何的 VAO 都必须绑顶点属性**。
3. **buffer 没保留引用被 GC**：`gl.bindBuffer(gl.ARRAY_BUFFER, gl.createBuffer())` 这种写法拿不到 JS 引用，
   缓冲区可能被回收 → 几何为空。必须 `const vbo = gl.createBuffer()`。
4. **几何本身退化**：复用主体几何时，若主体是**薄片**（如纸飞机形状），特殊对象在侧视时厚度趋 0、
   缩放到很大也只是一条线。给特殊对象单独的**有体积**形体（头/胸/翼/尾）。

**验证方式**：“画得出来”应当用**结构断言**而不是数像素（像素统计在自检上下文里不稳定：并发动画循环、
拖尾累积、分辨率都影响它）。在渲染代码里埋一行探针（`gl.getParameter(gl.CURRENT_PROGRAM) === prog.p`、
实例 buffer 的位置、几何跨度、`gl.getError()`），自检直接断言这四个量 —— 上面四类事故全都能被抓出来。

## 5. 怎么"诚实地"验证（不要只截图说好看）

无头浏览器自动化 + 三条硬要求：
1. **真实时钟**：`--virtual-time-budget` 会把 `performance.now()` 冻住，测出的每步耗时全是 0。
   正确做法：本地起一个 python HTTP 服务托管页面（顺带处理 POST 回传），Chrome 以真实时钟跑，
   页面把结果 `fetch` POST 回来落盘 JSON。（脚本见 `D:\boids\tools\headless_test.py`；
   无头下 WebGL 需要 `--enable-unsafe-swiftshader`。）
2. **真实画面**：页面用 `gl.readPixels` 把渲染结果读回、编码 PNG、POST 落盘，再用人眼核验——
   "数值对但画面空"是最常见的失败。注意 readPixels 必须在 `render()` 之后**同一 JS 任务内**同步调用。
3. **判据必须可证伪，并且要有消融对照**：
   - 局部对齐度（每个体的邻居速度单位向量平均长度）→ 对齐规则；
   - 聚拢度（到群心的均方根距离 ÷ 世界边长，均匀分布≈0.5）→ 凝聚规则；
   - 撞车率 / 最小间距、以及"两只正面对飞不穿过"的专项 → 分离规则；
   - 阈值取**与实测同量级**（撞车率实测 1e-4 就写 <1e-3，不要写 2e-2）；
   - **消融**：同一份代码只把一个权重设为 0，要求指标显著变差。否则一个"所有个体朝同一方向直线飞"
     的退化实现也能通过全部指标（这是真实踩过的坑）。
   - 全局序参量 φ=|Σv̂|/N 波动极大（局部规则/全局量），只作展示与"从随机起始显著上升"的证据，不做质量门槛。
4. 2D 模式会自发形成旋转"风车/环"（局部对齐 0.9+、全局 φ≈0.05）——这是真实的涌现图案，要写进文档而不是当 bug 修。

## 5.4 自检用例的两个结构性坑（都真实踩过）

- **基线函数必须重置"别的用例会改"的每一个参数**：`applyBaseParams()` 里漏了 `solid`，
  结果后面的频率专项继承了实心墙用例的 `solid=true` → 居中块被正确跳过 → 平移 0 次。
  症状是"功能好像没生效"，实际是基线没归位。（同一个坑第一次是漏了 `wSep`：对撞用例继承了消融的 0。）
  凡是用例会写的参数（权重、边界模式、自动居中及频率、诊断计数器）都要在基线里显式写死。
- **要证"功能有效"，必须造一个它会失败的场景**：
  - "自然状态下的群心偏离"不能用来验证自动居中——初始方向随机、整体动量≈0，群本来就不漂（实测 4.2），
    "关掉居中"也看不出问题，判据于是**时通时挂**。
  - 正确做法：强制一个确定性整体漂移（每步把全体速度设成同一方向）再对比开/关，结果才是决定性的
    （实测群心偏差：开 2.46 / 关 31.1）。
- **别拿内部缓存量当观测量**：`_cx` 是每 12 步刷新的圆均值，频率调快时会把"缓存陈旧 + 群心自身每步抖动"
  一起测进去，得出**结论相反**的假象（越频繁反而偏得越多，4.15 vs 2.13）。观测量要自己现算。

## 6. 观感（“温馨/画质高”怎么落地，全是可复现的工程手段）

- **背景**：不要纯黑或单色。做一个垂直色阶（地面暗→地平线暖桃→玫瑰→天顶柔蓝紫）+ 低垂暖阳（核心+大晕）
  + 横向拉伸的云（fBm + 域扭曲，靠太阳侧镀暖光）+ 地平线薄雾。
- **云/噪声不能逐帧算**：5 个倍频的全屏噪声在软件光栅下几十毫秒。**启动时烘进一张小纹理（如 640×400）**，
  之后每帧只多一次采样；用 `uTime` 推动 UV 就能让云“慢慢地走”，也不花钱。
- **色调映射要“只压亮度”**：逐通道 Reinhard 会把高亮处的饱和度冲掉（密集处塌成白）。
  正确做法：`L=dot(c,luma); c *= (L/(1+kL))/L`——保留色相与饱和度比例。
- **稠密群体用 alpha 混合，不要用加法**：加法在密处把颜色平均掉（12000 个个体实测塌成一坨近白）；
  换成 `SRC_ALPHA, ONE_MINUS_SRC_ALPHA` 后是“一片有色的个体”，轮廓与个体颜色都保住。
  发光物件（捕食者光晕/拖尾）才用加法，且光晕那一遍可以关深度测试（真实 bloom 也绕过遮挡物）。
- **配色要掺“个体随机”**：只按速度/属性上色时，群体的取值集中 → 全群同色。
  用 `t = 0.4*属性 + 0.6*个体哈希`，确保个体之间有色差。
- **大物件默认别太大**：特殊对象（捕食者）默认 3~5 倍个体尺寸就够醒目，给用户一个滑块（如 2~9）微调。

## 5.5 流畅性："缩放下每只鸟都在剧烈震动"怎么修（可量化）

先把它变成数（页面端 `?jitter=1`）：
- `turnDeg` = 速度方向的**每步转角**均值（度）。整体平滑转弯也产生转角，单看不够。
- `roughDeg` = 上式的**二阶差分**均值 = **主判据**：平滑转弯接近 0，锯齿式乱甩才大。
- `maxTurnDeg` / 单步转角 >25° 的占比：极端事件规模。

四个独立来源，逐层治（实测 3000 只 3D，`roughDeg 1.19 → 0.46`）：

| 来源 | 修法 |
|---|---|
| **温度噪声是白噪声**：每步换一个完全独立的随机方向（主因） | 改成**沿时间平滑插值的 wander**：相位连续推进，在噪声表里相邻两格插值（约 0.45 秒转一次） |
| **仿真步长 = 真实帧时间**：掉帧时 dt 变大 → 位移与转向都跳 | **固定步长累加器** + **渲染位置插值**（没插值的话高刷屏上会"动一帧停两帧"） |
| **机体朝向直接绑瞬时速度** | 渲染用**低通速度**（一阶低通 ~6-7Hz）；物理不变 |
| **上参考轴在 `|f.y|>0.97` 处硬切** / 零速度兜底写死 +z | 按 `|f.y|` **平滑插值**；兜底方向改用上一帧的平滑方向（否则凭空 180° 翻转） |
| 低速时方向不可靠（速度被撞到近零向量） | 按原方向放大到 minSpeed 之前，先把方向朝上一帧的平滑方向收敛 |

⚠️ **wander 比白噪声"更热"**：白噪声的随机踢腿互相抵消，wander 会持续推同一方向约 0.45 秒
= 给每只鸟加了持续漂移速度 → **会把群吹散**（聚拢度 0.25→0.36，均匀起始甚至收不成群）。
换噪声模型后**必须重调幅度**（实测从 0.6 降到 0.2 左右），并在"形状仍在变 churn"与"群收得住"之间取平衡。

⚠️ **聚拢度必须时间平均**：单点快照方差极大（同一配置实测 0.32~0.38），拿单点比大小会得出**相反结论**
（曾经出现"噪声越小反而越松"的假趋势）。

⚠️ **极值要追到机制**：`maxTurn ≈ 180°` 不是噪声，而是"零速度兜底把方向设成固定 +z"与"上轴硬切换"。

## 6. 交付习惯

- 单文件、零依赖（不用 CDN，国内环境常常取不到）。
- README 的性能/质量表**从 report.json 生成**（写个小脚本），别手抄：手抄必然与实测脱节，审查会打。
  ⚠️ 生成脚本的**锚点必须唯一**：曾经用 `| 规则 |` 当锚点，它在第 1 节的规则表里也出现，
  `index()` 取到第一个 → 把两表之间的**整段正文删掉**（文件从 14KB 掉到 8KB）。改成唯一锚点，
  并加"替换后文件不得明显变短，否则中止"的断言；改完连跑两遍确认幂等。
- **手动 `render()` 必须先把相机矩阵算好**：把相机矩阵更新抽成 `updateCameraMatrices()`，循环与手动渲染共用。
  否则“测试里渲染的画面”与“用户看到的”不是一回事（症状：自检里特殊对象数到 0 像素）。
- **无头工具必须禁缓存**：`--disable-http-cache` + URL 加时间戳。Chrome 会直接吃 HTTP 缓存里的旧页面副本，
  于是“同一份代码两次抓图结果差 5 倍”、耗时测的其实是旧代码。这类“测的不是当前版本”的坑极难发现，
  因为它每次都“看起来跑通了”。
- **生成的文档表会替换一个区间**：锚定 start/end 的刷新脚本会把区间内的正文一并替换。
  任何手写正文都不要插在那两个锚点之间，否则下次刷新静默消失（症状：“我明明写过，grep 找不到”）。
- **看图迭代要留一条快通道**：抓图流程别绑定在几分钟的自检上。加一个 `?shotonly=<阶段>` 参数
  + 工具侧 `only:<阶段>` 模式，几秒就能出新图（`python tools/headless_test.py only:solid`）。
- **报告表格的生成器要对"专项记录"做通用分派**：对撞只有 `minDist`、撞墙有 `wallGap`、居中频率有
  `maxCentroidOff`，硬编码字段名会让生成器接二连三地 KeyError 打挂。按 `test` 名分派取关键量。
- **跑基准时机器上不能有别的负载**（这条踩了两次）：一次是并发跑后台任务，一次是**回复里挂着的实时
  预览窗在后台跑着同一个仿真**。同一份代码测出 3000 只 2.8ms → 9.9ms/步（差 3 倍）。
  所以：① 报告里同时给"与负载无关"的量（邻居检查次数 / 候选测试次数 / 平均邻居数），它们才是优化真假的证据；
  ② 工具别把 Chrome 的 stderr 丢掉（页面抛异常时那是唯一线索）；③ 无头跑的等待上限给足（负载下会顶穿）。
- 同一机位、同一距离抓多个时刻的图，是核对"形状/朝向是否真的在变"的唯一可靠办法（指标噪声很大）。
- 审查要分头做（算法数学 / 渲染与性能 / 交付严谨性），并保留"发现了什么、怎么修的"表格。
