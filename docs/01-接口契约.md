## 1. 分层与调用方向（单向，不许反向）

```
┌──────────────────────────────────────────────────────────────┐
│ 桌面壳  pywebview (Edge WebView2)                             │
│   ui/index.html + app.js  —— 只发 JSON-RPC，不读库、不发外网   │
└───────────────────────────┬──────────────────────────────────┘
                            │ JSON-RPC 2.0 over stdio (UTF-8, 一行一消息)
┌───────────────────────────▼──────────────────────────────────┐
│ rpc/server.py  —— 方法表 + 参数校验 + 流式通知                 │
└───────────────────────────┬──────────────────────────────────┘
                            │ 进程内函数调用
┌───────────────────────────▼──────────────────────────────────┐
│ runtime/  单轮 loop：组装上下文 → 调模型 → 执行工具 → 落 trace │
│   registry.py（工具注册表） context.py（会话上下文）           │
└───────────┬───────────────────────────────┬──────────────────┘
            │ 模型可见工具                   │ 读写
┌───────────▼──────────────┐    ┌───────────▼──────────────────┐
│ tools/*.py（6 主线 + 1 降级）│    │ state/db.py（SQLite + FTS5） │
└───────────┬──────────────┘    └──────────────────────────────┘
            │ 只经此层出网
┌───────────▼──────────────────────────────────────────────────┐
│ providers/*（arxiv/openalex/s2/web/github/llm）               │
│ fetch/http.py —— 统一限速 / 退避 / 缓存 / UA / 超时           │
│ data/raw/ 原件 ｜ data/text/ 纯文本 ｜ data/cache/ 抓取缓存    │
└──────────────────────────────────────────────────────────────┘
```

三条硬规则：

1. **前端只调 RPC**：不直接读 SQLite、不直接发 HTTP。单入口才可能把每次调用记进 `tool_traces`，指标才是真数。
2. **模型只看得见 `tools/`**：加能力 = 加一个工具或一个 provider，不许在 loop 里塞特例分支。
3. **出网只走 `fetch/http.py`**：限速、退避、缓存、UA 全在这一处；绕过它的请求在 review 里直接打回。

## 2. JSON-RPC 2.0 传输层

- **传输实现有两种，方法表与语义完全相同**（分发逻辑只有一份，在 `rpc/methods.py`）：
  1. **stdio**：一行一个 JSON 对象，UTF-8 无 BOM —— 桌面壳拉起的后端进程、CLI 冒烟测试、自动化测试都用它
  2. **桌面壳**：pywebview 窗口 + **同样的 `python -m scholarscout --rpc` 子进程**（`desktop/rpc_client.py` 管进程与帧，`desktop/bridge.py` 只做转发）。壳里**不 import 任何业务模块**，理由：
     - 分发只有一份：桌面与 CLI 走的是同一条必经之路，测试覆盖的就是用户跑的那条
     - 后端崩了窗口还在，界面能把错误显示给人看，而不是整个应用消失
     - 中文路径与编码坑（`docs/03 §9`）被挡在子进程里：子进程强制 `PYTHONUTF8=1` / `PYTHONIOENCODING=utf-8`
     - 界面要做到"点了就有反应"，后端只要保证"回了就是真的"

壳暴露给 JS 的方法（都在 `desktop/bridge.py`，返回值统一 JSON 字符串）：
核心四个 `info()` / `rpc(method, params_json)` / `reveal(path)` / `shutdown()`，
另有 `open_url(url)` 与六个无边框窗控 `window_mode()` / `win_minimize()` / `win_toggle_maximize()` /
`win_close()` / `win_move(x, y)` / `win_resize(width, height)`；
事件反向推给 `window.scoutEvent({method, params})`，窗口未就绪时先缓冲再补发（避免开窗瞬间丢事件）。
  选择依据：壳与后端同机时用桥更简单；后端需要独立进程/远程时用 stdio。**客户端看到的方法与事件一致**。
- 版本：JSON-RPC 2.0；**通知**（无 `id`）用于流式事件
- 启动顺序：壳启动 → 装配上下文（`app.build_context`）→ 调 `system.health` 自检 → 调 `session.list` 渲染侧栏
- 错误码：

| code | 含义 |
|---|---|
| -32700 / -32600 / -32601 / -32602 / -32603 | JSON-RPC 标准（解析/请求/方法不存在/参数非法/内部错误） |
| -32000 | 未登录或未配置模型（缺 API key） |
| -32001 | 外部服务不可用（arXiv/S2 挂了或限速中） |
| -32002 | 资源不存在（source_id / doc_id 查不到） |
| -32003 | 抓取被拒（403/429/robots） |
| -32004 | 超时 |
| -32005 | 取消（用户点了停止） |

**并发**：请求**并发处理**（读一行 → 工作线程分发 → 带锁写回），响应按 `id` 配对、**允许乱序**。
这不是性能优化而是可用性要求：一轮 `chat.send` 会阻塞 3–12 分钟，期间界面必须还能
点开资料预览、点「停止」；单线程实现下这两件事都会排到队尾，用户看到的是"点了没反应"。

### 3.2 会话与对话（主线入口）

| `session.messages` | `{session_id, limit?=50, before_idx?}` | `{items:[message], has_more}` | v0.1 |
| `chat.send` | `{session_id, text, toolsets?=["research"], mode?="sync"}` | `mode="sync"`（**默认**）：先流事件，最后 `{turn_id, session_id, message_id, stop_reason, usage, tool_calls, refs, text}`；`mode="async"`：**立即**返回 `{turn_id, session_id, accepted:true}`，整轮结论走 `chat.done` 事件（带 `text` + `message_id`）或 `chat.result` 补取 | v0.2（2026-10-12 加 `mode`，语义见下） |

|   ↳ 被拒的三种情形 | — | 提交未被接受时**抛错而不是回 `{ok:false}`**（调用方读的是 `result["text"]` 这类键，形状不同的成功响应会以别的方式崩）：`turn_in_progress` → `-32600`（同一会话已有一轮在跑，`data.turn_id` 是在跑的那一轮）；`at_capacity` → `-32001`（并发上限 3 已满，`data.running[]` 给出谁在跑）；`shutdown` → `-32001`。错误 `data` 恒带 `{reason, running[]}`（**拒绝要如实告知**，不排队 —— docs/20 §5.3） | `runtime.max_parallel_sessions`（默认 **3**）同时最多三份 token 在烧 |
|   ↳ 工具预算 | `runtime.max_tool_calls_per_turn`（**默认 12**，与 `config.py:145` / `docs/20 §5.1` 同一口径） | 用满预算后**再给一轮且不给工具**，模型必须收口；只有模型还想继续调工具才 `tool_limit` | 轮次预算 = 工具预算 + 1 |
| `chat.cancel` | `{session_id?}` 或 `{turn_id?}` | `{ok, turn_id, note}`（无在跑轮次 → `{ok:false, reason:"no_running_turn", note}`） | v0.1；v0.2 起**只影响被点到的那个会话**，语义见下 |
|   ↳ 取消语义 | — | **按 `session_id` 取消**（界面用这个：整轮结束前前端拿不到 `turn_id`）；执行时机是**步间检查**，正在跑的那一步结束后才生效，界面必须如实提示；两个都给时以 `turn_id` 为准；没有在跑的轮次回 `{ok:false, reason:"no_running_turn"}` 而非假装成功。**每会话每轮各持一个 `threading.Event`**（`TurnHandle.cancel_event`）→「取消 A 误伤 B」在机制上不可能。兼容阶梯：该会话**没有工作单元**时（CLI / 脚本直调）回退到全局 `running` 注册表找它、并把 `turn_id` 记进全局 `cancelled` 集合（老契约，`tests/rpc/test_cancel_and_session_usage.py` 钉着四条） | — |
| `chat.status`（**v0.2 新增**） | `{session_id?}` | `{running:[{session_id, turn_id, phase, started_at}], capacity:{max, used}}`；给了 `session_id` 再带 `session`：`{session_id, running, usage}`（该会话没有工作单元时 `usage:null`）；不给则带 `sessions:[{session_id, running, turns, tool_calls, tokens:{prompt, completion}, last_turn_id, last_stop_reason}]` | 多会话并行的**观测口**：界面靠 `running` 给在跑的会话画「进行中 + 停止」、靠 `capacity` 判「还能不能再开一个」。`phase ∈ queued\|thinking\|tool\|writing\|done`；`started_at` 是 `time.monotonic()`（**只用于算时长，不是墙上时间**）；`max` 读 `runtime.max_parallel_sessions`（默认 **3**）。`usage` / `sessions[].*` 是**本进程热缓存**，**权威源仍是 `usage_records`**（`session.usage`） |
| `chat.result`（**v0.2 新增**） | `{turn_id}` | `TurnResult`：`{turn_id, session_id, message_id, text, stop_reason, tool_calls, usage, refs, error}`；取不到 → `{ok:false, reason:"unknown_turn", turn_id, note}` | 迟到 / 掉线重连**补取**一轮的结论。结果信箱只留**最近 32 轮**、且**只在一轮收尾后才进信箱**（还在跑或已挤出的都取不到 → 如实回 `unknown_turn`，绝不回一个「看着像结果」的空壳）；与 `chat.done` 事件是**同一个 `TurnResult`**，两者并存 |

| `session.pin` | `{session_id, pinned?=true}` | `{ok, pinned}` | **不动 `updated_at`**（置顶不是"有新活动"） |
| `session.delete` | `{session_id}` | `{ok, deleted}` | 级联清理消息与轨迹，不碰资料库/花费账本 |
| `session.export` | `{session_id, fmt?:"md"\|"html"}` | `{ok, fmt, path, chars, text, bytes?}` | `md`（默认）导可复制的 Markdown；`html` 导**自包含单页 HTML**（内联 `markdown.js`、正文走 base64 所以 `</script>` 也截不断、无外部资源、深浅色跟随系统），此时不回 `text`。两者正文**同源**（同一份 `build_markdown`：只导对话 + 工具轨迹摘要，**不导 `role=tool` 原始 JSON**，绝对路径打码） |

| 方法 | 参数 | 返回 | 说明 |
|---|---|---|---|
| `archive.list` | `{query?, tier?, source_type?, year_from?, limit?=50, offset?=0}` | `{items:[source_card], total}` | `query` 走 FTS（trigram；短查询自动 LIKE 兜底，见 `02 §4.1`） |

| `archive.paths` | `{doc_id}` | `{raw_path, text_path, exists:{raw,text}}` | 取资料在磁盘上的确切位置（前端可复制路径） |
| `archive.reindex` | `{}` | `{ok, total, buckets, layout, index_path, files[], removed[]}` | 重建 `data/library/` 下的资料索引（全库 `index.md` + 各桶 `index.md`）。**只读库、零模型调用**；桶按 `ctx.config.library.layout`（默认 `<会话>/<格式>`）切分，返回里的 `layout` 是**实际用的**段名串，`removed[]` 是换布局后清掉的过期索引目录。改名/迁移后界面靠它一键重算（命名与分桶口径见 `docs/19`） |
| `archive.download` | `{doc_id?, source_id?, url?, force?:false}` | `{ok, reason?, path?, bytes?, mime?, ext?, doc_id?, source_id?, url?, http_status?, large?, already?, threshold_bytes?}` | **按需下载**：把 `doc_id` / `source_id` / 直接给的 `url` 对应的文件真下载到 `data/raw/`（走 `fetch/http.py`，人类可读路径按 `docs/19` 布局）。**默认关**：开关 `features.enable_download=false` 时**不动网**，回 `{ok:false, reason}`；文件超过 `fetch.large_file_mb`（默认 **20**MB）抽取阈值时**默认拒绝**，回 `{ok:false, reason, large:true, threshold_bytes}`，**只有 `force:true` 才落盘**（界面先二次确认、再带 `force` 重试）；网络失败同样回 `{ok:false, reason}` 而不抛。`large` = 该文件是否超过 `fetch.large_file_mb` 抽取阈值（超了只落盘、不抽正文，见 §5.2）。出网层另有**硬上限** `fetch.max_bytes`（同为 20MB），超了由 `fetch/http.py` 直接拒收（`FetchError.kind=too_large`，是错误码不是 `extract_status`）。用于**源码包 / 视频 / 音频**等「需到原站看或手动下载」的资料 |
| `trace.list` | `{session_id?, turn_id?, tool_name?, limit?=100}` | `{items:[tool_trace]}` | **论文所有调用类指标的取数入口** |

> `source.get` **未实现**（按 source 反查 documents/summaries/mentions 的聚合口没有落地；现由 `archive.get` + `archive.list` 覆盖），见 §3.11。

> **正文不入库，但路径必须可发现**（用户 2026-10-05 明确）：`documents.raw_path` / `documents.text_path` 是唯一入口，
> 上面三个方法构成"找到它 → 打开它 → 定位到它"。路径一律由 `paths.py` 生成并断言在 `data/` 之下；
> RPC 层只回**相对路径 + 数据根目录**，不回任意绝对路径（防越权）。
>
> **路径口径（2026-10-11 起）**：命名与放置改成人可读方案（`docs/19`）——
> `data/raw/<布局段…>/<标题>--<sha8>.<ext>`、`data/text/<布局段…>/<标题>--<sha8>.txt`；
> 布局段由 `config.yaml` 的 `library.layout` 决定（默认 `<会话>/<格式>`），支持 `session` / `format` /
> `collected` / `published`（`type` 是 `format` 的旧称），**未知段直接报错**。
> **全文路径不再由 `doc_id` 拼**（老函数 `raw_path_for` / `text_path_for` 只作历史回落，生产路径不许再调）；
> 相对路径由 `paths.py` 的 `resolve_rel` 还原成绝对路径，白名单仍是 `data/` 与 `run/`。

### 3.7 设置（`settings.*`）

设置栏把「能改的东西」收成一份白名单（`settings_io.FIELDS`），**分工照 Hermes**：

| 内容 | 落在哪 | 规则 |
|---|---|---|
| 模型 / 检索 / 预算 / 生成策略（含 `runtime.plan_by_model`） | `config.yaml` | 深合并在原文件上写回，**不动**用户自己加的键；先写 `.tmp` 再 `os.replace`（原子） |
| API Key（LLM / Tavily / Serper / Brave / Google CSE / S2 / GitHub / MinerU） | `.env` | **只写不回读**：`settings.get` 只返回 `secrets_configured` 布尔，值永不进前端 |
| 主题 / 界面缩放 / 三栏宽度 | 浏览器 `localStorage` | 纯本机界面偏好；改完立刻生效，不需要重启 |

`generation.style`（D4 风格档）：取值 `default` / `academic` / `tutor` / `concise`，
**默认档不加任何字符**，所以不改它时系统提示词与本功能上线前逐字节相同（实验臂哈希不变）。
写错的值在**设置面板就被拦下**（`Field.choices`）与**启动时 load_config 直接报错** —— 静默回默认档
等于"用户以为改了、其实没改"，这正是下面第 1 条要禁的那类失败。风格档会进 `system_prompt_hash`，
所以论文里报告结果必须写明用的哪一档（见 `docs/07`）。

三条硬约定：

1. **不认识的键直接报错**（`-32602`）。静默忽略拼错的键＝用户以为改了、其实没改。
2. **改了 `llm.chat.model` / `base_url` 会顺手摘掉 `.env` 里同名的 `LLM_MODEL` / `LLM_BASE_URL` 覆盖**
   （那两个变量优先级高于 YAML，不摘掉的话改动静默失效），并把这件事回在 `notes` 里告诉用户。
3. **可清理的只有缓存类目录**（`fetch_cache`、`run_tmp`）；`data/raw`、`data/text`、`data/notes`
   与数据库**拒绝清理** —— 那是资料本体。

改了模型设置时后端**立即重建模型客户端**，不用重启应用。

**每个密钥字段都必须能在面板里填**（有测试钉住）：只存在于后端白名单、面板上没有入口，
等于用户只能去手改 `.env`。

配对码口径（照 Hermes `gateway/pairing.py`，逐条锚点见 `docs/18 §③`）：字母表
`ABCDEFGHJKLMNPQRSTUVWXYZ23456789`（**剔掉 0/O/1/I 防混淆**）、长度 `8`、TTL `3600s`、
同平台待批 ≤3、连续错码 5 次锁 `3600s`。
**方向与 Hermes 相反**：Hermes 由机器人生成已带 openid 的码；本项目由向导先生成「不带身份」的码，
用户把码发给机器人 → `claim` 回填 openid → `verify` 批准，**openid 自动落库**，用户不必手抄。

**三条不变量有测试钉住**（`tests/rpc/test_feishu_methods.py`、`tests/state/test_feishu_pairing.py`）：
错码/过期/未 claim 都被拒且**不写白名单**；正确码写白名单并**收回临时放行**；
`feishu.status` 的 JSON 里既不出现 Secret 值、也不出现 App ID 值。

**`feishu.probe` 的非阻塞口径也有测试钉住**（`tests/rpc/test_feishu_methods.py`、`tests/fetch/test_feishu_onboard.py`）：
凭据没配 / 没出网客户端 / 传输抛异常 / 回包 `code!=0` 一律回 `{ok:false, bot_name:"unknown"}` 且**不抛**；
成功时取 `bot.app_name` 与 `bot.open_id`、报 `token_expire`，**token 值不出现在返回值里**。

**运行时拦截（`channels/feishu.py`）也有反例桩测钉住**（`tests/channels/test_feishu_stub.py`）：
默认 `pairing` 下未授权私聊**不执行任何会话**、只回配对提示；`allowlist` 下名单外**直接丢弃并记日志**；
群聊遵守 `@提及` 策略；未授权私聊的整条消息**先当配对码登记**（登记成功只回执、不跑会话）；
「临时放行」在 `feishu.pairing.verify` 成功时**收回**。渠道层取白名单状态**只经 `feishu.access`**，放行之后**只经 `feishu.pairing.remember`** 对齐真实 open_id，不读库、不出网。

### 3.9 渠道发文件（`channel.send_file`，docs/17 §3.12）

把一份文件**私聊**发给发来消息的人：生成物（知识地图 / 学习路线 / 笔记）、已入库资料、项目内路径三类。
实现 `rpc/channel_file.py`（`@method("channel.send_file")`）；**渠道层只递三个字段**（谁要 / 哪一类 / 关键词），
查库、导出、上传、发送都在主进程（`channels/` 不许 import `state` 与 `fetch`）。

| 方法 | 参数 | 返回 | 说明 |
|---|---|---|---|
| `channel.send_file` | `{platform?="feishu", open_id, kind?="artifact"\|"library"\|"path", query?="", session_key?="", domain?="feishu"}` | 见下「分支表」 | `open_id` 是发送者的私聊 id（**必填**）；`kind` 不在枚举里 → 按 `artifact` 处理，**回包的 `kind` 如实写 `artifact`**；`query` 的含义随 `kind` 变：`artifact` 时是子类型 `topic`/`route`/`note`（空 = 三类里最新那件），`library` 时是标题模糊词，`path` 时是相对/绝对路径；`session_key` 只用来把 `chat_id` 换成 `session_id`（**只读**，不为一次发文件凭空建会话）；`domain` 传 `feishu`/`lark`，未知值回退 `feishu` |

**分支表（回包字段逐字对齐实现）**：

| 分支 | 返回 |
|---|---|
| 平台不是飞书 | `{ok:false, reply:"本渠道目前只支持飞书，发文件功能还没做到别的平台。"}` |
| 缺 `open_id` | `{ok:false, reply:"发不了：这条消息里没有发送者的 open_id（无法定位私聊对象）。"}`（这两个分支**没有 `kind` 字段**，实现里就是 `{ok:false, reply}`） |
| 找到并发出 | `{ok:true, kind, file_name, message_id, reply:"已发送：<文件名>（<n> KB）"}` |
| 找不到目标 | `{ok:false, kind, reply, candidates:[...≤6]}`：`reply` 是一句话 + 「现在能发这些：」候选清单，**绝不猜一个文件发出去** |
| 发送失败（含空文件 / 超 30 MB / 权限不足 / 开关关着） | `{ok:false, kind, file_name, reply:"没发出去：<error>"}`，`error` 是**可读中文**（如权限提示），不是栈 |
| 没有数据库 | `RpcError(-32000, "没有数据库，无法解析要发哪份文件")`（唯一会抛的分支） |

**口径**：`ok:false` 一律带 `reply`（渠道层拿它原样回给用户，不在渠道层拼文案 —— 那里看不见候选清单）；
`path` 类只允许 `data/` 与 `run/` 之下（`paths.resolve_rel`），越界给明确原因；
30 MB / 非空 / `file_type` 枚举与两个后台权限见 `docs/17 §3.12`。桩测：`tests/rpc/test_channel_file.py`。

## 5. 工具契约（模型可见）

### 5.0 通用约定

- 命名：`namespace.action`，namespace ∈ `{research, source, topic, route, note, kb}`
- 每个工具 = `ToolSpec{name, description, parameters(JSON Schema), handler, toolset}`
- JSON Schema 一律 `additionalProperties: false`，参数校验失败 → `-32602`
- **返回统一包络**（这是可追溯性的根）：

```json
{
  "ok": true,
  "data": { },
  "error": null,
  "refs": {"source_ids": [], "doc_ids": [], "chunk_ids": [], "note_ids": [], "route_ids": []}
}
```

> 规则：**任何进入回答的 id 必须回填 `refs`**。回答里写了没回填的 id，等于假引用 —— 评测里算错，答辩时算失信。

- 所有工具调用落 `tool_traces`（名字、args 摘要、结果摘要、时延、成败）
- `toolset` 取值：`research`（默认开）｜ `kb`（默认关，消融开关）

**工具名的两副面孔（真机跑出来才知道的硬约束）**：

| 场景 | 形式 | 例 |
|---|---|---|
| 注册名 / 文档 / 事件 / `tool_traces` / 论文 | 点号命名空间（**规范名**，唯一真相） | `research.search` |
| 发给模型的 `tools[].function.name` 与模型回传的 `tool_calls[].name` | 点换成双下划线（**线上名**） | `research__search` |

原因：OpenAI 兼容 API（DeepSeek 实测）校验 `^[a-zA-Z0-9_-]+$`，**带点直接 400**，
整个工具层会整体不可用。转发由 `runtime/registry.py` 的 `wire_name()` / `canonical_name()` 双向映射，
调用进来时 `get_spec()` 两种名字都认；注册名禁止包含 `__`（否则映射有歧义，注册即报错）。

### 5.1 `research.search`

```
input : {query: str, sources?: ["arxiv","bing","duckduckgo","searxng",
                                "tavily","serper","brave","google_cse","auto"],
         limit?: int = 10, year_from?: int, sort?: "relevance"|"date", lang?: "zh"|"en"}
output: {items: [source_card], provider_status: [{provider, ok, n, interval_s?, error?}]}
```

**来源分三层**（`providers/settings.py` 是唯一真相）：

| 层 | 来源 | 要不要 key | 本机实测 |
|---|---|---|---|
| 学术 | `arxiv` | 免 | ✅ 可用（≥3s 限速；只索引英文） |
| 学术 | `openalex` | 免 | ✅ 可用（1.6s 返回真综述，带被引数/DOI/摘要；`robots.txt` 是 `Allow: /`） |
| 代码/教程 | `github` | 免（可选 token 提额） | ✅ 可用（0.9s 返回真仓库；未认证 Search API 10 次/分钟 → 间隔 6s） |
| 通用 | `searxng` | 免（自建实例） | 需 `search.searxng_base_url`；容器没起时 provider 会直接告诉你怎么修 |
| 通用 | `bing` / `duckduckgo` | 免（抓结果页） | ⚠️ robots 禁止搜索页 / 国内需梯子 → **默认关**，要抓得开 `search.allow_searchpage_scraping` |
| 商用 | `tavily` / `serper` / `brave` | 要（`.env`） | 未配 key 时如实报 `missing_api_key` |
| 商用 | `google_cse` | 要（`GOOGLE_CSE_KEY` + `search.google_cse_cx`） | 每天 100 次免费额度 |
| 学术 | `semantic_scholar` | 要（`S2_API_KEY`） | 无 key 恒 **429**（真机实测）→ 按"需要 key"处理，不进 `auto` |

- `sources` 省略或写 `["auto"]` → 用 `search.providers`（默认 `auto`）：**只带现在真能用的来源**
  （arxiv + openalex + 已配实例的 searxng + 已配 key 的商用来源）；抓取类来源不会被 auto 带上，
  避免每次检索都去撞超时/被拒
- **缺 key、缺配置、被 robots 拦**都写进 `provider_status.error`（`missing_api_key` /
  `missing_config` / `blocked_by_robots` / `unknown_provider`）——
  状态码 `not_implemented` 保留但**本版已无来源会用它**（配置里允许写的名字都已实现）
  "没搜到"与"这层没配"必须能分开，否则模型会拿旧结果硬凑（真机实测过）
- 真机自检：`.venv/Scripts/python.exe scripts/check_search_sources.py --all`

`source_card`：

```json
{"source_id":"src_xxx","title":"…","url":"…","domain":"arxiv.org","authors":["…"],
 "year":2025,"venue":"NeurIPS","source_type":"arxiv","tier":1,"tier_label":"一手权威",
 "score":0.82,"snippet":"…","has_full_text":true}
```

- **必须落库后才返回 `source_id`**；同一 URL 复用既有 id（`sources.url_canonical` 唯一约束保证）
- **判重闸门（A3）**：同一会话内，查询与 `research_states.used_queries` 里任一条的
  **二字符组 Jaccard ≥ 0.6** 即判为"换词重搜"，抛 `ValueError` 拒绝执行（错误里必须带上
  "之前那条查询 + 缺口清单给的方向"，只说不行的提示等于没提示）。
  判据与 `scripts/diagnose_turns.py` **共用同一个实现**（`runtime.research_state.similarity`）——
  两处各写一份相似度迟早给出两套数字，"用同一把尺子复测改进"就无从谈起。
  **记账的写者只有一个（`runtime/loop.py`）**：工具只**读**台账判重、自己不写 ——
  两个写者会丢更新（真机抓到：工具写进去的查询被循环在轮末用内存状态整表覆盖，
  第 2 轮照样重复搜）。循环在每次**搜成功**后 `record_query` 并立即落库；
  失败（含全员失败、异常）不记，否则一次网络抖动就把这个方向锁死。
  没有 `session_id` 时不做判重（判重是会话内的概念，评测脚本直接调工具不该被拦）。

- 每个 provider 独立限速；某个 provider 失败**不阻塞**其他，只在 `provider_status` 里标红
- 网页来源统一 `source_type="web"` → 判权默认落到 tier 4；但**域名规则优先**，
  所以 bing/商用检索命中的 `nature.com`、`.edu.cn` 等仍按域名判到 tier 1–2

### 5.2 `source.fetch`

```
input : {url?: str, source_id?: str, force?: bool = false}
output: {doc_id, source_id, mime, chars, lang, bytes, ext, raw_path, text_path,
         requested_url, fetched_url, used_landing_page,
         extract_status, extract_engine, extract_detail, truncated,
         summary: {summary_id, title_zh, summary_short, points, prompt_version, degraded, guard_failed}}
```

- **这一步同时完成"取资料"与"出摘要"**（流水线见 `04-摘要提取方案.md` §4）：正文抽取 → 清洗 → 截断 → 提示词 → 模型 → 解析 → 守卫 → 落 `summaries`
- 原件落 `data/raw/<布局段…>/<标题>--<sha8>.<ext>`；**全文纯文本**落 `data/text/<布局段…>/<标题>--<sha8>.txt`（**库里只放摘要，不放正文**）
- **优先抓真文件、不抓落地页**：有明确文件入口的来源先取文件（`arxiv.org/abs/<id>` → `arxiv.org/pdf/<id>`），
  拿不到（404/被拒/超时）再回落到原 URL。抓的哪一种**如实记在** `requested_url` / `fetched_url` /
  `used_landing_page`（`true` 表示抓的是落地页）。**`sources.url` 始终是用户/检索给的那个地址**（"去原站"的入口），去重逻辑不变
- 去重顺序：`sha256` → 命中即回，不重抓（摘要已存在则一并返回，不重复调模型）
- `extract_status` ∈ `ok` | `mineru_ok` | `no_text_layer` | `mineru_failed` | `blocked` | `empty`
  | **`skipped_large`**（超过抽取阈值，只登记元数据 + 保留源地址）| **`skipped_media`**（音视频，用户明确不抽）
- **`too_large` 不是 `extract_status`，而是出网层的 `FetchError.kind`**：响应超过 `fetch.max_bytes`
  （出网层**硬上限**，默认 20MB，`fetch/http.py`）时直接**拒收**，本次抓取算失败（见 §5.2 大文件策略那条，
  以及 `docs/19` §8.3 两条阈值的分工）；「落盘后要不要抽正文」是另一条阈值 `fetch.large_file_mb`
- **`extract_detail` 记"为什么"**（如 `没有文字层（多为扫描版）→ 交给 MinerU；failed: model service is temporarily unavailable`、
  `文件 31457280 字节超过阈值 20971520 字节（20MB），未抽取正文`）。只有状态没有原因的话，论文里就是黑盒
- **大文件策略（阈值可配）**：`fetch.large_file_mb`（默认 **20**，单位 MB，`large_file_bytes = int(mb * 1_000_000)`）。
  **超过阈值不抽正文**，只登记大小 / 类型 / 源地址，标 `extract_status="skipped_large"`；
  `bytes` 字段回真实字节数。音视频与源码仓同样落 `skipped_media` / `skipped_large` 并标
  "需到原站看 / 需手动下载"（下载入口见 `archive.download`，§3.3）
- 支持抽取的格式（**全部标准库，零新增运行期依赖**）：
  - PDF → `pymupdf`（`tools/source_fetch.py` 内本地抽字），抽不出文字层再走 MinerU
  - Office 三件套 `.docx/.xlsx/.pptx` → `fetch/office.py`（zip + XML）
  - **`.epub`** → `fetch/formats.py`（zip + XHTML，按章抽字）；**`.rtf`** → 控制字剥离；
    **`.zip/.tar/.tar.gz/.tgz/.tar.bz2/.tar.xz`** → **只列目录当元数据**（不解内容）；
    `.svg/.xml/.rss/.atom` 等 XML 文本原样解码
  - 文本类 `.md/.py/.json/.csv/.yaml/.ipynb/.sql/.txt` 等**原样解码**，不过 HTML 提取器（洗了会丢缩进与代码结构）
  - 其余（含 HTML）走 `fetch/html_text.py` 抽正文
- PDF 抽取顺序：**pymupdf 本地抽取 → 抽不到文字层才走 MinerU**（`features.enable_mineru` 控制开关）；
  MinerU 优先用精准接口（配了 `MINERU_API_TOKEN`），401/额度不足自动退回免 token 的 Agent 轻量接口
- `extract_engine` ∈ `local`（pymupdf / HTML 解析 / 原样解码）| `local-office`（Office 三件套）|
  **`local-ebook`**（epub）| **`local-archive`**（压缩包目录）| `mineru` | `none`（跳过抽取）
- 扫描件或抽不出文字 → **走 MinerU 官方接口**（决议 8），失败也不阻塞：`degraded=1`，用元数据出摘要
- 全文超限（默认 6 万字符）→ 只保留前 N 字符并记 `truncated=1`，**摘要照出**（决议 9）
- 摘要用便宜档模型；正文不入库、不进 FTS（决议 5/6）

### 5.3 `source.grade`（"判断权威性 / 判断相关性"的落点）

```
input : {source_ids?: [str], urls?: [str], topic?: str,
         use_model?: bool = true, limit?: int = 20}
output: {items: [{grade_id, source_id, tier, tier_label, authority, relevance,
                  relevance_source, verdict, matched_rule, reason, signals, guard_failed}],
         skipped: [{source_id|url, reason}],
         counts: {核心: n, 相关: n, 外围: n, 排除: n},
         topic, relevance_engine}
```

- `verdict` ∈ `核心` | `相关` | `外围` | `排除`；阈值写在 `grading/relevance.py:verdict_for`（docs/02 §3.1）
- **authority 由规则表 `source_tier_rules` 判定，不由模型拍脑袋** —— 可解释、可复现，论文里能算一致率
- **relevance 才交给模型**（给了 `topic` 且 `use_model=true` 时），且必须给 `signals` 与 `reason`；解析失败**退回本地确定性打分**并标 `guard_failed=1`
- 没给 `topic` 时只判权威性，`relevance=null`、`relevance_source="none"`
- **三个参数都不给**时，顺手判最近入库、`tier` 还为空的前 20 条（`limit` 可调）
- 结果写入 `source_grades`（**只追加**）并把 `tier/authority` 反范式化回 `sources`

### 5.4 `topic.build_map`

```
input : {topic: str, source_ids?: [str], max_nodes?: int = 20, use_model?: bool = true}
output: {topic_id, topic, mode, source_count,
         nodes: [{nid, label, kind, source_ids, dropped_source_ids}],
         edges: [{src, dst, rel}],
         stats: {nodes, edges, ungrounded_nodes, dropped_edges, ungrounded_labels}}
```

- `kind` ∈ `concept` | `method` | `dataset` | `tool` | `venue` | `source`
- `rel` ∈ `prerequisite` | `variant` | `uses` | `evaluates`（模型给了别的词就落 `uses`）
- **候选来源三级取**：给了 `source_ids` 就用它 → 否则取该主题下判权为「核心/相关」的来源 → 否则取最近入库的 25 条
- **每个 node 至少挂 1 个真实 source_id**；挂不上的节点保留但 `label` 前缀 `[无出处]` 并计入 `stats.ungrounded_nodes`，白名单外的 id 进 `dropped_source_ids`
- 端点不存在的边一律丢弃（计入 `stats.dropped_edges`）
- `mode` ∈ `model`（模型梳理）| `flat`（没有模型或输出不可解析时的**兜底扁平图**：每个来源一个节点、无边）
- 结果落 `topic_maps`（`graph_json`），`topic.get` 可取回

### 5.5 `route.plan`

```
input : {topic, level?: "入门"|"进阶"|"研究", weeks?: int = 4, weekly_hours?: int = 6,
         source_ids?: [str], use_model?: bool = true}
output: {route_id, topic, level, mode,
         weeks: [{idx, goal, checkpoint, items: [{kind, title, source_id?, why, est_minutes}]}],
         stats: {weeks, items, resource_items, grounded_resource_items, exercise_items,
                 ungrounded_items, ungrounded_titles, dropped_duplicates, sources_used}}
```

- `kind` ∈ `paper` | `doc` | `video` | `code` | `exercise`（模型给别的词就落 `doc`）
- **条目分两类，出处要求不同**（口径见 docs/05 §3.2）：
  - **资料类**（`paper`/`doc`/`video`/`code`）声称"这里有一份资料" → 必须挂库里已有的 `source_id`，
    否则 `source_id = null` 并计入 `ungrounded_items`（`why` 里要说明是补充项）
  - **行动类**（`exercise`）是"你要动手做的事/产出" → 来源列写 `-`，**不计入** `ungrounded_items`
    （练习本来就没有出处；把它算成"无出处"既误报，又会反向逼模型硬挂一个来源 = 真幻觉）
- 同一来源在一条路线里只出现一次（重复条目丢弃并计入 `dropped_duplicates`）
- `est_minutes` 卡在 10–600；`weeks` 卡在 1–24
- `mode` ∈ `model` | `skeleton`（没模型时的兜底：按 tier 与年份把已有资料均匀排进各周，不做内容推断）
- 结果落 `learning_routes`（`plan_json`）；`route.export` 导出成带 `why` 与来源的 Markdown

### 5.6 `note.save`

```
input : {kind: "summary"|"note"|"card", title?: str, content?: str,

output: {note_id, kind, title, path, card_count, cards}
```

- `kind=card` 走**抽背卡**：批量给 `cards`，或给一对 `title`（问题）/`content`（答案）；每张必须是正反面齐全

### 5.9 `route.revise`（增量修改已有路线）

```
input : {route_id: str, instruction: str}
output: {route_id, version, summary, changes: [{target, before, after}], weeks, refs}
```

- **只输出补丁**：模型被要求只回 `{"summary", "ops"}`（见 `prompts/revise-route.md`），
  **不重吐整条路线** —— 没被点到的部分逐字节不变（挂好的出处不会丢）。
  操作白名单：`set_plan_field` / `set_week_field` / `set_item_field` / `add_item` / `remove_item` /
  `add_week` / `remove_week`；周号与条目号**都是 1 起**；一次最多 50 处。
- **不合法就整条拒绝**（`PatchError` → `-32602`）：操作名/字段名/周号/类型写错、`source_id` 不在
  当前候选里、把资料类条目的 `source_id` 改成空 —— 一律拒绝，**不写半截**。
- **先归档再升版**：`artifact_versions(kind='route', artifact_id, version=N)` 存改动前的正文，
  主表 `learning_routes.version` 加一、`updated_at` 更新。改错了能取回旧版（`route.versions`）。
- 与 `route.plan` 的分工：新方向 `route.plan`；改已有路线用 `route.revise`。
  它把"改一处"的代价从"重生成整条"降到一次短调用，代价是**声明多约 504 字符/次调用**（≈ +11%）。

| 7 | 纯文本是否另存 | **另存** `data/text/<doc_id>.txt` |
| 8 | 扫描版 PDF | **不自己造轮子**，走 **MinerU 官方 API**（免登录轻量接口优先，大文件用需 token 的精准接口），见 `04-摘要提取方案.md` §7 |
| 9 | 超长文档 | **只存原件，摘要照出**，`documents.truncated=1` 标记 |

**仍未定（不阻塞 M1）**：`data/text/` 单文件上限、MinerU 配额记账方式、摘要人工修订入口 —— 见 `02 §9`。


### 5.10 `research.board`（B2 证据表 / B4 时间线 / B7 看板）

```
input : {session_id: str}
output: {goal, questions:[{index,text,status}], gaps:[{kind,detail,suggest}],
         queries:[str], sources:[source_card],
         evidence:{mode:"support_checks"|"ledger"|"empty", rows:[...],
                   strength_counts:{}, weak_count:int, total:int},
         timeline:{groups:[{year:int|null, items:[source_card]}], known_years:[],
                   missing_recent_years:[], internal_gap_labels:[], undated:int},
         artifacts:{maps:[], routes:[], notes:[]},
         counts:{sources, with_summary, without_text, queries, open_questions}}
```

**为什么合成一个 RPC**：这三节是"用户打开右栏"的同一个动作，拆三个方法会让前端连打三枪、
还可能出现"证据表是新的、时间线是旧的"这种不一致。

三条口径（每一条都对应一个曾经的错法）：

| 口径 | 规则 | 为什么 |
|---|---|---|
| 证据强度**确定性判定** | `summary`（引用来源里有摘要）+ `supported/partial` → 强；`title` 或 `unsupported/unknown` → 弱 | 让模型打分是不确定的东西，而这张表存在的意义恰恰是**可复算** |
| 证据来源**跨会话解析** | 核查引用的来源按 id 全库查，**不限本会话** | 只在会话内查时，真机 23 行里有 15 行显示"没有可解析的来源"（那些来源是生成产物那一轮带出来的） |
| 缺口**取不到就不编** | 年份未知单列一桶、不进任何"缺哪年"判断；缺口分"最新之后空档"与"区间内部空档"两类 | 与 `eval/metrics.py` 同口径；把没年份的当成老资料会得出错误结论 |

`mode` 必须回给前端：`support_checks`＝来自引用核查；`ledger`＝本会话还没核查过，
按「子问题 × 已收集来源」聚合；`empty`＝什么都没有。**不许让 `ledger` 假装成核查结论。**

只读：不写库、不调模型、不产生任何费用（界面上也这么写，用户不该猜数字是怎么来的）。


### 5.11 间隔重复（`note.due` / `note.review` 的排期字段）

`note.review` 除了记账，还会按 **SM-2** 算出下一次复习时间并回显（`interval_days`、`due_at`、
`interval_label` 如"6 天后"、`streak`、`lapses`）。`note.due` 给出**今天该练的队列**：
新卡（从没排过）+ 到期卡（`due_at <= now`）。

| 项 | 口径 |
|---|---|
| 三档 → q 值 | `good`=5 / `fuzzy`=3 / `bad`=1；**q<3 视为没记住**（`fuzzy` 恰好落在"通过"上，这是有意的） |
| EF 更新 | 每次评都更新：`EF' = EF + (0.1 - (5-q)*(0.08 + (5-q)*0.02))`，下限 **1.3** |
| 答对后的间隔 | 第 1 次成功 1 天、第 2 次 6 天、之后 `round(上次 × EF')` |
| 没答对 | 连续成功清零、间隔回到 1 天、`lapses+1`（**不沿用旧间隔** —— 沿用会越攒越长，最后干脆想不起来） |
| `due_at` 为空 | **算到期**。宁可多练一次，也不让一张没有排期的卡永远沉在库里（老数据、导入的卡走这条） |
| `limit` | **只截断返回条数，不改变计数** —— 界面上"今天该练 N 张"不能随 limit 变（真踩过） |

算法出处：SuperMemo SM-2（<https://super-memory.com/english/ol/sm2.htm>，`docs/14 §2` 已登记）。
**为什么不直接上 FSRS**：它要用大量复习记录拟合参数，本机没有那种数据量，硬上等于编参数。

实现：纯算法在 `learning/srs.py`（不读钟，`now` 一律注入，测试才能钉住口径）；
落库与队列在 `state/learning.py`。**不花 token** —— 排期是确定性结果，问模型等于把可复算的
东西换成不可复算的东西。界面：抽背卡页显示"今天该练 N 张（新卡 M）"+「只练到期的」；
每评完一张回显"下次复习：X 天后"。


### 5.12 学习者画像（`learner.profile`）

跨会话汇总"这个人学到哪了"，每轮以两三行注入系统消息（`learner_profile.render_profile_note`）。
**只读、零模型调用** —— 掌握度是按确定性规则从 `card_reviews` 的排期算出来的，
让模型"感觉"用户水平既不可复算、也会随措辞漂移。

| 项 | 口径 |
|---|---|
| 熟 | `streak >= 2` 或 `interval_days >= 6`（连着答对过，或已排到一周后） |
| 复习中 | `streak == 1`；**以及"评过但还没有排期"的老数据**（B6 之前的行） |
| 薄弱 | `lapses >= 1` 或最近评价是 `bad` |
| 未练 | 没有复习记录 |
| 掌握度 | `熟 / 有记录的卡` —— **未练的卡不进分母**（把没练过的算成不会，画像必然难看，用户会以为系统在打击他；与 `card_stats.recall_rate` 同口径） |
| 主题维度 | 只取产物的 `topic`（路线/地图）—— 卡片没有 topic 字段，硬凑主题就是编 |
| 卡片维度 | 按**卡片组标题**单列（卡片不挂主题），界面上与主题分开显示 |
| 活跃度 | 近 14 天复习次数与"有复习的天数" |

注入的那两行只放能改变行为的信息（主题数/掌握度/近 14 天活跃/最薄的三块/已做过的主题），
**没有原料时整段为空**（不注入空话）。生成一句自然语言的"画像描述"要模型调用，
必须用户点按钮才发生，属后续项；当前版本不含。


### 5.13 跨会话记忆（`memory.*`）

关于**用户**的稳定事实（身份/背景、长期偏好、持续目标、硬约束），落 `user_facts` 表，
每轮以几行注入（`memory.render_facts_note`）。与画像的分工：画像是**算出来的**
（掌握度/主题，零模型调用），记忆是**理解出来的**（需要一次模型调用）。

| 项 | 口径 |
|---|---|
| 抽什么 | 只抽**稳定事实**；一次性任务细节、能随时重读的百科信息、任何推测，一律不抽。提示词 `prompts/memory-extract.md` 里正反两面都列了 |
| 双账（`target`） | 每条带 `target ∈ {"user","memory"}`（**代码层校验**，`runtime.memory.TARGETS`；迁移 `0016` 加列 `target TEXT NOT NULL DEFAULT 'user'`）：`user`=关于用户（身份/背景/长期偏好/目标），`memory`=agent 自己的工作笔记（环境/约定/工具坑）。注入时**分两段**（【关于这个用户的长期记忆】/【我自己的工作笔记】），两段**合占 600 字符预算**（总量与本功能上线前一致，不增每轮 token） |
| 抽几次 | **每会话最多一次**，且要有"值得记"的迹象（用户说过≥2 轮，或这次会话产出了产物）；由 `runtime.memory.should_extract` 判定 |
| 判重 | 本地只兜**近似文本**（包含关系，短句≥6 字；或二字符组相似度≥0.75）；**语义判重交给模型** —— 抽取时把已有记忆一起塞进提示词。理由：能抓乱序改写的"字符集重合度"会把"偏好中文"和"不喜欢中文"判成同一条，误合并比漏合并危险 |
| 注入预算 | 600 字符上限（**两本账合占，总量不变**），超了只发**最新的几条**（老的留在库里，不删），并**追加一行合并引导**（≤40 字）指向设置面板 / `memory.remove` —— 让用户知道该整理了 |
| 合并引导（写入侧） | 抽取入库会**顶破**注入预算时，`extract_facts` **不静默丢旧**：回 `current_entries` + `reason`，提示"请合并后重发"（照 Hermes 满载拒绝 add 的做法） |
| 冲突 | 注入文本里明写"**与用户当前说法冲突时以当前说法为准**" —— 记忆是背景，不是命令 |
| 出口 | 必须能看、能改、能删（`memory.list/update/remove` + 看板里的列表与删除按钮）。**没有出口的自动记忆＝污染源**，一次误抽会污染之后所有轮次 |
| 开销 | 抽取是一次小调用，按 `purpose="memory"` 记进 `usage_records`（**不许变成看不见的暗开销**）；`generation.memory_by_model=false` 可关，关掉仍能手动整理 |


### 5.14 历史压缩（三层，D3）

| 层 | 做什么 | 花不花钱 |
|---|---|---|
| 工具结果瘦身（`context_budget`） | 同来源只回锚点、snippet 截断、旧工具结果折叠成一行 | 不花 |
| 保头保尾裁剪（`_fit_history`） | 超 `runtime.max_history_chars` 时裁掉中段 | 不花 |
| **模型摘要式压缩（`runtime/compaction.py`）** | 把未被提要覆盖的那段压成「目标／已确认结论（带来源 id）／未决问题／用户偏好」 | **每段一次小调用** |

口径：

1. **触发**：未被提要覆盖的那段超过 `runtime.compact_after_chars`（默认 4000 字符）才压，
   且至少 1200 字符（更短的话规则式裁剪就够了）。开关 `generation.compact_by_model`（默认开）。
2. **同一段只压一次**：提要与「已覆盖到第几条消息」一起存进研究台账（`history_summary` /
   `history_summary_count`），下次只压**新增**部分，并把上一版提要作为「续写」起点喂进去。
   这条是成本底线 —— 否则「省 token」的功能会变成每轮多花一次调用。
3. **位置固定**：提要插在 system 提示词**之后、历史之前**。位置固定，服务端缓存才能在
   两次压缩之间稳定命中；每次压缩只让缓存冷一次，而不是每轮都冷。
4. **失败退回规则式裁剪**：模型调用失败、或返回空 → 不写提要，`_fit_history` 照旧工作，
   本轮不受影响。压缩是省钱手段，不能因为它把一轮弄挂。
5. **开销如实记账**：`usage_records.purpose="compact"`，界面「本会话累计」里看得到。
6. **提要里只认带来源 id 的结论**：提示词要求「只压缩、不新增」，注入文本也写明
   「只信这里列出的、带来源 id 的结论」—— 压缩最危险的是把没证据的转述固化下来。

### 5.16 `research.overview`（跨会话看板汇总）

个人中心「研究看板汇总」用它。**只读、零模型调用**，数字全部来自库：

- 只汇总"有台账或至少带出过一个来源"的会话 —— 纯聊天会话不进列表（否则一屏空行）；
- 子问题覆盖只数 `status == "covered"` 的，模型没回填就保持 open（不猜）；
- `without_summary` = 来源里还没有摘要的条数（提示"这份还没读透"，不是错误）；
- `totals.coverage_rate` 在没有子问题时是 **null** 而不是 0（0 会被读成"一个都没覆盖"）。

### 5.17 顺序子任务（子 Agent P1，`runtime/subtasks.py`）

复刻 Hermes「orchestrator → leaf 委派」的**隔离语义**，但拍扁成**同进程内的顺序小循环**：
每个子任务是一个**独立的 mini-loop**（自建 messages + 自己的工具子集与小预算），
只把**最终文本**带回来（父只见 summary）。**不做并发、不开进程、不引依赖**。

| 项 | 口径 |
|---|---|
| 入口 | `run_subtask(ctx, goal, *, toolset="research", max_tool_calls=2, emit=None, seq=0) -> SubTaskResult`；`run_subtasks(ctx, goals, *, per_task_budget=2, total_budget=None, emit=None) -> list[SubTaskResult]` |
| 子任务来源 | `open_goals(state)`：研究台账里 `status != "covered"` 的子问题（接现有「缺口驱动续搜」） |
| **默认关** | `runtime.subtask_enabled`（**默认 false**）。关着时 `run_subtasks` 直接回空表：不触发、不记账、不发事件 |
| **总额度池** | `total_budget`（**工具调用数**）。不传＝主轮预算的 1/2；**传入值也被夹到 1/2 上限**（子任务不该吃掉主 loop 一半以上）。池子耗尽后，剩余子任务标 `stop_reason="budget"`（不跑、不发事件） |
| 隔离 | **不往 `messages` 表写任何东西**；用**独立的系统提示词** `SUBTASK_SYSTEM_PROMPT`，不碰 `runtime/prompts.py` → **`system_prompt_hash` 不变** |
| 落库/可观测 | 工具调用落 `tool_traces`，`tool_name` 前缀 **`subtask:`**（与主循环的调用分得开，论文里能单独统计）；`SubTaskResult.{goal, text, refs, tool_calls, usage}` |
| 记账 | 每次模型调用按 `usage_records.purpose="subtask"`（新 purpose 值）如实记账，`session.usage` 的 `by_purpose` 里看得到 |
| 事件 | `chat.subtask_start` / `chat.subtask_done`（**不动 `chat.delta`**）；子任务 `stop_reason` ∈ `completed` / `tool_limit` / `error` / `empty` / `budget` |
| 失败隔离 | 任一子任务异常只影响它自己（该条 `stop_reason="error"`），其余照跑 |

**为什么不照抄 Hermes 的 `delegate_task`**（依据 `docs/16 §3.1/§3.2`）：它是为"上下文爆炸 + 多独立工作流"
设计的真·子 agent（新会话、阻塞工具黑名单、独立预算、并发 10 路）；本项目单机、成本敏感，
Anthropic 自述多智能体 token 约 10–15×。所以这里**只搬隔离语义**：同进程、顺序、一个总额度池。

> **额度口径的演进（§5.18 起）**：P1 的 `total_budget` 是"不传即取主轮预算的 1/2"的**独立池**。
> 模型可见的委派入口 `research.delegate`（§5.18）改为**与主循环共用同一本账**：子任务实际消耗的
> 工具调用数从本轮主循环的剩余预算里扣（见 `runtime/toolctx.py:TurnBudget`）。

### 5.18 `research.delegate`（把独立子问题交给子任务，模型可见的委派入口）

把 §5.17 的顺序子任务**做成一个模型能主动调用的工具** —— 让模型自己判断"这几个调研子问题彼此独立、
可以分别探下去"，而不是靠提示词硬编流程。

```
input : {goals: [str]}          # 一次 1–3 个子问题；上限硬卡（>3 直接 ok=false）
output: {items: [{goal, text, stop_reason, tool_calls}], counts: {requested, ran, failed},
         consumed_tool_calls: int}
```

- **注册名 `research.delegate`**（规范名，唯一真相），线上名 **`research__delegate`**；`toolset=research`。
  schema：`{type:"object", properties:{goals:{type:"array", items:{type:"string"}, minItems:1,
  maxItems:3}}, required:["goals"], additionalProperties:false}`。
- 行为：把 `goals` 逐个交给 `run_subtasks`（同进程、顺序、每个子问题一个隔离 mini-loop），
  每个只回**结论正文**（父只见 summary）。子问题要写成**独立、可单独回答**的短句。
- **一次最多 3 个**：schema `maxItems: 3` + handler 硬校验（schema 不一定被模型遵守），超了回 `ok=false`。
- **额度同一本账（本节的硬口径）**：本轮主循环持有 `TurnBudget(total=max_tool_calls_per_turn)`，
  主循环每执行一次工具 `spend(1)`；委派把子任务实际消耗的 `sum(len(result.tool_calls))` **spend 回同一个
  `TurnBudget`**。委派可用的池子 = `min(P1 上限, 主账剩余)`（P1 上限 = `max_tool_calls_per_turn` 的 1/2）；
  主账剩余为 0 时**直接拒**（`ok=false` + "额度不足"），不绕过去。主循环的**剩余预算因此变少**：
  委派花掉的额度会占用后续主循环的工具调用次数（同一本账的直接后果）。
- **四种失败一律 `ok=false` + 可读原因，绝不把异常抛回主循环**（照 `research.search` 的失败回包约定）：

  | 情形 | `error` 前缀 | 触发条件 |
  |---|---|---|
  | 开关关 | `子任务总开关未打开：…` | `runtime.subtask_enabled=false`（**复用 P1 开关，不新增开关**） |
  | 额度尽/不足 | `额度不足：…` | 主账剩余 ≤ 0（子任务消耗要从主预算里扣） |
  | 参数非法 | `参数非法：…` | `goals` 非数组 / 空 / 超过 3 个 |
  | 内部异常 | `内部异常：<类型>: <消息>` | `run_subtasks` 之外的意外（try/except 兜住，不外抛） |

- **失败隔离**：单个子任务失败只影响它自己（该条 `stop_reason="error"/"budget"/"empty"`），其余照跑；
  仅当**全部**子任务都没产出文本时整体才回 `ok=false`。
- **落库/可观测**：子任务的工具调用仍落 `tool_traces`（前缀 `subtask:`），模型调用记账 `purpose="subtask"`；
  委派本身作为一次普通工具调用落 `tool_traces`（`research.delegate`），并触发
  `chat.subtask_start` / `chat.subtask_done`（**不动 `chat.delta`**）。
- **提示词代价（必读）**：为了让模型知道这个工具的存在与调用纪律，`runtime/prompts.py` 新增
  「委派规矩」一段（`DELEGATE_RULE`）→ **`system_prompt_hash` 随之改变**。
  既然 prompt.py 变了，第 5 章（`docs/05`/`docs/06`）的数字与哈希引用都要按新提示词**重跑**（本次不重跑）。
