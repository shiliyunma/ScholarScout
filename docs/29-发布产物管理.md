# 29 发布产物管理（版本 / 归档 / 怎么找旧版本）

> 建立 2026-10-26 ｜ 触发原因：v0.1.0 发完之后，包留在仓库根目录、`pyproject.toml` 还写着
> 旧版本号，而 v0.1.0 的包已经**丢了**（只剩 `RELEASE_NOTES-v0.1.0.md` 里那串 SHA256）。

这份文档回答四个问题：**产物放哪、版本号从哪来、怎么一键发版、旧版本在哪找**。

---

## 1. 结论先看

| 问题 | 答案 |
|---|---|
| 发布包放在哪 | 本机 `releases/v<版本>/`（**不进 git**，见 `.gitignore` 的 `*.zip` 与 `/releases/`） |
| 历史版本在哪找 | **GitHub Releases**：<https://github.com/shiliyunma/ScholarScout/releases> |
| 版本号写在哪 | **只有 `pyproject.toml` 的 `[project].version` 一处** |
| 发一版要几条命令 | 一条：`python scripts/release.py` |
| 怎么确认发出去的 exe 是新版本 | `scripts/release.py` 会跑一次 `ScholarScout.exe --version`，不含当前版本号就直接失败 |

---

## 2. 产物布局（本机）

```
releases/
  v0.1.1/
    ScholarScout-Portable-v0.1.1.zip   产物本体（约 38 MB，673 个条目）
    SHA256SUMS                         一行：<sha256>  <文件名>（`sha256sum -c` 直接可用）
    RELEASE_NOTES.md                   这一版发什么（「本版变更」正文取自 CHANGELOG.md）
    MANIFEST.json                      机器可读身份：version/commit/built_at/bytes/sha256/exe_bytes/skill_count
  v0.1.0/
    MISSING.md                         本地副本已丢失 —— 如实写缺失，**不伪造哈希与体积**
```

`releases/` 整目录在 `.gitignore` 里：zip 动辄几十 MB，**产物不进 git**，仓库里只留
"怎么打、打过什么"的说明与台账（本文 §5）。对外分发一律走 GitHub Releases。

为什么不再把 zip 放在仓库根目录：v0.1.1 的包就曾经躺在根目录、`git status` 里永远多两行
未跟踪文件 —— 既容易被 `git add -A` 顺手带进历史（38 MB 进 git，历史再也删不掉），
又没有归处（下一版一覆盖，上一版的哈希就找不回来了，v0.1.0 就是这么丢的）。

---

## 3. 版本号：一个事实源

`pyproject.toml` 的 `[project].version` 是唯一手写的地方。其余全是它的下游：

| 读取点 | 怎么拿到 | 说明 |
|---|---|---|
| `scholarscout.__version__` | `importlib.metadata` → `pyproject.toml` → `_VERSION` | 装出来的包读元数据；源码树向上找 `pyproject.toml`；冻结包读 exe 旁边的 `_VERSION` |
| exe 旁边的 `_VERSION` | `scripts/build_bundle.py` 打包时从 `pyproject` 写出 | 打包版 `--version` 靠它，**不需要在代码里再抄一遍版本号** |
| 界面「关于」/ `chat.status` | 同 `__version__` | `desktop/bridge.py`、`rpc/research.py` 只读这一个值 |
| `scripts/release.py` | 读 `pyproject.toml` | **不接受命令行传版本**——传了就又多一处事实源 |

三处都读不到时 `__version__` 退到 `0.0.0+unknown`（显眼，不会被当真版本）。
`tests/test_version_alignment.py` 钉住「`pyproject` 与 `__version__` 必须相等」这道闸。

> v0.1.1 修的就是这个：`pyproject` 当时写 `0.1.0`、包名却叫 v0.1.1，
> 打包版 `--version` 也报 `0.1.0` —— 用户报 bug 给的版本号是错的，而界面上完全看不出来。

## 4. 一键发版：`scripts/release.py`

```bash
cd "D:/AI+教育毕设毕设/ScholarScout"
python scripts/release.py                # 全流程（PyInstaller 构建约 1-3 分钟）
python scripts/release.py --skip-build   # 复用已有构建目录（只重打 zip 与哈希）
python scripts/release.py --force        # 该版本目录已有产物时覆盖重打（旧 SHA256 即作废）
```

**构建永远发生在空目录里**：默认构建目录是 `build/release/v<版本>/bundle/`，每次
先整个删掉再建（`build_bundle.py --clean`）。所以 zip 的来源目录里**不可能**有上一轮
运行留下的 `run/`、`data/`、`.env`、`config.yaml`、`*.db`、`*.log` —— 这是结构保证，
不是"发版前记得手工删一遍"。项目根的 `ScholarScout-Portable/` 是你的日常产物目录，
发版**不碰**它（里面可能有你跑过留下的资料）。

它按顺序做七步，**任一步失败就整体失败**（不"打个警告继续走"）：

| 步 | 做什么 | 失败条件 |
|---|---|---|
| 1 | 读 `pyproject.toml` 的版本，定位 `releases/v<版本>/` | 版本不是三段数字；同名 zip 已存在且没给 `--force` |
| 2 | 调 `scripts/build_bundle.py` 构建自包含包（PyInstaller onedir） | 构建非 0 退出 |
| 3 | 自检产物：无 `.env` / `config.yaml` / `*.db` / `*.log`，无 `data/` 与 `run/` | 扫到任一 |
| 4 | 自检产物：`skills/` 的 `SKILL.md` 篇数 > 0；跑 `ScholarScout.exe --version` | 版本号与 `pyproject` 不一致 |
| 5 | 打 zip（标准库 `zipfile`，本机没有 `zip` 命令），顶层套 `ScholarScout-Portable-v<版本>/` | — |
| 6 | 算 SHA256 → `SHA256SUMS`；「本版变更」取 `CHANGELOG.md` 的 `## [<版本>]` 一节 | CHANGELOG 缺本节或正文为空 |
| 7 | 写 `RELEASE_NOTES.md` + `MANIFEST.json`（含 `git rev-parse HEAD` 与构建时间） | — |

产物 zip 顶层**套一层目录**（v0.1.0 的包是平铺的 673 个条目，解压会把 `_internal/`、
`skills/` 撒进用户当前目录）。解压后是 `ScholarScout-Portable-v0.1.1/ScholarScout.exe`。

打完脚本会打印 zip 的 SHA256 与 commit。**接下来两步是手工的**（脚本不替你按发布按钮）：

1. 把 zip 传到 GitHub Releases，tag 用 `v<版本>`，正文贴 `RELEASE_NOTES.md`；
2. 在下面 §5 的台账里补一行（版本 / 日期 / commit / SHA256 / 体积）。

## 5. 发版台账

对账用：每个版本的产物是哪次提交、什么时候打出来的、哈希多少。**哈希以本表为准**，
改了产物（重打、换打包脚本）就更新这一行，旧值注明作废。

| 版本 | 日期 | commit | zip 字节 | SHA256 | 说明 |
|---|---|---|---|---|---|
| v0.1.0 | 2026-10-26 | — | 39,883,274 | `50d15029ac4add4706ded53685cf92bd6059a9e5db870577dcbbc94d5a0fc4f1` | 首个公开版本；**本地副本已丢失**，哈希取自 `RELEASE_NOTES-v0.1.0.md`，包只在 GitHub Releases |
| v0.1.1 | 2026-10-26 | — | — | — | 发布工程规范修正；见 `releases/v0.1.1/MANIFEST.json` |

> 台账里"commit"一列要求填**打包时**的 `HEAD`（`MANIFEST.json` 的 `commit` 字段就是它）。
> 如果打包后又改了代码再提交，这一版的产物与那个 commit 就不再是一一对应的 —— 要么重新打包，
> 要么在说明里写清"产物基于 <commit>，仓库在其后另有提交"。

---

## 6. 旧版本在哪找

1. **GitHub Releases**（唯一权威）：<https://github.com/shiliyunma/ScholarScout/releases>
   —— 每个 tag 挂着 zip 与 `SHA256SUMS`，v0.1.0 只有那边有。
2. **本机**：只有当前这一版的 `releases/v<版本>/`；换机器或清盘就没了，所以别把它当归档。
3. **对账**：§5 台账。哈希相同即为同一份产物；不同就是重打过，以台账最新行为准。

下载后先校验再解压 —— 值不一致说明下载不完整或被篡改：

```powershell
Get-FileHash .\ScholarScout-Portable-v0.1.1.zip -Algorithm SHA256   # Windows
```

```bash
sha256sum -c SHA256SUMS   # macOS / Linux（zip 与 SHA256SUMS 放同一目录）
```
