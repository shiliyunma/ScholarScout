### 1.2 加载方式（谁扫描、谁 import、谁注册）

链路是**目录扫描 → 按路径 import `__init__.py` → 模块调用 `register()` → 进平台注册表**：

1. **发现**：`gateway/config.py:222-234` 的 `_scan_bundled_plugin_platforms()` 扫 `plugins/platforms/*/`，
   条件是「子目录有 `__init__.py` **且** 有 `plugin.yaml`（或 `plugin.yml`）」（`config.py:230-231`）。
2. **装载器**：`plugins/plugin_loader.py` 负责「把 `plugins/<kind>/<name>/` 当包 import」：
   - `iter_plugin_dirs()`（`plugin_loader.py:38-43`）：**只收有 `__init__.py` 的子目录**，并跳过 `_`/`.` 开头的名字；
   - `load_plugin_module()`（`plugin_loader.py:82-120`）：先按路径建父包、再建兄弟子模块、最后 exec `__init__.py`（**顺序**是为了让相对 import 能解析）。
3. **入口**：`plugins/platforms/feishu/__init__.py:1` 只有一行 —— `from .adapter import register`
   （`:3` 导出 `__all__ = ["register"]`）。**即插件的入口函数就是 `adapter.register`。**
4. **注册**：`adapter.py:4296-4298`
   ```python
   def register(ctx) -> None:
       """Plugin entry point — called by the Hermes plugin system."""
       ctx.register_platform(
           name="feishu", label="Feishu / Lark", adapter_factory=FeishuAdapter,
           check_fn=feishu_deps_present, ensure_deps_fn=check_feishu_requirements,
           is_connected=_is_connected, validate_config=_is_connected,
           required_env=["FEISHU_APP_ID", "FEISHU_APP_SECRET"], ...
   ```
   `register_platform` 落到平台注册表的 `PlatformEntry`（`gateway/platform_registry.py:41-99` 定义该 dataclass；
   注册表本体 `PlatformRegistry` 在 `platform_registry.py:102`；懒加载 `register_deferred` 在 `:156`）。
   Gateway 取用时走 `create_adapter()`（`platform_registry.py:349`）。
5. **配置桥**：飞书设置 → 环境变量的桥接在插件的 `apply_yaml_config_fn` 钩子里（`config.py:766-767` 的注释指向 `plugins/platforms/feishu/adapter.py`）。

> **一句话**：Hermes 的飞书渠道 = `plugins/platforms/feishu/` 下的一个目录插件；`__init__.py` 把 `adapter.register` 暴露成入口，
> 装载器按目录把它 import 进来后调用 `register()` → `ctx.register_platform(...)` 进注册表，Gateway 再 `create_adapter("feishu", cfg)`。
> **证据行**：`plugins/platforms/feishu/__init__.py:1`、`adapter.py:4296-4298`、`gateway/platform_registry.py:41 / :102 / :349`、`gateway/config.py:222-234`。

### 1.3 为什么会有「webhook」这条路；它和 websocket 的分工

- **默认走 websocket**：`adapter.py:1311` 的 `connection_mode` 默认值是 `"websocket"`（`FEISHU_CONNECTION_MODE` 可改）。
  websocket 由本机 **主动外连** 飞书服务器（`adapter.py:3694-3718` 用官方 `FeishuWSClient`），**不需要公网可达地址**。
- **webhook 是可选模式**：只有显式设成 `connection_mode: webhook` 才**绑定本地端口、等飞书 POST 事件进来**
  （`gateway/config.py:243-248`：`PORT_BINDING_PLATFORM_VALUES` 含 `"feishu"`，但 `PORT_BINDING_CONDITIONAL_MODES = {"feishu": "webhook"}`
  表示**仅 webhook 模式**才 bind；`platform_binds_port()` 在 `config.py:256-261` 落实这条判断）。这就**必须有一个飞书服务器能访问到的回调地址**。
- **结论**：我们要拍扁时，**webhook 路线的唯一代价就是「公网可达地址」**；若只想先把链路跑通，Hermes 侧的 websocket 模式零公网要求。

### 1.4 webhook 模式需要哪些凭据与权限

- **凭据**：`FEISHU_APP_ID` + `FEISHU_APP_SECRET`（必填，`plugin.yaml:13-23`）；webhook 模式还需
  **`FEISHU_VERIFICATION_TOKEN` 或 `FEISHU_ENCRYPT_KEY` 至少一个**——否则 `connect()` 直接报错返回 False（`adapter.py:1417-1419`）。
- **权限/订阅**：飞书后台要给应用**订阅事件**（如 `im.message.receive_v1` 等；适配器侧的事件处理表见 `adapter.py:2749-2757`）。
  具体在飞书开发者后台点哪些权限项 **unknown**（本机没有可用凭据进后台核对，不臆造）。
- **两个安全层**（拍扁时要照抄）：
  1. **verification token**：比对 body/header 里的 `token`（`adapter.py:2708-2717`，`hmac.compare_digest`）；
  2. **签名**：`x-lark-signature == sha256(timestamp + nonce + encrypt_key + body)`（`adapter.py:2759-2771`，同样 `compare_digest`）；
  另外 `type=url_verification` 的挑战要在**通过 token 校验之后**才回 `challenge`（`adapter.py:2719-2722`，防未授权者用来证明自己控制了端点）。

## ② 拿到自建应用后，在 **Hermes 里启用** 的逐步清单

> 前置：已在飞书开放平台创建**自建应用**并拿到 `app_id` / `app_secret`。

1. **装依赖**：插件的 `install_hint` 就是 `Run \`hermes setup\` to install Feishu support.`（`adapter.py:4303`），
   `setup_fn=interactive_setup`（`adapter.py:4304`）。即走一次 **`hermes setup`** 让平台插件把 SDK 装上（懒装机制：`check_fn=feishu_deps_present`、`ensure_deps_fn=check_feishu_requirements`，`adapter.py:4300-4301`）。
2. **填配置**（二选一，别把密钥写进 `config.yaml`）：
   - **环境变量 / `.env`**：`FEISHU_APP_ID`、`FEISHU_APP_SECRET`（`plugin.yaml:13-23`）；
   - 飞书专属设置在 `config.yaml` 的 `platforms.feishu` 段（YAML→env 桥见 `adapter.py::_apply_yaml_config`，被 `config.py:766-767` 引用）。
3. **选连接模式**：
   - **先走 websocket（推荐，零公网）**：不设或设 `FEISHU_CONNECTION_MODE=websocket`（默认，`adapter.py:1311`）。
   - **或走 webhook**：设 `FEISHU_CONNECTION_MODE=webhook`，并配
     `FEISHU_VERIFICATION_TOKEN` 与/或 `FEISHU_ENCRYPT_KEY`（`adapter.py:1312-1313`）。
4. **（仅 webhook）回调 URL 要求**：
   - 默认监听 `webhook_host=127.0.0.1` / `webhook_port=8765` / `webhook_path=/feishu/webhook`（`adapter.py:149-151`）；
     可在配置里覆盖（`FEISHU_WEBHOOK_HOST` / `FEISHU_WEBHOOK_PORT` / `FEISHU_WEBHOOK_PATH`，读取处 `adapter.py:1325-1327`）。
   - **回调 URL = `http(s)://<公网可达的 host>:<port><path>`**，填进飞书后台的事件订阅。
   - 路由注册见 `adapter.py:3728`：`app.router.add_post(self._webhook_path, self._handle_webhook_request)`。
5. **「需要公网可达地址」这一点与可选方案**（webhook 专用；websocket 不需要）：
   - **内网穿透**：frp / ngrok / cpolar / cloudflared 把本机 `127.0.0.1:8765` 映射到一个公网域名；
   - **云主机**：项目上阿里云/腾讯云轻量服务器（或已有 VPS），跑 gateway 并用反代（Nginx/Caddy）加 TLS 暴露 `/feishu/webhook`；
   - 无论哪种，飞书侧只认那个**公网 https 地址**（是否强制 https **unknown**，以后台要求为准）。
6. **起网关并核对**：`hermes gateway ...` 系列命令拉起飞书适配器；启动日志会打印
   `[Feishu] Connected in <mode> mode`（`adapter.py:1446`），失败则打印 `FEISHU_APP_ID or FEISHU_APP_SECRET not set` / `lark-oapi not installed`（`adapter.py:1409 / :1421`）。
   > 确切的启用子命令名（如是否 `hermes gateway setup feishu`）**unknown**：本机未跑过，未在源码里核到该子命令串，不写死。

## ③ 拍扁进 ScholarScout 的设计（遵守分层，只用标准库）

### 3.1 放哪一层 / 叫什么名字

分层是 `desktop/ → rpc/ → runtime/ → tools/ → {providers, fetch, grading, state}`（`docs/03 §2:135`）。
飞书回调是一个**「外部消息进 → 汇入一次会话」的前门**，职责与 `desktop/` 同类（外壳/入口），因此：

- **新增顶层包 `channels/`**，本文件建议落点 **`channels/feishu.py`**（+ 可选 `channels/__init__.py`）。
- **它只准 import `rpc/`（进程内 dispatch）**，不直接碰 `runtime/tools/state/providers`——与 `desktop/` 只经 `rpc/server.py` 通信同一条纪律。
- ⚠️ **门禁要求**：`tests/test_layering.py` 有元规则 `test_every_top_level_package_has_a_rule`（`:97-102`）——
  **新顶层包必须登记进 `RULES` 表**，否则当场红。建议在 `test_layering.py:23` 的 `RULES` 里加：
  `"channels": ("runtime", "tools", "state", "providers", "fetch", "grading", "learning"),`
  （即「只经 rpc」的硬约束）。**这条一旦加，任何从 `channels/` 直连下层的 import 都会失败——正是我们要的。**

### 3.2 用标准库 `http.server` 接回调（**不新增依赖**）

不引 aiohttp/fastapi，直接用 `http.server.ThreadingHTTPServer` + `BaseHTTPRequestHandler`：

```
POST <FEISHU_WEBHOOK_PATH>  →  读 body(限长) → 校验 → 分派到事件处理 → 200 {"code":0,"msg":"ok"}
```

要点（对齐 Hermes 的真实做法，避免自造轮子踩同样的坑）：
- **只收 `application/json`**（Hermes 也这样：`adapter.py:2679-2682`）；
- **限长**：body 超过阈值直接 `413`（Hermes 用 1 MB，`adapter.py:155 / :2685-2687`）；
- **限速**：按 `app_id:path:remote_ip` 做滑动窗口（Hermes 60s/120 次，`adapter.py:156-157 / :2776-2785`）；
- **只绑定 `127.0.0.1`**（默认），公网由内网穿透/反代承担，进程本身不直接暴露；
- 依赖政策：这套只用 stdlib，`deps-allowlist.txt` 不用动（`docs/03 §5`）。

### 3.3 签名校验怎么做（照抄 Hermes 的两层）

1. **verification token**：取 `payload.header.token`（或 `payload.token`），与本地 `verification_token` 用 `hmac.compare_digest` 比对（`adapter.py:2708-2717`）。
2. **签名**：取 `x-lark-request-timestamp`、`x-lark-request-nonce`、`x-lark-signature` 三个头，
   计算 `sha256(timestamp + nonce + encrypt_key + body_str)` 与签名 `compare_digest`（`adapter.py:2759-2771`）。
3. **URL 挑战**：`type == "url_verification"` 时**先过 token** 再回 `{"challenge": ...}`（`adapter.py:2719-2722`）。
4. **失败即拒**：任何一层不过都回 `401` 并记录（`adapter.py:2716-2717 / :2725-2726`）。
> 只依赖 `hmac` / `hashlib`（stdlib）。**encrypt_key 只要不落盘明文**（读 `.env`，与 `LLM_API_KEY` 同规矩）。

### 3.4 消息如何变成一次会话请求（走哪个 RPC）

- **事件映射**：`im.message.receive_v1`（`adapter.py:2750`）→ 取出 `text` 内容。
- **会话映射**：用 `chat_id` 当 `session_key` 去换/建 `session_id` —— 调 RPC **`session.create {title?, session_key?}`**（`docs/01 §3.2:87`）；
  同一 `chat_id` 复用同一 `session_id`（会话连续）。
- **发一轮**：调 RPC **`chat.send {session_id, text, toolsets?}`**（`docs/01 §3.2:90`）。
  这一层只在 `rpc/` 边界调用，不 import `runtime/loop`。
- **回复**：把这一轮最终文本发回飞书群（用飞书 REST 的「回复消息」；凭据与 token 获取走同一份配置）。

### 3.5 回复与流式怎么用现有事件

现有流式事件是 `chat.delta / chat.tool_call / chat.tool_result / chat.done / chat.error`（`docs/01 §4:189-193`）：

- **第一版（最省）**：只监听 **`chat.done`**，其最终 `text`（或在 `chat.send` 的同步返回里拿 `text`）一次性发回飞书；
  `chat.error` 则发一条失败提示。**不做逐字流式**——飞书改消息有频率与配额，逐 delta 打点会打爆 API。
- **进阶（可选）**：按节流（如 ≥1s 或每 N 字符）把累积文本 `edit_message`/patch 到同一条飞书消息上（Hermes 就有 `edit_message`，`adapter.py:1616`）；
  `chat.tool_call/tool_result` 可作为「正在检索…」的进度提示，但**默认不发**，避免刷屏。
- **停止语义**：`stop_reason` 取值固定（`docs/01 §4:196-198`），映射成人话发回（如 `no_new_evidence` → “没有找到新资料，先到这里”）。

### 3.6 无公网地址时，用「桩回调」本地自测整条链路

目标：**在没有任何飞书凭据、也没有公网地址的情况下**，把「签名校验 → 解析 → RPC → 回复」整条链路跑通。

1. **构造一个真事件体**：写一份 `tests/fixtures/feishu_message_receive.json`，
   形如 `{"header":{"event_type":"im.message.receive_v1","token":"<本地 verification_token>"}, "event":{...}}`。
2. **本地算签名**：用本地的 `encrypt_key` 按 §3.3 的公式算出 `x-lark-signature`（脚本里 `hashlib.sha256`）。
3. **两条自测路径**（任选）：
   - **进程内直调**：测试直接调用 `channels.feishu` 的请求处理函数，传入构造好的 headers+body，断言它调了 `chat.send` 且回复文本符合预期（**不打网络**）；
   - **真起服务打 HTTP**：在 `127.0.0.1:<测试端口>` 起 `ThreadingHTTPServer`，用 `curl`/`http.client` POST 上面那份 body + 头，断言 `200` 与回复。
4. **断言**：签名错的 body 必须 `401`；token 错的必须 `401`；正常 body 必须走到 `chat.send` 并返回回复。
5. 这套测试**零外部依赖**（std-lib + 本地假模型），可进 CI 门禁。

## ④ 当前卡点与拿证后的继续点

**当前卡在两个前置条件（都是「用户提供」型，本机无法自行满足）**：

1. **没有自建飞书应用** → 拿不到 `FEISHU_APP_ID` / `FEISHU_APP_SECRET`（以及 webhook 的 `verification_token` / `encrypt_key`），
   飞书后台的事件订阅权限项也无法逐一核对（对应 1.4 里标 **unknown** 的部分）。
2. **没有公网可达的回调地址** → webhook 模式无法在飞书后台填 URL（`gateway/config.py:248` 决定了 feishu 只有 webhook 模式才需要地址）。
   （注：**websocket 模式不受此限**，可先用它把 Hermes 侧链路验证掉。）

**用户拿到自建应用后，从哪一步继续**：

1. **Hermes 侧**：按 §② 第 1–3 步填 `.env` 的 `FEISHU_APP_ID/SECRET`，**先用 websocket 模式** 起网关，确认
   `[Feishu] Connected in websocket mode`（`adapter.py:1446`）与「群里 @ 机器人能收到回复」。
2. **再决定是否上 webhook**：需要 webhook 时按 §② 第 4 步选内网穿透或云主机，把公网 URL 填回飞书后台。
3. **ScholarScout 侧**（**不依赖任何凭据，可**现在就开始**）：先落 `channels/feishu.py`（§3.1 落点）+
   在 `tests/test_layering.py::RULES` 登记 `channels`（§3.1 门禁）+ §3.6 的「桩回调」自测。
   等真实凭据到位，只需把 §3.6 的桩 body 换成飞书真事件、把「回复」从本地断言换成飞书 REST 发送，**链路其余部分一字不改**。
