### 1.3 为什么会有「webhook」这条路；它和 websocket 的分工

- **默认走 websocket**：`adapter.py:1311` 的 `connection_mode` 默认值是 `"websocket"`（`FEISHU_CONNECTION_MODE` 可改）。
  websocket 由本机 **主动外连** 飞书服务器（`adapter.py:3694-3718` 用官方 `FeishuWSClient`），**不需要公网可达地址**。
- **webhook 是可选模式**：只有显式设成 `connection_mode: webhook` 才**绑定本地端口、等飞书 POST 事件进来**
  （`gateway/config.py:243-248`：`PORT_BINDING_PLATFORM_VALUES` 含 `"feishu"`，但 `PORT_BINDING_CONDITIONAL_MODES = {"feishu": "webhook"}`
  表示**仅 webhook 模式**才 bind；`platform_binds_port()` 在 `config.py:256-261` 落实这条判断）。这就**必须有一个飞书服务器能访问到的回调地址**。
- **结论**：我们要拍扁时，**webhook 路线的唯一代价就是「公网可达地址」**；若只想先把链路跑通，Hermes 侧的 websocket 模式零公网要求。

**本项目 2026-10-14 的落点（用户拍板"飞书改走 A"）**：跟上 Hermes 的默认 —— 入站走 **websocket 长连接**
（官方 SDK `lark-oapi`，`channels/feishu_ws.py`），**webhook 那条路整体删除**。这是一组真实取舍，写进论文用：

| | **A：websocket 长连接（现选）** | **B：webhook + 内网穿透隧道（旧路，已删）** |
|---|---|---|
| 依赖 | 引入并维护第三方官方 SDK `lark-oapi`（含 `websockets`/`requests` 等传递依赖） | 只用 stdlib `http.server`，**零新增运行期依赖**（白名单只 4 项） |
| 接入便捷 | 本机主动外连，**不需要公网地址 / 回调 URL / 隧道**；飞书后台不填回调 | 必须有**飞书能访问到的公网地址**；隧道域名会变、重启即失效，要重填后台 |
| 运维面 | 断线由 SDK 长连接自愈；**没有本地监听端口**，不暴露任何入站面 | 要自己起监听 + 起隧道 + 解析 banner 里的公网 URL + 回打自检；多两个后台进程 |
| 安全校验 | 报文走**已认证的长连接**，不校签（verification token / 签名 / challenge 一套**无意义**，已删） | 必须自实现两层校验（token + HMAC 签名）与 `challenge`，且要防未授权者拿 challenge 探测端点 |
| 真实成本 | `import lark_oapi` 本机**首次约 116 秒**（SDK 上千子模块要写 `.pyc`），之后约 14 秒 | 无 import 成本；但每条消息都经公网隧道，稳定性受隧道与网络环境影响 |

**一句话**：B 换来的是**依赖最小化**（运行期白名单守住 stdlib），代价是**接入与运维都更重**（公网地址、隧道生命周期、自实现校验）；
A 换来的是**接入便捷**（零公网、零后台回调、零本地端口），代价是**多一个第三方 SDK 与一次 116 秒的冷启动**。
本项目当前优先"用户在飞书里发一条消息就能跑通"，所以选 A。

### 1.4 webhook 模式需要哪些凭据与权限

- **凭据**：`FEISHU_APP_ID` + `FEISHU_APP_SECRET`（必填，`plugin.yaml:13-23`）；webhook 模式还需
  **`FEISHU_VERIFICATION_TOKEN` 或 `FEISHU_ENCRYPT_KEY` 至少一个**——否则 `connect()` 直接报错返回 False（`adapter.py:1417-1419`）。
- **权限/订阅**：飞书后台要给应用**订阅事件**（如 `im.message.receive_v1` 等；适配器侧的事件处理表见 `adapter.py:2749-2757`）。
  具体在飞书开发者后台点哪些权限项 **unknown**（本机没有可用凭据进后台核对，不臆造）。
- **两个安全层**（拍扁时要照抄）：
  1. **verification token**：比对 body/header 里的 `token`（`adapter.py:2708-2717`，`hmac.compare_digest`）；
  2. **签名**：`x-lark-signature == sha256(timestamp + nonce + encrypt_key + body)`（`adapter.py:2759-2771`，同样 `compare_digest`）；
  另外 `type=url_verification` 的挑战要在**通过 token 校验之后**才回 `challenge`（`adapter.py:2719-2722`，防未授权者用来证明自己控制了端点）。

   - **环境变量 / `.env`**：`FEISHU_APP_ID`、`FEISHU_APP_SECRET`（`plugin.yaml:13-23`）；
   - 飞书专属设置在 `config.yaml` 的 `platforms.feishu` 段（YAML→env 桥见 `adapter.py::_apply_yaml_config`，被 `config.py:766-767` 引用）。
3. **选连接模式**：
   - **先走 websocket（推荐，零公网）**：不设或设 `FEISHU_CONNECTION_MODE=websocket`（默认，`adapter.py:1311`）。
   - **或走 webhook**：设 `FEISHU_CONNECTION_MODE=webhook`，并配
     `FEISHU_VERIFICATION_TOKEN` 与/或 `FEISHU_ENCRYPT_KEY`（`adapter.py:1312-1313`）。

   - 默认监听 `webhook_host=127.0.0.1` / `webhook_port=8765` / `webhook_path=/feishu/webhook`（`adapter.py:149-151`）；
     可在配置里覆盖（`FEISHU_WEBHOOK_HOST` / `FEISHU_WEBHOOK_PORT` / `FEISHU_WEBHOOK_PATH`，读取处 `adapter.py:1325-1327`）。
   - **回调 URL = `http(s)://<公网可达的 host>:<port><path>`**，填进飞书后台的事件订阅。
   - 路由注册见 `adapter.py:3728`：`app.router.add_post(self._webhook_path, self._handle_webhook_request)`。
5. **「需要公网可达地址」这一点与可选方案**（webhook 专用；websocket 不需要）：
   - **内网穿透**：frp / ngrok / cpolar / cloudflared 把本机 `127.0.0.1:8765` 映射到一个公网域名；
   - **云主机**：项目上阿里云/腾讯云轻量服务器（或已有 VPS），跑 gateway 并用反代（Nginx/Caddy）加 TLS 暴露 `/feishu/webhook`；
   - 无论哪种，飞书侧只认那个**公网 https 地址**（是否强制 https **unknown**，以后台要求为准）。
6. **起网关并核对**：`hermes gateway ...` 系列命令拉起飞书适配器；启动日志会打印
   `[Feishu] Connected in <mode> mode`（`adapter.py:1446`），失败则打印 `FEISHU_APP_ID or FEISHU_APP_SECRET not set` / `lark-oapi not installed`（`adapter.py:1409 / :1421`）。
   > 确切的启用子命令名（如是否 `hermes gateway setup feishu`）**unknown**：本机未跑过，未在源码里核到该子命令串，不写死。

## ③ 拍扁进 ScholarScout 的设计（遵守分层；入站用官方 SDK 的长连接）

### 3.1 放哪一层 / 叫什么名字

分层是 `desktop/ → rpc/ → runtime/ → tools/ → {providers, fetch, grading, state}`（`docs/03 §2:135`）。
飞书回调是一个**「外部消息进 → 汇入一次会话」的前门**，职责与 `desktop/` 同类（外壳/入口），因此：

- **新增顶层包 `channels/`**，落点 **`channels/feishu.py`**（传输无关的入站核：解析 / 拦截 / 跑一轮 / 回包）
  + **`channels/feishu_ws.py`**（唯一的传输适配层：官方 SDK 的长连接）+ `channels/__init__.py`。
  **传输与业务分开**是本轮的关键设计：入站核**不碰任何 socket**（只认"已解好的事件报文"），
  所以桩事件（甚至一个 dict）就能把整条链路测到底；换传输（或加第二个平台）不必动入站核一行。
- **它只准 import `rpc/`（进程内 dispatch）**，不直接碰 `runtime/tools/state/providers`——与 `desktop/` 只经 `rpc/server.py` 通信同一条纪律。
- ⚠️ **门禁要求**：`tests/test_layering.py` 有元规则 `test_every_top_level_package_has_a_rule`——
  **新顶层包必须登记进 `RULES` 表**，否则当场红。**已登记**（`test_layering.py` 的 `RULES` 里）：
  `"channels": (...)`（即「只经 rpc」的硬约束）。**这条一加，任何从 `channels/` 直连下层的 import 都会失败——正是我们要的。**

### 3.2 入站传输：官方 SDK 的 websocket 长连接（**新增一枚依赖，见 §1.3 取舍**）

**已落地** `channels/feishu_ws.py`：用官方 SDK `lark-oapi`（PyPI 包名 `lark-oapi`）的
`lark_oapi.ws.Client` 起**长连接**，注册 `im.message.receive_v1`，把 SDK 事件对象归一成
`{"header": ..., "event": ...}` 报文交给入站核 `feishu.FeishuMessageHandler.handle_event`。

要点（每条都有出处或实测）：
- **零公网、零回调、零本地端口**：本机**主动外连**飞书服务器，因此**不需要**回调地址 / 内网穿透 / 反代，
  也不绑任何监听端口（不暴露入站面）。这正是相对 webhook 路线（旧 §3.2）的核心收益。
- **不校签**：报文由 SDK 在**已认证的长连接**上收到，不存在"谁都能往这个端口 POST"的前提，
  所以 verification token / 签名 / `challenge` 那一套**没有意义**（随 webhook 一起删掉了）。见 §3.3。
- **`extra_ua_tags=["channel"]` 不能省**（照 Hermes `adapter.py:3702-3712`）：不加这个 UA 标签，
  飞书**不会把群里的 `@` 事件推给长连接**，群聊 `mention` 策略会静默失效。**本条本机无凭据、未实测**，是照参照实现抄的。
- **`import lark_oapi` 很慢**：本机**首次约 116 秒**（SDK 上千子模块要写 `.pyc`），之后约 14 秒。
  所以长连接适配层**绝不在 import 期加载它** —— 只有真要连的那一次才 `importlib.import_module`；
  前提自检走 `importlib.util.find_spec`（**只查规格、不 import**，几毫秒返回）。
  副作用是**桩测完全不需要装 SDK**（`tests/channels/test_feishu_ws_stub.py`）。
- **依赖政策**：这一项**动白名单** —— `deps-allowlist.txt` 与 `pyproject.toml`（`lark-oapi>=1.7,<2`）都已登记，
  审批记录写明"用户（张思浩）2026-10-14 拍板飞书改走 A"（`docs/03 §5/§6`）。
- **出站开关仍是 `runtime.feishu_reply_enabled`**（默认 `false`，关着时渠道层**一次外网都不发**，见 §3.7）。
  **入站没有开关键**：长连接由一键入口显式拉起，关掉就是停那个进程。

### 3.3 长连接为什么**不校签**（旧 webhook 的两层校验已随路线删除）

旧 webhook 路线要照抄 Hermes 的两层校验（verification token + `sha256(timestamp + nonce + encrypt_key + body)` 签名 +
`url_verification` 挑战），因为那是一个**任何人都能往 `127.0.0.1:8765` POST** 的本地 HTTP 端点；
现在入站是长连接，**这套校验没有意义**：

- 报文由 SDK 在**已认证的长连接**上收到 —— 官方 SDK 的 WS 分支走
  `EventDispatcherHandler._do_without_validation`（`lark_oapi/event/dispatcher_handler.py:167`）；
- 因此 `FeishuWsClient` 用 `EventDispatcherHandler.builder("", "")` 传**空凭据**，不注册任何校验回调；
- 对应的实现与常量（`compute_signature` / `signature_valid` / `token_valid` / `is_challenge` / `challenge_body`）
  以及 `FEISHU_VERIFICATION_TOKEN` / `FEISHU_ENCRYPT_KEY` 两个键**已随 webhook 一起删除**。

**安全边界改成什么**：长连接的信任来自 SDK 的**认证握手**（`app_id` + `app_secret` 换 token 才能连上）；
应用层的访问控制**一点没少** —— 仍是「运行时拦截在会话之前」：群聊按 `@提及` 策略、私聊按
`pairing|all|allowlist` 策略（未授权私聊不跑任何会话），见 §3.4 与 §5.1。凭据仍**只进 `.env`、只写不回读**。

### 3.4 消息如何变成一次会话请求（走哪个 RPC）

- **运行时拦截先于会话**（**已落地**，`channels/feishu.py::FeishuMessageHandler.run_turn`）：每来一条消息，
  先经 `feishu.access` RPC 取「该 open_id 是否在白名单 / 是否临时放行 / 当前 DM 策略」，再做放行判定
  （**渠道层不读库**，白名单状态一律走 RPC）。规则：
  - **群聊**（`chat_type=group`）：`disabled` 一律丢弃；`mention` 策略下**仅在被 @ 时响应**，
    否则丢弃。@ 判定按 `bot.open_id` 优先、`bot.app_name` 兜底（`FEISHU_BOT_OPEN_ID` / `FEISHU_BOT_NAME`）。
    这两个身份可直接**联网探测**：`feishu.probe` → `POST /open-apis/auth/v3/tenant_access_token/internal`
    换 token → `GET /open-apis/bot/v3/info` 取 **`bot.app_name`**（名）与 **`bot.open_id`**（自身 id）
    （**已实测**，回包形状见 `docs/18 §④`）；探测失败/`code!=0` 一律回退 `unknown`、**不阻塞**。
  - **私聊**：`all` 放行；`allowlist` 只放行白名单，**名单外直接丢弃并记日志**；
    `pairing`（默认）**未授权不执行任何会话**，只回配对提示。未授权私聊的整条消息**先当配对码登记**
    （`feishu.pairing.claim`：用户把向导生成的码私聊发回来），登记成功只回执、不跑会话。
  - **临时放行**：`feishu.pairing.create` 打开、`feishu.pairing.verify` 收回；放行期间未授权私聊可先跑
    （但码消息仍先试登记）。
- **事件映射**：`im.message.receive_v1`（`adapter.py:2750`）→ 取出 `text` 内容（`chat_type` 与 `mentions` 一并解析）。
  长连接侧由 `feishu_ws.event_to_payload` 归一成报文（SDK 事件对象 → 普通 dict；缺 `header.event_type` 时补成本模块唯一订阅的那条）。
- **会话映射**：用 `chat_id` 当 `session_key` **幂等**换/建 `session_id` —— 调 RPC **`session.ensure {session_key, source}`**
  （`rpc/session.py:33`；`ensure` 与 `create` 的区别：`create` 是一次性新建、key 撞唯一约束就报错，`ensure` 存在即返回）。
  同一 `chat_id` 复用同一 `session_id`（会话连续）；事件源写 `source="feishu"`。
- **发一轮**：调 RPC **`chat.send {session_id, text}`**（`rpc/session.py:196`）同步拿 `{"text", "stop_reason", ...}`。
  这一层只在 `rpc/` 边界调用，不 import `runtime/loop`。
- **回复**：把这一轮最终 `text` 交给**注入的发送器** `sender(chat_id, text)`。真实部署注入走飞书 REST 的
  「回复消息」实现；本地桩/无凭据时默认 `RecordingSender` **只记录 + 告警**（不假装发成功）。

### 3.5 回复与流式怎么用现有事件

现有流式事件是 `chat.delta / chat.tool_call / chat.tool_result / chat.done / chat.error`（`docs/01 §4:189-193`）：

- **第一版（最省）**：只监听 **`chat.done`**，其最终 `text`（或在 `chat.send` 的同步返回里拿 `text`）一次性发回飞书；
  `chat.error` 则发一条失败提示。**不做逐字流式**——飞书改消息有频率与配额，逐 delta 打点会打爆 API。
- **进阶（可选）**：按节流（如 ≥1s 或每 N 字符）把累积文本 `edit_message`/patch 到同一条飞书消息上（Hermes 就有 `edit_message`，`adapter.py:1616`）；
  `chat.tool_call/tool_result` 可作为「正在检索…」的进度提示，但**默认不发**，避免刷屏。
- **停止语义**：`stop_reason` 取值固定（`docs/01 §4:196-198`），映射成人话发回（如 `no_new_evidence` → “没有找到新资料，先到这里”）。

### 3.6 无凭据、不联网时，用「桩事件」本地自测整条链路

目标：**在没有任何飞书凭据、也不连飞书服务器、连 SDK 都没装的情况下**，把「归一 → 解析 → 拦截 → RPC → 回复」整条链路跑通。

1. **构造一个真事件体**：**不落地 fixture 文件**，直接在 `tests/channels/test_feishu_stub.py::_message_payload`
   里拼 `{"header":{"event_type":"im.message.receive_v1"}, "event":{...}}`（形状与长连接归一后的报文一致）。
2. **两条自测路径**（传输与业务已分开，两条都真跑）：
   - **进程内直调入站核（`test_feishu_stub.py`）**：直接调 `FeishuMessageHandler.handle_event(payload)`
     —— 它**传输无关、不碰 socket**，所以一个 dict 就能把整条链路测到底（真落库 + 断言回复文本）；
   - **长连接适配层桩测（`test_feishu_ws_stub.py`）**：给 `FeishuWsClient` 注入**替身 SDK**（`WsSdk` 只抽了三个名字），
     断言它注册了 `im.message.receive_v1`、`extra_ua_tags=["channel"]`、`domain` 正确，并验证
     `event_to_payload` 把 SDK 事件对象（含下划线内部字段）归一成了干净报文。
3. **断言**：正常事件必须走到 `chat.send` 并把回复交给注入的 `RecordingSender`；未授权私聊**不跑会话**只回配对提示；
   群聊遵守 `@提及` 策略；适配层**绝不外抛**（回调抛异常会顺着 SDK 收包线程让整条链路静默失聪，必须只记日志）。
4. 这套测试**零外部依赖、零凭据、不 import SDK**（std-lib + 本地假模型 + `RecordingSender` + 替身 SDK），已进 CI 门禁。
   **长连接的「真连一次」不在桩测范围内** —— 那要真凭据，属 §5.2 的「用户提供」项。

### 3.7 出站发送器（把一轮回答推回飞书）

**已落地** `fetch/feishu_send.py`（出网只走 `fetch/http.py`；渠道层不许 import `fetch`，所以这里是**渠道层形状**的工厂
`build_sender(http, enabled=...) -> sender(chat_id, text) -> dict`，由**入口层**注入 `channels/feishu.py`）：

- 端点 `POST /open-apis/im/v1/messages?receive_id_type=chat_id`（`fetch/feishu_onboard.py::ONBOARD_OPEN_URLS` 基址 +
  `?receive_id_type=chat_id`）；鉴权 `Authorization: Bearer <tenant_access_token>`，token **复用** `fetch_tenant_token`（不重写）；
- body `{receive_id, msg_type:"text", content, uuid}`：`content` 是**一个 JSON 字符串** `{"text": ...}`（不是对象），`uuid` 是幂等键；
- 成功回包 `{code:0, msg:"success", data:{message_id:"om_..."}}`；
- **两条口径**：① 失败（缺凭据 / 取 token 失败 / 网络错误 / 非 JSON / `code!=0`）一律回 `SendOutcome(ok=False)`、**不抛**
  （发送发生在「一轮跑完之后」，不该把会话/回调搞崩）；② 发送**不缓存**（写操作，`post_json(cache=False)`）。
- **默认关**：`runtime.feishu_reply_enabled=false`（或缺凭据 / 无出网客户端）时，发送器**一次外网都不发**，只告警、回 `ok=False`。

### 3.8 长连接适配层（`channels/feishu_ws.py`）

**已落地**。它是入站传输的**唯一实现**，职责就三件：

1. **装配** `FeishuWsClient`：`FeishuWsClient.build_client()` 用 `EventDispatcherHandler.builder("", "")`
   （空凭据，不校签，见 §3.3）注册 `register_p2_im_message_receive_v1`，再建
   `lark_oapi.ws.Client(app_id, app_secret, log_level, event_handler, domain, extra_ua_tags=["channel"])`；
2. **归一**：`event_to_payload(event)` 把 SDK 事件对象递归换成普通 dict（下划线开头的内部字段丢弃），
   缺 `header.event_type` 时补 `im.message.receive_v1`，再把报文交给
   `feishu.FeishuMessageHandler.handle_event`；
3. **生命周期**：`start()` **阻塞**跑 SDK 收包循环（Ctrl-C 收尾）；`stop()` 尽力收尾 ——
   `lark_oapi` 的长连接**没有公开关闭接口**（`ws.Client` 只有 `start()`，重连循环活着是为了断线自愈），
   所以真实语义就是**进程退出即断开**（代码里留了"将来 SDK 提供 `close()/stop()` 就顺手调"的口子）。

- **启动日志**（`START_LOG_TEMPLATE`）明说什么都不需要：
  `[Feishu] websocket 长连接启动：app_id=... domain=...（本机主动外连，不需要公网地址 / 回调 URL / 隧道；事件订阅勾选 im.message.receive_v1）`。
- **SDK 可注入**（`WsSdk` 只抽 `client_cls` / `event_handler_cls` / `log_level` 三个名字），
  所以桩测不 import 真 SDK；`load_sdk()` 是**全项目唯一** `import lark_oapi` 的地方。
- **回调绝不外抛**：`on_message_event` 捕获一切异常只记日志 —— 回调抛异常会顺着 SDK 收包线程上去，
  一条坏消息就够让整条链路静默失聪。
- **没有配置键**：入站不再有任何开关/端口/路径（`feishu_listener_*` 三枚已删）；
  出站开关仍是 `runtime.feishu_reply_enabled`。`feishu.status` 也**不再上报** `listener_*` 字段。

### 3.10 仍需人工的飞书后台步骤（脚本代替不了）

飞书后台的操作**没有开放 API 能替你点**（`docs/18 §④`）：建应用、开能力、勾事件都得人工。
本方案只有**四步**，且**没有"填回调地址"这一步**：

1. **建「自建应用」** → 拿 `App ID` / `App Secret`（进 `.env`，可用向导 `--setup-feishu` 填）。
2. 给应用**开启「机器人」能力**。
3. **事件订阅**勾上 **`im.message.receive_v1`**（收到消息）。
4. **不需要填回调地址**（长连接由本机主动外连，飞书侧没有公网回调要访问）。

> **与旧 webhook 路线的差别**（写论文/答辩会问）：旧路线第 4 步要"内网穿透拿公网地址 → 填进后台事件订阅 →
> 隧道换域名就得重填"；长连接把第 4 步整条删掉，代价是引入 `lark-oapi` 这枚依赖与它 116 秒的冷启动（§1.3）。
> 这四步的文案也**印在一键开机的输出里**（`_print_backstage_steps`），且桩测断言**不得出现"填回调地址"**。

### 3.11 入站即时回执（用户不必等 3–12 分钟才知道"收到了"）

**问题**：一轮要跑 **3–12 分钟**（实测 P50 15.3s / P95 46.3s 是短任务；E3 那种出产物的任务
单题 146–228s，本机模型慢时更久）。而入站链路在**跑完这一轮**之前**一句话都不回** ——
用户在飞书里看到的只有"发出去的消息"，分不清"机器人没收到"、"收到了在跑"、"链路坏了"。
长连接**没有 ack 回执这一层**（SDK 收包成功 ≠ 用户看得见），所以要**自己回一条**。

**挂点**：`channels/feishu.py::FeishuMessageHandler.run_turn` 里，**白名单放行之后、`session.ensure` 之前**
调 `send_ack(message)`。位置是硬约定（`tests/channels/test_feishu_ack.py` 用**动作序列**钉住，
不是比时间戳 —— Windows 上 `time.monotonic()` 粒度 ~15.6ms，同一批动作拿到相同值就是**空断言**）：

```
send:已接受消息，正在处理中 → session.ensure → chat.send → send:<这一轮的回答>
```

五条硬约定（都有用例）：

| # | 约定 | 为什么 |
|---|---|---|
| 1 | **回执在这一轮之前**（不是"跑完顺手补一条"） | 它就是"收到了"的唯一凭据 |
| 2 | **失败不拖垮轮次**：发送器抛异常、或回 `ok=false`（网络/限流/平台报错）只记日志，照常落库、照常回回答 | 回执是锦上添花，不能变成链路的单点（`test_ack_failure_*` 两例） |
| 3 | **空文案 = 关掉**：`runtime.feishu_ack_text: ""` 时一条都不发，**且不记告警** | 那是用户显式选择，不是异常 |
| 4 | **未授权者收不到回执**：`pairing` 未配对 / `allowlist` 名单外的人在更早的拦截里就返回了（`pair` / `drop`） | 回执是"开始处理"的凭据，不是"收到消息"的收条 —— 否则它白白变成一台"机器人活着"的探测器 |
| 5 | **按 `message_id` 去重**：飞书会重推同一事件（长连接重连 / 平台重试），只回执一次 | 不希望用户看到双份"已接受消息" |

**开关与作用域（用户会问的那几个）**：

- 回执**没有自己的开关键**，它与回答**共用 `runtime.feishu_reply_enabled`**（§3.7）：关着时
  渠道层注入的是一个"只记录 + 告警、绝不发外网"的发送器，所以**回执也一次外网都不发**
  —— 渠道层不需要、也不该另立一个开关。
- 文案默认 **`已接受消息，正在处理中`**（`config.DEFAULT_FEISHU_ACK_TEXT`），
  `runtime.feishu_ack_text` 可改；**空串是合法取值**（关掉）。
  默认值定义在 `config` 这一层（不是 `channels`），因为 `channels` 已经 import `config`，
  反向 import 会成环。

**配置怎么传到渠道层**（渠道子进程**没有配置对象** —— 它只当 RPC 客户端、不读 config、不开库，
见模块顶注的纪律 1）：

```
config.yaml runtime.feishu_ack_text
  → 父进程 supervisor.config_env(ctx)   # 新增函数：child_env() + 把配置翻译成环境变量
  → 子进程环境变量 FEISHU_ACK_TEXT
  → runner.run(ack_text=…)（没显式给就用 feishu.ack_text_from_env()）
  → FeishuWsClient.ack_text
  → FeishuMessageHandler.ack_text
```

- **空串也必须注入**（`if isinstance(text, str)` 而不是 `or 默认`）：用 `or` 兜默认会把
  用户"显式关掉"的选择吃掉，等于关不掉。
- **读不到配置时一个键都不注入**（`ctx` 没有 `config` 的老调用点 / 桩 ctx）：那时渠道层走
  自己的缺省，**不编值**。
- 单进程入口 `scripts/feishu_ws_up.py` 没有父进程注入，所以它**直接**把
  `ctx.config.runtime.feishu_ack_text` 传给 `build_client(ack_text=…)`，并在空文案时**打印一行
  告知**"回执已关，要等整轮跑完才有回应"（别让人以为坏了）。
- 走的就是既有的那条通道（与凭据 / `FEISHU_DM_POLICY` 同一条路：**环境继承**），
  所以不落第二份配置副本。

**去重器 `RecentMessageIds` 是有界的**（`ACK_DEDUPE_SIZE = 256`，`deque` + `set` + 锁）：
长连接进程跑几天，无界集合就是内存泄漏。**拿不到 `message_id` 时不判重**（空 key 恒放行）——
宁可多回一条，也绝不能把后面所有消息都当"重复"静默吞掉（那是一条静默失聪的链路）。
去重是"**记了就发一次**"：发送失败也占掉这个 id（宁可漏一条回执，也不给用户双份）。

**桩测**（`tests/channels/test_feishu_ack.py`，11 条，零凭据 / 零网络 / 不装 SDK）：上面五条各一例，
外加传参链路两条（`supervisor.config_env` 注入 + 空串原样带下去；`FeishuWsClient` 把 `ack_text`
转交给它自己建的 handler），以及 `ack_text_from_env` 的"缺省=开 / 环境变量给空串=关"。
`tests/channels/test_channel_runner.py` 里子进程那条端到端断言**两条出站**（先回执、后回答），
它同时就是"配置 → 环境变量 → 渠道核心"确实通了的证据。
**入站核的其它用例默认把回执关掉**（`FEISHU_ACK_TEXT=""`，见两个 stub 文件里的 `_isolate`）：
回执会让每个"跑一轮"的用例多一条出站消息，那是**另一个功能**的断言面。

> **仍未实测的点（如实标注）**：① 真飞书上的回执**没连过**（本机无凭据）；
> ② SDK 收包回调跑在它自己的线程里、可能并发进来，去重器有锁但**没做过真并发压测**。

### 3.12 纯文字化与发文件（2026-10-18 落地，以代码为准）

两个功能同批落地，出自用户的两句要求：「飞书里看到的一堆符号」「如果可以发送文件，请开发发送文件的渠道」。
三个代码入口：`fetch/feishu_send.py`（纯文字化 `to_feishu_text` / 上传发送 `send_file`）、
`rpc/channel_file.py`（RPC `channel.send_file`）、`channels/feishu.py`（意图解析 `parse_file_request` 与 `deliver_file`）。

#### 3.12.1 为什么必须纯文字化：飞书 `text` 消息不解析 markdown

飞书的 `text` 消息没有 markdown 渲染（要富文本得另发 `post`）。我们的回答由模型产出，天然带
`**粗体**`、`## 标题`、`| 表 |`、围栏代码 —— 原样发出去就是一堆符号，比纯文字更难读。
所以**所有出站文本**（回答 / 回执 / 配对提示 / 文件回执）在 `send_text` 里**统一**过
`to_feishu_text`。挂在 `send_text` 而不是各调用点，因为漏一处就是一处乱码。

| 输入 | 输出 | 规则 |
|---|---|---|
| `## 标题` | `标题` | `#`~`######` 连同其后空白整段去掉 |
| `**粗**` / `__粗__` | `粗` | 粗体标记去掉、内容保留（`__` 版要求两侧不是单词字符，避免吃掉 `a_b_c`） |
| `*斜*` / `_斜_` | `斜` | 斜体同上 |
| `> 引用` / `>> 引用` | `引用` | 引用符**整串一次剥净**（只剥一层会让 `>>` 第二次调用再剥一次 → 不幂等） |
| `- 项` / `* 项` / `+ 项` | `· 项` | 无序列表换中点；有序 `1.` **保留**（飞书里本来就看得懂） |
| `\| a \| b \|` | `a  b` | 去管道、单元格间留两个空格；`\|---\|---\|` 分隔行与水平线**整行删掉** |
| `[标题](url)` | `标题 url` | 纯文字里链接点不动，所以把地址留在文字后面 |
| 行内代码 `` `x` `` / ` ``x`` ` | `x` | 反引号按**整串**配对；只认单个反引号会把 ``x`` 剥成 `` `x` ``（又变出可剥对象） |
| 换行 | 换行 | **全部保留**；正文连续空行压成一个，**代码区内的空行一个都不动** |

剥完为空 → `ok=false`「剥掉 markdown 后正文为空，未发送」（不冒充"发过了"）。

#### 3.12.2 幂等机制：代码区边界跟着输出走（`CODE_OPEN` / `CODE_CLOSE`）

**这不是装饰，是修过的真 bug**（`tests/fetch/test_feishu_text.py` 有正反例）。
`f = to_feishu_text` 必须满足 `f(f(x)) == f(x)`：回执、文件回执这类文本会经
`send_text → to_feishu_text` **再走一遍**；输出若不在 f 的不动点上，第二次调用就继续剥。

原实现把围栏行（`` ``` ``）删掉、**代码内容原样留下** → 输出里"代码已裸露、保护却没了"，
第二次调用就把 `# 注释` 当标题剥掉、把 `| a | b |` 当表格拆开、把 `**x**` 当粗体剥掉（实测 30 例里 8 例如此）。
现在**围栏换成两行标记，标记跟着输出走**：

```
┌──── 代码 ────
# 这里是代码，不是标题
| a | b |
└─────────────
```

- `CODE_OPEN = "┌──── 代码 ────"`、`CODE_CLOSE = "└─────────────"`（`fetch/feishu_send.py` 常量）；
- 第二次调用见到 `CODE_OPEN` 就**原样保留区内容**直到 `CODE_CLOSE`：代码里的 `#`、`*`、`|`、缩进、空行**一个字节都不动**；
- 选箱线字符而不是 `---`/`***`：`_HR_RE` 不认它（不会被当水平线删掉），飞书里显示成一条分隔线；
- **围栏没闭合也强制收口**：末尾补一个 `CODE_CLOSE`，否则下一次调用会把后面的行当正文继续剥；
- 输入是 `` ``` `` 还是 `~~~`、是标记还是围栏，**输出统一成同一对标记**（同一个不动点）。

#### 3.12.3 发文件链路：上传拿 `file_key` → `msg_type=file`

```
POST /open-apis/im/v1/files                    # multipart：file_type / file_name / file
  → {"code":0,"data":{"file_key":"file_v2_…"}}
POST /open-apis/im/v1/messages?receive_id_type=open_id
  body: {"receive_id":"ou_…","msg_type":"file",
         "content":"{\"file_key\":\"file_v2_…\"}","uuid":"<幂等键>"}
```

- `content` 是**一个 JSON 字符串**（不是对象），与文本消息同一条规矩；
- `uuid` 是幂等键：同一 uuid 飞书去重，失败重发不会重复投递；
- **收件人钉死 `open_id`，形参里没有 `chat_id`** → 结构上发不了群。群 id 是 `oc_…`，真传进来只会被平台判
  `230034 receive_id 无效`，而不是"悄悄发到群里"。这是 `docs/21 §2.1` 的 `dm_only` 口径落在类型签名上；
- 上传与发送两步失败合到同一个出口 `FileOutcome`
  （`ok` / `message_id` / `file_key` / `file_name` / `size_bytes` / `code` / `error`）。

#### 3.12.4 官方硬限制（2026-10-18 核实，代码顶注带出处）

| 项 | 值 | 代码落点 |
|---|---|---|
| 单文件上限 | **30 MB**（`MAX_FILE_BYTES = 30 * 1024 * 1024`）；图片另限 10 MB | `_check_file` |
| 空文件 | **不允许**（0 字节直接拒） | `_check_file` 的 `size <= 0` |
| `file_type` 枚举 | **只有** `opus` / `mp4` / `pdf` / `doc` / `xls` / `ppt`（+ 官方兜底档 `stream`） | `FILE_TYPE_ENUM` |
| 后缀映射 | 只映射**确定属于枚举**的 `.opus/.mp4/.pdf/.doc/.xls/.ppt` | `_FILE_TYPE_BY_SUFFIX` |
| **其余一律 `stream`** | `.md` / `.txt` / `.csv` / `.docx` / `.xlsx` / `.pptx` / 无后缀 … | `file_type_for()` 的 `get(suffix, "stream")` |

- **为什么不把 `.docx` 报成 `doc`**：那是猜的，猜错会被 `230055`（`file_type` 与消息类型不匹配）拒。
  官方原文允许"不属于以上枚举类型，可以使用 `stream`"—— 兜底是唯一正确解，不是偷懒；
- 副作用如实写：`stream` 在飞书里是**通用文件**，预览器不一定认 markdown/office —— 能下载、不保证内嵌预览；
- 超限 / 空文件**本地就拒**（`_check_file` 在打接口之前跑）：这两个原因用户自己能修，不必先吃一个平台错误码；
- 另记一条（同一份官方表）：**文本消息体上限 150 KB**（超了 `230025`），本项目目前按"够用"处理，**未单独复核该数字**。

#### 3.12.5 需勾的两个权限（只勾一个会在另一半失败）

| 阶段 | 端点 | 权限（**勾一个即可**） | 没勾的表现 |
|---|---|---|---|
| 上传 | `POST /open-apis/im/v1/files` | **`im:resource`** 或 `im:resource:upload` | 上传被拒（`99991672`：应用缺少权限） |
| 发送 | `POST /open-apis/im/v1/messages` | **`im:message`** 或 `im:message:send_as_bot` | 消息发不出（`99991672` / `230027`） |

**只勾一个必在另一半失败**：常见形态是上传拿到 `file_key`、发送那条被拒 → 用户看到"上传了但没收到文件"。
两个都勾上还要**发布版本**（后台勾完权限不发布不生效）。同批会撞的还有 **机器人能力没开**（`230006` / `234007`）
与**接收者不在可用范围**（`230013`）。这些都在 §3.10 的四步之外，`docs/21 §7.2` 的人工步骤清单里也注了。

#### 3.12.6 "发我文件"的触发：规则解析，不新增模型可见工具

`channels/feishu.py::parse_file_request` 用规则判"这条消息是不是要文件"，是就交 `channel.send_file`
**完全不跑模型**（工具表、系统提示、`chat.send` 一个字都不动）。确定性动作（查库 → 导出 → 上传 → 发送）
不需要模型参与，反而更省 token、更不会瞎发。

拦截位置是硬约定（`feishu.py::run_turn`）：**在 `authorize_message` 放行之后、`send_ack` 与 `session.ensure` 之前**。
放行之后是安全要求（否则「发我笔记」就是一条**越权读取通道**）；跑轮次之前是成本要求
（能确定的事不必花 3–12 分钟一轮）。

三类目标（`kind`）：

| kind | 指什么 | 取法 | 落到哪个文件 |
|---|---|---|---|
| `artifact` | **本会话最近的生成物** | 先按 `session_id` 挑，挑不到退全库最新；`query` 装的是子类型 `topic`/`route`/`note`（空 = 三类里最新那件） | `data/exports/topic_<slug>.md` / `route_<slug>.md` / `note_<slug>.md` |
| `library` | **已入库资料，按标题** | `documents.title` / `sources.title` 的 `LIKE` 语义模糊匹配（纯 Python 过滤），发**原件**（`raw_path` 优先，退 `text_path`） | 库里的 `raw_path` / `text_path` |
| `path` | **项目内路径** | 只允许 `data/` 与 `run/` 之下（`paths.resolve_rel`）；绝对路径先经 `paths.rel_to_home` 收进项目范围 | 用户给的那个文件 |

**识别是保守的**（否则一句问话就能把问答劫走）：

- 必须**同时**有发送动词（`发我 / 给我 / 传我 / 发送 / 导出 / 来一份 …`）**和**文件类目标；
- **长度 ≤ 40 字**：一整段话里夹一句"发我"不算指令（最便宜的护栏）；
- 动词后紧跟 `讲 / 说 / 解释 / 分析 / 看看 / 写 / 推荐 …` → 是**提问**（「给我讲讲学习路线」）；
- 目标里出现 `，,；;！!？?` → 是**一句话**不是目标（实例：「发我一下这篇文章的主要贡献，顺便说说它的局限」38 字，长度护栏拦不住）；
- 两种语序都认：**动词在前**（`发我学习路线`）与**目标在前**（`把学习路线发我`）；
- 识别不到一律 `None` → 走正常问答。

#### 3.12.7 找不到不发 / 失败一律 `ok:false + reason`

| 情形 | 用户看到什么 | 代码 |
|---|---|---|
| 目标找不到 | 一句话说明 + **候选清单（≤6 条）**，**绝不猜一个文件发出去** | `_not_found_reply` / `MAX_CANDIDATES` |
| 生成物导出失败 | 「找到了这件生成物，但导出文件时失败了（详见运行日志）」 | `_artifact_target` |
| 资料有记录但原件不在盘上 | 「库里记着这份资料，但原件在盘上找不到（可能被移动/删除）」 | `_document_target` |
| 路径越界 | 「只允许发项目目录（data/ 与 run/）里的文件」 | `_path_target` |
| 空文件 / 超 30 MB | 「文件是空的（飞书不允许 0 字节文件）」/「X.X MB 超过飞书上限 30 MB」 | `_check_file` |
| 权限没勾 | **可读中文**，不是栈：「应用缺少权限：去飞书后台给应用勾上 `im:resource`（上传文件）与 `im:message:send_as_bot`（发消息），发布后重试」 | `ERROR_HINTS` / `explain_code` |
| 出站开关关着 | 「没发出去：未配置文件发送器：未开启出站发送（`runtime.feishu_reply_enabled=false`）」 | `build_file_sender` 的三道闸门 |
| 后端 / 传输异常 | 「暂时发不了文件：后端没有给出结果（详情见运行日志）」 | `deliver_file` 的 `except` |

三条工程口径：**不抛**（长连接回调里抛异常 = 整条链路静默失聪，`build_file_sender` 连
`except Exception` 都兜了）；**`ok:false` 必带 `reply`**（渠道层拿它原样回给用户，不在渠道层拼文案 ——
那里看不见候选清单）；**出站开关与回答共用** `runtime.feishu_reply_enabled`（默认关，关着一次外网都不发）。

回包只有六个字段：`ok` / `kind` / `file_name` / `message_id` / `reply` / `candidates`（后四个按分支出现）；
全量入参/回包见 `docs/01 §3.9`。

> **仍未实测的点（如实标注）**：本机无飞书凭据，上传与发送只在桩测里跑过（`tests/fetch/test_feishu_file_send.py`、
> `tests/rpc/test_channel_file.py`、`tests/channels/test_feishu_file_request.py`）；30 MB / 空文件 / 权限不足
> 三条是**按官方文档与错误码写死**的，没有真撞过平台。

## ④ 当前卡点与拿证后的继续点

**当前只卡在一个前置条件（「用户提供」型，本机无法自行满足）**：

1. **没有自建飞书应用** → 拿不到 `FEISHU_APP_ID` / `FEISHU_APP_SECRET`，长连接就换不到 token、连不上；
   飞书后台的事件订阅权限项也无法逐一核对（对应 1.4 里标 **unknown** 的部分）。
   **（P1）**：自建应用这一步现可由**联网自动建应用**（`feishu.onboard.begin/poll`，方案见 `docs/18 §③`）自动完成并回填凭据；
   离线时仍走手工填。
2. ~~**没有公网可达的回调地址**~~ → **已不再是卡点**：2026-10-14 改走 websocket 长连接后，入站是**本机主动外连**，
   不需要任何公网地址 / 回调 URL / 隧道（这正是选 A 的收益，见 §1.3）。

**用户拿到自建应用后，从哪一步继续**（原 webhook 路线的"再决定是否上 webhook / 选穿透或云主机"两步**整条取消**）：

1. **飞书后台**：按 §3.10 四步建应用、开机器人能力、勾 `im.message.receive_v1`（**不填回调地址**）。
2. **ScholarScout 侧**：`python scripts/scout.py --setup-feishu` 把凭据写进 `.env`（**只写不回读**），
   或手工填 `.env` 后跑 `.venv/Scripts/python.exe scripts/feishu_ws_up.py --check` 自检；
   自检过了就 `.venv/Scripts/python.exe scripts/feishu_ws_up.py` 起长连接，去飞书私聊机器人。
3. **链路其余部分一字不改**：入站核（解析 / 拦截 / `session.ensure` + `chat.send` / 回包）与出站发送器都已落地，
   长连接适配层只负责"收事件 → 归一 → 转交"。
