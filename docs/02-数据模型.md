## 0. 设计原则

1. **库里放摘要，正文落文件，原件留磁盘**（决议 5）
   - `data/raw/` 原件（PDF / HTML）
   - `data/text/` 抽取出的**全文纯文本**（人可 grep、可备份、以后做 RAG 的原料）
   - SQLite 里：出处、**摘要**、会话关联、检索索引 —— **正文不进库、不进 FTS**
2. **可追溯性是第一约束**：任何进入回答的 `source_id` / `doc_id` 都必须能在库里找到，且能反查"它在哪次会话、哪一轮被用到"（`source_mentions`）
3. **索引由触发器维护**，不在应用层手动同步（照 Hermes `state.db` 的做法）
4. **分层规则数据化**：来源权威性来自 `source_tier_rules` 表，不由模型自由心证
5. **摘要版本化**：摘要行带 `prompt_version`（提示词内容哈希），改提示词**不重算历史**（照 AIHOT）
6. **迁移幂等 + 版本化**：`schema_version` + 编号迁移文件，重复执行不报错

## 1. 命名与类型约定

| 约定 | 规则 |
|---|---|
| 主键 | `TEXT`，前缀化短 id：`src_` / `doc_` / `sum_` / `ses_` / `msg_` / `trc_` / `tpm_` / `rte_` / `not_` |
| 时间 | `TEXT`，ISO-8601 带时区，如 `2026-10-05T10:46:00+08:00`（不用 `datetime('now')` 默认值，由应用层统一生成） |
| 布尔 | `INTEGER` 0/1 |
| 结构化字段 | `*_json` = `TEXT`，应用层负责序列化（保持 sqlite3 stdlib 兼容） |
| 外键 | 必须显式声明；连接时 `PRAGMA foreign_keys=ON` |
| 检索 | 只对 `summaries` 与 `messages` 建 FTS5；**正文文件不建索引**（见 §4.3 边界） |

### 3.1 判权结果（M4 新增，迁移 0002）

```sql
CREATE TABLE IF NOT EXISTS source_grades (
  id              TEXT PRIMARY KEY,          -- grd_*
  source_id       TEXT NOT NULL REFERENCES sources(id) ON DELETE CASCADE,
  topic           TEXT,                      -- 判相关性时的主题；空 = 只判权威性
  tier            INTEGER NOT NULL,
  tier_label      TEXT NOT NULL,
  authority       REAL NOT NULL,             -- 0..5，由规则表算出
  relevance       REAL,                      -- 0..5，可为空
  verdict         TEXT NOT NULL CHECK (verdict IN ('核心','相关','外围','排除')),
  matched_rule_id INTEGER REFERENCES source_tier_rules(id) ON DELETE SET NULL,
  signals_json    TEXT,                      -- 命中了哪条规则、主题词覆盖、时效等
  reason          TEXT,
  relevance_source TEXT,                     -- none | local | model
  guard_failed    INTEGER NOT NULL DEFAULT 0,
  model           TEXT,
  prompt_version  TEXT,
  created_at      TEXT NOT NULL
);
```

**为什么判权要单独一张表、而且只追加不覆盖**：

1. 论文要回答"这条判断是怎么来的" —— 命中了哪条规则（`matched_rule_id`）、哪些信号、哪版提示词，都留在行里
2. 换个主题重判会产生**新行**，旧判断不丢；"最新一条"用 `ORDER BY created_at DESC, rowid DESC`（同一秒内的多条必须靠 rowid 兜底）
3. `sources.tier/authority` 只是**反范式化的快照**（列表筛选用），权威记录永远是 `source_grades`

**判定阈值（写进论文，`grading/relevance.py:verdict_for`）**：

| 条件 | 结论 |
|---|---|
| `authority < 1.5` | 排除 |
| `relevance < 2.0`（含"主题词一个都没命中"被压到 ≤1.5） | 排除 |
| `authority >= 4.0` 且 `relevance >= 4.0` | 核心 |
| `relevance >= 3.0` | 相关 |
| 其余 | 外围 |

**权威性公式**：`authority = tier 基准分 × 规则权重`，卡到 0–5。基准分
`{1: 5.0, 2: 4.0, 3: 2.5, 4: 1.0}`（`grading/tiers.py:TIER_BASE_AUTHORITY`）。

**匹配细则**：`url_regex > domain > domain_suffix > source_type`，第一条命中即停。
`domain` 规则**同时认子域**（规则 `nature.com` 命中 `www.nature.com`、`zhihu.com` 命中 `zhuanlan.zhihu.com`）——
这是 E1 评测集跑出来的必改项（docs/05 §3.5）；`domain_suffix` 是纯后缀匹配（`.gov.cn` 与 `.gov` 是两条规则）。

**相关性刻意不使用 tier**（照 AIHOT：分级只用来调门槛，不让"来源名气"污染打分）。
本地打分对中文主题词给**二元组部分credit**（`grading/relevance.py:term_coverage`）：
整体命中记 1，否则按二元组命中比例给分，全不中则一票压到不相关区间。

```sql
  extract_engine TEXT,                    -- local | mineru（agent / precise 记在 extract_detail）| none
  extract_detail TEXT,                    -- 为什么降级/失败（迁移 0004）：如"没有文字层…；failed: model service ..."

CREATE INDEX IF NOT EXISTS idx_documents_sha    ON documents(sha256);
CREATE INDEX IF NOT EXISTS idx_documents_status ON documents(extract_status);
```

**正文的存放规则（重要边界）**

| 内容 | 放哪 | 进 FTS 吗 |
|---|---|---|
| 原始 PDF / HTML | `data/raw/<sha256[:2]>/<sha256>.<ext>` | 否 |
| 抽取出的全文纯文本 | `data/text/<doc_id>.txt` | **否**（决议 6：只检索摘要与会话） |
| 中文标题 / 短摘要 / 要点 | `summaries` 表 | **是** |
| 会话消息 | `messages` 表 | **是** |

## 4.1 检索索引（只有两张 FTS5 表）

```sql
-- 摘要检索（中文标题 + 短摘要 + 要点）
CREATE VIRTUAL TABLE IF NOT EXISTS summaries_fts USING fts5(
  title_zh, summary_short, points_json,
  content='summaries', content_rowid='rowid',
  tokenize='trigram'
);

-- 会话历史检索
CREATE VIRTUAL TABLE IF NOT EXISTS messages_fts USING fts5(
  content,
  content='messages', content_rowid='rowid',
  tokenize='trigram'
);
```

### 为什么用 trigram，以及它的代价（**实测数据，2026-10-05 本机**）

环境：Python 3.11.5 / **SQLite 3.42.0** / FTS5 已编译 / `tokenize='trigram'` 建表成功。

| 查询 | 长度 | 结果 |
|---|---|---|
| `智能体` | 3 | 命中 |
| `教育智` | 3 | 命中 |
| `教育智能体` | 5 | 命中 |
| `Retrieval` | 9 | 命中 |
| **`教育`** | **2** | **❌ 未命中** |

**结论：trigram 的查询必须 ≥ 3 个字符。** 中文双字词（"教育""智能""模型"）是最常见的一类查询，它们走不了 FTS 索引。

**兜底方案（必须实现，否则用户搜"教育"会得到 0 条结果）**：

```sql
-- 查询长度 < 3 时，退化为 LIKE；摘要表本身很短（80-160 字/行），全表扫描成本可接受
SELECT ... FROM summaries WHERE summary_short LIKE '%' || ? || '%' OR title_zh LIKE '%' || ? || '%';
```

落地要求（进 `state/search.py`）：
1. 查询规范化后按字符数分流：`len >= 3` 走 FTS5 MATCH；`len < 3` 走 LIKE
2. 两条路径返回**同一结构**的 `Hit`，上层无感
3. 单测必须覆盖：两字查询有结果（走 LIKE）、三字查询有结果（走 FTS）、两字查询结果与三字包含关系一致
4. 报告里注明当前走的是哪条路径（评测时能区分"检索算法不同"与"真的没有资料"）

> 备选方案（已否决，留档）：二元组切分列 + `unicode61`。它能解决双字词，代价是多一套切分代码与两组索引列。用户 2026-10-05 选择 trigram，理由是「仅检索概要与会话记录即可」，且 LIKE 兜底足以覆盖短摘要场景。

## 4.2 触发器（索引自动同步）

```sql
CREATE TRIGGER IF NOT EXISTS summaries_fts_ai AFTER INSERT ON summaries BEGIN
  INSERT INTO summaries_fts(rowid, title_zh, summary_short, points_json)
  VALUES (new.rowid, new.title_zh, new.summary_short, new.points_json);
END;
CREATE TRIGGER IF NOT EXISTS summaries_fts_ad AFTER DELETE ON summaries BEGIN
  INSERT INTO summaries_fts(summaries_fts, rowid, title_zh, summary_short, points_json)
  VALUES ('delete', old.rowid, old.title_zh, old.summary_short, old.points_json);
END;
CREATE TRIGGER IF NOT EXISTS summaries_fts_au AFTER UPDATE ON summaries BEGIN
  INSERT INTO summaries_fts(summaries_fts, rowid, title_zh, summary_short, points_json)
  VALUES ('delete', old.rowid, old.title_zh, old.summary_short, old.points_json);
  INSERT INTO summaries_fts(rowid, title_zh, summary_short, points_json)
  VALUES (new.rowid, new.title_zh, new.summary_short, new.points_json);
END;

CREATE TRIGGER IF NOT EXISTS messages_fts_ai AFTER INSERT ON messages BEGIN
  INSERT INTO messages_fts(rowid, content) VALUES (new.rowid, new.content);
END;
CREATE TRIGGER IF NOT EXISTS messages_fts_ad AFTER DELETE ON messages BEGIN
  INSERT INTO messages_fts(messages_fts, rowid, content) VALUES ('delete', old.rowid, old.content);
END;
CREATE TRIGGER IF NOT EXISTS messages_fts_au AFTER UPDATE ON messages BEGIN
  INSERT INTO messages_fts(messages_fts, rowid, content) VALUES ('delete', old.rowid, old.content);
  INSERT INTO messages_fts(rowid, content) VALUES (new.rowid, new.content);
END;
```

> 触发器只能搬列，不能调用 Python。摘要的三段文本全部是 `summaries` 表上的实列。

## 7. 摘要（本项目最核心的一张表）

```sql
CREATE TABLE IF NOT EXISTS summaries (
  id              TEXT PRIMARY KEY,       -- sum_*
  doc_id          TEXT NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
  source_id       TEXT NOT NULL REFERENCES sources(id) ON DELETE CASCADE,

  input_chars     INTEGER NOT NULL DEFAULT 0,   -- 实际送进模型的字符数
  input_truncated INTEGER NOT NULL DEFAULT 0,   -- 1 = 正文被截断后才送（照 AIHOT 的 6000）
  degraded        INTEGER NOT NULL DEFAULT 0,   -- 1 = 没拿到正文，只靠元数据出的摘要
  guard_failed    INTEGER NOT NULL DEFAULT 0,   -- 1 = 长度/可溯源守卫未通过但仍然存了
  error           TEXT,
  created_at      TEXT NOT NULL,
```

```sql

-- 抽背「练」模式的账本：按**卡**记，而不是按笔记行记
-- （一行卡片笔记通常有好几张卡 —— `## Q1… ## Q2…`，按行记等于把 10 张压成一个数）
CREATE TABLE IF NOT EXISTS card_reviews (

```

**口径**：`note.stats.recall_rate = good / 评过的卡数`，**没评过的卡不进分母**
（把没练过的算成"不会"，第一轮记住率必然很难看，用户会以为系统在打击他）。

### 8.1 产物版本（`artifact_versions`）

增量修改是"只改几处"，可一旦改错就得能退回去 —— 而路线是花钱生成的。所以每次修改都
**先归档旧版、再把新版写进主表**（`learning.revise_route`）：

```sql
CREATE TABLE IF NOT EXISTS artifact_versions (
  kind         TEXT NOT NULL CHECK (kind IN ('route','map')),
  artifact_id  TEXT NOT NULL,
  version      INTEGER NOT NULL,      -- 被归档的那一版号
  payload_json TEXT NOT NULL,
  note         TEXT,                  -- 这次修改的一句话说明
  created_at   TEXT NOT NULL,
  PRIMARY KEY (kind, artifact_id, version)
);
```

**为什么需要版本表**：增量修改"只改几处"，可一旦改错，用户就没法退回上一版 —— 而路线是花钱生成的。
所以每次修改都**先归档旧版、再把新版写进主表**（`learning.revise_route`），
`learning_routes` 因此多了 `version`（当前版本号，默认 1）与 `updated_at` 两列。

### 8.2 跨轮研究台账（`research_states`，迁移 0010）

多轮调研里"第二轮不知道该看什么"是结构性缺陷，不是模型笨：计划留在消息历史里，
而历史会被 `_fit_history` 裁掉；没有落库的"已搜过什么/还缺什么"，模型只能换词重搜。

```sql
CREATE TABLE IF NOT EXISTS research_states (
  session_id   TEXT PRIMARY KEY,
  payload_json TEXT NOT NULL,   -- {goal, questions[], used_queries[], seen_sources[], empty_rounds}
  updated_at   TEXT NOT NULL
);
```

**口径**（这三条决定了数字可不可信）：

| 字段 | 谁写 | 取不到怎么办 |
|---|---|---|
| `questions[].status` | 模型在回复末尾用状态标记回填（`<!--research-state:{"covered":[1,3]}-->`） | 解析不出来就**保持 open**，绝不猜 |
| `used_queries` | `research.search` **搜成功**后追加 | 搜失败不写（一次网络抖动不能锁死一个方向） |
| `seen_sources` | 每轮把工具返回的 `refs.source_ids` 并进来 | 同上 |
| `empty_rounds` | 连续几次检索没有新增来源 | 有新来源立刻清零（不能提前放弃还有产出的方向） |

台账每轮渲染成一段说明注入到**消息末尾**（不是头部）：放头部会每轮改前缀，
服务端上下文缓存必然不命中（缓存命中与未命中的输入单价差一个量级）。

**用法量记一列**：`usage_records.cached_tokens`（迁移 0009）只记服务端真的报过缓存字段的调用，
没报就留 `NULL` —— 写成 0 会被误读成"缓存全没命中"。

### 8.3 抽背排期（`card_reviews` 扩列，迁移 0011）

间隔重复（SM-2）的排期直接挂在复习记录上，**不另开一张表**：排期是"这张卡最近一次复习结果"
的派生值，分两张表就会出现"复习记录与排期不一致"且没法自证的中间态。

```sql
ALTER TABLE card_reviews ADD COLUMN ease REAL;            -- EF，下限 1.3
ALTER TABLE card_reviews ADD COLUMN interval_days REAL;   -- 当前间隔（天）
ALTER TABLE card_reviews ADD COLUMN streak INTEGER NOT NULL DEFAULT 0;   -- 连续成功次数
ALTER TABLE card_reviews ADD COLUMN lapses INTEGER NOT NULL DEFAULT 0;   -- 答错累计
ALTER TABLE card_reviews ADD COLUMN due_at TEXT;          -- 下次该练的时间；**空 = 到期**
```

口径见 `docs/01 §5.11`（三档 → q 值、EF 公式、答对/答错的间隔规则、`due_at` 为空算到期）。
