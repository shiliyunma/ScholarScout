# Agent 能力提升方案（诊断 → 业界做法 → 候选清单）

> 起因（用户原话，2026-10-07）：
> 「我们的 Agent 在运行时，基本上只有第一轮是有用的……我看回答满不满意，满意生成产物，
> 不满意也只能告诉他继续搜索，这样的过程是相当单一的，并且效果也似乎不理想。
> 去调研一下如何能提升我们的 Agent 的功能性（添加一些有用的功能）以及生成的质量呢
> （包括生成其他内容、产生一些新的界面之列的）？」

本文分四节：**诊断（有真机证据）→ 业界做法（有出处）→ 候选清单（带代价与验证方式）→ 建议顺序**。
每条候选都标了编号（A/B/C…），方便逐条拍板。

---

## 1. 诊断：为什么"只有第一轮有用"

### 1.1 真机证据（`scripts/diagnose_turns.py`，库内 63 条工具轨迹）

| 会话 | 轮次 | 工具调用 | 第 2 轮起重复查询 | 第 2 轮起新发现的来源 |
|---|---|---|---|---|
| 调研一下LLM WIKI | 3 | 11 | 1 | **1** |
| 调查一下openclaw这个 | 2 | 16 | 0 | 3 |
| 新调研 | 2 | 14 | 2 | **0** |

- 3 个多轮会话里 **2 个（67%）**在第 2 轮起出现重复查询（判据：与之前查询的二字符组 Jaccard ≥ 0.6）；
- 「新调研」第 2 轮**一个来源都没新增** —— 14 次工具调用基本是重复检索 + 存笔记；
- 「调研一下LLM WIKI」三轮的查询几乎都指向**同一文档家族**（Karpathy 的 llm-wiki gist）：
  第 1 轮 `LLM Wiki` / `LLM wiki knowledge base automatic wiki generation` /
  `Karpathy LLM wiki pattern`，第 2 轮 `Karpathy llm-wiki methodology original document`，
  第 3 轮 `Karpathy llm-wiki knowledge base markdown` / `LLM wiki persistent knowledge base instead of RAG` /
  `Karpathy llm-wiki.md gist original methodology document` —— **换词，不换靶**。
- 顺带查出两个小缺口：`tool_traces.message_id` **全是空的**（轨迹无法关联到具体消息，只能靠时间戳），
  `result_digest` 里**不含 id**（于是"这轮发现了哪些新来源"只能从 `source_mentions` 反查）。

> 样本只有 3 个多轮会话 —— 这是**方向性证据**，不足以下统计结论；但和用户的体感一致，值得当依据。

### 1.2 代码定位（为什么会这样）

| 机制现状 | 位置 | 后果 |
|---|---|---|
| 一个 turn 内跑 ReAct 循环，最多约 10 次工具调用，**没有跨轮的目标/计划状态** | `runtime/loop.py` | 第 2 轮只带着"消息历史"重新开始，意图靠模型每次现推 |
| 系统提示词把流程写成**固定顺序**（search → fetch → grade → build_map → plan → notes） | `runtime/prompts.py` | 第 2 轮"继续搜索"自然回到同一步：再 search 一遍，不会换策略 |
| **没有覆盖度/缺口概念**：库里知道有哪些来源，但没有任何东西告诉模型"还缺什么子问题/哪一年/哪类来源" | 无 | 于是"继续"＝同质重复，无法收敛 |
| 用户的"不满意"是**自由文本**，没有把它结构化成可执行计划的地方 | 无 | 「继续搜索」只能被理解成"再搜一次" |
| 历史超长会被裁剪（`runtime.max_history_chars`，默认 12000） | `runtime/loop.py` | 第 1 轮的关键细节可能在后面几轮被裁掉，agent 想接着用也拿不到 |
| 产物只有 4 种（知识地图/路线/抽背卡/笔记），且**大多整条重生成**（路线已有增量修改，地图/笔记还没有） | 工具层 | 用户能"看"的界面少，能"操作"的产物更少 |
| 工具集里没有"读自己已有产物"的入口（如 `route.get` / `topic.get` 只在界面用） | 工具层 | agent 不知道自己上一轮产出了什么，容易前后重复 |

**一句话**：现在的循环是"每轮从零现推意图 → 按固定顺序搜一遍 → 出结论"，
**缺少三样东西**：① 显式的跨轮研究状态（目标/子问题/证据）；② 用证据缺口驱动下一步的机制；
③ 让用户能"操作产物"而不只是"读回答"的界面。

## 3. 候选清单（带代价与验证方式）

> 分档：**A＝马上可做（小时级，无新依赖）**、**B＝中期（天级，仍是现有栈）**、**C＝大改（需要新依赖/新架构）**。
> 每条都给：解决 1.2 里哪一个缺口 / 怎么做 / 代价（token·时延·依赖） / 怎么验证 / 风险。

### A 档（马上可做）

| # | 做什么 | 解决哪个缺口 | 代价 | 验证方式 |
|---|---|---|---|---|
| **A1** | **研究档案（research state）落库**：每轮把"目标 / 已确认结论 / 待解子问题 / 已用证据"写成一条结构化记录，下一轮开头注入（而不是重发全部历史） | 跨轮没状态 | 每轮多 1 次小模型调用（产/更）或纯本地规则更新；省下的历史重发反而省钱 | 同一目标连问 3 轮，第 2/3 轮的查询与第 1 轮**不重复**（用 `diagnose_turns.py` 复测） |
| **A2** | **缺口驱动检索**：本地先算覆盖缺口（缺哪一年/哪类来源/哪个子问题没有摘要），把它作为**必须回答的清单**塞进第 2 轮的提示词 | 没有缺口概念 | 纯本地计算 + 提示词加几行（≈ +200 字符/轮） | 「继续搜索」后再无新来源＝失败；要求该轮至少新增 N 条来源且命中缺口 |
| **A3** | **查询去重闸门**：`research.search` 在工具层拒掉"与本次会话已搜过的查询高度相似"的请求，并**回一句提示**（"这个已搜过，换角度或换来源"） | 原地打转 | 零模型成本（本地判重） | 用现有 3 个多轮会话回放：重复查询应被拦下并改写 |
| **A4** | **产物读回工具**：给模型 `route.get` / `topic.get` / `note.list` 的读取能力（只读、无成本） | agent 不知道自己产出过什么 | 工具声明 +约 300 字符/次调用（可只在该会话已有产物时挂上） | 第 2 轮说"在上一版路线上继续"，模型应先读再改 |
| **A5** | **把"不满意"结构化**：界面上把自由文本换成可点选维度（缺深度 / 缺来源 / 缺对比 / 想换角度 / 想动手做），点选后拼成一句结构化指令 | 反馈不可执行 | 纯前端 + 提示词模板 | 点不同维度后，第 2 轮的工具构成应不同（现在三轮几乎一样） |

### B 档（中期）

| # | 做什么 | 解决哪个缺口 | 代价 | 验证方式 |
|---|---|---|---|---|
| **B1** | **子问题分解 + 逐条收敛**：把目标拆成 3–6 个子问题（带编号），每条标注"有无证据"，每轮只解决未收敛的条目 | 没有计划 | 1 次分解调用 + 每轮按缺口检索 | 子问题收敛率；到第 3 轮仍未收敛的条目要能被解释 |
| **B2** | **证据表（evidence table）产物**：把「结论 — 支撑来源 — 证据强度（有摘要/仅标题） — 年份」做成一张可点开的表；用户可直接看到哪条结论弱 | 界面单一 + 弱证据不可见 | 纯本地从库生成（复用 `support_checks`） | 表里每条结论可点到来源；弱证据条数可见 |
| **B3** | **对比矩阵产物**：给定 N 个对象 × M 个维度（论文/系统/框架），从已入库资料填表，空格＝没证据 | 生成"其他内容" | 1 次模型调用 + 本地校验（空格不许编） | 空格率、编造检出率 |
| **B4** | **时间线产物**：把某方向的关键节点按年排出来（论文/版本/里程碑） | 生成"其他内容" | 1 次模型调用 + 本地按年份校验 | 时间线里的年份必须能在库里找到出处 |
| **B5** | **产物迭代扩展到地图/笔记**（把 `route.revise` 的补丁机制推广） | 产物只能重生成 | 复用已有补丁引擎，加 2 个工具 | 改一处后未被点到的部分逐字节不变 |
| **B6** | **抽背卡的间隔重复**（SM-2/FSRS）：按复习记录排下次复习时间，界面显示"今天该练的 N 张" | 学习闭环不完整 | 纯本地算法 + 一张表 | 复习队列符合算法；到期卡数可核对 |
| **B7** | **研究看板界面**：把 子问题 / 证据 / 结论 / 产物 排成一个可点开的板子（右栏新增页签） | 过程不可见、交互单一 | 纯前端 + 1 个只读 RPC | 真机截图；板子上每个格子可溯源 |

### C 档（大改）

| # | 做什么 | 代价 / 风险 |
|---|---|---|
| **C1** | 多智能体编排（检索员 / 分析员 / 审稿员分工），像 Hermes 的 delegate 那样并行子代理 | 需要并发子进程与预算控制；成本成倍；对本机是负担 —— 需要先论证收益 |
| **C2** | 本地全文检索/向量检索（把已抓全文做索引，支持"在我已收集的资料里检索"） | 需要嵌入模型或本地索引（新依赖/新模型），与"正文不入库"的既有决议冲突，需重新拍板 |
| **C3** | 报表级导出（PDF/docx/静态站点） | docx 已有脚本可复用；PDF 需要额外依赖或走打印路径 |

---

## 4. 建议顺序

1. **先做 A1 + A2 + A3**（"让第 2 轮真的有新信息"）—— 这是痛点正中心，且几乎零成本；
2. **再做 A5 + A4**（用户能结构化表达不满 + agent 能读回产物）—— 让交互不再只有"继续搜索"；
3. **然后 B2 / B3 / B7**（新产物 + 新界面，直接回应"生成其他内容和界面"）；
4. B5 / B6 与 C 档按兴趣排。

每条都用 `scripts/diagnose_turns.py` 的**同一口径**复测（重复查询数、每轮新增来源数），
避免"感觉变好了"。
