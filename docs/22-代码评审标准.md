# 22 · 代码评审标准（双轴）

> 来源：`matt-engineering-skills` → `code-review`（双轴评审）。本文把它**落成可执行标准**，并根据本仓库
> 的实际历史补「触发点」与「已知陷阱」两节。
> **本文不复制仓库规则** —— `AGENTS.md`、`docs/项目规则.md`、`docs/03` 才是规则本体；本文只规定**怎么审**。

---

## 0. 一句话

一次评审 = 对**同一个基准**做**两条互不污染**的检查：**Standards**（守不守本仓库写下来的规矩）与
**Spec**（做没做对需求）。两轴**分开报、不合并、不排序** —— 代码可以完全合规但做错事，也可以做对事但违纪。

---

## 1. 先钉基准

| 情况 | 基准 |
|---|---|
| 审一个分支 / PR / 一次批量改动 | `git diff <fixed-point>...HEAD`（**三点**，对 merge-base 比） |
| 审仓库当前全量状态（不按 diff） | 基准 = `HEAD`；**Standards 轴全量扫**，Spec 轴对照契约文档 |

开工前必须验证：`git rev-parse <ref>` 能解析、diff **非空**。基准无效或空 diff 要**在开审前就报错**，
不能拖到两条子评审里去发现。

---

## 2. 两条轴（并行、互不污染）

| 轴 | 回答什么 | 依据 |
|---|---|---|
| **Standards** | 这段代码**守不守**本仓库文档化的编码标准？ | `AGENTS.md`、`docs/项目规则.md`、`docs/03`、`scripts/check.sh`、`deps-allowlist.txt`、`pyproject.toml` |
| **Spec** | 这段代码**做没做对**需求？ | 契约文档（`docs/01/02/17/19/20/21`）+ 用户逐字下达的硬要求 |

两条轴**各起一个独立评审**（Hermes：`delegate_task` 两路并行），各自返回报告，最后**并列贴出**。

**禁止**：把两轴结论合成为"总分"、跨轴挑一个"最严重"、为了让报告好看而重排条目。两轴的意义就是防止
一轴掩盖另一轴。

---

## 3. Standards 轴

### 3.1 标准来源（按优先级）

1. `AGENTS.md` / `docs/项目规则.md`（最高）
2. `docs/03-目录结构与规则文件.md`（分层、目录、禁越层）
3. `scripts/check.sh` 的八项门禁（**它查的，评审里不要再查**）
4. `deps-allowlist.txt`（依赖白名单）
5. `pyproject.toml` 的 ruff / mypy 配置
6. 以上都没有写的地方 → 才落到下面的**味道基线**

### 3.2 三条应用铁律

1. **仓库标准优先于基线**：仓库文档明确认可的做法，即使基线会挑刺，也**压掉**。
2. **基线永远是判断**：写法是"**疑似** Feature Envy"，不是"违规"。给证据，不定罪。
3. **工具已强制的跳过**：ruff / mypy / pytest / 门禁能抓的（格式、类型、未用导入、测试红），评审里**不报** ——
   报了只是噪音。

### 3.3 味道基线（Fowler《重构》第 3 章）

| 味道 | 它是什么 | 怎么修 | 本仓库已知触发点 |
|---|---|---|---|
| **Mysterious Name** | 函数/变量/类型名不揭示它做什么、装什么 | 改名；起不出诚实的名字 = 设计浑 | `tests/desktop/test_turn_spinner.py` 的 `probe`（135 行） |
| **Duplicated Code** | 同一逻辑形状散在多处 | 抽出共享形状，两边调用 | `"ok": False` 信封 47 处 / 16 文件；`tools/source_fetch.py` 重复注释 |
| **Feature Envy** | 方法过度伸手进别人的数据 | 把方法移到它嫉妒的数据上 | 待查 |
| **Data Clumps** | 几个字段/参数总是一起旅行 | 捆成一个类型 | 待查 |
| **Primitive Obsession** | 原始类型/字符串顶替一个领域概念 | 给这个概念一个小类型 | 同上：结果信封没有类型 |
| **Repeated Switches** | 同一类型上的 switch/if 级联在多处重复 | 多态，或共享一张映射 | `learning/route_patch.py:109 apply_ops` |
| **Shotgun Surgery** | 一个逻辑改动逼你散点改很多文件 | 把一起变的东西聚到一个模块 | 待查 |
| **Divergent Change** | 一个文件因几个无关原因被改 | 拆开，一个模块只因一个原因变 | `runtime/loop.py:248 run_turn`（**475 行**，2026-10-19 实测；原始评审时 453）、`settings_io.py`（混着 data_usage/cleanup/optimize） |
| **Speculative Generality** | 为不存在的需求加抽象/参数/钩子 | 删掉，直到真需要 | `settings_io.py:102 _f(*path, **kwargs)` |
| **Message Chains** | 长链 `a.b().c().d()` | 藏在第一个对象的一个方法后面 | 待查 |
| **Middle Man** | 类/函数主要只是转发 | 砍掉，直接调真目标 | 待查 |
| **Refused Bequest** | 子类忽略/覆盖了继承来的大部分 | 改组合 | 待查 |

---

## 4. Spec 轴

### 4.1 spec 从哪来（按序）

1. commit message 里的 issue 引用（`#123`、`Closes #45`）；
2. 调用方直接给的文件路径；
3. `docs/` 下与本次改动对应的契约/设计文档；
4. 都没有 → **先问**。问不到就跳过 Spec 轴，并在报告里写明"无 spec 可比"。

### 4.2 三类必须报的偏差

| 类型 | 定义 | 为什么重要 |
|---|---|---|
| **缺失 / 半成品** | spec 要求了，代码没有或只做一半 | 最常见的"以为做了" |
| **超出 spec** | 代码有、spec 没写 | 可能是好的增量，但**必须**回填文档，否则下次评审无从判断 |
| **实现了但不对** | 看着做了，实际与 spec 冲突 | **最危险**：测试可能全绿，行为却相反 |

每条 finding **必须引用 spec 原文**（哪份文件、哪一句/哪一条），并给出代码位置。

---

## 5. 输出格式

按轴分节，**不合并**：

```
## Standards
硬违规（引用规则 + file:line）
判断性问题（味道名 + 片段 + 一句修法）
一句话：几条硬违规 / 几条判断 / 最严重那条

## Spec
缺失 / 超出 / 不一致（各带 spec 位置 + 代码位置）
一句话：三类各几条 / 最严重那条
```

每轴控制在 **400 字以内**（表格可略超）。末尾给**每轴各一句**总结，**不跨轴选冠军**。

## 6. 本仓库的落地约定（Hermes）

- 两轴用 `delegate_task` **并行**两路；提示词里要把**味道基线全文**贴给 Standards 那一路（它没有别的来源）。
- 门禁（`scripts/check.sh` 八项）**已经**覆盖 lint/format/types/tests/rules-sync/deps-approval/ui-assets/code-map ——
  评审里不要重复，只审它**抓不到**的东西（分层、职责、命名、静默吞错、文档一致性）。
- 评审**只读**：禁改文件、禁提交。清单先出，用户挑完了再动手。
- 审完的清单落盘（`docs/评审-*.md`），别只留在对话里。

## 7. 已知陷阱（本仓库踩过的，写进标准免得再踩）

1. **守卫会悄悄失效**：`_between(a, b)` 里若结束锚点排在起始锚点**之前**，切片退化成取几千字符，
   守卫就再也拦不住新代码。写守卫时**必须**有一条"反例必须红"的用例。
2. **"改完没跑"等于没改**：今天有两轮测试是"声称修了、其实没复跑"→ 门禁红。
   任何"修好了"必须附**单跑 + 整目录复跑**的输出。
3. **不要用 `sleep` 断时序**：Windows 的计时粒度会让断言变成空判。用 `Barrier` / `Event`，
   并用"注入对端延迟"证明不是靠运气绿。
4. **测试的假绿比假红更贵**：多条用例共用一份 spy，后一条清空前一条的记录 → 同时制造假红与假绿。
   共享状态必须显式 `reset`，或干脆串行。
5. **"声明的总数"是硬断言**：报告里写"共 N 条"时，要能被数出来；数不上就对不上，不能糊。
