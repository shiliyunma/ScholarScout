## §1 一句话结论与现状盘点

**一句话**：**凭据、开关、状态、白名单、配对审批、测试、引导页**这七件事全部可以收进桌面应用；
**真正做不了的是"替人点平台后台"** —— 飞书重置 App Secret / 开机器人能力 / 勾事件 / 发布，
QQ 建应用 / 认证 / 发布 / **把机器人拉进群** / **群主授予主动消息权限**，微信的**扫码登录本身**。
这些一律走"**应用内逐条引导 + 可点深链**"（§2 逐条给了出处），不假装能自动化。

### 2.1 飞书（自建应用）

| # | 问题 | 结论 | 出处 / 核实方式 |

| F1 | **重置 App Secret 有没有 API？** | ❌ **没有**。只能登录开发者后台 → 应用详情 → 「凭证与基础信息」页人工重置 | **核实方式**：本机依赖 `lark_oapi 1.7.4` 的 `api/application/v6/resource/` 目录里只有 `application.py`（`get`/`list`/`patch`/`underauditlist`）、`application_management.py`（`update`）、`application_app_version.py`、`bot.py`、`scope.py`、`owner.py`、`collaborators.py`、`visibility.py`、`contacts_range.py`、`app_badge.py`、`app_recommend_rule.py`、`feedback.py`、`app_usage.py` —— **没有任何 secret / reset 端点**（对整棵 `api/application/` 树搜 `app_secret`、`/secret`、`reset` = 0 命中）。官方后台入口：<https://open.feishu.cn/app>。**结论**：应用内能做的只有**深链 + 步骤引导**，这一点正好满足用户"不想进某个文件夹里改"的诉求 |

| F3 | **开机器人能力 / 勾事件订阅 / 勾权限 / 发布版本 / 发布应用 能否 API？** | ❌ **都不能**（自建应用侧） | `docs/17 §3.10` 与 `docs/18 §④` 已核（项目结论：这四步"只能在飞书开发者后台人工点"）；补充核实：本机 Hermes 的飞书适配器**也没有任何**程序化调用后台的代码 —— 对 `adapter.py` 搜 `open-apis/application`、`/app_secret`、`reset_secret` = **0 命中**（即"连 Hermes 都替代不了"）。官方文档入口：<https://open.feishu.cn/document/> |
| F4 | **长连接的连接 / 断开能否程序控制？** | 连接 **✅ 能**；断开 **❌ 不能**（无公开接口，真实语义是"进程退出即断开"） | 本机 `lark_oapi 1.7.4` 的 `ws/client.py`：**公开方法只有 `start()`**（`:164`）；`_disconnect()` / `_reconnect()` 都是**私有**（`:361` 起）。**意外收获**：SDK 留了两个**公开状态钩子** `on_reconnecting` / `on_reconnected`（`:160-161`，`_fire_on_reconnected` 在 `:392`）→ 正好当**连接健康检查**的信号源（§3 第 3 项）。取舍详见 `docs/17 §3.8` |
| F5 | 群主动消息能不能发？ | **平台允许**（机器人已在群内且有发消息权限即可）；**本项目口径是"只私聊不发群"**（`docs/20 §6.3`）——这是**项目决策，不是平台硬限**，如实区分 | `docs/17 §3.7`（出站走 `POST /open-apis/im/v1/messages`）、`docs/20 §6.3` |

### 2.2 微信（iLink Bot API）

> **前提如实说明**：iLink 是腾讯 2026-03 前后推出的**官方**微信机器人通道（第三方材料称需签《微信 ClawBot 功能使用条款》）；
> **本机没有找到可稳定引用的官方规范文档 URL** → 下面凡标 ③ 的都是二手材料，**只描述"实际怎么用"**，不当平台承诺。

| # | 问题 | 结论 | 出处 |
|---|---|---|---|
| W1 | **凭据获取是否只能扫码？** | ✅ **只能扫码**（二维码登录）：SDK 侧 `await bot.login()` 显示二维码 → 微信扫 → 机器人上线；凭据由服务端在扫码后下发并被 SDK 持久化（"凭证自动保存，会话自动恢复"）。**没有"填 AppID/Secret 就上线"这条路** | ③ <https://www.wechatbot.dev/>（iLink Bot SDK 文档原文："`await bot.login() // 显示二维码 → 微信扫码`"、"在微信中扫描二维码 → 机器人上线。凭证自动保存，会话自动恢复"、共享能力列表含"二维码登录 / 长轮询 / context_token 管理"）；③ <https://cloud.tencent.com/developer/article/2729953>（"点击连接后，系统弹出二维码。用同一个微信扫这个码 → 同意授权『ClawBot 功能』"）。**官方 iLink 规范 URL：unknown** |
| W2 | **能否程序化续期？** | ⚠️ **只能部分**：`context_token` 需**每 24h 由用户给 bot 主动发一条消息**才能续；SDK 的"会话自动恢复"只解决"凭证还在磁盘上" | ③ 腾讯云开发者社区文章（"iLink 的协议要求 每个用户每 24h 至少给 bot 主动发一条消息 才能续『context_token』配额"）。**官方口径 unknown** → 落到设计上：我们只能做**倒计时提醒 + 一键引导**，做不了全自动（§3 第 3 项） |
| W3 | **会话过期怎么处理？** | ❌ **无自动重扫 API**：过期即需**人在手机微信里再扫一次码**；`bot_id` 与微信 openid **1:1 写死在腾讯侧**，换微信号 = 重走扫码流程 | ③ 同上（"bot_id 绑定不可恢复……换微信号 = 重新走一遍扫码流程"）。设计含义：**二维码必须在桌面应用里能显示出来**（§3 第 8 项），否则用户就要回到命令行 —— 这正是用户要避免的 |
| W4 | 主动推送有配额吗？ | ⚠️ 有：称"每位用户 24 小时内最多 10 条主动推送"，超出后接口返回 **429**（被动回复不计） | ③ 同上。设计含义：`docs/20 §6.3` 的"轮次完成提醒"在微信上**必须降频/合并**，不能每条都推 |

### 2.3 QQ（QQ 机器人开放平台 / bot.q.qq.com）

| # | 问题 | 结论 | 出处（官方文档，均为本机 curl 抓到的原文） |
|---|---|---|---|
| Q1 | **建应用 / 主体认证 / 发布（公开服务）能否 API？** | ❌ **不能**：全部在 QQ 开放平台网页管理端完成 | 官方 FAQ <https://bot.q.qq.com/wiki/bot_FAQ/>：「如何进入 QQ Bot 管理端创建机器人」= 登录 QQ 开放平台、**认证主体后，在机器人入口进入管理端**；「旧版管理端机器人提交上架审核」= 旧版已停审，**改用新版 QQ Bot 管理端**设置"使用的范围"；「机器人提示可添加群聊已满」给出认证分级（**未认证**：机器人仅管理员使用，只能加到管理员自己是群主的群；**个人认证**：可设公开使用，进群上限 **500**；**企业认证**：所有场景） |
| Q2 | **开 intents 能否 API？** | ✅ **不需要 API**（intents 是**建连时**用位掩码声明的，不是后台申请）；但 **❌ 部分 intent 受权限限制，改不了** | 官方文档 <https://bot.q.qq.com/wiki/develop/api-v2/dev-prepare/event-emit/websocket.html>：Identify 报文原文 `{"op":2,"d":{"token":"QQBot {AccessToken}","intents":513,"shard":[0,1],...}}`；同页 WebSocket 错误码表含 **4013 无效的 intent**、**4014 intent 无权限**、**4914 机器人已下架，只允许连接沙箱环境**、4915 机器人已封禁 |
| Q3 | **拉机器人进群能否 API？** | ❌ **不能**。官方路径就是"**升到最新版移动 QQ，由群主/管理员添加**"。API 侧只有**生成分享链接**与**查询状态**，没有"把我加进这个群"的接口 | ① 官方 FAQ <https://bot.q.qq.com/wiki/bot_FAQ/>：「机器人如何公开添加进群、频道」= 企业主体公开使用已开放、个人主体陆续开放中，**个人主体如需添加群聊，机器人创建者仅可添加自己是群主/管理员的群聊（升级最新版移动 QQ 添加）**；② 唯一可程序化的相关接口：`POST /v2/generate_url_link` **生成机器人分享链接**，官方描述用途是"**邀请用户添加机器人为好友**"，回 `{"data":{"url":"https://qun.qq.com/qunpro/robot/qunshare?robot_appid=...&robot_uin=...&data=xxx"}}`（<https://bot.q.qq.com/wiki/develop/api-v2/autogen/api/v2_generate_url_link.post.html>）；③ 群聊管理侧只有 `GET /v2/groups/{group_openid}/bot_state`（机器人状态）、`GET /v2/groups/{group_openid}/join_request_list` + `POST .../approval_join_request`（**审批别人**入群）；④ 发送群消息页错误码表给出 **40034101 / 40054003「机器人非群成员 请先将机器人加入群聊」**（<https://bot.q.qq.com/wiki/develop/api-v2/autogen/api/v2_groups_group_openid_messages.post.html>） |
| Q4 | **群主动消息是否必须在后台申请？（40034105）** | ⚠️ **不是在后台填工单申请，而是"群主在 QQ 客户端点机器人开权限"**；权限没开时 API 直接回 **40034105** | ① 官方 FAQ <https://bot.q.qq.com/wiki/bot_FAQ/>：「在群里@机器人不回复，但私聊可以（**机器人在群中主动发送消息失败**）」= 升级最新版手机 QQ，**添加机器人入群时群主在群中或成员列表里点击机器人，进行权限设置**：①接收全量消息能力 ②**主动推送消息能力**（"如定时任务推送等"）③机器人撤回成员消息能力（需设为群管理员）；② 错误码原文（发送群聊消息页）：**40034105 主动消息发送失败，无权限 请检查机器人权限设置**；同页还有 **40034100 主动消息发送超过频控限制**、40034027「该事件不支持回复消息」、40034128「被动回复时间或次数超限」；③ 频控（官方 <https://bot.q.qq.com/wiki/develop/api-v2/server-inter/message/overview.html>）：群主动消息 **Bot 维度 企业/个人认证 60/qpm、未认证 30/qpm**，单关系 20/qpm，**每群每天上限 1000 条**；被动回复**有效期 5 分钟、每条最多回复 5 次**；④ 审核环节确实存在：同页原文"**有关主动消息审核，可以通过 事件订阅 Intents 中审核事件 MESSAGE_AUDIT 返回 MessageAudited 对象获取结果**" |
| Q5 | **群 openid 怎么拿？** | **从群消息事件里带回来**：`GROUP_AT_MESSAGE_CREATE` / `GROUP_MESSAGE_CREATE` 的报文里含 `group_openid`；发送用 `POST /v2/groups/{group_openid}/messages`。**官方 API 侧没有"机器人群列表"接口**（"机器人"分组只有 `GET /users/@me`、`GET /users/@me/guilds`（**频道**列表）、`POST /v2/generate_url_link`） | 官方文档 <https://bot.q.qq.com/wiki/develop/api-v2/server-inter/message/overview.html> 的"收发场景"表（QQ 群聊：接收事件 `GROUP_AT_MESSAGE_CREATE` / `GROUP_MESSAGE_CREATE`）；群消息接口路径见发送群聊消息页；"没有群列表接口"是**本机核对官方文档侧边栏（站点 v1.36.0 的 JS 配置）**得出的：`群聊管理` 分组只有群信息/机器人状态/入群申请/入群自动审批/群成员管理/撤回，`机器人` 分组只有 `users_me` / `users_me_guilds` / 生成分享链接 / 菜单指令面板 —— **标"据官方文档目录推断"，不是平台承诺**。设计含义：**群台账只能"第一次收到该群消息时登记"**（§5.3） |

### 2.4 硬限总表（"哪些点不了、应用只能替你做什么"）

| 人工动作 | 平台 | 应用内能给什么 |
|---|---|---|
| 重置 App Secret | 飞书 | **深链** <https://open.feishu.cn/app> + 步骤说明；改完回应用里重填（只写不回读） |
| 开机器人能力 / 勾 `im.message.receive_v1` / 发布版本 | 飞书 | 引导页逐条勾选表 + 深链（F3） |
| 扫码登录（必须人扫） | 微信 | **在应用里显示二维码** + 倒计时 + 过期自动刷新 + 重扫引导（W1/W3） |
| 每 24h 给 bot 发一条消息续 context_token | 微信 | 倒计时提醒 +"去发一条"引导（W2）；**不能代替人发** |
| 建应用 / 认证 / 发布公开服务 | QQ | 引导页 + 深链 <https://q.qq.com/> |
| **把机器人加进群**（移动 QQ，群主操作） | QQ | 生成分享链接（`/v2/generate_url_link`）+ **"未进群"状态灯**（`bot_state` / 40034101 的实时提示） |
| **群主开"主动推送消息能力"** | QQ | 该群卡片上一行"主动消息：未授权（40034105）"+ 告诉群主点哪里（Q4 原文） |

| # | 能力 | UI 明细（用什么控件 / 显示什么） |
|---|---|---|
| 1 | **凭据填写（只写不回读）** | `.set-row` 里两个输入框（App ID / App Secret，`type=password`）+ 「保存」；保存后**只显示**"已配置 ✅ / 未配置 ⬜"（服务端只回 `app_id_set` / `secret_set` 两个布尔，**连尾号都不回**）。**绝不回显任何片段**（沿用 `profile.js::paintStatus` 的布尔口径） |
| 2 | **渠道开关（启动 / 停止）** | 每个平台卡片头一行：状态点（`--ui-green` 运行 / `--ui-yellow` 连接中 / `--ui-red` 错误 / `--ui-text-tertiary` 停止）+「启动」「停止」两个按钮；**没有在跑时点停止 → 明确提示"当前未运行"**（不假装成功，照 `chat.cancel` 的既有铁律） |
| 3 | **连接状态与健康检查** | 只读状态行：`连接：长连已建立 / 重连中 / 未连接`（飞书用 `on_reconnecting`/`on_reconnected` 钩子，F4）、`最后一条消息：3 分钟前（群：…）`、`最后一次错误：40034105 主动消息无权限`、`重连次数：2`；底部一条「自检」按钮 = `channel.test`（发一条测试消息或只探测凭据），回 `{ok, latency_ms, bot_name, error}` |
| 4 | **白名单与配对审批（一键放行）** | `.set-row` 列表：待批（码的**倒计时** + 来源名 + `user_id` 尾号）→「放行」/「忽略」；已放行列表 → 「撤销」；顶部三选一策略（`pairing` / `all` / `allowlist`）。复用已有 `feishu.pairing.*`，泛化成 `channel.pairing_*` |
| 5 | **每群绑模块（`channel_prompts`）** | 表格：`平台 / 会话名 / 会话 id（尾号）/ 模块（下拉：research / kb / 默认）`；新增行由"首次收到该群消息"时自动登记（§5.3）。**模块只作为 `chat.send` 的 `toolsets` 运行时参数**，不注入系统提示（§8 哈希那条） |
| 6 | **发测试消息** | 「发测试消息」按钮 + 目标（home chat / 指定 chat_id）+ 结果行（成功给 `message_id` 尾号，失败给**平台原始错误码 + 中文解释**，如 40034105） |
| 7 | **逐条人工步骤引导页 + 可点后台深链** | 每平台一段有序清单（勾选状态由后端探测决定：凭据有没有 / SDK 在不在 / 连没连上 / 白名单空不空），每步末尾一个**深链按钮**（飞书后台、QQ 管理端、微信二维码）。**飞书那四步的文案直接沿用 `docs/17 §3.10`**（且不出现"填回调地址"） |
| 8 | **二维码展示区（微信专用）** | 卡片里一块**可滚动的等宽二维码渲染区**（在应用窗口里显示，不让用户回命令行）+「已扫码」状态 +「重新生成」。iLink 只能扫码（W1），所以"把二维码画在应用里"是**必需项**而不是增强 |

**不做**（明确排除，避免膨胀）：渠道消息的**完整历史浏览**（消息本来就落 `messages`，去会话里看）、渠道级**模型/预算独立设置**（沿用 §5 的全局设置）、**多账号**（单用户单账号）。

## §4 进程模型（取舍 + 建议）

**问题**：渠道跑在桌面应用**进程内**（线程），还是**独立子进程**（关窗仍收消息）？

| | **A：进程内（`desktop/` 里起线程）** | **B：独立子进程（supervisor 模式，建议）** |
|---|---|---|
| 关窗后 | ❌ **立刻断**：飞书长连断、微信若用的是长轮询也会停、QQ WS 断 | ✅ **继续收**（应用退成"窗口关了但 supervisor 还活着"或托盘模式） |
| 微信/QQ 的"贵动作" | 断线重连/重扫码的代价直接落到用户头上（微信 24h 内要续 context_token，掉太久可能重扫） | 会话可长期保活，扫码一次用很久（W1–W3 的直接收益） |
| 崩溃隔离 | ❌ 一个平台的 SDK 抛异常有可能带崩整个应用（`docs/17 §3.8` 已踩过"回调抛异常让整条链路静默失聪"） | ✅ 渠道进程炸了自动重启，UI 与其它渠道不受影响 |
| 装配成本 | 最省：直接用 `AppContext`，零 IPC | 要管 pid、日志、退出回收；渠道进程必须**经 RPC** 跟主进程说话 |
| 与 `docs/20` 的写库纪律 | 天然合规（进程内单写连接） | ⚠️ **必须让渠道进程当 RPC 客户端、不自己开库**（否则又变成多进程写 SQLite） |
| 复用现成件 | — | ✅ 已有同构先例：`desktop/rpc_client.py`（子进程 + 一行一 JSON，按 id 配对）+ `python -m scholarscout --rpc` |

**建议：B（独立子进程 + 主进程当 supervisor）**，三条理由：
1. **用户的目标是"日常操作全在应用里"，而渠道的价值恰好在"应用不在前台时也在收"** —— A 会让"关窗"等于"离线"，把最贵的一次性动作（扫码/重连）反复还给用户；
2. **失败隔离是硬需求**：`channels/` 已有的纪律是"回调绝不外抛"，但那是代码纪律；进程隔离是**机制保证**；
3. **零新依赖、零新范式**：子进程 + 一行一 JSON 本项目已有（`rpc_client.py` / `--rpc`），渠道进程只是**第二个同类客户端**。

**代价（照实写）**：多一层 IPC（UI 看到的状态来自渠道进程，晚一个心跳）；多一类要管的生命周期（pid 文件落 `run/channels/<platform>.pid`、日志落 `run/channels/<platform>.log`、`stop` 要能精准停 —— 照 `docs/17 §3.9` 用 PID 精准停，Windows 下 `MSYS_NO_PATHCONV=1 taskkill /F /PID`）；
以及**"关窗"语义要重新定**：建议"关窗 = 应用退到托盘/后台，渠道继续跑"，并在设置里给一个明确的「退出应用时也停止渠道」开关（默认**不停**）。

create table if not exists channel_prompts (

### 7.2 各平台的人工步骤清单（写进引导页，逐字可照做）

- **飞书**（沿用 `docs/17 §3.10`，**不出现"填回调地址"**）：① 建「自建应用」→ 拿 App ID/App Secret；② 开启「机器人」能力；③ 事件订阅勾 **`im.message.receive_v1`**；④ **不需要填回调地址**（长连接由本机主动外连）。
  - **要发文件再加两个权限（`docs/17 §3.12`）**：上传要 **`im:resource`**（或 `im:resource:upload`），发送要 **`im:message`**（或 `im:message:send_as_bot`）。
    **只勾一个必在另一半失败**（上传成功、发送被拒 → 用户看到"上传了但没收到文件"）；勾完还要**发布版本**才生效。
- **微信**：① 在应用里点「扫码登录」→ 用本人微信扫应用里显示的二维码 → 手机端同意授权（首次必须手机确认）；② （每天）给 bot 主动发一条消息以续 `context_token`（应用给倒计时提醒，**不能替用户发**）。
- **QQ**：① 登录 <https://q.qq.com/> 认证主体 → 管理端建机器人 → 拿 AppID/AppSecret；② 在管理端设置"使用的范围"（未认证 = 只有自己是群主的群；个人认证 = 公开、进群上限 500）；③ 用**最新版移动 QQ**、由群主/管理员把机器人加进目标群；④ 群里**群主点机器人**，打开「主动推送消息能力」（否则定时推送回 40034105）；⑤ 发一条群消息 → 应用自动登记该群 `group_openid`。

## §9 优缺点与取舍（不接受只有方案没有取舍）

### 9.1 进程内 vs 独立进程 → 选独立进程（理由见 §4）；**代价照实说**

- 好处：关窗仍收、崩溃隔离、扫码/重连这类贵动作只做一次；
- **真代价**：① 多一层 IPC，界面状态晚一个心跳；② 生命周期要管（pid/日志/残留进程），Windows 下还得处理 `taskkill` 的 MSYS 路径转义坑；③ **"关窗"语义要重新定义**（否则用户以为关了应用就不收消息了，结果还在烧配额）；
- **反向的诚实提醒**：如果用户其实只会在"开着应用时"用渠道，那 A 方案更省、更少故障点 —— 本文选 B 是因为**微信/QQ 的会话重建代价高**（重扫码 / 重新加群），而这两种恰恰是他明确说"以后也要这么做"的。

### 9.2 应用内向导 vs 命令行工具

| | 优 | 劣 |
|---|---|---|
| **应用内向导（本设计）** | 用户原话就是这个；二维码/深链/状态灯都能就地显示；凭据只写不回读有现成的 UI 口径 | 要维护 UI 代码（本项目 UI 是**无构建原生 JS**，改一次得跑 `--check-ui` + `node --check` + **真机看图**）；引导页文案会随平台后台改版过期 |
| 命令行工具 | 好写、好测、与 CI 亲 | 用户明确说"不想进具体某个文件夹里面"；命令行**显示不了二维码**（微信这条路直接做不了） |

**结论**：**以应用内为主**，命令行保留一条**只读**的等价入口（`scout.py --channel-status`，给排障与自动化用），**不重复实现写入逻辑**。

### 9.3 把密钥交给应用保管 —— 真实利弊

| 优 | 劣 |
|---|---|
| 用户不用手编 `.env`（他明确烦这个）；写入是原子的、有键名白名单、改错会**报错而不是静默忽略** | **应用成了唯一能读密钥的本地进程**：任何能读该用户文件系统的程序（同机其它用户态进程、备份/同步软件）都能读 `.env`。我们只能做到"不进仓库、不进日志、不回显、不落第二份"，**做不到"密钥不可被本机读取"** |
| 与 Hermes 同规矩（设置进 `config.yaml`、密钥只进 `.env`），以后迁移/对照成本低 | 一旦应用被"误配置"（例如把 `.env` 同步到网盘），密钥就出门了；缓解：`.env.example` 里写明风险 + 引导页提示不要同步该目录 |
| 有明确的"清除"路径（传空串擦除） | **没有"看密钥"的入口**是**有意为之**：忘记了就得去平台后台重置（这正是用户本来要做的动作，但变成主动选择而不是被迫） |

### 9.4 `channel.*` 统一命名空间 vs 另起一套 / 只保留 `feishu.*`

- 统一（本设计）：一套 UI、一套测试、加平台=加一张卡片；代价是**双写期**（`feishu.*` 与 `channel.*` 并存）与一次契约收敛；
- 只保留 `feishu.*`：短期最省，但"以后微信和 QQ 也要这样"会立刻逼出三个平行命名空间（`wechat.*` / `qq.*`），三套重复的配对/状态/凭据逻辑；
- 完全重写：违反项目"一次只改一个文件或一个函数"的协作铁律。

### 9.5 一平台一卡片 vs 一张大表

卡片（本设计）能让**每个平台说自己的话**（微信说"扫码"，QQ 说"群主点一下"，飞书说"去后台重置 Secret"）；
大表看起来整齐，但 **三个平台的"不能做"完全不同**，塞进同一张表只会把"为什么不能做"藏起来 —— 而用户这次问的核心恰恰就是"哪些是做不了的"。
