## 2. 模块边界（谁可以 import 谁）

```
desktop/   ─┐
channels/  ─┴→  rpc/  →  runtime/  →  tools/  →  {providers/, fetch/, grading/, library/, state/}
                                          ↑
                                      state/ 不被 providers 反向依赖
```

| 规则 | 说明 |
|---|---|
| `tools/*` 不许 import `rpc/*` | 工具是模型可见层，不知道自己被谁调 |
| `providers/*` 不许 import `state/*` | provider 只负责取数据，落库是 tools 的事 |
| `desktop/*` 只经 `rpc/server.py` 通信 | 壳里不许出现 sqlite3 或 httpx |
| `channels/*` 只经 `rpc/` 说话 | 渠道层是入口（与 `desktop/` 同级）：不读库、不出网、不碰 runtime/tools；直连下层当场红（`tests/test_layering.py::RULES["channels"]`） |
| `library/*` 不许 import `runtime`/`rpc`/`desktop`/`tools` | 资料归档与索引是领域逻辑（与 `grading/`、`learning/` 同级）：只读库 + 落盘，被 `rpc/`、`tools/` 调用（`tests/test_layering.py::RULES["library"]`） |
| `state/*` 是唯一碰 SQL 的地方 | 其他模块不许出现 `execute(` |
| `fetch/*` 是唯一出网的地方 | 其他模块不许 import httpx（除了 providers 的 base 抽象） |

**新增一个能力时的落点（按顺序问自己）**：
1. 是"取数据"吗 → 加 `providers/` 里的一个 provider，或复用现有
2. 是"模型要能主动做的一件事"吗 → 加 `tools/` 里一个工具 + 在 `docs/01` 里加 schema
3. 是"前端要展示的界面"吗 → 加一个 RPC 方法 + `ui/` 一页
4. 都不是 → **先别写**，回 `docs/01` 讨论（铁律 #1）

## 3. 规则文件

- **规则正文的唯一权威副本是 `docs/项目规则.md`**（`<!-- RULES:BEGIN -->` 与 `<!-- RULES:END -->` 之间）
- **`AGENTS.md` 是必须存在的分发副本**（Hermes 与各类 AI 助手读它）
- **`CLAUDE.md` 是可选副本**：2026-10-05 项目所有者决定不创建（本机不用 Claude Code）。要启用时 `cp AGENTS.md CLAUDE.md` 再改开头两行注释即可，正文必须逐字一致
- 校验：`scripts/check_rules_sync.py` —— 必需副本缺失或不一致 = 门槛不过 = 不合；可选副本不存在只提示
- 为什么不各自维护：规则漂移比重复更危险（AI 会按旧规则写代码）
- 规则正文包含七节：协作铁律 / 技术栈 / 命名 / 错误处理 / 依赖政策 / 门槛与关键路径 / 提交与 PR

## 4. 门槛（对应铁律 #4）

```bash
bash scripts/check.sh          # 全跑；任何一个不过，退出码非 0
bash scripts/check.sh --fast   # 跳过"类型"与"测试"两项，其余照跑（提交前快速自检）
```

门槛组成：

| 步骤 | 命令 | 不过的后果 |
|---|---|---|
| lint | `ruff check src tests scripts eval` | 不合 |
| 格式 | `ruff format --check src tests scripts eval` | 不合 |
| 类型 | `mypy src eval` | 不合 |
| 测试 | `pytest -q` | 不合 |
| 规则同步 | `python scripts/check_rules_sync.py` | 不合 |
| 依赖审批 | `python scripts/check_new_deps.py` | 不合 |
| 前端资源 | `python scripts/scout.py --check-ui` | 不合 |
| 代码地图 | `python scripts/make_code_map.py --check` | 不合 |

**lint 的规则集在 `pyproject.toml` 的 `[tool.ruff.lint]`**（不在本文件复述）。除常规的
`E/F/I/UP/B/SIM/RUF` 外，刻意只加了两条 docstring 规则：**`D100`（模块必须有 docstring）
与 `D104`（包必须有 docstring）**。理由是"这个文件是干什么的"唯一不会腐烂的位置就是模块 docstring
—— 与代码同文件、同一个提交、编辑器与 `pdoc` 直接读 —— 所以交给 lint 强制，而不是另写一份说明文档。

- **为什么是两条**：`__init__.py` 归 `D104`、其余模块归 `D100`；只开 `D100` 会把所有包的入口漏掉。
- **为什么不开整个 `D` 族**：`D2xx`/`D4xx` 是 docstring 的**格式**规则（摘要后空行、首行句号结尾…），
  会与中文 docstring 的全宽标点打架（`RUF001-003` 已经 ignore 全宽标点），再引格式规则只制造噪音。
- **已知盲区**：`_` 开头的模块被 ruff 当私有，`D100` 不管它（当前 linted 范围内只有 `tests/desktop/_ui.py` 一处）。
- **验收**：新增 `.py` 文件忘了写模块 docstring，`check.sh` 的 lint 项当场红 —— 不需要谁记得去检查。

## 5. 依赖审批机制（对应铁律 #6）

1. 运行期依赖写在 `pyproject.toml` 的 `dependencies`，同时必须列进 `deps-allowlist.txt`
2. `scripts/check_new_deps.py` 逐条比对；**出现未列入白名单的依赖，退出码 1**
3. 申请新增时在本文件 §6 追加一行，写清：用途 / stdlib 为何不行 / 体积 / 许可证
4. `dev` 组（pytest/ruff/mypy）与构建后端不进运行期白名单，但也要在 §6 登记

## 6. 依赖登记表

| 依赖 | 用途 | stdlib 为何不行 | 状态 |

| `PyYAML` | 读 `config.yaml` | 无内置 YAML | 已批准 |
| `pywebview` | 桌面壳（Edge WebView2） | 无内置 | 已批准 |
| `pymupdf` | PDF 文字层抽取（PDF/HTML/Doc 等） | 无内置 PDF 解析 | **已批准** 2026-10-05（AGPL-3.0，约 20 MB） |
| MinerU 官方 API | 扫描版 / 复杂版式解析（**非 Python 依赖，走 HTTP**） | 不自己写 OCR | 已批准（免登录轻量接口 + 需 token 的精准接口） |
| SearxNG（Docker 容器，**非 Python 依赖**） | 通用网页检索（免 key、返回 JSON） | 抓结果页违约且质量差（docs/03 §7） | 已批准（`deploy/searxng/`，本机自用，一条 `docker compose up -d`） |
| `pytest` / `ruff` / `mypy` / `hatchling` | dev + 构建 | — | 已批准（非运行期） |
| `pyinstaller` | **打自包含 Windows 包**（`scripts/build_bundle.py`） | 无内置打包器 | **已批准** 2026-10-07（大浩明确要求"搞一个 windows 的安装包，点开即用"）；只进 `[project.optional-dependencies] build`，**运行期不依赖** |
| `csc.exe`（.NET Framework 4.x，**Windows 自带，非 Python 依赖**） | 编译项目根的 `ScholarScout.exe` 启动器 | 不装 PyInstaller / MSVC | 免安装即可用（`C:\Windows\Microsoft.NET\Framework64\v4.0.30319\csc.exe`）；**只在构建时需要**，运行 exe 只需系统自带的 .NET Framework |

**启动器为什么不是 PyInstaller 打包**：把应用 freeze 进 exe，每改一次代码都要重新打包 ——
那才是"会因为版本更替失效"。这里的 exe 只负责"找项目 → 找解释器 → 拉起 `scout.py --desktop`"，
业务代码全在项目里，随时更新都不用重编 exe（`packaging/launcher/ScholarScoutLauncher.cs`，111 KB）。

**那为什么又有一个自包含包**（2026-10-07）：两者解决的是不同问题，**不是替代关系**。
启动器给"本机有项目、有 `.venv`"的自己用（改代码不用重打包）；自包含包给"别人的机器没有环境"用
（`scripts/build_bundle.py`，PyInstaller，把解释器+依赖+界面资源+提示词全带上，拷过去点开即用）。
代价写在脚本开头：**改一次代码就要重打一次包** —— 这正是启动器继续存在的理由。
打包后 `paths.home()` 指向 **exe 所在目录**（不是临时解包目录），所以 `data/`、`run/state.db`、
`config.yaml` 都落在 exe 旁边，**整个目录拷走资料一起走**。

**图标不需要图像库**：`scripts/make_icon.py` 复用已批准的 `pymupdf` 做缩放（把 PNG 当单页文档渲染），
再用 stdlib `struct` 拼 ICO 容器（PNG-in-ICO，Vista+ 支持）—— 不引入 Pillow。

**通用/商用检索没有新增任何 Python 依赖**：六个来源全用已批准的 `httpx` 手写（`providers/{bing,duckduckgo,searxng,tavily,serper,brave,google_cse}.py`），
所以 `deps-allowlist.txt` 不用动。

## 9. Windows 中文路径下的已知坑（必读，能省一小时）

**现象**（2026-10-05 本机实测）：`uv pip install -e .` 之后，`.venv` 里的解释器**启动即崩**，连 `print(1)` 都跑不了：

```
Fatal Python error: init_import_site: Failed to import the site module
UnicodeDecodeError: 'gbk' codec can't decode byte 0xae in position 16: illegal multibyte sequence
```

**原因链**：

1. 项目路径是 `D:\AI+教育毕设毕设\ScholarScout`（**含中文**）
2. editable 安装会写 `.venv/Lib/site-packages/_editable_impl_scholarscout.pth`，内容是 **UTF-8** 的 `D:\AI+教育毕设毕设\ScholarScout\src`
3. CPython 3.11 的 `site.py` 读 `.pth` 用的是 **locale 编码**（zh-CN Windows = GBK）→ 解码失败 → 解释器起不来
4. **`PYTHONUTF8=1` 也救不了**（已实测），因为它不影响 `site.py` 读 `.pth` 的那次解码

**规则（本项目自定）**：

1. **禁止 `uv pip install -e .` / `pip install -e .`**（比铁律 #6 更硬：这条直接让环境不可用）
