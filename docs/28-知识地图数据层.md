# 28 · 知识地图数据层（两层图 · 增量生长 · 路径与搜索）

> **一句话**：知识地图从「每调一次就整张重画」改成**两层 + 增量**——概念层随资料收录长大，
> 旧节点 `nid` 不变、旧边一条不删、同一批来源重复应用不产生任何变化（也不再多花一次模型钱）；
> 资料层不落库，按「两个来源共同支撑 ≥ 2 个概念」现场推出来。

## 一、两层图是什么

### 1.1 概念层（落库：`topic_maps.graph_json`）

```
nodes: [{nid, label, kind, source_ids[], dropped_source_ids[]}]
edges: [{src, dst, rel}]
      + applied_source_ids[]（水位）+ growth{batches, last_batch, last_added, last_updated}
```

- `kind ∈ concept | method | dataset | tool | venue | source`
- `rel ∈ prerequisite | variant | uses | evaluates`
- `source_ids` 是节点的**出处**：这是概念层里唯一的事实来源，资料层完全靠它推导。
- `dropped_source_ids` 是「模型声称的出处不在本主题白名单里」——**留着不删**，方便回答
  「这个说法本来想挂哪篇」。

### 1.2 资料层（**不落库**，按需现算：`topic.get_source_graph`）

- 节点 = 本主题出现过的**来源**（`sources` 行），id 就是 `source_id`；
- 边 = **两个来源共同支撑 ≥ `min_shared` 个概念**，`weight` = 共同概念数；
- 没有新的表、没有新的字段：同一份概念图 + 同一批来源行，永远算出同一张资料图。

为什么不落库：多存一份就是多一处会过期的真相。概念图一变，资料层必须跟着变 —— 现算是
唯一不会忘记同步的做法（节点数最多几十，算一次是微秒级）。

## 二、资料层怎么推（规则与阈值）

1. **共同支撑**：对每个概念节点，把它 `source_ids` 里的每个来源记一次「该来源支撑这个概念」。
   之后对来源两两求交集，交集大小就是这条边的 `weight`。
2. **阈值默认 2**：共享 1 个概念太容易撞（任何两篇讲 RAG 的都会共享一个泛概念），默认 2 才勉强
   表达「这两篇在讲同一件事」。`min_shared=1` 用于调试/小主题看全貌，**夹在 1–20**（越界夹取、
   不报错 —— 阈值不是非法参数，只是问得比数据细）。
3. **绝不自环**：单个来源只跟自己有交集的情况不算边（只连 `left < right` 的有序对）。
4. **顺序是确定的**：节点按 `source_id` 字典序、边按 `(-weight, src, dst)` 排序。所以
   **边的方向取决于随机 id**，任何断言/界面都只能依赖「哪一对」，不能依赖 `source -> target`
   的方向（`tests/rpc/test_topic_graph_methods.py::test_source_graph_min_shared_switch` 就是
   这么钉的）。
5. **图上挂过、库里查不到的来源也保留**：节点标 `missing=true`、标签退到 `source_id`。
   一条来源被删了不该让图悄悄少一个点 —— 那会让用户以为「这段关系从来不存在」。
6. `has_text` 取自 `documents` 有没有抽取记录（与 `research_board` 同口径）：界面据此决定
   「点进去能看全文」还是「只有元数据」。

## 三、增量生长与幂等（四条铁律）

### 3.1 水位：`applied_source_ids ∪ 所有节点的 source_ids`

判定「这批来源是不是新的」只看**集合**：``batch - applied ≠ ∅`` 才工作。为什么还要扫节点：
`topic.build_map` 早先生成的老图**没有水位字段**，只看水位会把图上已有来源当成新的，白调一次
模型。两者取并集，老图一进来就是幂等的。

整批都被吸收过 → 原地返回、**一个字段都不动**（`changed=false`），**不构造提示词、不调模型**。

### 3.2 标签是身份（标签归一）

同一标签（去 `[无出处]` 前缀、去首尾空白、`casefold`）视为同一个概念，新来源挂上去，
而不是再造一个同义节点。所以第二篇讲 RAG 的论文会让 `RAG` 节点的 `source_ids` 变长，
而不是多出一个 `rag` 节点。

### 3.3 `nid` 稳定，但**补丁里的 `nid` 是局部的**

旧节点的 `nid` 永不改（界面的选中态、`route.topic_map_id` 的关联都靠它）。但生长时模型
**只看这一批新来源**，它的编号从 `n1` 重新数 —— 所以合并规则是：

- `nid` 撞上已有节点**且标签对得上** → 同一个概念，合并 `source_ids`；
- `nid` 撞上但**标签对不上** → 它说的是另一个概念，按新节点处理（`_fresh_id` 换号）。

这条规则是补来的：没有它，扁平兜底补丁的第一个节点（`n1`）会把新来源挂到旧图的 `n1` 上，
图看起来「长了一个来源、少了一个概念」，而且**永远长不出新节点**。

### 3.4 只增不删（单调）

- 既有节点、既有边**永不删除**（宁可多留一条旧边，也不让用户上次看到的关系凭空消失）；
- 节点数上限（默认 30，与 `topic.build_map` 的上界一致）只截**新加的尾巴**：旧节点一条不动，
  被截掉的新节点会在 `dropped_nodes` 里报数，`added` 只报**真正留在图里**的那些。

### 3.5 退化要留原因

模型胡言乱语/超长截断 → 走扁平兜底（每个新来源一个 `source` 节点、无边），但**原因必须回给
调用方**：`topic.grow_map` 的 `mode` / `mode_reason` 是**本次调用**的口径，图里存的那份另给
`graph_mode` / `graph_mode_reason`。图里的 `mode` 记的是「这张图怎么来的」，不该被一次退化改写；
而「这次为什么没长好」只存在于返回值里，丢了就不可诊断。

## 四、原子替换（写库那一步）

`replace_topic_map_graph` 两道保险：

1. **先序列化、后动库**：`json.dumps` 失败时旧图一个字节都没被碰过；
2. **单条 `UPDATE` 走一个写事务**：SQLite 不会出现写了一半的 `graph_json`，异常就 ROLLBACK。

为什么不是「插新行、删旧行」：那会让 `topic_maps.id` 变掉，前端手上的 `topic_id` 与外键一起失效。
原地替换才叫「同一张图长大了」。返回 `False`（该行不存在）→ 调用方抛 `-32002`，**不静默新建**。

## 五、在图上找东西（`topic.find_path` / `topic.search_nodes`）

两层共用一套口径（`layer ∈ concept | source` 决定查哪张图），返回形状一致：

- **`find_path`**：BFS 定长 → 只在**最短路上**枚举（`dist(起点)+dist(终点)==最短长度`），最多 3 条。
  - 按**无向**连通走：`prerequisite` 有方向，但用户问的是「这两块有没有关系」，按箭头方向判可达
    会让一半查询变成「没有路径」。边上仍保留存储方向，界面照原方向画箭头。
  - 找不到 / 超 `max_depth`（默认 4，夹 1–8）→ `paths:[]`，**不报错**。
  - 起点 == 终点 → 一条零长度路径（`nodes` 1 个、`edges` 空），如实说「就是同一个点」。
- **`search_nodes`**：标签**子串**匹配（`casefold`），前缀命中 → 度数高的 → 标签字典序；
  回 `{id,label,kind,weight}`，`weight` 与 `topic.get_map` 同口径（度数）。
  **空查询回 `nodes:[]` 而不是全图** —— 空串「匹配所有」在界面上就是「刚点开搜索框糊一屏」。

`layer` 给了不认识的名字一律 `-32602`，不静默回概念层：两层返回形状一样，静默回退用户看不出来。

## 六、未接线：`library.updated`

`tools/topic_map.py::grow_map_on_library_update` 是**留给事件入口的**（本轮只导出，没有订阅
`library.updated`）。它和手动入口的唯一区别：**主题还没有图时安静跳过**，不从空图凭空造一张
（一次入库就把用户没看过的主题塞满列表）。手动 `topic.grow_map` 相反 —— 没图就从空图长起
（`created=true`）。

接线时要补的三件事：

1. 事件里拿到 `source_ids` 后先查「这个主题有没有图」（`latest_topic_map`），没有就返回
   `changed=false` + 原因；
2. 一次入库可能带来多条来源 —— **按主题合并成一批**再成长，不要逐条调（每条一次模型调用）；
3. 失败不能影响入库：成长是"锦上添花"，异常只记日志，不回滚资料。
