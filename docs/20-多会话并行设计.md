# 20 多会话并行设计（接口先行）

> 状态：**v1.0 待拍板** ｜ 2026-10-12
> 起因（用户原话）：「在其中一个会话运行时，我想切换到其他会话，会导致本次会话出现异常，我希望你通过多 Agent 来实现不同会话同时工作。」
> 用户已拍板三项：① **并发上限 3**（同时最多 3 个会话在跑）；② **直接并行、不排队**（A 在跑时，B 发问立刻开跑）；③ **跑完要提醒**（非当前活跃会话的一轮完成时：应用内角标 + 可选的私聊推送）。
> 参照物：`docs/16-Hermes架构对照与借鉴方案.md`（本项目自己的架构对照，本文所有取舍与它保持一致：借 Hermes 的**隔离思想**，不借它的多进程/多平台外壳）。
> 关联：`docs/01 §2/§3.2/§4`（传输、方法表、事件表）、`docs/02 §5`（表结构）、`docs/14 §3 C1`（多智能体不做）、`docs/16 §3`（子 Agent 专题）。
> 本文只做设计，**不改代码**。所有现状结论都带 `文件:行号`，均现查本工作区（HEAD `0503419`），读不到的写 `unknown`。

**本文分九节**：§1 诊断 → §2 目标架构 → §3 接口先定 → §4 数据与存储 → §5 预算与成本 → §6 失败隔离与取消 + 提醒 → §7 测试策略 → §8 分阶段实施 → §9 优缺点与取舍。

## §1 诊断：为什么"切会话就出错"

**一句话**：后端读循环**早已不是**阻塞根因（`serve()` 已是并发实现），真正让"切会话就出错"的是 ——
**界面只有"全局单飞闸 + 单一进行中槽"**（前端把整轮绑定在"当前显示的会话"上），叠加**事件信封不带 `session_id`**（界面无法把事件分派回它所属的会话），再加上**运行时/存储的共享可变状态在多线程下会互相踩**。三者叠加，缺一不可。

### 1.1 逐条证据

| # | 现象 | 证据（`文件:行号`） | 结论 |
|---|---|---|---|
| A | 「切到别的会话发问，发不出去」 | `desktop/ui/app.js:291-293`：`send()` 第一行 `if (state.sending \|\| !state.sessionId) return;`；`app.js:725`：`state.sending` 是 **state 上的一个布尔**（全应用一份） | **UI 单飞闸**：A 会话在跑时 `state.sending === true`，B 会话的发送被**静默丢弃**（连提示都没有）。这是用户看到的第一症状 |
| B | 「切过去以后，A 的回复跑到当前会话里 / 当前会话卡住」 | `desktop/ui/app.js:298`：`state.pending = makePending()`（**只有一个**进行中槽）；`api.js:342-343`：`const trace = state.pending; if (!trace) return;`（**不看 session_id**）；`api.js:323-360` 整个 `window.scoutEvent` 只有 `session.updated` 一条按 `p.session_id === state.sessionId` 判过（`api.js:328`），其余全部无脑塞进 `state.pending` | **单一 pending 槽 + 事件不按 session 分派**：A 的 `chat.delta/tool_*/done` 会写进"此刻挂载的那个气泡"。切到 B 后 `openSession` 把 `#messages` 清空（`app.js:394`），A 的气泡变成游离节点；若 B 已开跑，`state.pending` 被 B 覆盖 → **A 的收尾（`app.js:305-321` 的 `setFinal`/`finish`）直接写进 B 的气泡**。这就是"串会话" |
| C | 「切走后按停止，停不下来 / 停错会话」 | `desktop/ui/app.js:833-838`：`stopTurn()` 用 `state.sessionId` 取消 —— **总是取消"当前显示的"那个会话** | 切走 A 后无法再停 A；对 B 发取消会得到 `{ok:false, reason:"no_running_turn"}`（`rpc/session.py:236-241`） |

| F | 「后端读循环会阻塞吗」 | `rpc/server.py:113-161`：`serve()` **是并发的**（工作线程 + 写锁），`test_serve_concurrency.py` 已钉住"长任务期间取消必须立刻被处理" | **读循环阻塞已不是主因**。但仍有一个**容量闸**（见 1.3），并行 3 会话 + UI 调用会把它打满 |
| G | 「并行时代码会崩」 | `state/sessions.py:185`：`append_message` 用 `with db.transaction() as conn:` → `state/db.py:101-111` 的 `BEGIN/COMMIT` 走的是**同一个共享连接**（`db.py:40-42`，`check_same_thread=False`） | **SQLite 单连接上的显式事务不可重入**：两会话同时落消息 → 第二个 `BEGIN` 直接 `sqlite3.OperationalError: cannot start a transaction within a transaction`。**并行前必须先修**（§4） |
| H | 「共享可变状态」 | `rpc/registry.py:24-57` 的 `AppContext` 是**进程内一份**（`app.py:74` 装配一次），`turn_context()`（`registry.py:43-51`）把 `cancelled`/`running` 两个**全局可变对象按引用**传给每一轮的 `TurnContext`（`runtime/loop.py:86-96`） | 多轮并行时这些对象被多线程读写，且 `running`/`cancelled` 现在**裸 dict/set、无锁**（`loop.py:332`/`:506` 写，`rpc/session.py:235/242` 读） |

**注意区分（这是三件不同的事）**：
1. **读循环阻塞** —— 已修（`rpc/server.py`），但留下容量闸，见 1.3；
2. **UI await 导致** —— 半对：`desktop/rpc_client.py:39` 把 `chat.send` 的等待上限放到 1800s，且 `call()`（`rpc_client.py:240-270`）已按 id 信箱并发安全 —— **传输层不阻塞**；真正卡住的是 `app.js` 的 `await scout.call("chat.send", …)`（`app.js:304`）把整轮绑在**一个会话的界面状态**上；
3. **全局状态互盖** —— 真存在，含 UI 的 `state.sending`/`state.pending` 与后端的 `AppContext.cancelled`/`running` + 共享 DB 连接。

### 1.2 事件信封：现状不带 `session_id`（逐事件核实）

`rpc/server.py:21-35` 的 `NOTIFICATION_METHODS` 里，只有 `session.updated` 的载荷带 `session_id`（`rpc/session.py:193`）。其余全部**只有 `turn_id`**：

| 事件 | 载荷（现状） | 证据 |
|---|---|---|
| `chat.delta` | `{turn_id, seq, kind, text}` | `runtime/loop.py:348-357`、收尾那条 `:562-567` |
| `chat.tool_call` | `{turn_id, seq, call_id, tool, args_digest, args_preview}` | `runtime/loop.py:624-635` |
| `chat.tool_result` | `{turn_id, seq, call_id, ok, digest, latency_ms, refs}` | `runtime/loop.py:675-687`；失败路径 `:709-713` |
| `chat.error` | `{turn_id, code, message}` | `runtime/loop.py:416-420` |
| `chat.done` | `{turn_id, stop_reason, usage, refs}` | `runtime/loop.py:568-572` |
| `chat.subtask_start` / `chat.subtask_done` | `{turn_id, seq, index, …}` | `runtime/subtasks.py:344-348` / `:430-440` |
| `practice.delta` | `{note_id, card_index, delta}` | `rpc/learning.py:295-299` |
| `session.updated` | `{session_id, title, source}` ✅ | `rpc/session.py:193` |

`docs/01 §4`（第 234-246 行）的事件表同样没有 `session_id` 列 —— **契约层面就缺了这一格**，所以前端"串会话"不是前端一个人的锅，是契约缺字段。
**关键点：`chat.send` 的返回值里其实已经有 `session_id`**（`TurnResult.as_dict()`，`runtime/loop.py:141-152`）—— 只是它随**整轮结束**才回来，对"实时分派事件"毫无帮助。

### 1.3 后端容量闸（并行前必须一并调）

- `rpc/server.py:109-110`：`MAX_CONCURRENT_REQUESTS = 4`；`:143`：`slots = threading.Semaphore(max_workers)`；
- `:154-158`：主线程 `for line in input_stream: slots.acquire(); Thread(...).start()` —— **`slots.acquire()` 在主线程上**。

于是：**3 个会话各占 1 个槽 + UI 的任意调用（预览/列表/设置）就能打满 4 个槽 → 读循环当场阻塞**，`chat.cancel` 又会排队（回到老症状）。
设计结论：**读循环永不阻塞**（不在读循环上 `acquire`），容量上限交给"会话调度器"而不是"读循环闸"。

## §2 目标架构：每会话一个独立工作单元

### 2.1 一张图

```
        pywebview 壳（JS）  ── 一行一 JSON ──►  rpc/server.py
             ▲  事件按 session_id 分派              │  ① 读循环：只读+转发，**永不阻塞**
             │                                      ▼
             │                               rpc/dispatch（不变）
             │                                      │
             │                          chat.send → SessionRuntime.submit_turn()  ← 立即返回 turn_id
             │                                      │
             │                        ┌─────────────┴──────────────┐
             │                        │  会话工作单元池（上限 3）    │  threading.ThreadPoolExecutor(max_workers=3)
             │                        │  ┌──────────┬──────────┬──────────┐
             │                        │  │ ses_A    │ ses_B    │ ses_C    │
             │                        │  │ TurnHandle│TurnHandle│TurnHandle│  每单元自带上文/预算/取消事件/事件通道
             │                        │  └────┬─────┴────┬─────┴────┬─────┘
             │                        └───────┼──────────┼──────────┼───────┘
             │                                ▼          ▼          ▼
             │                     loop.run_turn(session_id=A)  ...（互不共享可变状态）
             └──────────── 事件（带 session_id）────────┘
                                                   │
                              state/  单写连接 + 写锁（一写多读，WAL）
```

### 2.2 每个工作单元 = 一个会话的全部活动状态

| 单元自带 | 内容 | 现在放在哪（要搬进来） |
|---|---|---|
| 会话标识 | `session_id` | 已有（`loop.run_turn` 入参） |
| 进行中一轮 | `turn_id` / `stop_reason` / 已收敛的 `TurnResult` | `ctx.running[session_id]`（`registry.py:36`，裸 dict）→ 搬进单元 |
| 取消信号 | 每轮一个 `threading.Event` | `ctx.cancelled: set[str]`（`registry.py:34`，裸 set）→ 每轮一个 Event，避免全局集合跨会话误伤 |
| 事件通道 | `emit(kind, payload)` **且强制注入 session_id** | `ctx.emit`（`registry.py:33`，全局一个）→ 单元持有"给本会话加封套的 emit" |
| 预算账 | 本轮 `TurnBudget`（`runtime/toolctx.py:24-53`）+ 会话累计 | 本轮已有；会话累计新增（§5） |
| 工具集 | `toolsets` | 已有（入参） |
| 结果信箱 | 最近 N 条的 `turn_id → TurnResult`（供 `chat.result` 补取） | 现在没有 → 新增 |

**不变的部分**：`runtime/loop.run_turn` 的**内部逻辑一字不改**（它已经是"给定 session_id 跑一轮"的纯函数式实现，`loop.py:204-583`）；`tools/`、`providers/`、`grading/`、`state/` 的接口也不动。并行是**加一层调度**，不是重写内核。

### 2.3 `SessionRuntime` 的职责边界与生命周期

```python
# runtime/session_runtime.py（新文件，runtime 层）
@dataclass
class TurnHandle:
    session_id: str
    turn_id: str
    cancel_event: threading.Event
    started_at: float
    phase: str = "queued"        # queued|thinking|tool|writing|done

class SessionRuntime:
    """每个会话一个工作单元；上限 max_concurrent 的线程池执行；**读循环永不阻塞**。"""

    def __init__(self, ctx: AppContext, *, max_concurrent: int = 3,
                 idle_reap_s: float = 900.0, keep_results: int = 32) -> None: ...

    # -- 提交：立即返回，不等结果 --------------------------------------------
    def submit_turn(self, *, session_id: str, text: str,
                    toolsets: Sequence[str], emit: Emitter) -> dict:
        """{'ok': True, 'turn_id': ...} 或
           {'ok': False, 'reason': 'turn_in_progress'|'at_capacity'|'global_budget_exceeded'
                                  |'session_tool_limit_exceeded',
            'turn_id'?: str, 'running'?: [...]}"""

    # -- 取消：步间检查，只影响指定会话 --------------------------------------
    def cancel(self, *, session_id: str | None = None,
               turn_id: str | None = None) -> dict:
        """{'ok': bool, 'turn_id': str, 'note': str}；无在跑轮次 → {'ok': False, 'reason': 'no_running_turn'}"""

    # -- 观测 ----------------------------------------------------------------
    def status(self, session_id: str | None = None) -> dict:   # 哪些会话在跑/跑在什么阶段/容量
    def result(self, turn_id: str) -> TurnResult | None:        # 迟到/掉线重连补取

    # -- 生命周期 ------------------------------------------------------------
    def reap_idle(self, *, idle_s: float | None = None) -> int   # 释放空闲单元的会话级缓存（不丢库里的东西）
    def shutdown(self) -> None                                   # 置取消标志，不 join（工作线程是 daemon）
```

**生命周期四态**（每个会话一个）：
1. **建**：`submit_turn` 时若该会话没有单元就建一个（单元注册表用 `threading.Lock` 保护）。
   **硬约束：一个会话同时只能有一轮在跑** → 同一会话第二次 `submit_turn` 返回 `{ok:false, reason:"turn_in_progress"}`。
   为什么必须这样：`messages.idx` 是**会话内**自增且 `UNIQUE(session_id, idx)`（`migrations/0001_init.sql:135`），`research_states` 是**一会话一行**（`migrations/0010_research_state.sql:11-15`），同一会话两轮并行会互相覆盖台账与消息序号 —— 那不是"并行"，是数据损坏。
2. **跑**：线程池（`max_workers = max_concurrent`）执行 `loop.run_turn(...)`；`phase` 随事件更新（给 `chat.status` 与界面角标用）。
3. **收**：轮次结束 → `TurnResult` 进"结果信箱"（保留最近 `keep_results` 条）→ 摘掉该会话的 in-flight 标记 → 触发**提醒钩子**（§6.3）。
4. **销**：`reap_idle` 释放空闲单元（默认 15 分钟无活动）；**库里才是真源**，单元只是热缓存，销毁不丢任何持久数据。关窗走 `shutdown()`（不 join，与 `serve()` 的 daemon 语义一致，`rpc/server.py:131`）。

## §3 接口先定（铁律：先定接口再填实现）

### 3.1 事件信封：统一带 `session_id`

**信封（所有 notification 同一形状）**：

```json
{"jsonrpc": "2.0", "method": "chat.delta",
 "params": {"session_id": "ses_7fk2m9qa", "turn_id": "trn_3bq8", "seq": 4, "kind": "text", "text": "……"}}
```

- `session_id`：**必填**，`NOTIFICATION_METHODS`（`rpc/server.py:21-35`）里的每一条都要有；
- `turn_id`：`chat.*` 家族必填；`practice.delta` / `session.updated` 不要求（前者用 `note_id`，后者本身就是会话级）；
- `seq`：沿用现有语义（`loop.py:353` 累计 delta 序号 / `:629` 工具步号），不新增含义。

**需要改的事件（补 `session_id`）**：`chat.delta`、`chat.tool_call`、`chat.tool_result`、`chat.error`、`chat.done`、`chat.subtask_start`、`chat.subtask_done`、`practice.delta`。
**落地位置**：`runtime/loop.py` 的 8 处 `_emit(...)`（`run_turn` 手里就有 `session_id`，零成本）；`runtime/subtasks.py` 从 `ctx.session_id` 取（`toolctx.py:62` 已有该字段）；`rpc/learning.py:296-299` 从 `row["session_id"]` 取（`learning.py:288` 已读出）。
**建议做法**：加一个 `runtime/loop.py::bind_emitter(emit, session_id) -> Emitter`（把 session_id 塞进 payload 再转出），在 `SessionRuntime.submit_turn` 里包一次 —— 这样"事件必带 session_id"是**机制保证**，不靠每处 `_emit` 记得写。

**契约测试**：参数化断言"`NOTIFICATION_METHODS` 里每个事件名在跑一轮后，其 params 必含非空 `session_id`"（防止以后加事件忘带）。

### 3.2 RPC：`chat.send` 立即返回 `turn_id`

| 方法 | 旧签名（现状） | 新签名 | 谁改 |
|---|---|---|---|
| `chat.send` | `{session_id, text, toolsets?}` → **阻塞整轮**返回 `{turn_id, session_id, message_id, text, stop_reason, tool_calls, usage, refs, error}`（`rpc/session.py:196-217`） | `{session_id, text, toolsets?, mode?="sync"}` → **立即**返回 `{turn_id, session_id, accepted: true}`；整轮结论走 `chat.done` 事件 | 后端（新增 `mode`），界面按阶段适配 |
| `chat.cancel` | `{session_id?\|turn_id?}` → `{ok, turn_id, note}`（`rpc/session.py:220-247`） | **签名不变**，语义补强：**可取消任意会话**（不再只对当前显示的）；无在跑轮次仍回 `{ok:false, reason:"no_running_turn"}` | 后端（已基本具备） |
| `chat.status`（**新增**） | — | `{session_id?}` → `{running: [{session_id, turn_id, phase, started_at}], capacity: {max: 3, used: 1}, global_budget: {...}, session_tool_budget: {...}}`（两个预算键的**字段级契约见 `docs/01 §3.2` 末尾两张表**，此处不重复） | 后端（新增） |
| `chat.result`（**新增**） | — | `{turn_id}` → `TurnResult` 或 `{ok:false, reason:"unknown_turn"}`（迟到/掉线补取） | 后端（新增） |
| `chat.done`（事件） | `{turn_id, stop_reason, usage, refs}`（`loop.py:568-572`） | 增 `session_id` + **`text`（最终正文）** + `message_id` | 后端 |
| `session.updated` | `{session_id, title, source}` | 不变（唯一已合规的事件） | — |

**为什么要 `chat.done` 带 `text`**：`chat.send` 不再阻塞返回，界面就必须从**收尾事件**拿最后那句权威正文（`loop.py:558-567` 的收尾 `chat.delta` 已给出最终正文，`chat.done.text` 是它的显式版本，便于前端一次落定）。同时保留 `chat.result(turn_id)` 供迟到/重连场景补取 —— 两者并存，代码里都是同一个 `TurnResult`。

**兼容策略（"界面先改还是后端先改"的答案）**：**后端先加能力、默认走旧语义；界面改完再切默认**。
- 阶段 1-3：`chat.send` **默认 `mode="sync"`**，行为与今天逐字一致（阻塞返回整轮）——现有界面不改任何一行也照常工作，新增的 `session_id` 只是"多带了个字段"，不破坏任何断言（`tests/rpc/test_stream_wiring.py` 等读事件的用例需同步补断言，但**不改变语义**）；
- 阶段 4：界面已改成多会话槽后，把 `mode` 默认切成 `"async"`，并在 `docs/01 §3.2` 记录版本号与切换日期（口径变更必须留痕，与 `docs/05` 的"改口径=改文档"纪律一致）。
- `chat.status` / `chat.result` 是**纯新增**，任何阶段都可先上，老前端不调用即无影响。

### 3.3 前端需要的新状态（属 `desktop/ui/`，本轮不动，设计写清）

| 旧 | 新 |
|---|---|
| `state.sending: bool`（`app.js:725`） | `state.turns: { [session_id]: {turnId, trace} }` —— **每会话一个槽** |
| `state.pending`（单槽，`app.js:298`） | 按 `session_id` 取槽（`api.js:342-343` 的 `state.pending` 改为 `state.turns[p.session_id]`） |
| `send()` 的全局闸（`app.js:292`） | 按会话判：**只禁"该会话自己在跑"时重复发送** |
| `stopTurn()` 用 `state.sessionId`（`app.js:838`） | 界面上每个在跑的会话行各给一个「停止」，传该行的 `session_id` |
| `openSession()` 无守卫（`app.js:390`） | 若该会话在跑，重进时按 `session_id` 重建气泡（不清屏、或重绘后把进行中槽挂回去） |
| 无未读概念 | `chat.done` 到达且 `session_id !== 当前显示` → 左栏会话行加 `.is-unread` 角标 + 顶栏计数；点开即清 |

## §4 数据与存储：SQLite 并发写

### 4.1 现状与真风险

- 单一连接：`state/db.py:40-42`（`check_same_thread=False` + `isolation_level=None`）；WAL/`busy_timeout=5000` 已开（`db.py:48-53`）；
- **显式事务走这条唯一连接**：`db.py:101-111` 的 `transaction()` 发 `BEGIN` / `COMMIT`；
- 用它的地方：`state/sessions.py:185`（**每一次 `append_message`**）、`sessions.py:352`、`state/pairing.py:301`、`library/migrate.py:222`。

**风险（真会崩，不是理论）**：两个会话的轮次同时落消息 → 第二个 `BEGIN` 在同一连接上抛 `sqlite3.OperationalError: cannot start a transaction within a transaction`；更隐蔽的是**交错**：A 的 `BEGIN..COMMIT` 窗口会把 B 的自动提交写入裹进同一事务，A 一旦回滚就把 B 的写入一起回滚 —— 这是**跨会话的数据损坏**，不报错、只丢数据。

### 4.2 选择：**一写多读 + 应用层写锁**（不做 WAL 放任、不做每会话连接）

| 方案 | 评价 | 结论 |
|---|---|---|
| A. `BEGIN IMMEDIATE` + `busy_timeout` 靠 SQLite 自己重试 | WAL 下同一时刻**只允许一个写事务**，其他线程会拿到 `SQLITE_BUSY`；`busy_timeout` 只救"另一进程持锁"的场景，救不了**同一连接上的重入**（同一连接的第二个 BEGIN 不是 BUSY，是直接报错） | ❌ 治不了本 |
| B. **读连接 + 单写连接 + `threading.RLock`**（本设计选它） | 读走只读连接（WAL 下读不阻塞写）、写走专用写连接且**串行化**（写操作本身不慢：一条 INSERT/UPDATE 微秒级）；`transaction()` 改成"持写锁的上下文" | ✅ **选它** |
| C. 每会话一条连接 | WAL 仍只允许一个写者，写者之间照样 `SQLITE_BUSY`；文件句柄随会话数增长；`Database` 对象被到处传（`ToolContext.db`、`AppContext.db`），改成 per-session 是大改 | ❌ 复杂度不换收益 |
| D. 换 Postgres / 上 ORM | 违反"零新依赖 + 全本地"（`docs/项目规则 §4`） | ❌ 不可能 |

**选 B 的理由（一句话）**：写操作本身极短（单条 INSERT），瓶颈是模型与出网；用**一把写锁**把"写事务"串起来，比让 3 个线程去抢 SQLite 的 `SQLITE_BUSY` 再猜重试更可预测、零新依赖、不改表结构。**读路径（列表/预览/用量）不受影响**，仍可并发。

**§4.1 的坑正好被 B 覆盖**：并行会话的 `append_message` 会在写锁前排队，每次只有一个 `BEGIN..COMMIT` 在飞，`messages.idx` 的 `SELECT max(idx)+1` 与 INSERT 在同一临界区里，`UNIQUE(session_id, idx)` 不会被破。

### 4.3 表是否已按 session 隔离（逐表核实）

| 表 | 是否按 session 隔离 | 证据 |
|---|---|---|
| `sessions` | ✅ 主键 `id`（= session_id） | `migrations/0001_init.sql:110` |
| `messages` | ✅ `session_id` + `UNIQUE(session_id, idx)` | `migrations/0001_init.sql:135` |
| `research_states` | ✅ `session_id TEXT PRIMARY KEY`（一会话一行） | `migrations/0010_research_state.sql:11-15` |
| `usage_records` | ✅ 带 `session_id` / `turn_id` / `purpose` / `est_cost` / `created_at` | `migrations/0001_init.sql:159-168` |
| `tool_traces` | ✅ 带 `session_id` / `turn_id` / `step` | `migrations/0001_init.sql:150-158` |
| `sources` / `documents` / `summaries` | ⚠️ **全局**（跨会话共享的资料库） | 天生共享：同一篇论文被两个会话检索到是**正确**的，靠 `source_mentions` 记归属；但并发写 `documents`（`UNIQUE(source_id, sha256)`，`:74`）需要 §4.2 的写锁兜住竞态 |
| 学习产物（`topic_maps` / `learning_routes` / `notes`） | ⚠️ 带 `session_id` 但语义是"全局可见产物" | 并行时两会话各自产出不冲突；`note.save` 等按 session 记账正确 |

**结论**：**会话级数据已经天然隔离得很好**（这是本设计能便宜落地的最大前提）；需要补的只有"共享资料库表的并发写"与"单连接显式事务"，两者都被 §4.2 的方案覆盖。

## §5 预算与成本（用户对成本敏感：上限必须写清怎么算、超了怎么办）

### 5.1 三层上限

| 层 | 键（新增的标 ✱） | 默认 | 怎么算 | 超了怎么办 |
|---|---|---|---|---|
| 单轮工具预算 | `runtime.max_tool_calls_per_turn` | 12（现状 `config.py:87`） | 每轮工具调用次数（`TurnBudget`，`toolctx.py:24-53`） | `stop_reason="tool_limit"`（现状语义不变） |
| **会话累计** | `runtime.max_tool_calls_per_session` | **`None` = 不限**（不写也是不限；`null` / `''` / `0` 同义；**`bool` / 负数 / 非数字串 → 启动报错**，不再静默归一成"不限"） | `state/traces.py::count_tool_calls`：`SELECT count(*) FROM tool_traces WHERE session_id = ?`（**沿用工具轨迹表，未新建计数表**；落库口径 → 重启后仍准；子任务内部调用按主会话记账，故同样计入） | **✅ 已实现**：**每一次执行工具之前**判一次 → 超限的调用**不执行**（每个未执行调用补一条如实 tool 回复）+ 本轮回无工具收口 `stop_reason="session_tool_limit"`；该会话后续 `submit_turn` 拒绝 `session_tool_limit_exceeded`（详见 §5.1.1） |
| **全局并发** | ✱ `runtime.max_parallel_sessions` | **3**（用户拍板） | 线程池 `max_workers` = 同时最多 3 份 token 在烧 | 第 4 个 `submit_turn` 拒绝：`{ok:false, reason:"at_capacity", running:[...]}`（**不排队**，见 §5.3） |
| **全局用量封顶** | ✱ `runtime.daily_token_budget` | 0 = 不限 | 滚动 24 小时：`SELECT coalesce(sum(prompt_tokens+completion_tokens),0) FROM usage_records WHERE created_at >= ?` | 见 §5.2 |
| 全局金额封顶 | ✱ `runtime.daily_cost_budget` | 0 = 不限 | `sum(est_cost)` 同上 | 同上；**但只有配了单价才有值**（§5.4） |

#### 5.1.1 会话级工具上限（✅ 已实现，2026-10-22）

> 这一节以前只是承诺（"60 = 12 × 5 轮"），落地时**按用户的成本口径改了默认**：**默认不限**。
> 理由：上限是给用户自己拧的闸，不是替用户拍的数字；拍错了会让正常会话在第 4 轮被闷死，
> 而真正的兜底已经有 `daily_token_budget`。

- **键名**：`runtime.max_tool_calls_per_session`（`config.example.yaml` 里带注释示例）。
  **默认 `None` = 不限**；`null` / `''` / `0` 都是"不限制"，与 `daily_token_budget` **共用**
  合法值判断（`config._optional_positive_int`）。**分歧一处**：`bool` / 负数 / 非数字串在
  `load_config` 就报 `ValueError`（错误带键名），不再静默归一成"不限" —— 那种静默等于
  "一个 typo 把这条闸关掉"，用户看不出来（见 `docs/23` 2026-10-23 那一条）。
- **计数来源**：`state/traces.py::count_tool_calls(db, session_id=...)` →
  `SELECT count(*) FROM tool_traces WHERE session_id = ?`。**没有新建计数表、也没有内存计数器**：
  每次判定都数落库的行，所以①重启进程后照样准；②多会话并行时不会各记一份账；
  ③子任务（`research.delegate`）内部的调用按主会话 `session_id` 落轨迹，**同样计入**（烧的是同一个会话的钱）。
  口径是"**累计发生过**"（含失败与未注册的工具调用）。
- **检查点两处**（缺一处就漏，与 §5.2 的全局封顶同构）：
  1. `runtime/loop.py::run_turn` 里 `enumerate(reply.tool_calls)` 循环的**每一次执行工具之前**
     —— 正在跑的这一轮也要当场停手；
  2. `runtime/session_runtime.py::submit_turn()` —— 已到顶就**拒绝新轮次**，不排队、不偷偷放行。
- **超限行为**（三级，逐级变狠）：
  1. **不执行**：剩下的那一批调用一个都不跑；
  2. **如实回话**：每个未执行的调用都补一条 `role="tool"` 结果（`"未执行：本会话工具调用已达上限 N 次
     （已用 M 次，runtime.max_tool_calls_per_session）。"`，N/M 是真实数字，不写死）—— assistant 的 `tool_calls` 每个 id 必须有对应结果，
     否则报文残缺、回放会炸；随后给一次**无工具收口**（`tools_for_round=None` + 一段 system 说明），
     让模型用已有资料如实总结，**已生成的正文一个字不丢**；
  3. **收口理由** `stop_reason="session_tool_limit"`（已并入 `docs/01 §4` 枚举）；一个字都没说出来时
     给一条可读说明并**指明出路**（新开会话 / 调高该键）。
  4. **后续新轮**直接拒绝：`{ok:false, reason:"session_tool_limit_exceeded", session_tool_budget:{...},
     running:[...], note}`。这条闸**不随时间回血**（与每日封顶不同：它没有 24 小时窗口）。
- **读数口**：`chat.status.session_tool_budget` = `{enabled, session_id, limit, used, remaining, exceeded, reason}`。
  未配置 → `enabled=False` 且各项 `None`（**不假报 0**，0 会被读成"一次都没用过"）；
  配了但没给 `session_id` → 只回 `limit`，`used`/`exceeded` 为 `None`（没有会话就无从计数，不猜）。
- **不改提示词**：收口的 system 说明是**消息级**追加，`runtime/prompts.py::build_system_prompt` 一个字没动
  → 黄金哈希仍为 `beaa67c49be0`（`test_prompt_arms` / `test_style_prompt` / `test_search_intent_gate` 三处钉值全绿）。
- **验证**：`tests/runtime/test_session_tool_budget.py` 10 条（16 个用例，含参数化）：默认不限不动旧行为 /
  超限不执行且补如实 tool 回复 / 收口正文不丢 / 拒新轮带 `session_tool_limit_exceeded` / status 快照形状 /
  重启后仍准 / 上限 3 时第 4 次被拒且文案带数字 / 跨轮累计（两轮 3 次后第 4 次拒）/ 新会话从 0 起 /
  `null` 时 `count_tool_calls` 一次都不被调用（零开销）/ 非法值归一为不限。

### 5.2 全局封顶怎么落地

- **检查点两处**（都必须有，缺一处就漏）：
  1. `SessionRuntime.submit_turn()` 之前 —— 已超则直接拒绝新轮次；
  2. `loop.run_turn` 里**每一次模型调用之前**（紧挨 `traces.record_usage`，`loop.py:366-375`）—— 正在跑的一轮也要当场收口。
- **超了怎么办（三级，逐级变狠）**：
  1. 当前轮：**不再给工具**（等价于把 `tools_for_round` 置 `None`，`loop.py:337` 已有这个开关），让模型用**已有资料如实总结** —— 绝不半句丢掉（与 `no_new_evidence` 的处理方式一致，`loop.py:474-490`）；
  2. 该轮收尾 `stop_reason="budget"`（**新增取值**，需同步 `docs/01 §4` 的 `stop_reason` 枚举，`:248`）；
  3. 后续 `submit_turn` 一律拒绝，直到次日余额恢复；界面顶栏红色徽标显示"今日已用 X / 上限 Y"（读 `chat.status.global_budget`）。
- **口径纪律**：单价未配置时 `est_cost` 是 `null`（`rpc/session.py:299` 的既有口径）→ **金额封顶只能按 token 算**，这一点必须在界面写清，否则用户以为设了金额上限就安全。

### 5.3 "上限 3 + 不排队"的边界（必须挑明）

用户拍了"直接并行不排队"。当 ≤3 个会话时无歧义；**第 4 个**会话要发问时，"不排队"只剩下"拒绝"。设计取**拒绝 + 如实告知**：
```
{"ok": false, "reason": "at_capacity", "running": [{session_id, title, started_at}, ...]}
```
界面提示："当前已有 3 个会话在跑，先停一个或等一个结束"，并在提示里给**一键停最早那个**的入口。
（这条需要用户点头：另一条路是"第 4 个排队、腾出槽位自动开跑"，但那正是他明确不要的"排队"。）

### 5.4 峰值成本的量级（写论文要能讲）

并行 3 × 单轮约 10 次模型调用 → 最坏在同一时刻有 ~30 次模型调用在飞。**这就是"上限 3"的全部意义**：把最坏峰值从"用户手速 × 不限"压到常量 3 倍单会话。对照 Anthropic 多智能体系统的自述成本（token 约 10–15×，见 §9.3 引用）—— 每会话隔离**不是多智能体**，开销远低于它，理由也正在这里。

## §6 失败隔离、取消与提醒

### 6.1 失败隔离

1. 每一轮在**自己的线程**里跑；异常在 `loop.run_turn` 内部一律收敛成 `stop_reason`（`loop.py:493-503`），**不外抛**；
2. `SessionRuntime.submit_turn` 再包一层 `try/except`（防"loop 之外"的意外，例如包装 emitter 时出错）→ 只写本会话的 `chat.error` + 本会话的 `stop_reason="error"`；
3. **不共享可变状态**：每轮的 `TurnBudget`（`toolctx.py:24`）本来就是新造一份（`loop.py:314`）；本设计把 `running`/`cancelled` 从全局裸容器搬进各自的工作单元（§2.2）——"一个会话炸"在物理上就碰不到别的会话；
4. 共享资源（LLM 客户端、HTTP 客户端、DB）的**不隔离部分必须显式加锁**：`fetch/http.py:109-131` 的 `_RateLimiter` 现在是**裸 dict + 无锁**（`:118-131`），3 会话并发抓同一 host 会绕过 `min_interval_s` → **必须先加锁**（这把"并行不会绕过限速"从注释变成事实，`subtasks.py:12-14` 与 `config.py:104-106` 都这么声称过）。

### 6.2 取消（步间检查，只影响一个会话）

- `chat.cancel({session_id})` → `SessionRuntime.cancel()`：按 `session_id` 找到该单元的 `TurnHandle` → `cancel_event.set()`；
- `loop.run_turn` 的每轮开头检查（把现在的 `ctx.is_cancelled(turn_id)`，`loop.py:101-102`/`:334`，改成读该 Handle 的 Event）→ `stop_reason="cancelled"`；
- **只影响被取消的那一轮**：Event 是**每轮一个对象**，不是全局 `set[str]` —— 从机制上杜绝"取消 A 误伤 B"；
- 语义不变的部分照旧保留：没有在跑轮次回 `{ok:false, reason:"no_running_turn"}`；界面如实写"当前这一步结束后生效"（`rpc/session.py:228-229` 的既有口径）。

### 6.3 提醒机制（用户拍板的第三件事）

**触发点**：`SessionRuntime` 的轮次收尾处（§2.3 生命周期第 3 态）。

**（1）应用内角标（默认开）**
- `chat.done` 到达且 `params.session_id !== state.sessionId`（非当前活跃会话）→ 左栏该会话行加 `.is-unread` + 顶栏计数；
- 依赖**前置条件**：前端必须先有"每会话槽"（§3.3）——否则 `chat.done` 连"属于哪个会话"都判不出，角标无从谈起。**这是提醒功能的先决改造，不是可选装饰**。
- 成本：零（纯前端）。

**（2）可选外部私聊推送（默认关）**
- 复用现成出站：`channels/feishu.py` + `runtime.feishu_reply_enabled`（`config.py:122-124`，默认关）+ `session_key` 映射（`state/sessions.py:103-123`，外部 `chat_id` ↔ 会话）；
- 新增一个开关 ✱ `runtime.notify_turn_done`（默认 `false`）与一个钩子 `on_turn_done(session_id, title, stop_reason, text_preview)`：**只在"非活跃会话 + 轮次完成"时**私聊推一条摘要（标题 + 首 200 字 + stop_reason）；
- **只私聊、不发群**：群里的主动消息平台不允许（与 `docs/17` 的通道纪律一致）；实现时只走单聊 `receive_id_type=open_id`；
- **QQ：本项目当前没有 QQ 通道**（全盘搜 `src/` 的 `qq|napcat|onebot` = **0 命中**，只有 `channels/feishu.py`）。设计里 QQ 只写作"同一个钩子的第二实现，需要时再接"，**不假装已支持**（Hermes 侧的 qqbot 通道与本项目无关）。

## §7 测试策略

三轮并行必须能被**断言**，不能只靠肉眼。

### 7.1 事件不串会话（最关键）

`tests/rpc/test_parallel_sessions.py`（新文件）：
- 用**桩模型**（项目已有范式：`tests/rpc/test_stream_wiring.py`、`tests/desktop/_ui.py` 的读取口）让会话 A、B 各跑一轮，正文里带各自可识别的标记（如 `A-正文-1`、`B-正文-1`）；

- 断言 3（分派）：给前端分派函数喂一串混合事件，断言 `state.turns[session_id].trace` 只收到自己那条。

### 7.2 真并行（不是排队）

- A、B 两会话各提交一轮；桩模型在 B 的第一个工具调用里 `Event.wait()` 卡住；
- 断言 **A 的 `chat.done` 在 B 仍在跑时就到达** —— 证明线程池真并行；
- **用 `threading.Event` 而不是 `sleep` 赌时序**（照 `tests/rpc/test_serve_concurrency.py:59-77` 的写法，那里已经示范了"等信号、不 sleep 赌"）。

### 7.3 取消生效且只影响一个

A 跑着 → `chat.cancel(session_id=A)` → 断言 A 收 `stop_reason="cancelled"`，**B 的 `chat.done` 仍是 `completed`**；
再断言对已结束的 A 再取消 → `{ok:false, reason:"no_running_turn"}`（不假装成功，`rpc/session.py:236-241` 的既有铁律）。

### 7.4 库仍一致

两会话并行跑完 → 断言：
- `messages`：每个 session 的 `idx` 从 0 **连续无重复**（`UNIQUE(session_id, idx)` 未被破），且条数与桩模型脚本预期一致；
- `research_states`：各会话恰好一行；
- `usage_records`：`session_id` 与产出**归属正确**（A 的 token 记在 A 上）；
- `PRAGMA integrity_check` 返回 `ok`。
另有专门的存储级用例 `tests/state/test_db_concurrent_writes.py`：两线程各调 `append_message`（N 次），断言**无 `OperationalError`**、idx 连续（直接钉住 §4.1 的坑）。

### 7.5 容量闸与读循环（补强现状）

- 提交第 4 个会话 → `{ok:false, reason:"at_capacity"}`，且**没有第 4 个线程起来**（断言线程名集合）；
- 3 个 `chat.send` 在跑时，第 4 条 `chat.cancel` 仍**立即**被处理 —— 这条会**打红现在的 `MAX_CONCURRENT_REQUESTS=4`**（§1.3），正是设计要改的点，测试先行、改动随后。

### 7.6 前端契约（不动 `ui/` 也能先立规）

用 `tests/desktop/_ui.py` 的 `APP_JS` 合并文本做漂移断言（阶段 5 才落地）：`scoutEvent` 里出现按 `p.session_id` 取槽的代码、`state.turns` 存在、`send()` 不再有全局 `state.sending` 闸。

## §9 优缺点与取舍（不接受只有方案没有取舍）

### 9.1 线程池 vs 进程池 vs 单线程事件循环

| 方案 | 优 | 劣 | 结论 |
|---|---|---|---|
| **线程池**（`concurrent.futures.ThreadPoolExecutor`） | 瓶颈是**等待外部 IO**（模型 HTTP、arXiv、网页），线程在 IO 期间释放 GIL → 真并行；零新依赖（stdlib）；项目已在用（`runtime/subtasks.py:24/158`）；共享一个 LLM/HTTP 客户端与一个 SQLite 文件天然可行 | 共享对象必须自己加锁（§4.2、§6.1）；一个会话的 GIL 密集段会轻微拖慢别人（我们的轮次里没有 GIL 密集段） | ✅ **选它** |
| 进程池 | 绕 GIL | 模型客户端/HTTP 连接池/DB 句柄要跨进程重建；stdio 管道与 pywebview 壳要重设计；`usage_records`/`tool_traces` 要跨进程合并；SQLite 单文件多进程写反而更容易 `SQLITE_BUSY`。**收益在 IO 密集场景 ≈ 0** | ❌ |
| 单线程 asyncio | 调度更省 | 全链路（`providers/llm.py` 用 `httpx.Client` 同步接口、`fetch/http.py` 同步、`sqlite3` 同步）改 async 是大改；同步驱动会阻塞事件循环；3 并发**不需要** C10K 级调度 | ❌ |

### 9.2 并行 vs 排队

| | 优 | 劣 |
|---|---|---|
| **并行（用户拍板）** | A 在等长调研时能立刻在 B 开新问题（这正是他抱怨的"只能等"）；每个会话的等待时间被**重叠**掉 | 峰值成本 ×3；同一 host 的并发抓取要靠限速器兜住（**现在无锁，必须先修**）；调试/trace 更复杂（必须靠 `session_id`/`turn_id` 对齐）；账单更难预测 |
| 排队 | 成本可预测；实现简单（一个 FIFO） | 用户明确不要 —— "切会话就出错"的本质就是"只能等" |

**为什么这里适合并行（三条硬理由）**：
1. 瓶颈是**等待外部 IO**，不是 CPU —— 并行能把等待重叠，收益直接体现在"用户等多久"上；
2. 天然可隔离的边界早已存在：库表本来就按 `session_id` 隔离（`messages` / `research_states` / `usage_records` / `tool_traces`，§4.3），不需要发明新的隔离维度；
3. 规模小（单用户、上限 3）—— 不需要分布式协调、不需要锁管理器、不需要消息队列。

### 9.3 业界做法（注明出处）

- **Actor 模型 / 每会话一个独立单元**：Hewitt 1973 提出的 Actor 模型把"隔离的状态 + 只靠消息通信"作为并发的基本单位；Erlang/Akka 里的经典用法就是**每个会话一个 actor/进程，凭"let it crash" 只让出问题的那一个崩溃**。本设计的"每会话一个工作单元 + 独立预算/取消/事件通道"是它的**同进程、低成本版**（不引入消息队列，用线程 + 队列即可）。
- **成本参照**：Anthropic《How we built our multi-agent research system》自述多智能体方案 token 约 **10–15×** 单智能体（<https://www.anthropic.com/engineering/multi-agent-research-system>；本仓库 `docs/14 §3 C1` 与 `docs/16 §3.2` 已引用同一来源）。因此本设计**不做多智能体编排**，只做"每会话隔离"—— 用户说的"多 Agent"落到这里就是**多工作单元**，务实的口径差异要写进论文/答辩。
- **Hermes 的对照**：Hermes 的 `delegate_task` 是"新 `AIAgent` + 独立 `SessionDB` 句柄 + 独立 `IterationBudget` + `parent_session_id` 血缘"（`docs/16 §3.1`）。我们借它的**隔离思想**（每单元独立预算/独立会话/独立事件），不借它的**多进程与多平台外壳**（`docs/16 §4` 已把这一条列入"不建议借鉴"）。
