# 第 3 章 系统设计

> 本章讲**怎么设计的、为什么这么设计**，不讲跑分（那是第 5 章）。所有接口、DDL、目录与规则的
> 权威文本在 `docs/01`–`docs/04`，本章是它们的论文表达：把散在设计文档里的**取舍与代价**讲成一条线。
>
> 写作纪律：**每个设计决定都写出被放弃的替代方案**，否则读者无法判断这个决定是不是拍脑袋。

## 3.1 需求与设计约束

系统的目标用户是"要在一个陌生方向上做调研并学会它"的人（本项目以本科生的研究方向调研为场景）。
需求归纳为六条，每条都带出一个设计约束：

| 需求 | 具体含义 | 带出的约束 |
|---|---|---|
| R1 **开放世界调研** | 任意方向、任意语言的主题，都能拉到可用的资料 | 不能只接一个文献库；来源要分学术/代码/通用三层 |
| R2 **学习辅助** | 产出知识地图、学习路线、抽背卡，而不是"给一堆链接" | 产物必须挂在真实资料上，否则学术上是编的 |
| R3 **全本地** | 笔记、资料、会话、产物都在本机，可离线复现 | SQLite + 文件系统；正文不入库但仍可定位 |
| R4 **成本可控** | 用户为模型调用付费，不能"问一句花一块" | 预算写死进提示词；有可量化的省钱手段与对照实验 |
| R5 **可计量** | "有没有编造"必须是能算出来的比率 | 反幻觉守卫 + 两类指标（可归属率、语义支持度） |
| R6 **桌面可用** | 双击即用，不需要命令行与前端构建 | 极简壳 + 无构建前端 + exe 启动器 |

**一条贯穿全系统的取舍**：这是一个"用户主导的调查工具"，不是"自动写综述的 Agent"。
因此在 R2 与 R4 的交叉点上做了最关键的一个决定 —— **产物按需生成**（3.5.3）：
知识地图/路线/抽背卡在用户明确要求前不生成。它同时降低了成本、并避免把"系统自己的判断"
强加给用户。

## 3.2 总体架构

分四层、调用方向**单向**（`docs/01 §1` 把这条写成硬规则：下层不许反向调用上层）：

```
┌──────────────────────────────────────────────────────────────┐
│ ① 壳层  desktop/  pywebview 5.4 + 无构建前端（HTML/CSS/JS）    │
│    不 import 任何业务模块，只做界面与 JSON-RPC 的搬运          │
└───────────────┬──────────────────────────────────────────────┘
                │ JSON-RPC 2.0 over stdio（子进程：python -m scholarscout --rpc）
┌───────────────▼──────────────────────────────────────────────┐
│ ② 传输层  rpc/  方法表 + 流式事件（notification）+ 错误码       │
│    会话/资料库/产物/设置/导出/用量 全部经此暴露                 │
└───────────────┬──────────────────────────────────────────────┘
                │
┌───────────────▼──────────────────────────────────────────────┐
│ ③ 运行时层  runtime/  单轮工具循环、工具注册表、系统提示词      │
│    context_budget/ 喂回模型前瘦身、预算与中断（步间检查）        │
└───────┬───────────────────────────────┬──────────────────────┘
        │                               │
┌───────▼──────────────┐   ┌────────────▼──────────────────────┐
│ ④a 能力层 tools/      │   │ ④b 支撑层                        │
│  research.search      │   │ providers/ 12 个来源适配器        │
│  source.fetch/grade   │   │ summary/   摘要流水线 + 守卫      │
│  topic.build_map      │   │ grading/   判权 + 语义支持度      │
│  route.plan/note.save │   │ state/     SQLite + FTS5 + 迁移   │
└───────────────────────┘   └───────────────────────────────────┘
```

**为什么这样分（与被放弃的方案对比）**：

| 决定 | 替代方案 | 为什么不用替代方案 |
|---|---|---|
| 壳层不 import 业务模块，走子进程 RPC | 单进程直接调函数 | 壳是 GUI 依赖（pywebview/WebView2），业务要能**在没有 GUI 的机器上跑评测与 CLI** |
| 复刻"下半身"（JSON-RPC + SQLite + 工具注册表 + 提示词外置） | 直接复用 Hermes 的库 | 她的设计决策可搬，**库依赖不可搬**（前端无构建 + 要离线跑） |
| 工具注册表 + 模型可见 schema | 把工具写死在提示词里 | 工具描述要能被程序检查（schema 校验、名字合法性、白名单） |
| SQLite + FTS5 单文件库 | 独立向量库 | 中文检索用 trigram 够用；**少一个服务就少一类故障**（R3） |

## 3.3 数据模型设计

三组表，对应三条业务线（完整 DDL 见 `docs/02`，本节只讲取舍）：

| 表组 | 表 | 承担什么 |
|---|---|---|
| 来源与内容 | `sources` / `documents` / `summaries` | 一条来源 → 一份原件 → 一份摘要 |
| 会话与轨迹 | `sessions` / `messages` / `tool_traces` / `usage_records` | 谁在什么时候问了什么、系统做了什么、花了多少 |
| 产物与关联 | `topic_maps` / `learning_routes` / `notes` / `mentions` | 产物本体 + "这条资料是哪次会话带出来的" |

**三条关键设计决定**：

1. **正文不入库，只入摘要 + 路径**（R3）。库内只存元数据与摘要，正文落 `data/text/`、原件落 `data/raw/`，
   用路径指向。理由：全文入库会让库膨胀一个量级、迁移与备份变重，而**本系统的产物只依赖摘要**；
   需要原文时按路径现读（`archive.get {text:true}`）。
   - 代价（如实写）：跨机器迁移时库能走、正文不会自动跟着走，必须一起拷 `data/`。
2. **检索索引只有两张 FTS5 表，中文用 `tokenize='trigram'`**，查询少于 3 字时走 `LIKE` 兜底。
   理由：trigram 对中文免分词可用，但 SQLite 3.42 的 trigram 对 <3 字符查询返 0 条 ——
   短查询（"RAG""VLA"）恰恰是学术检索里最常见的，所以必须有兜底而不是"用户自己把词写长点"。
3. **出处靠 `mentions` 关联表**，而不是把 source_id 塞进消息文本。理由：产物与资料是多对多，
   且"这条资料是哪次会话、哪一轮带出来的"是第 5 章 E3 覆盖率指标的唯一取数入口。

**为什么刻意不用向量库**：向量检索的价值在"语义召回"，而本系统的召回由**外部来源**（arXiv/OpenAlex/
GitHub/通用搜索）承担，库内检索只是次要通道（默认关闭的 `kb.*`）。引入向量库要新增嵌入模型依赖 +
一个可失败的服务，收益不对称。

## 3.4 检索与判权设计

### 3.4.1 三层来源，按"能问什么"分工

| 层 | 来源 | 免 key | 说明 |
|---|---|---|---|
| 学术 | arXiv、OpenAlex | ✅ | arXiv 只索引英文、≥3s 限速、必须带 `Accept` 头；OpenAlex 免 key 但**摘要字段是"词→位置"倒排**，必须按位置还原 |
| 代码与教程 | GitHub | ✅ | 未认证 10 次/分钟（节流 6s），认证走 token（30 次/分钟） |
| 通用 | 自建 SearxNG（Docker） | ✅ | 本机聚合 `360search`+`sogou`+`bing`；`keep_only` ≠ 启用，必须显式 `disabled:false` |
| 通用（商用） | Brave / Google CSE / Serper / Tavily | ❌ | 有 key 才启用 |
| 抓取 | Bing / DuckDuckGo 结果页 | — | **默认关**，必须显式开（违 robots 且质量差，实测见 `docs/03 §7`） |

`providers: ["auto"]` 只带"此刻真能用的"来源，并把不可用原因分三类错误码返回给界面：
`missing_api_key` / `missing_config` / `blocked_by_robots` —— **"没配"和"被拦"要能区分**，
否则用户不知道是该去填 key 还是该放弃这条来源。

### 3.4.2 判权：确定性优先，模型只补"相关性"

判权（这条来源属于哪个层级）分两段：

- **层级判定（本地、确定性）**：表驱动规则（域名后缀、机构、期刊/会议白名单），
  同一输入永远同一输出，可离线复算；
- **相关性判定（可用模型）**：只有"这条资料是否切题"才交给模型，且**本地打分与模型打分都落库**，
  便于算一致性（第 5 章 E1 的 κ）。

**刻意不做的事**：不用模型给"层级"打分。层级是**信任等级**，它必须能被审计与复现；
相关性是**语义判断**，才需要模型。把两者混在一起会让"为什么这条被排到前面"变成不可解释。

## 3.5 生成与反幻觉设计

### 3.5.1 工具契约：模型能调什么、返回什么

模型可见 6 个工具（`docs/01 §5`）：`research.search`、`source.fetch`、`source.grade`、
`topic.build_map`、`route.plan`、`note.save`。三条约束：

1. **线上工具名用 `__` 而不是 `.`**：OpenAI 兼容接口要求 `^[a-zA-Z0-9_-]+$`，
   注册名带点、线上名替换 —— 这是实测撞出来的（`Invalid 'tools[0].function.name'`）。
2. **工具结果必须能被瘦身**（3.6）：工具返回结构化 `{ok, data, refs}`，
   而不是一大段人话文本，否则"喂回模型前裁剪"无从下手。
3. **失败要显式**：全部来源失败时返回 `ok=false` + 原因，而不是"成功但空列表"。

### 3.5.2 反幻觉：两级证据

生成类工具（`topic.build_map`、`route.plan`）拿到的候选资料来自 `source_context.py` 的**三级取法**
（本次会话带出的 → 全库同类 → 全库），产物里每个资料类条目必须挂一个**真实存在的** `source_id`。
守卫在写库前校验 id 存在性、是否属于本次允许集合、是否越权 —— 不通过就剔除并记 `dropped_source_ids`。

**边界（本项目最重要的诚实声明）**：守卫只保证"引用是真的"，**不保证"资料支持这句话"**。
因此指标分两条：

| 指标 | 回答 | 取数 |
|---|---|---|
| 出处覆盖率 | 有多少条目能指回真实来源（**可归属率**） | E3 报告 |
| **引用语义支持度** | 引用到的资料**是否真的支持该断言** | `support_checks` 表（第 4.6 节，第 5 章 §5.7.4） |

支持度校验按**证据等级分层**：抓过原文的来源有摘要+要点（强证据），没抓过的只有标题/年份/域名
（弱证据）。**混在一起算会被标题字面重合污染**，所以必须分开报。

### 3.5.3 产物按需生成

产物的默认策略是**按需**：系统不主动生成，而是在对话中显式询问/或在界面上提供三个按钮；
用户点了才做，且那条请求是一条**真实用户消息**（会话记录里看得见"我点过要什么"）。

对照臂保留自动生成（`generation.auto_artifacts` + `--auto-artifacts`）作为实验条件。
**为什么强调"提示词分档就是实验条件"**：两档提示词必须**逐字**可比，所以用**内容哈希**钉住
（按需档 `f68b1b7abb03`、对照臂 `af6f1b33e12c`），改一个字测试即红 —— 见第 5 章 §5.7.1。

## 3.6 成本与预算设计

用户的原话是"体感上的缓存并不是很有效果，因为我在 API 平台看到了高昂的费用"。
要如实回答这个问题，先得把账单**解剖**（数字来自本机实测）：

| 事实 | 实测值 |
|---|---|
| 每轮固定重发：系统提示词 | 1,181 字符 ≈ **393 tokens** |
| 每轮固定重发：6 个工具声明 | 4,675 字符 ≈ **1,558 tokens** |
| 一轮对话的模型调用次数 | 约 **10 次**（每次都要重发前面所有工具结果） |
| 单条工具结果最长 | 9,583 字符 ≈ **3,194 tokens** |
| 库内 38 条来源摘要合计 | ≈ **32,442 tokens** |

由此确定**四个杠杆与一个明确的"不做"**：

| 杠杆 | 做法 | 实测效果 | 默认 |
|---|---|---|---|
| 上下文瘦身 | 喂回模型前去重/截断/折叠 | 同题输入 **−15%** | **开** |
| 历史正文预算 | 长会话保头保尾（首句定义任务必须留） | 防长会话线性膨胀 | 12,000 字符 |
| 关闭深度思考 | `thinking={"type":"disabled"}` | completion **162 → 36** | **开思考**（质量优先） |
| LLM 响应缓存 | key = 整个请求体哈希 | 交互命中率≈0，只对评测复跑有用 | 关 |
| ~~精简工具声明~~ | 量过后判**不做** | 收益 <3% 且伤工具选择 | — |

**贯穿的成本原则**：**砍有量级的那条，没量级的明确跳过**。
"工具声明占 1,558 tokens/轮"看着大，但其中绝大部分是 JSON-Schema 的必需结构，
真正可删的描述文字只有约 500 字符 —— 动它省不到 3% 却可能让模型选错工具，所以记下"跳过"。

## 3.7 界面与交互设计

三栏（会话列表 / 对话 / 资料库与产物），设计约束来自"东西要能实际用"这一条：

| 交互 | 设计决定 | 理由 |
|---|---|---|
| 会话行菜单 | 右侧「⋯」含 置顶/重命名/分享（导出 Markdown）/删除 | 分享先做成可复制的 Markdown，不做协作服务 |
| 置顶 | 只改 `pinned`，**不动 `updated_at`** | 置顶不是"有新活动"，否则排序语义被污染 |
| 设置栏 | 模型 / 生成策略 / 检索与预算 / 外观 / 数据 五组 | 三条硬约定见下 |
| 长任务 | 「停止」按钮 + **如实提示"当前这一步结束后生效（步间检查）"** | 后端是步间检查，提示不能含糊 |
| 成本可见 | 每轮显示真实 token；**本会话累计**显示在输入框右下 | 用户在意账单，就给他可核对的数字 |
| 窗口 | 记住大小/位置，对话区随窗口变宽 | 存的是**逻辑像素**（物理/逻辑单位不一致会开出错误尺寸） |
| 主题 | 令牌整套取自用户日常用的桌面端（浅色近白、深色中性黑） | 用户明确"不要深蓝色" |

**设置栏的三条硬约定**（写进 `docs/01 §3.5`）：

1. **不认识的键直接报错** —— 静默忽略拼错的键，等于"你以为改了其实没改"；
2. **密钥只写不回读** —— 界面只显示"已配置（留空则不修改）"，永远不回显；
3. **可清理的只有缓存** —— 资料本体与数据库拒绝清理，避免一键误删。

## 3.8 工程规范设计（AI 协作下的一致性保障）

本项目全程以"人定接口、AI 填实现"的方式推进，工程规范因此不是形式要求而是**正确性前提**：

| 规范 | 落地物 | 防的是什么 |
|---|---|---|
| 先定接口/数据模型/目录，再填实现 | `docs/01`–`docs/04`（冻结版） | AI 顺手造出两套命名 |
| 一次只改一个文件/函数，小 PR 勤提交 | 55 次提交、每次可回滚 | 大改无法定位回归 |
| 规则写进规则文件 | `AGENTS.md`；`CLAUDE.md` **不创建** | 多个规则文件会漂移 |
| lint+类型检查+测试+构建全绿才合 | `scripts/check.sh`（6 项门槛） | "本地能跑"式交付 |
| 新增依赖要审批 | `deps-allowlist.txt` + `check_new_deps.py` | AI 随手 import 不存在的包 |
| 关键路径人工逐行 review | 守卫/权限/迁移/密钥路径 | 自动化测不到的语义错 |

**门槛真的在拦人**（不是摆设）：本轮就拦下了三段真错 —— ruff 的嵌套 `if`、
mypy 对 `data_usage` 的类型标注（`dict[str,int]` 里塞了 `str` 的路径）、
以及前端复选框"值缺失时显示为勾上"与"默认关"相反的默认值 bug。

## 3.9 设计决策记录（精选）

| # | 决策 | 理由 | 代价（如实写） |
|---|---|---|---|
| D1 | core 知识库降级为可插拔次要通道，主线 = 开放世界调研 + 学习辅助 | 用户要的是"任意方向都能查" | 库内检索能力变弱 |
| D2 | 正文不入库，只留摘要与路径 | 库小、迁移轻 | 迁移必须连 `data/` 一起拷 |
| D3 | 判权表驱动确定性，相关性才用模型 | 层级必须可审计、可复现 | 规则表要人工维护（迁移 0003 补过域名） |
| D4 | 检索类请求一律不缓存，只有内容抓取吃缓存 | 检索结果是时变的，缓存会把瞬时失败钉住 6 小时 | 重复检索会多花钱（量小） |
| D5 | 反幻觉守卫只验 id 存在性 + 另设语义支持度校验 | 两种错误的代价不同，指标必须分开 | 语义支持度只能是模型估计，非金标准 |
| D6 | 产物按需生成，自动生成留作对照臂 | 尊重用户主导 + 省钱 | 需要额外的探针题集才能度量（第 5 章 §5.6） |
| D7 | 提示词外置、版本=内容哈希 | 提示词改一个字就是换了实验条件 | 每次改动要更新哈希钉子 |
| D8 | 桌面壳不 import 业务模块 | 评测/CLI 要能在无 GUI 环境跑 | 多一层 RPC 调试成本 |
| D9 | exe 只是启动器，不是打包成品 | 改代码永不用重编 | 依赖本机 Python 环境 |
| D10 | 主题令牌整套沿用用户日常界面体系 | 用户明确不要深蓝 | 与"设计感原创"无关，是可用性优先 |

## 3.10 本章小结

- 六条需求各自带出可检验的约束，其中 R4（成本）与 R5（可计量）直接决定了指标设计与实验方案；
- 架构的关键不是"分层"，而是**单向依赖 + 壳与业务解耦**：它让同一套代码既能在 GUI 里跑，
  也能在无界面环境下跑评测（第 5 章全部数字由此可得）；
- 数据模型的关键取舍是**正文不入库**与**只有两张 FTS**；
- 生成侧的关键取舍是**按需生成**与**两级反幻觉证据**；
- 成本侧的关键方法论是**先把账单解剖，再砍有量级的那条**；
