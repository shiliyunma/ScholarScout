# 04 摘要提取方案（参照 AIHOT 实测）

> 状态：**v0.1** ｜ 2026-10-05 ｜ 依据：本机 `D:\AI+教育毕设毕设\AIHOT-main` 源码实测 + MinerU 官方接口文档
> 对应决议：第 5 题（库里只放摘要，不切块）、第 6 题（trigram 只检索摘要与会话）、第 8 题（扫描版走 MinerU）、第 9 题（超长文档只存原件仍出摘要）

## 1. 结论先行

| 决策 | 内容 |
|---|---|
| 入库内容 | **只放摘要**（标题 + 短摘要 + 要点 + 相关性理由）。正文**不入库**，落 `data/text/<doc_id>.txt` |
| 生成方式 | **一次 LLM 调用**：正文截断 → 提示词 → 结构化输出 → 确定性守卫。**不做 map-reduce 分块摘要** |
| 截断阈值 | 正文送入模型前截到 **6000 字符**（照 AIHOT）；本地硬上限 60 000 字符 |
| 超长文档 | 原件照存，摘要照出（基于正文前 6000 字符或元数据），`documents.truncated=1` 标记 |
| 提示词 | **外置成 Markdown 文件 + 规则片段复用**，版本 = 内容哈希（照 AIHOT） |
| 扫描版 | 不自己造轮子，走 **MinerU 官方 API**（两种，见 §7） |

## 2. AIHOT 到底怎么做的（本机实测，带锚点）

| 机制 | 实现 | 锚点 |
|---|---|---|
| 正文截断 | `clampText(cleanArticleTextForLLM(input.text), 6000)` —— **不切块，直接截到 6000 字符一次总结** | `packages/backend/src/editorial/writing.ts:290` |
| 本地硬上限 | `MAX_BODY_CHARS = 60_000`，超出 `slice(0, 60000)` | `writing.ts:13-14` |
| 清洗规则 | 去 `<script>/<style>`、去所有标签、去 URL、解 HTML 实体、压空白 | `writing.ts:38-54` |
| 按体裁分支 | article / short-post / long-post / 各自带引用版 / empty 兜底，共 6 个摘要提示词 | `writing.ts:284-307`；`industry/prompts/summarize-*.md` |
| 规则片段复用 | 每个摘要提示词都拼进 4 个规则片段：答案前置 / 标题自洽 / 领域 / **反幻觉** | `industry/prompts/summarize-article.md:12-18` |
| 答案前置规则 | 第一句必须可独立理解（30-70 字），不许"本文介绍了"开头；后面只补 1-2 个要点 | `industry/prompts/rules-answer-first-summary.md:1-9` |
| 反幻觉规则 | **12 条**：数字/版本必须原文可查、不确定宁可省略、相对时间不许换算成年份、不许强化语气、排他性表述要有原文 | `industry/prompts/rules-anti-hallucination.md:1-12` |
| 提示词版本 | 版本 = **提示词内容的哈希**；改提示词只影响新资料，历史结果不重算 | `editorial/prompts.ts:51`；`analyze.ts:37` |
| 结构化输出 | 强制 `title_zh: …` / `summary_zh: …` 两行标签；`parseTranslateOutput` 逐行正则解析 | `writing.ts:321-338` |
| 长度守卫 | 不合长度要求就**确定性压缩**（按句/小句裁剪），**不发起第二次修复调用** | `writing.ts:257 answerFirstSummaryLengthOk` / `:270 compactAnswerFirstSummary` |
| 落库带版本 | `analyses` 表有 `prompt_version`、`model`、`summary_zh`、`output jsonb` | `database/migrations/0001_core.sql:173-192` |

**一句话**：AIHOT 的摘要方案是"**截断 + 外置提示词 + 结构化输出 + 确定性守卫 + 版本化落库**"，全程没有分块、没有 map-reduce、没有第二次修复调用。这与你第 5 题的选择完全一致。

## 3. 照搬什么、改什么

| 项 | 处置 | 理由 |
|---|---|---|
| 一次调用 + 截断 | **照搬** | 简单、可复现、成本可控 |
| 提示词外置成 md | **照搬** | 改标准不用改代码；答辩好讲 |
| 规则片段复用（`{{> rules-x}}`） | **照搬** | 反幻觉规则要出现在每一个摘要提示词里，复制粘贴必然漂移 |
| 答案前置 | **照搬** | 摘要第一句可被独立引用，正好服务"检索命中即看懂" |
| 反幻觉 12 条 | **照搬** | 学术场景更要命（编个 benchmark 分数就完了） |
| 长度守卫不打补丁调用 | **照搬** | 省一半 token，且结果确定 |
| prompt_version 落库 | **照搬** | 论文里要能说清"这批摘要出自哪版提示词" |
| 数字保留清单 | **改** | 从"模型名/参数/分数/价格"改成**学术版**：方法名、数据集、指标与分数、参数量、年份与会议、代码/数据可用性 |
| 输出字段 | **改** | AIHOT 只要标题+摘要；我们要**短摘要 + 要点 JSON + 相关性理由**（后者喂给 `source.grade`） |
| 体裁分支 | **改** | article/short-post 换成 **论文 / 官方文档 / 博客 / GitHub 仓库 / 扫描件** |

## 4. 我们的摘要流水线（四步）

```
取正文 ──> 清洗 ──> 截断+拼提示词 ──> 调模型 ──> 解析 ──> 守卫 ──> 落 summaries 表
  ①         ②          ③              ④        ⑤      ⑥          ⑦
```

| 步 | 做什么 | 失败时 |
|---|---|---|
| ① 取正文 | PDF/HTML → 纯文本。先用本地抽取（`pymupdf`）；无文字层或字符数过少 → 走 MinerU（§7）。落 `data/text/<doc_id>.txt` | `extract_status='no_text_layer'`，元数据仍可出摘要（`degraded=1`） |
| ② 清洗 | 照 `writing.ts:38`：去标签、去 URL、解实体、压空白 | 出错则用原始文本，记 `clean_failed` |
| ③ 拼提示词 | `clamp(body, 6000)` + 体裁提示词 + 4 个规则片段 | — |
| ④ 调模型 | 摘要用**便宜档模型**（照 AIHOT 的能力分层 `modelFor`） | 失败重试 1 次，仍失败 → `degraded` 摘要（只用标题+摘要字段） |
| ⑤ 解析 | 逐行正则取 `title_zh:` / `summary_zh:` / `points:` 标签 | 丢标签 → 取首行当标题、其余当摘要 |
| ⑥ 守卫 | 长度合规检查 + 数字可溯源检查（§8 自动化那条）；不合规就确定性裁剪 | 裁剪仍不合规 → 原样存 + 记 `guard_failed` |
| ⑦ 落库 | `summaries` 表，带 `model` + `prompt_version` + `input_chars` + `degraded` | — |

## 6. 摘要字段（三档）

| 字段 | 长度 | 内容 | 用途 |
|---|---|---|---|
| `title_zh` | 10-25 字 | 中文标题，专有名词保留原文 | 列表展示、FTS 检索 |
| `summary_short` | 80-160 字，最多 3 句 | 答案前置：第一句是谁做了什么/关键结果 | FTS 检索、卡片 |
| `key_points` | JSON 数组，2-4 条 | 每条一个可验证事实（数字优先） | 学习路线条目、抽背卡 |
| `why_relevant` | 1 句 | 与当前查询的相关性理由 | `source.grade` 的 `reason` 字段 |

> AIHOT 只做前两项。我们的第 3 项是学习路线的原料，第 4 项是"判断相关性"可解释性的原料。

## 7. MinerU 接入（对应第 8 题）—— **已实现（`fetch/mineru.py`）**

官方文档核对（`https://mineru.net/apiManage/docs`，2026-10-05）+ 本机真机实测：

| 对比维度 | 精准解析 API | Agent 轻量解析 API |
|---|---|---|
| Token | **需要**（API 管理页创建） | **无需**（IP 限频防滥用） |
| 接口 | `/api/v4/extract/task`（单文件）／`/api/v4/file-urls/batch`（批量） | `/api/v1/agent/parse/url` ／ `/api/v1/agent/parse/file` |
| 模型 | pipeline（默认）/ **vlm（推荐）** / MinerU-HTML | 固定 pipeline 轻量 |
| 文件大小 | ≤ 200 MB | ≤ 10 MB |
| 页数 | ≤ 200 页 | ≤ 20 页 |
| 批量 | ≤ 200 个 | 单文件 |
| 输出 | Zip（Markdown + JSON，可导 docx/html/latex） | 仅 Markdown（CDN 链接） |
| 调用 | 异步（提交 → 轮询） | 异步（提交 → 轮询） |
| 配额 | 每账号每天 **1000 页**最高优先级，超出降级 | IP 限频 |

**实现细节（真机拿到的契约，写代码时别猜）**：

- 提交返回 `{"code":0,"msg":"ok","data":{"task_id":"…"}}`
- 轮询端点就是 **`GET /api/v1/agent/parse/{task_id}`**（试过 `…/result?task_id=`、`…/status?task_id=`，都回
  `-10002 invalid task_id` —— 不是那两个）
- `data.state` ∈ `waiting-file / uploading / pending / running / converting / done / failed`
- **done** → Agent 给 `data.markdown_url`（CDN 上的 Markdown，要再下一次）；精准接口给 `data.full_zip_url`（Zip 里的 `full.md`）
- **failed** → `data.err_code` + `data.err_msg`（如 `-30003 file page count exceeds lightweight API limit`）
- 无 token 打精准接口 → **HTTP 401 `login required`** → 代码自动退回 Agent 接口，
  **并且轮询也要换回 Agent 的 URL**（拿 Agent 的 task_id 去查 `/api/v4/...` 永远查不到 —— 单元测试抓到的真 bug）

**⚠️ 当下已知问题（如实记录，不粉饰）**：2026-10-05 多次实测，免 token 的 Agent 接口**提交成功但解析失败**，
`state=failed` / `err_msg=model service is temporarily unavailable`（换 arXiv、清华镜像、w3.org 三个源都一样）
→ 所以"扫描版 PDF 能抽出正文"这条**还没有端到端成功过**。
代码行为是正确的（失败如实记 `extract_status=mineru_failed` + `extract_detail` 保留服务端原话，
`degraded=1` 摘要照出），但要在论文里写这个能力，得等服务恢复后重跑，或配 `MINERU_API_TOKEN` 走精准接口。

**复查（2026-10-06，用项目自己的代码探的）**：

1. **Agent 通道仍然不可用**：`parse_pdf_url(http, "https://arxiv.org/pdf/1706.03762", token=None)`
   → `state=failed` / `model service is temporarily unavailable`（3 秒内就失败，不是超时）。
2. **`.env` 里的 `MINERU_API_TOKEN` 是空值**（实测值长度 = 0，`mineru_token()` 返回 `None`）——
   也就是说本项目**一直只走过免 token 的 Agent 通道**，从没走过精准接口。
   环境变量名两边是一致的（`fetch/settings.py` 的 `MINERU_TOKEN_ENV` = `settings_io` 的 `SECRET_FIELDS`
   = `MINERU_API_TOKEN`），**不是代码 bug，是密钥没填**。
3. **本机拿不到"公网可达的扫描版样本"**：MinerU 只接受公开 URL（本地文件会回
   `MinerU 只能解析公开 URL`）；试了 arXiv 的 1992–1994 年老论文（本地验证**都带文字层**，不是扫描版），
   `archive.org` 在本机**请求超时**（国内网络）。

**所以 B8（扫描版端到端）要跑通，缺的是两样外部条件**：

| 缺什么 | 谁来补 | 补上之后怎么验（几分钟） |
|---|---|---|
| **MinerU Token**（mineru.net 注册后创建） | 你（我造不出来也不该造） | 设置 → 检索与预算 → MinerU Token 填入，我用 `parse_pdf_url` 打一个公网 PDF 看 `engine=precise` + 正文非空 |
| 一个**公网可达的扫描版 PDF** | 你给一个 URL（或挂个梯子让 archive.org 可达） | 端到端跑 `source.fetch`，看 `extract_status=ok` + `extract_detail` 记 `precise 解析` |

在补上之前，界面已经会**主动说明这个状态**（设置面板：开关开着但没配 token 时给出警告，
写明免费通道的失败原话与"填 Token 改走精准接口"）——避免把"服务不可用"误读成"这个 PDF 没内容"。

**我们的接入策略（两级）**：

1. **默认**：本地 `pymupdf` 抽文字层 → 够用就不出网（省钱、离线可用、毫秒级）
2. **降级**：本地抽不出（`extract_status='no_text_layer'`）或字符数 < 阈值
   - 文件 ≤ 10 MB 且 ≤ 20 页 → **Agent 免登录 API**（不用 token，最省事）
   - 否则 → **精准解析 API**（token 放 `.env` 的 `MINERU_API_TOKEN`）
3. **再降级**：MinerU 也失败 → `extract_status='mineru_failed'`，用元数据出 `degraded=1` 摘要，**不阻塞整条流水线**

异步轮询要落 `provider_status` 表，配额耗尽的 429 单独记，避免评测时把"配额用完"算成"系统不会解析"。

## 8. 怎么证明摘要好（论文第 5 章要用）

| 指标 | 怎么算 | 数据来源 |
|---|---|---|
| **事实可溯源率** | 摘要里每个数字/版本号在原文能否 `grep` 到。**可全自动**——这正是 AIHOT 反幻觉规则的可执行版本 | `summaries` + `data/text/` |
| 长度合规率 | `80 ≤ len ≤ 160` 且句数 ≤ 3 | `summaries.summary_short` |
| 答案前置率 | 第一句是否独立可理解（人工抽检 20 条，2 人判） | 人工表 |
| 要点覆盖率 | 关键要点（人工标注的 gold points）被 `key_points` 覆盖的比例 | gold set |
| 消融 | **去掉规则片段** vs 带规则片段，比较事实可溯源率 | 两次跑，同 gold set |

> 对照臂：`无规则片段` / `带全部规则片段` / `带规则且带截断`（三档），数字进论文表格。

## 9. 明确不做

- ❌ 不做 map-reduce / 分块摘要（留给以后可能出现的 RAG）
- ❌ 不做正文入库 + 全文索引（用户决议 5/6）
- ❌ 不做第二次"修复调用"改摘要（照 AIHOT：用确定性守卫）
- ❌ 不自己写 OCR（走 MinerU）

## 10. 与检索的关系（重要边界）

`documents` 正文**不进 FTS**。因此：

| 能搜到 | 搜不到 |
|---|---|
| 中文标题、短摘要、要点（`summaries` 表） | 正文里的具体句子 |
| 会话历史消息（`messages` 表） | 摘要里没提到的技术细节 |

想搜正文 → 以后加向量检索（RAG）时再说。**这条边界要写进论文，否则会被问"为什么搜不到正文"。**
